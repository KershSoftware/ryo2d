## Top risks (read these first)

1. **The backlog's "colliders under a sheared parent" route is the wrong one.** Physics skips `PrebuiltShape` (the shape built ahead on the builder thread) whenever the collider's world transform applies scale or mirroring (physics/AGENTS.md, step 5, `sync_collider_with`). Every tile part under a scaled/sheared layer would be rebuilt on the main thread at landing and at every reshape. One-way directions use the collider's rotation only (`physics/one_way.rs:66-67`), so a shear silently gives wrong normals. `shape::build` itself is fine under any linear map (polylines and hulls map exactly), but the cost and the one-way risk are not. Better seam: bake the cell-to-pixel map into `TileColliders::at()`/`px()` (`physics/tiles.rs:658`, `:679`) and into occluders' `px` (`tilemap/occluders.rs:~309`), so parts stay at `Transform::IDENTITY` under an unscaled parent.
2. **"Cell to pixel" is not a handful of places.** `cell * cell_size` is open-coded in at least 14 sites (group 1 lists them). A missed one stays orthogonal silently (class tiles, reload, nav, occluders, tile-shape placement). A single `CellGeometry`/`Orientation` value stored with the layer (`TileLayerData`, spawn.rs:210, and `LayerKind::Tiles`, map.rs:160) and used by all of them is the only safe design.
3. **Hex collision.** The square-specific part of `physics/tiles/outline.rs` is smaller than it looks: `unit_edges` (:146), `boundary_edges` (:~205), `Outlines::apply`'s unit list (:~330), `Cells` and `sides`. The tracing and splicing (`trace`, `splice`, `sharper`, integer points, edges leaving a point) are geometry-agnostic. But hex needs 6 border units (3 owned per cell), a global lattice (rows offset by half a cell, vertical pitch 3/4 of the height, so cell-fraction points `GRID` per tile do not hold hex corners), edge steps within `Out`'s `i16` (:76-80), and `pack::chunk` (pack.rs:47) to chunk by the lattice. Slopes, authored shapes and one-way have no hex meaning and must be refused or defined.
4. **Infinite maps touch four dense structures, not one.** `TileGrid` (grid.rs:52-62), `TileColliders` (a dense `Vec<TileCell>` plus a public `u32` x/y API and 8192 cap, physics/tiles.rs:424, :498-525), occluders' `Group.chunks`/`sides` as dense `Vec`s (occluders.rs:107-131), and `Tracked.versions` (kinds.rs:520-590). Collision's first build also allocates the full dense `size.x*size.y` cell vector (collision.rs:~351). `UVec2` chunk coordinates are in `ChunkKey` (chunks.rs:58-62), `MapOccluder.chunk` (public, occluders.rs:~50) and `TileGrid::chunk_version`; they must become `IVec2`.
5. **Draw order cannot express floors with `(z, sort_y)`.** `DrawOrder` (render/entities.rs:59-100) is z, then screen y. An elevated floor drawn shifted up has a screen y that is wrong as a depth. Entities take their key from `GlobalTransform.y` (`y_sort_key`, entities.rs:878). Correct iso sorting needs a depth key from cell space (x + y + floor bias) for both tile bands and entities, and a way to tell which map and floor an entity stands on. This is a render API addition, not a tile-layer tweak.
6. **Propagation fix still leaves an O(N) scan.** The `Changed<Transform>`/`Changed<ChildOf>`/`Added<Interpolated>` filter checks a tick per entity, about 17,000 for the edit map, three runs a frame. Skipping unchanged subtrees removes the random-access walk (the 17-24 ns), not the scan; expect roughly 85 percent of the miss gone, not all. The backlog's "44 µs inside the target" assumes zero propagation cost. Measure with `static_frame` before promising the target. See group 5.
7. **Streaming reuses less of the landing than it looks.** The off-thread job is `Worker<Landed>` (spawn.rs `spawn_maps` `Local<Worker<Landed>>`), one FIFO thread typed to whole-map landings; a chunk generator closure shares it and queues behind a big landing. On the web the job runs inline in the frame it is sent (jobs.rs:51-65), so a game's generator becomes a main-thread hitch there. `landing_job` clones the whole asset's layers (spawn.rs:~870 `asset.layers.clone()`); a streamed map's chunks live only in the entity's `TileLayerData`, so hot reload (`MapApplied`, `assign` needs equal size, grid.rs:~224) would wipe or fight generated chunks.
8. **Tiled parity items not answerable from the repo** (no Tiled source here; check Tiled's format docs before the design): oblique's fields (Tiled 1.12; nothing in the repo), Wang terrain on hex maps, the default tile-object alignment per orientation (6a's `Alignment::parse` maps unspecified to BottomLeft, objects.rs:42; Tiled uses Bottom for isometric), staggered/hex tile placement formulas, and the origin of an iso map (Tiled puts the top of cell (0,0) at x = height * tilewidth / 2, so layer space has a non-zero origin shift).

## 1. Cell and pixel

**Today.** A cell `(x, y)` is the rectangle `(x, y) * cell_size` in the layer's own pixels. Layer pixels become world through the layer entity's `GlobalTransform` (the layer is a child of the map, at its offset, spawn.rs:988-1016). A tile draws as an axis-aligned quad that "stands on the cell's bottom edge from the left, however large" (render/tiles.rs:110-135) plus the tileset offset. Row order within a chunk is the cell order (y, then x). `cell_size` lives on `TileLayerData` (spawn.rs:214) and `LayerKind::Tiles` (map.rs:166), defaulting to `TileMap::tile_size` (map.rs:185). Orientation is nowhere.

Seams (all assume the square rectangle):
- `tilemap/edit.rs:396-444`: `layer_space`, `world_to_cell` (`floor(inverse(local) / cell)`), `cell_to_world` (`(cell + 0.5) * size`), through `MapsView` (view.rs:190, :200). Iso: affine, so these are easy. Staggered/hex: need offset-coordinate round trips and nearest-hex pick. `local_to_world` (edit.rs:396) walks ancestors with `MAX_DEPTH`, fine.
- `tilemap/edit.rs:166-196`, `spawn.rs:722-730`, `reload.rs:693`: class tiles spawn at `(cell + 0.5) * cell_size`. Three copies of the formula.
- `render/tiles.rs:70-107` (`chunk_instances`) and `:110-135` (`instance`): instance place from `cell`/`cell_size`. Needs a "cell's bounding box top-left" from the orientation; the "stand on the box's bottom edge from the left" rule is Tiled's for iso too (the tile image is as wide as the diamond), so the rule can stay and only the box origin changes. Hex 120° rotation adds a rotated quad: `axes()` (:~210), `flipped_uv` (:~165) and the diagonal-swapped `drawn` size must take the rotation.
- `render/tiles.rs:773-800` (`View::draw`): chunk culling is `floor(camera box in layer px / chunk_px)` clamped to `[0, chunks-1]`. This assumes axis-aligned square chunks and origin (0,0). Iso: map the camera's four corners into cell space (affine inverse) for a chunk bounding box. That over-gathers corner chunks, and each gathered chunk is built and allocated in the arena before any visibility test (the world-box cull happens later in the batch), so test the projected chunk's box against `camera_box` before `self.chunk(...)`. `layer.margin` (tiles.rs:480-492, "how far a tile may draw past its cell") is in layer px and must be converted to cells.
- `render/tiles.rs:877-891`: y-sorted row items: `sort_y = placed(0, (row+1)*cell.y).y`. See group 4.
- `render/batch/chunks.rs:58-62` (`ChunkKey.chunk: UVec2`), `:88-97` (`ChunkRow.row: u32` "the cells' row in the layer"), `:303-325` (row runs via `chunk_by(a.1 == b.1)`, so rows must be contiguous in instance order).
- `tilemap/kinds.rs:203-225` (`placed`): authored tile shapes (tile-image px) to cell units via `px / cell` with the "bottom edge from the left" rule. Iso: image px must go through the inverse of the cell map to unit-square cell space (a diamond collision polygon becomes the unit square). `corner_of`/`slope_corner`/`full_cell` (kinds.rs:~255-300) assume the unit square cell. Hex: the cell is not a unit square, so these shape classes do not apply.
- `tilemap/tiled/objects.rs`: `position` is the top-left of the object's rectangle in map px, `rotation` about it (objects.rs:353-395). Tiled's iso objects store positions in tile-height units along the diamond's axes (and size mixed: tile objects keep image px), so every shape converts on load: points to projected space; a Rect or Ellipse becomes a Polygon (the engine's `ObjectShape::Rect` has no skewed form, map.rs:111); `MapObject.size` and `object_parts` (spawn.rs:1045-1070: centre = position + rotate(half)) assume an upright rectangle. `Alignment::parse` default (objects.rs:42) is orientation-dependent in Tiled.
- Flips: `tiled/data.rs:14-32` `decode_gid` (FLAG_BITS 0xF000_0000 drops bit 28, the hex 120° rotation). `tilemap/tile.rs` `TileFlip(u8)` (3 bits; `from_bits` masks `& 7`, `rotated_cw` table of 8 states). Cell layout (grid.rs:22-47): flips in bits 28-30 via `flip.bits() << 28`, so **bit 31 is free** and a 4th flip bit fits the 4-byte cell, but `decode` reads `from_bits((cell >> 28) as u8)` and masks to 3 bits, and the tests iterate 0..8. Touch list: `TileFlip`, `rotated_cw`, grid encode/decode, `flipped_uv`, `axes`, `kinds::placed`, `wang::flipped` (wang.rs:~80), `decode_gid`.

Staggered/hex change neighbour offsets by row parity (wang.rs uses the fixed `DIRECTIONS` offsets throughout, and passes changes on within "a square around the painted cell"). Hex needs its own position table (Tiled's hex wang ids differ); check Tiled first.
- `tilemap/padded.rs`: only reads `tileset.tile_size`/per-tile image sizes (padded.rs:160, :252); the slot is a square `layout.cell` holding each tile with its padding. **Nothing assumes the cell's shape.** Iso/hex tiles are just bigger or odd-shaped images. - Loader: `tiled/build.rs:799-811` (orientation and infinite refusals, with `tiled/build.rs:687-688` for layer `chunks`), `tiled/raw.rs:24-28` (`RawMap`: no `staggeraxis`, `staggerindex`, `hexsidelength`), `tiled/xml.rs:395-397` (TMX `<chunk>` is detected and turned into a refusal), `xml.rs:467-475`. The pinned tests: `isometric_hexagonal_staggered_oblique_and_infinite_maps_fail_naming_6b` (tiled/mod.rs:843-856) and `infinite_maps_are_refused_naming_6b`, plus xml.rs:850.

## 3. Collision

**Today.** A group of colliding layers (same cell size, offset, material from `collision_layer`/`collision_mask`/friction/restitution, collision.rs:60-120) becomes one `TileColliders` on the map entity (or on the group's first layer entity), cells classified by `kinds::layer_kind` (kinds.rs:659). `rebuild_tile_colliders` (physics/tiles.rs:1146) builds children `TilePart` entities at `Transform::IDENTITY` whose `Collider` shapes are in the entity's space: `at()`/`px()` multiply tile-unit points by `tile_size` (tiles.rs:658-685, also :729 for authored shapes). The tracing is incremental (`Outlines`, outline.rs), packed per 32x32 chunk (`pack.rs`: `PackKey::Loops(cx, cy)` by the loop's first corner, flat one-way `Row`s, sloped `Run`s) into `Collider::polyline`/`segments` (pack.rs:100-125). The first trace happens on the builder thread (`TileColliders::trace` -> `Traced`) and is consumed at `tiles.rs:1190-1200` only if generation and `tile_size` match.

- **Sheared parent.** `physics/shape.rs:57-190` `build(shape, map)` bakes the 2x2 linear map into the shape: Rect stays a cuboid only under a diagonal map, else a hull; Circle/Capsule stay round only under uniform scale, else 24-point hulls; Polygon is always a hull; Segment/Polyline/Segments map every point exactly. So a polyline outline under a sheared map is exact, but a convex hull under shear is "approximated by the convex hull of the mapped shape" only for shapes that were not already convex. The costs and the one-way trap are in Top risk 1. The character sweep (`sweep.rs`, `character.rs`) works on the baked world shapes and honours collider layer/mask (character.rs:44), so floors by collision layer is a real, existing lever.
- Tile shape seams (cell space is the unit square): `CellShape.polygons` (tiles.rs:~66-80), `SOLID`/`SLOPE_*` constants (tiles.rs:~110-125), `sides` module, `TileCell::Slope(SlopeCorner)`. Slope corners and one-way flats are square-cell concepts; for iso, decide whether `Slope`/`OneWay` are refused or ignored for non-orth layers (silent acceptance would be the "dead option" the spec forbids).
- Outline trace for iso: unchanged (cell space is square), as long as `at()` applies the map. `Collider::polygon` hulls in `solid_rects` mode (tiles.rs:~620-660) also work.
- Hex trace: see Top risk 3. What it would replace: `Unit` (outline.rs:94-100), `unit_edges` (:146-205), `boundary_edges` (:~205-225), the unit list in `apply` (:~330-345), `Cells::{at, before, edges, extent}`, `sides::*`, `GRID`/`SOLID`, `pack::chunk` and `loop_key`, `Boundary` (the occluders' facade, physics/tiles.rs, re-exported with `GRID` and `Point`). Also `TileRecord::of` and `same_settings` (settings that force a full rebuild: add the geometry).
- Nav reads this: `navigation/grid.rs:296-338` `block_tiles(tiles, origin)` uses `tiles.tile_size` and the cell index to cover rectangles; `rebuild_from_world` passes only the map's translation (grid.rs:341-360), so a scaled or turned map is not followed (documented in navigation/AGENTS.md).
- Collision per floor: already expressible as one group per floor if each floor layer carries a `collision_layer` bit (GroupKey includes material and offset, collision.rs:60-78), but the occluder groups key only by `cell` + `offset` (occluders.rs:~75-100), so shadows from stacked floors merge unless offsets differ. There is no floor notion in `CharacterController`; moving between floors means rewriting the character's `Collider::layer/mask`; collision layers are 32 bits.
- Limits that bite infinite: `MAX_SIDE` 8192 in two places (collision.rs:51, tiles.rs:424).

## 4. Drawing order and y-sort

**Today.** Everything resolves to `DrawOrder { z: i32, sort_y: Option<f32> }` (entities.rs:59-100): z first, plain before y-sorted within a z, y-sorted by `sort_y`, ties by the draw's `entity_order` then its `index` (`OrderedDraw::sort`, entities.rs:139-147). A tile layer's z is `root.z + layer index` (tiles.rs:~560). A plain layer's chunks are pushed in loop order `y` then `x` (tiles.rs:798-801) all at `DrawOrder::plain(z)`, so push order is draw order (ties by index). A y-sorted layer emits one item per (tileset, row, chunk, camera) at `sort_y = layer-left bottom of the row, through the layer's transform` (tiles.rs:877-891), so rows interleave with entities (`y_sort_key`, entities.rs:878: GlobalTransform y minus pivot plus `foot_offset` plus `sort_offset`). Tile objects on a y-sorted layer sort by their feet (tiles.rs:1108-1111).

Seams:
- Iso row order: the screen row is `x + y` (the diagonal), not the grid row. `chunk_instances` produces `(tileset, row, instance)` in row-major order and the store needs rows contiguous (`chunk_by(a.1 == b.1)`, chunks.rs:303-318); give it `band = x + y` and sort each tileset's instances stably by band (still right-down within a band; Tiled's right-down is a valid painter's order for iso/staggered within a chunk). `ChunkRow.row` becomes "sort band"; `sort_y` for a band = the screen y of the band's cell bottoms through the orientation, not `(row+1)*cell.y`.
- Staggered and hex: screen rows are the grid rows (every row is one y), so rows work as today with the orientation's row pitch; hex row pitch is 3/4 of the height. `ChunkRow.min/max` are bounding boxes from the instances' reach (chunks.rs:508-518), orientation-agnostic.
- Non-y-sorted iso layers: chunk pushes must be in a painter-valid order (row-major by chunk is valid for right-down; tall tiles crossing chunk borders are where it matters).
- Cross-floor order: Top risk 5. `z` is per layer, so floors as layers already stack as z; a tile on floor 1 always draws over an entity at floor 0's z even where the entity should be in front. Options: a new `sort depth` field in `DrawOrder` (f32 beside `sort_y`, from cell space), a per-entity floor/depth component read by `y_sort_key`, and the same on tile bands; or interleave z (floor k's layers and its entities share a z) so only same-floor sorting matters, which fails for tall walls of the floor above. Whichever is chosen, `DrawOrder::cmp` is crate-private (entities.rs:59), so this is an internal change with `layers_then_plain_then_sort_y` (entities.rs:988) as the pin.
- Lights/occluders per floor: lit flag is per layer (`info.lit`), not per floor depth.

## 5. Transform propagation

**Today** (`src/core/ecs/propagate.rs`, 370 lines, tests inline from :133). One system, `propagate_transforms`, with queries: `roots` (`Without<ChildOf>`, with `Ref<Transform>`, `&mut GlobalTransform`, `Option<&Children>`, `Has<Interpolated>`, `Has<PreviousGlobalTransform>`), `nodes` (`With<ChildOf>`), `grouping` (entities with `Children` and no `Transform`), and `changed: Query<(), Or<(Changed<Transform>, Changed<ChildOf>, Added<Interpolated>)>>` (:19, :43-46). Early out (:58-66): if no `RemovedComponents` of `ChildOf`/`Interpolated`/`Transform` and `changed.is_empty()`, return. Otherwise it walks **every root** and, by a `Local<Vec<(Entity, GlobalTransform, bool, bool)>>` stack (kept between runs, allocates nothing warm), **every descendant of every root**: a node recomputes when `parent_changed || Ref<Transform>.is_changed() || Ref<ChildOf>.is_changed()` and writes through `set_if_neq` (so an unmoved entity's `GlobalTransform` stays unchanged for downstream `Changed` readers). `sync_previous` (:104-120) runs at every visited node and inserts or removes `PreviousGlobalTransform` so it exists exactly under `Interpolated`. `grouping` entities push their children from the identity, "changed" only when the group's `Transform` was removed (:77-81; the test `a_grouped_child_is_left_alone_when_something_else_moved` pins that nothing else recomputes them).

- **Why three runs a frame.** `engine/mod.rs:481` registers it in `FixedSet::Transforms` (the end of each fixed step, after physics write-back), `engine/mod.rs:493` in `PostUpdateSet::Transforms` (per-frame edits), and physics' own `PhysicsSchedule` runs it as its third system each step (`physics/sync.rs:891`, a separate single-threaded schedule). Each system instance has its own `last_run` tick, so each sees the changes made since its own previous run; a fixed step that does not run in a frame means fewer runs. The three exist for correctness (game edits in Movement must be world-current before physics reads `GlobalTransform`; physics write-back must be world-current before the next Update; per-frame edits before rendering), so "run once" is not an option.
- The `Transform` insert hook `place_on_insert` (transform.rs:95, :161-177) sets `GlobalTransform` at once from the parent's current global, so spawns are placed before propagation. Skip designs must keep this and still treat the inserted entity as changed (its `Changed<Transform>` stays true, so it does).
- **Where "skip unchanged subtrees" hooks in.** Replace the root/stack seeding (:68-87):
  - *Walk up from `changed`:* collect changed entities into a `Local<Vec<Entity>>`, compute each one's depth by following `ChildOf`, sort ascending by depth (or process by topological order using a visited stamp), and for each changed entity compute `parent_global * local` from the parent's **stored** `GlobalTransform` (already current if the parent was processed first or never changed). Descend into the children only when the entity's result changed (value check; the current walk descends on the flag, so this also prunes equal-result subtrees) or when a descendant is itself in the changed set. This needs no marker components and no per-frame component churn. Cost: O(changed x depth) plus the children walked under changed parents; the problem case is a changed entity with a huge children list (the map entity itself moving), which is a real full walk and fine.
  - *Marker approach (bevy's `TransformTreeChanged`):* a system marks ancestors of changed entities; propagation descends only into marked children. Adds a component insert/remove per marked entity each frame and an extra system per run; worse for this engine's three-runs-a-frame shape.
  - The existing `RemovedComponents` triggers (`detached`: root placed by its own `Transform`; `untransformed`: grouped children from the identity; `uninterpolated`: `PreviousGlobalTransform` must be stripped from a whole subtree) still need subtree walks of just the affected entities. `Added<Interpolated>` also requires walking the subtree to insert `PreviousGlobalTransform` (`sync_previous` for every descendant). A newly parented entity under an Interpolated parent must get one too.
- **The scan stays.** Collecting `changed` still evaluates the `Or<Changed..>` filter on every entity with those components, a per-entity tick compare over the whole table; `is_empty()` today stops at the first hit. For 17,000 map children that is real (order of 1-2 ns each, three runs), so measure with `static_frame` (benches/tilemap.rs:406-635) and the `edit` bench before promising the target. A cheaper structural option that removes the scan for the map's parts is to keep static map children out of the scanned archetype (for instance spawn collider parts and occluders without a `Transform` component and give them a render/physics-only placement), but that changes `TilePart`/`MapOccluder` contracts and physics reads their `GlobalTransform`, so it is a bigger change than the backlog implies.
- **Tests and benches that pin it.** `propagate.rs` inline tests: `a_spawned_entity_is_placed_before_propagation`, `inserting_a_transform_places_the_entity_at_once`, `removing_child_of_makes_the_entity_a_root_at_its_local_transform`, `a_still_world_is_not_rewritten`, `a_child_of_a_grouping_entity_starts_from_the_identity`, `a_grouped_child_is_left_alone_when_something_else_moved`, `children_start_from_the_identity_once_their_parent_loses_its_transform`, `child_of_rotated_parent`, `three_levels_compose`, `unchanged_subtrees_are_not_rewritten`, `reparenting_recomputes`, `child_of_a_transform_less_parent_treats_it_as_identity`, `interpolated_ancestors_mark_descendants`, `despawning_a_parent_removes_descendants`. Others that schedule it: `tests/integration/transform.rs` (its `propagate` helper, :15; child-of-rotated-parent at :114, detach_keep_world at :138), `ecs/world_ext.rs:107-147`, `particles/mod.rs:1162`, `physics/sync.rs` (:1603, :3043, :3233, :3398, :3433), `benches/foundation.rs` (`propagate 10k, nothing moved` / `every root moved`: **no bench has one leaf moved in a big tree**, add one), `benches/tilemap.rs` `static_frame` and `edit`, and `tests/tilemap_alloc.rs` (a warm run allocates nothing: keep the `Local` stack, and any new `Local` scratch).
- Docs to change: `src/core/ecs/AGENTS.md` ("Propagation" bullet with the Known cost), `docs/backlog/tilemap.md` Limits, `docs/backlog/follow-ups.md`, skill `ryo-ecs-internals`.

## 6. Navigation

**Today.** `NavigationGrid` (navigation/grid.rs:55-107) is a bounded dense `Vec<CellState>`, square `cell_size: f32`, origin offset, `GridCoord{x,y}: i32`. `neighbors` (:190-232) is the hard-coded 8-direction square model with corner-cutting checks and `SQRT_2` costs; `line_of_sight` (:234-264) is Bresenham on the square grid; `world_to_grid`/`grid_to_world` (:124-146) are axis-aligned. `Pathfinder` (pathfinder.rs) is generic over `grid.neighbors` but hard-codes `octile_distance` (:454-465), a cross-product tie break on square coords (:384-391), and `PathfindingState::new` uses octile for `f_score` (:153). `Path::smooth_line_of_sight` (path.rs:177-202) and `PathNode.grid_coord` ride on `line_of_sight`. `block_tiles` (grid.rs:296-338) reads `TileColliders` (dense, `tile_size`, cell kinds) at the map's translation only. `rebuild_from_world` skips `TilePart` and uses `TileColliders` instead (:341-360). Nothing runs in the engine loop; games own the grid and pathfinder (navigation/AGENTS.md). Used by `crates/ryo2d-procgen/src/grid.rs:384-395` (`to_navigation_grid`) and `tests/integration/navigation.rs`.

Seams for hex/iso:
- Introduce a topology on `NavigationGrid` (enum or trait: `Square`, `Iso`, `Hex { axis, stagger }`) behind `neighbors`, `distance` (heuristic: octile for square and iso-as-square, axial/cube distance for hex), `world_to_grid`/`grid_to_world`, `line_of_sight` (hex: cube-lerp line; iso: Bresenham in cell space) and the tie-break. `Pathfinder` must call the grid's distance instead of the free `octile_distance`, and the `GridCoord` offset/cube conversion (stagger parity) belongs to the topology.
- Iso is a square graph in cell space: neighbours and heuristic are the existing ones (4 or 8 directions in cell space; in screen space the cost of a diagonal differs, so cost per step should follow world distance if paths are meant to look shortest on screen). Only the cell-to-world map changes.
- `block_tiles` must take the same `CellGeometry` as `TileColliders` and cover the cells a tile polygon touches (hex: nearest cell centre or polygon overlap), not rectangles.
- Bounded and origin-based (`in_bounds` at :148-151, `cell_index`): an infinite map needs a sparse or windowed grid (the demo pathfinding example is the user surface: examples/demos/pathfinding).
- `CellState`/`Path` types and the `NavAgent` API stay. The `GridCoord::new(x, y)` public API is square-offset coordinates; for staggered/hex say which coordinate system (offset as Tiled stores it) it holds.

## 7. Asset loading and the landing job

**Today.** The Tiled/LDtk readers are registry loaders (`TiledMapLoader`, tiled/mod.rs; `LdtkLoader`) on the asset workers; the loaded `TileMap` is an asset. A `MapRoot` entity (spawn.rs:118-195) names the asset. `spawn_maps` (spawn.rs:475-557, `PreUpdate`, after the asset pump): `readiness` decides Spawn/Failed; `landing_job` (:856-905) copies the asset's layers, class tiles, collision/shadow inputs and pads not-yet-padded tilesets into a `LandingJob`; `worker.send(job.run)` (Worker in jobs.rs, thread name "ryo2d map builder", started on the first job; `Local<Worker<Landed>>` in the system); the `MapLanding { job }` marker records the id; `worker.finished()` returns `Landed` (layers planned with class tiles out and every chunk dirty, `collision::Prepared`, `occluders::Prepared`, `MapApplied`, paddings); `is_stale` re-sends if a file reloaded meanwhile; `land` (:1076-1156) spawns layers, objects' entities, colliders, occluders, object components (observers run), class tiles, then `MapEvent::Spawned`. A panicking landing is retried once on the main thread, then `MapEvent::Failed` (`landing_failed`, :575). `reload_maps` (reload.rs) diffs a spawned map against `MapApplied` after a save. Where there is no thread (the web; `std::thread::Builder::spawn` fails) the job runs inline in `send` (jobs.rs:51-65, "expected on the web").

What a streamed chunk would reuse:
- **Reusable as is:** `TileLayerData` as the live copy (edits already change only this map); `TileGrid` versions as the change signal for the chunk store, collision and occluders (they all poll `chunk_version` once the grid is sparse); `kinds::layer_kind` classification; `sync_map_colliders` (FixedSet::Movement) and `sync_map_occluders` (PostUpdate) as the main-thread incremental path (an edit's chunk rebuild measured 20-23 µs, collision and shadows ~65-80 µs, edit bench), so a chunk of tiles written on the main thread already collides and casts shadows within the step/frame; `LayerTiles` class tiles; `PaddedCache`; `MapEvent` plus a new `ChunkLoaded`/`ChunkUnloading` message.
- **Not reusable:** the whole-map landing job and `Landed` (typed to the entire map; `MapLanding` is one job per map; `plan_layer` marks the whole grid dirty and takes class tiles by scanning every cell); `collision::prepare` and `occluders::prepare` build a whole group's dense state off-thread. A chunk-level off-thread classify/trace job is new, and the single FIFO worker would queue it behind a big landing; give chunk jobs their own worker (or a priority) and decide the web behaviour explicitly (inline = hitch; maybe cap chunks per frame).
- The generator hook runs where? A game closure filling a chunk on the builder thread must be `Send + 'static` and cannot read the `World`; on the main thread it runs in the frame (simple, deterministic, procgen-friendly). Both modes need "chunks near cameras/players" requests (a system reading `Camera` views or a `Tracks` component), a keep window, and an unload hook that returns the chunk's cells (save hook) before `remove_chunk`, then tears down the chunk's colliders (cells set to Empty through `TileColliders`), `MapOccluder`s of that chunk, `LayerTiles` class tiles, chunk-store arena entries (they free by KEEP_FRAMES when undrawn, chunks.rs `end_frame`/`evict_oldest`), objects spawned from it.
- Hot reload: `MapApplied` (reload.rs:125-) records what the file had; with a runtime-grown layer there is no file; with Tiled infinite maps a save changes chunks the game also touched. The three-way diff (file then / file now / entity now) `assign` implements per chunk needs a chunk-set version.
- Ready-check/`readiness` (spawn.rs:631) and `landing_stamp` (:602): unchanged. `MapRoot` for a code-built infinite map still needs a `TileMap` asset for tilesets/orientation (`Handle<TileMap>` from `Assets::add`); its `layers` hold no chunks.
- `inherit_tile_data` (spawn.rs:422) and `class_tiles` (:771) run on the main thread in `landing_job` over the asset; per-chunk streaming must reuse their results (cache `ClassTiles` on the map), not recompute per chunk.
