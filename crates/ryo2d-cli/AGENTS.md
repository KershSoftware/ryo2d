# AGENTS.md - The `ryo2d` command

The `ryo2d-cli` crate (binary `ryo2d`, `run_cli` in `src/lib.rs`) depends on the engine, so a game never compiles it. The engine's items it needs are `pub` there.

## Conventions

- **One parser, typed errors, exit codes that mean something** - `args.rs` is the one place arguments are read (clap derive: `Cli`, `Command`, one `*Args` struct per command), so a command's `--help` is generated from it and an unknown flag or command is clap's one error line with exit code 2 (`every_command_rejects_a_flag_it_does_not_know`, `an_unknown_command_is_one_error_line`). Failures are `CliError` (`error.rs`, thiserror), which keeps its cause as a source (`cli_errors_keep_their_cause`): `Workspace`, `Io { context, source }`, `Build { status }`, `GameExited { code }`, `NoBuild` and `Other`. `CliError::exit_code` is 1 for all but `GameExited`, whose code passes through clamped to 1..=255 (`exit_codes_pass_the_game_s_through_and_never_read_as_success`). The error is printed once, by `run_cli`
- **Workspace-aware** - Resolve the project root with `discover_workspace()` (wraps `Workspace::discover()`, which finds `Ryo.toml`). Never use raw cwd paths
- **Wrap Cargo, don't reimplement it** - `build` → `cargo build --release`; `dev` → `cargo run`; `run` executes the built binary
- **A release has no developer tools** - `build` compiles without debug assertions and without the `dev-tools` feature, so the console, the dev windows, the debug keys (but F5) and the log ring are not in the game. `build --dev-tools` adds `--features ryo2d/dev-tools` to the cargo command (`release_build_command`, tested on the command it builds) and prints one warning, `this build includes developer tools: do not ship it`. `build` embeds only the `[debug]` values Ryo.toml sets (`config/AGENTS.md`). An argument `build` does not know is an error naming it and the valid flags (`build_takes_dev_tools_and_nothing_else`), so a misspelt `--dev-tool` never makes a plain build; nothing is forwarded to cargo
- **`dev -p` names the engine's package** - `dev --profiler` (`-p`), or `[debug] enable_profiler = true`, adds `--features ryo2d/profiler` to `cargo run`, so a game needs no `profiler` feature of its own (the engine's macros are compiled with the engine's feature); `-p` also sets `RYO_PROFILER_AUTO_OPEN=1`. The limit: a game that renames its `ryo2d` dependency cannot use `-p`
- **The game's environment passes through** - `dev` and `run` start the game with the CLI's environment, so `RYO_LOG`, `RYO_CAPTURE_*`, `RYO_INPUT` and `RYO_HEADLESS` reach it; `check-ui` switches the log's stderr output off and prints its own lines
- **The CLI shows the engine's log** - `run_cli` turns the log's stderr output on first thing, in every build: the installed CLI is built without tools (whose stderr output starts off) and opens no log file, so without it Ryo.toml's warnings would go nowhere (`the_cli_shows_the_engine_s_warnings_in_every_build`, which also checks `check-ui` turns it off)
- **The engine's insides come through `ryo2d::tooling`** - the one doc-hidden, unstable module for tools (`embedded_config_env` with `EMBED_KEYS`, the save folder checks, the UI file checks, the log's stderr switch). The command uses nothing else that is not in the prelude; the rest of the engine's config and UI file code stays crate-private. A new need is added there, not by widening a module. The command's files include `src/assets/` by relative path, which a `cargo package` of this crate would have to replace
- **Build validates first** - `build` validates the `[release]` save folder name before compiling, and creates `release/data/` only in portable mode
- **Output** - Use the `Output::status/success/warning/error` helpers (Cargo-style right-aligned labels, no color)
- **Font licences** - `build` writes `release/licenses/` and `export` writes it into the release before zipping: the built-in fonts' licence texts (`src/assets/fonts/`, two SIL OFL 1.1 and one CC0) and a README naming the fonts, compiled in with `include_str!` (`commands/licenses.rs`). OFL condition 2 asks that every copy of the fonts carries them. A new built-in font needs its licence added there. The CLI has no web build; a game shipped to the web by hand must ship `licenses/` itself

- **`check-ui`** (`commands/check_ui.rs`) checks `*.ui.ron` files without running the game: the files given, or every one under the assets directory. The checks themselves live in `src/core/ui/file/check.rs` (the load checks, imports read from disk, image paths that do not exist), so the command only finds files, prints `path:line:column: message` and exits non-zero on any problem. Paths in UI files are asset paths, relative to the assets directory, and issue paths are printed the same way (`ui/menu.ui.ron`), with `/` separators; a file given that is not under the assets directory is reported as not an asset path.
- **`sheet`** (`commands/sheet.rs`) draws a skeleton's animations as a contact sheet through `testing::skeleton_sheet` (the testing module notes) and writes a PNG, `NAME.sheet.png` in the current folder unless `--out` says where (not beside the file, so nothing generated lands in the assets folder a release ships). An `--out` inside the assets folder (canonical, so a path that leaves and comes back in counts) is written with a warning that a release would ship it (`a_sheet_written_into_the_assets_folder_is_warned_of_and_written`), and a folder of `--out` that does not exist is made before anything is drawn, or the trouble said then (`a_missing_out_folder_is_made_before_drawing`). The project is found from the file's folder (`Workspace::discover_from`), and the file must be under its assets folder, both canonical: its images are asset paths from there, so a file outside is refused with a message before anything is drawn (`a_file_outside_the_project_s_assets_folder_is_refused`). `run` takes the drawing as a function, the seam the tests use: no GPU is a message, not a panic (`no_gpu_is_a_message_not_a_crash`), and the asset path handed on has `/` between folders (`the_sheet_is_drawn_from_the_file_s_asset_path_and_written`). An option it does not know, a missing value, `--moments` or `--hz` that is not a whole number and `--cell` not `WxH` are clap errors naming the trouble (`arguments_it_cannot_read_say_why`); `--animations`, `--skins` and `--once` take comma lists, and `--hz N` is `SheetOptions::fixed_hz`, stepping at the engine's default 60 steps a second unless given (`the_arguments_become_the_sheet_s_options`).

## Skills

- `.claude/skills/<name>/SKILL.md` is the one copy of each skill: `init` and `install-skills` ship it as it is. The crate's build script (`build.rs`, `list_skills`) writes `embedded_skills.rs` to `OUT_DIR`, an `include_str!` of every skill folder's `SKILL.md`, which `EMBEDDED_SKILLS` (`commands/install_skills.rs`) includes. An edited skill rebuilds through `include_str!`, and a new or removed folder reruns the build script, so a skill needs no step beyond writing it
- The listing printed during install reads each description from the skill's frontmatter (`skill_description`). Only `SKILL.md` is shipped: a skill that grows other files needs the installer to ship them too
- `installing_writes_every_skill_folder_as_it_is` installs into a temporary folder and checks it holds every skill folder's `SKILL.md` byte for byte, and nothing else
