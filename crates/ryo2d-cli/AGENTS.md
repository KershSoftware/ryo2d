# AGENTS.md - The `ryo2d` command

The `ryo2d-cli` crate (binary `ryo2d`, `run_cli` in `src/lib.rs`) depends on the engine, so a game never compiles it. The engine's items it needs are `pub` there.

## Conventions

- **One parser, typed errors, exit codes that mean something** - `args.rs` is the one place arguments are read (clap derive: `Cli`, `Command`, one `*Args` struct per command), so a command's `--help` is generated from it and an unknown flag or command is clap's one error line with exit code 2 (`every_command_rejects_a_flag_it_does_not_know`, `an_unknown_command_is_one_error_line`). The help is clap's too: a command's doc comment is its short help, its later paragraphs `--help`'s long help, and `after_help` constants carry examples and requirements, so nothing is hand-written elsewhere (`help_keeps_what_the_hand_written_help_said`, `ryo2d_help_lists_every_command`). clap is built without its `color` feature, so help and errors have no colour (`version_is_a_flag_and_help_has_no_colour`). A bare `ryo2d` prints the help to stderr and exits 2 (`a_bare_ryo2d_prints_the_help_and_exits_2`), and `--version` replaces the old `version` word. Failures are `CliError` (`error.rs`, thiserror), which keeps its cause as a source, so the message and the cause are separate and `report` joins them once for printing (`cli_errors_keep_their_cause`): `Workspace`, `Io { context, source }`, `Build { status }`, `GameExited { code }`, `NoBuild` and `Other`. `CliError::exit_code` is 1 for all but `GameExited`, whose code passes through clamped to 1..=255 (`exit_codes_pass_the_game_s_through_and_never_read_as_success`). The error is printed once, by `run_cli`
- **A prompt never acts without a person** - every question goes through `Prompt` (`prompt.rs`): with no terminal on stdin (`is_terminal`) nothing is read and the answer is no, and the end of input is no (`with_no_terminal_nothing_is_read_and_the_answer_is_no`, `end_of_file_is_no`); an answer is read a line each (`answers_are_read_a_line_each`) and the command then says which flag would do it. `init` with no name and no terminal fails naming `ryo2d init NAME` and creates nothing (`init_with_no_terminal_needs_a_name`). `dev` adds `[profile.dev.package."*"]` to Cargo.toml only on a yes (`a_yes_adds_the_profile_and_a_no_does_not`), and with no terminal prints the profile and a hint naming `--skip-opt-check` (`with_no_terminal_dev_leaves_cargo_toml_alone`). `init --skills claude|copilot|both|none` installs without asking; without it a terminal is asked (an empty answer is Claude, `an_empty_answer_to_the_skills_question_means_claude`) and no terminal installs none and says how, naming `install-skills --skills <claude|copilot|both|none>` (`init_with_no_terminal_and_no_flag_installs_no_skills_and_says_how`, `init_skills_flag_installs_what_it_names`); `install-skills` takes the same flag (`--skills none` says none were installed, `install_skills_none_says_it_installed_nothing`), and with neither flag nor terminal installs nothing and fails; an answer that is none of the options fails the same way (`install_skills_with_no_terminal_and_no_flag_installs_nothing`, `no_valid_answer_installs_nothing_and_says_so`, `an_answer_in_a_terminal_picks_the_assistant`). `netplay start` installs `matchbox_server` and `cloudflared` only on a yes, behind `install_if_agreed` (`netplay_never_installs_without_a_yes`). Tests build a `Prompt::scripted` and never read stdin
- **`init`'s files are templates** - `templates/*.tmpl` (`main.rs`, `Cargo.toml`, `Ryo.toml`, `README.md`, `.gitignore`, `build.rs`) are read with `include_str!` in `templates.rs`, and `templates::render` replaces `{{key}}` and fails naming any `{{` left (`a_placeholder_left_unreplaced_is_an_error`, `every_template_renders_with_init_s_values`). `tests/init_builds.rs` runs `init game --skills none` with a temporary `HOME` holding an empty `.ryo2d/engine` (and `LOCALAPPDATA` for Windows), points the generated dependency at this checkout, copies the workspace's `Cargo.lock` in (so the engine's tree stays locked; only the project and its `winresource` build dependency are resolved, which needs the registry) and `cargo check`s the project with `CARGO_TARGET_DIR` set to the workspace's target folder on the child only (`init_makes_a_project_that_builds`); the project is outside the repository so its workspace does not claim it. `init` refuses a name cargo would (a leading digit, a Rust keyword, `test`) before writing anything (`a_name_cargo_refuses_is_refused_before_anything_is_written`), and the new `.gitignore` leaves `Cargo.lock` to be committed, as a game is a binary (`a_new_game_s_gitignore_keeps_cargo_lock`). No command's help or `init`'s next steps promise what is not there (`help_text_promises_nothing_that_is_not_there`)
- **Workspace-aware** - Resolve the project root with `discover_workspace()` (wraps `Workspace::discover()`, which finds `Ryo.toml`). Never use raw cwd paths
- **Wrap Cargo, don't reimplement it** - `build` → `cargo build --release`; `dev` → `cargo build` and then the executable it reports, run by the command; `run` executes the built binary. Cargo says where things are (`cargo.rs`): `cargo::game` reads the target folder and the game's binary from one `cargo metadata --format-version 1 --no-deps`, and `cargo::build`/`cargo::execute` run `cargo build --message-format=json-render-diagnostics` (diagnostics stream to the terminal) and return the `executable` of the project's binary `compiler-artifact`, so the game's binary is chosen before building as `cargo run` chooses it (`default-run`, else the only bin, else an error naming the bins and asking for `default-run`) and built with `--bin` (`the_game_is_the_default_run_binary_or_the_only_one`), and a `CARGO_TARGET_DIR`, a configured `target-dir` and a workspace are honoured and nothing guesses a path or sets `CARGO_TARGET_DIR` (`the_target_folder_comes_from_cargo_metadata_and_honours_cargo_target_dir`, `build_returns_the_executable_cargo_reports`, `a_compile_error_is_a_build_failure`). The game runs from the project folder, as `cargo run` ran it (the binary test's game exits 3 only when `Ryo.toml` is in its working directory). `cargo::run_game` turns the game's failure into `GameExited` with its code (`run_game_s_failure_is_the_game_s_code`; 128 plus the signal for a Unix signal, `a_signal_is_128_plus_its_number`), which `run` and `dev` exit with (`a_game_s_exit_code_passes_through_run_and_dev`); `run` with nothing built says to run `ryo2d build` (`run_without_a_build_says_to_build`). `run` and `export` find the binary by that choice, not by the package name, with or without `.exe` (`cargo::find_binary`, `a_built_binary_is_found_with_or_without_exe`, `run_finds_the_release_binary_cargo_would_run`), and the bundle keeps the name cargo gave its executable, `.exe` included, whatever the host (`the_bundle_s_binary_keeps_the_name_cargo_gave_it`). The test crates build under `cli-test-crates` in the target folder cargo reports (a set `CARGO_TARGET_DIR` included), passing `CARGO_TARGET_DIR` to the child only. `dev` is not `cargo run`: it runs the built binary itself, so it does not set cargo's `CARGO_*` runtime variables or add `target/<profile>/deps` and build-script link paths to the library search path (`DYLD_FALLBACK_LIBRARY_PATH`, `LD_LIBRARY_PATH`, `PATH`); a game with a cargo-built dynamic library, or one that reads `CARGO_MANIFEST_DIR` at runtime, needs `cargo run`
- **A release has no developer tools** - `build` compiles without debug assertions and without the `dev-tools` feature, so the console, the dev windows, the debug keys (but F5) and the log ring are not in the game. `build --dev-tools` adds `--features ryo2d/dev-tools` to the cargo command (`release_build_command`, tested on the command it builds) and prints one warning, `this build includes developer tools: do not ship it`. `build` embeds only the `[debug]` values Ryo.toml sets (`config/AGENTS.md`). An argument `build` does not know is an error naming it (and a close match, if there is one) (`build_takes_dev_tools_and_nothing_else`), so a misspelt `--dev-tool` never makes a plain build; nothing is forwarded to cargo
- **`dev -p` names the engine's package** - `dev --profiler` (`-p`, `dev_takes_its_flags_in_either_form`), or `[debug] enable_profiler = true`, adds `--features ryo2d/profiler` to the cargo build, so a game needs no `profiler` feature of its own (the engine's macros are compiled with the engine's feature); `-p` also sets `RYO_PROFILER_AUTO_OPEN=1`. The limit: a game that renames its `ryo2d` dependency cannot use `-p`
- **The game's environment passes through** - `dev` and `run` start the game with the CLI's environment, so `RYO_LOG`, `RYO_CAPTURE_*`, `RYO_INPUT` and `RYO_HEADLESS` reach it; `check-ui` switches the log's stderr output off and prints its own lines
- **The CLI shows the engine's log** - `run_cli` turns the log's stderr output on first thing, in every build: the installed CLI is built without tools (whose stderr output starts off) and opens no log file, so without it Ryo.toml's warnings would go nowhere (`the_cli_shows_the_engine_s_warnings_in_every_build`, which also checks `check-ui` turns it off)
- **The engine's insides come through `ryo2d::tooling`** - the one doc-hidden, unstable module for tools (`embedded_config_env` with `EMBED_KEYS`, the save folder checks, the UI file checks, the log's stderr switch). The command uses the prelude, `ryo2d::testing` and `tooling` for the rest, and its tests may use `ryo2d::core::config` and `ryo2d::logging` (their tests build workspaces from a folder with `Workspace::from_path`, so `from_toml_str` stays crate-private); the rest of the engine's config and UI file code stays crate-private. A new need is added to `tooling`, not by widening a module. `tooling::VERSION` is the engine's version, which `--version` prints (`version_is_a_flag_and_help_has_no_colour`) The command's files include `src/assets/` by relative path, which a `cargo package` of this crate would have to replace
- **Export ships a game that runs** - `export`'s zip writes the release's top-level file named like the game's binary (the bundle's binary as `build` named it, `.exe` included, which gets 0o755 harmlessly) with mode 0o755 and every other file 0o644 (`the_exported_game_is_executable_and_its_assets_are_not`). It never zips the release's `data/`, which holds the developer's saves and settings from playing the bundle: a portable game gets an empty `data/`, any other none, and one line says it was left out (`an_export_never_ships_what_is_in_release_data`; a `data` folder deeper down is shipped, `a_folder_named_data_below_the_top_level_is_shipped`). The date in its name is the UTC date from `utc_date_stamp`, civil-from-days over `SystemTime` with no FFI and no `unsafe` (`the_date_stamp_is_the_utc_date`, leap days included)
- **Build keeps a portable build's saves** - `build` replaces everything in `release/` but `release/data/` when `[release] portable = true` (`rebuilding_keeps_a_portable_build_s_saves`); any other build removes `data/` (`a_build_that_is_not_portable_removes_the_data_folder`). Cleaning treats a link as a file, never following it, and an unreadable `release/` is an error (`cleaning_removes_a_link_to_a_folder_and_not_what_it_points_at`, `a_release_folder_that_cannot_be_read_is_an_error`)
- **Build validates first** - `build` validates the `[release]` save folder name before compiling, and creates `release/data/` only in portable mode
- **Output** - Use the `Output::status/success/warning/error` helpers (Cargo-style right-aligned labels, no colour)
- **Font licences** - `build` writes `release/licenses/` and `export` writes it into the release before zipping: the built-in fonts' licence texts (`src/assets/fonts/`, two SIL OFL 1.1 and one CC0) and a README naming the fonts, compiled in with `include_str!` (`commands/licenses.rs`). OFL condition 2 asks that every copy of the fonts carries them. A new built-in font needs its licence added there. The CLI has no web build; a game shipped to the web by hand must ship `licenses/` itself

- **`check-ui`** (`commands/check_ui.rs`) checks `*.ui.ron` files without running the game: the files given, or every one under the assets directory. The checks themselves live in `src/core/ui/file/check.rs` (the load checks, imports read from disk, image paths that do not exist), so the command only finds files, prints `path:line:column: message` and exits non-zero on any problem. Paths in UI files are asset paths, relative to the assets directory, and issue paths are printed the same way (`ui/menu.ui.ron`), with `/` separators; a file given that is not under the assets directory is reported as not an asset path.
- **`sheet`** (`commands/sheet.rs`) draws a skeleton's animations as a contact sheet through `testing::skeleton_sheet` (the testing module notes) and writes a PNG, `NAME.sheet.png` in the current folder unless `--out` says where (not beside the file, so nothing generated lands in the assets folder a release ships). An `--out` inside the assets folder (canonical, so a path that leaves and comes back in counts) is written with a warning that a release would ship it (`a_sheet_written_into_the_assets_folder_is_warned_of_and_written`), and a folder of `--out` that does not exist is made before anything is drawn, or the trouble said then (`a_missing_out_folder_is_made_before_drawing`). The project is found from the file's folder (`Workspace::discover_from`), and the file must be under its assets folder, both canonical: its images are asset paths from there, so a file outside is refused with a message before anything is drawn (`a_file_outside_the_project_s_assets_folder_is_refused`). `run` takes the drawing as a function, the seam the tests use: no GPU is a message, not a panic (`no_gpu_is_a_message_not_a_crash`), and the asset path handed on has `/` between folders (`the_sheet_is_drawn_from_the_file_s_asset_path_and_written`). An option it does not know, a missing value, `--moments` or `--hz` that is not a whole number and `--cell` not `WxH` are clap errors naming the trouble (`arguments_it_cannot_read_say_why`); `--animations`, `--skins` and `--once` take comma lists, and `--hz N` is `SheetOptions::fixed_hz`, stepping at the engine's default 60 steps a second unless given (`the_arguments_become_the_sheet_s_options`).

## Skills

- `.claude/skills/<name>/SKILL.md` is the one copy of each skill: `init` and `install-skills` ship it as it is. The crate's build script (`build.rs`, `list_skills`) writes `embedded_skills.rs` to `OUT_DIR`, an `include_str!` of every skill folder's `SKILL.md`, which `EMBEDDED_SKILLS` (`commands/install_skills.rs`) includes. An edited skill rebuilds through `include_str!`, and a new or removed folder reruns the build script, so a skill needs no step beyond writing it
- The listing printed during install reads each description from the skill's frontmatter (`skill_description`). Only `SKILL.md` is shipped: a skill that grows other files needs the installer to ship them too
- `installing_writes_every_skill_folder_as_it_is` installs into a temporary folder and checks it holds every skill folder's `SKILL.md` byte for byte, and nothing else
