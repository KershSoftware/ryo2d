# AGENTS.md - UI Module

## Architecture

The UI is built every frame in `Scene::ui` through `UiContext` (`immediate/context.rs`):

- **Absolute drawing** (`draw_*`, `ui.text(..).at(..)`) records at once: HUDs, debug overlays.
- **Widgets and containers** (`widgets/`, `containers.rs`) are laid out by the layout engine and report what the pointer, keyboard and pad did through a `Response` (`ui.button("Go").clicked()`), resolved before the scenes against last frame's layout (see Interaction).
- **Game data stays with the game**: widgets take `&mut bool`, `&mut f32`, `&mut usize` or `&mut String`. What a widget remembers itself (an open list, a caret, a scroll offset) lives in `UiMemory` under its id.
- **Popups** (`popup.rs`) are built where they are called and drawn when their scene's UI ends (see Popups and dialogs).

## Integration Point

`Scene::ui(&mut self, ui: &mut UiContext, ctx: &mut SceneContext) -> SceneAction` runs once per frame for the visible scenes, bottom-up, **before** the fixed steps (`Engine::ui_pass`, `engine/frame.rs`). Engine stats/FPS overlays and the dev console are drawn into the same `UiContext` after the scenes, on the overlay layer, so they appear on top of the scenes' pages and popups alike.

- **Input**: `UiContext` reads a `UiInput` snapshot of `Input` (blocks and consumption carried over). What the UI consumes (`consume_click`, `consume_escape`, `consume_key`, `consume_scroll`, widget clicks, the wheel a scroll area took and typed text) is applied to `Input` after the pass, so `update` and systems never see it: gameplay keys belong in `update` (`ctx.input`), keys the UI acts on in `ui` (`ui.input()`).
- **Time**: `ui.dt()` is real time, so UI animation runs through pause and slow motion.
- **Scene actions**: only the top scene's returned action counts (scenes below a transparent one draw, but their actions are dropped). It applies at once, before the fixed steps. If it brings a different scene to the top, the UI pass runs once more so the new scene's UI shows this frame.

API usage is covered by the `ryo-ui` skill.

## Layout and ids

Containers (`containers.rs`: `column`, `row`, `grid`, `stack`, `panel`) are laid out by the layout engine (`layout/`, the only code that names Taffy); `tree.rs` holds the subtree being built and its resolution.

- **Ids** (`id.rs`) come from call sites: a hash of the enclosing scope, the builder's `#[track_caller]` site and how often that site ran in the scope this frame. A helper called in a loop gets one id per call, and skipping an earlier call shifts the later ones; lists that reorder or filter use `.id(key)`, which replaces the count with the key. A container's id is the scope of what it contains, and `ui.scope(key, |ui| ..)` adds a keyed scope with no node, so a game's component salts its widgets' ids without touching layout.
- **Scenes are root scopes.** `SceneManager::ui_pass` brackets each scene's `ui` with `begin_scene(scope_id, is_top)` and `end_scene`; the overlays and the console are scene 0. The same code in two scenes makes two ids, and a scene's records and state carry its scope id, so they are forgotten when it exits (`SceneManager::take_exited`, drained by `Engine::draw_ui` into `UiMemory::forget_scene`).
- **Each top-level container lays out when its `.show()` returns.** Opening a container with none open starts a subtree (remembering its `at` rect and the clip in force); nested containers and leaves join it, and closing its root lays it out, places it by its anchor and offset in the UI (or at its `at` rect), snaps every rect to render pixels (`render::ui::snap_rect`) and resolves its draws. A leaf outside any container (`ui.text("..")` without `.at`) is a subtree of its own, laid out at once. So a top-level container's `Response` has this frame's rect; one inside another container has last frame's.
- **Text leaves** are measured by the text engine through the layout's measure callback, wrapped to the width they get (left-aligned when measured, so a centred text does not claim the whole row) and drawn at their unsnapped width, so snapping never wraps them. `UiText` draws itself when dropped: `ui.text("Hi");` is a statement.
- **Draws keep submission order through `order`.** Every draw takes `UiContext::next_order()` when it is recorded, inside a container or not; a container's draws reach `UiCommands` only when it is laid out, after absolute draws recorded later, and `emit_ui` orders by `ui_z(layer, order)`, never by position in the list.
- **Records are written for next frame's hit tests.** Each container writes a `Record` (rect, clip, layer, order, depth, scene, flags, focus scope, scroll ancestor, content size) into `UiMemory` when its subtree is laid out. Hit testing and navigation read last frame's records (`UiMemory::prev`), so input lands on what was drawn. The memory and layout engine keep one frame per engine frame: a rerun UI pass (a scene switched from `ui`) discards the first pass's records and ids with `UiMemory::restart_pass`.
- A container still open when a scene's `ui` ends (its contents panicked) is laid out by `end_scene`, warned once.

## Interaction

The pointer is resolved once per engine frame, before any scene's `ui` (`interact::resolve_pointer`, called by `Engine::draw_ui` on the frame's first UI pass, never on a rerun), against **last frame's records**: a click lands on what the player saw under the pointer, even if the widget moves or disappears this frame. The result is `UiMemory::interact` (`Interaction`); widgets read it through `UiContext::response(id, sense, disabled)`.

- **Topmost wins.** The candidates are the top scene's records under the pointer, inside their clip, with `CLICK`, `DRAG`, `BLOCKING`, `SCROLLABLE` or `DROP_TARGET`; the highest by layer, then order, decides. If it senses (`CLICK`/`DRAG`) and is not `DISABLED` it is hot; otherwise nothing is: a panel, a scroll area or a disabled widget blocks what is under it. The console window (while shown) is a blocker rect: the pointer there is nobody's and is not counted as over the UI.
- **Hovered is the topmost of everything.** `hovered` is the topmost record under the pointer among the candidates and the `HOVER` records (hover-only widgets, `Sense::hover()`), by the same clip and top-scene rules; `Response::hovered()` reads it. Hover-only records never become hot or active, block nothing, and count neither for `over_ui` nor for press consumption, so a hover-only widget drawn over a button reports `hovered()` while the button still takes the click (and is then not `hovered()` itself).
- **Only the top scene.** Lower scenes' records are never candidates, and `response` reports nothing for a scene that is not the top one or for a disabled widget, and no pointer input while the deprecated `mouse_occluded` is set.
- **Click on release.** A left or right press on the hot widget makes it active. Released over it (still hot, not dragged) the left button clicks (`clicked`), the right one `secondary_clicked`; a second left click on the same widget within the theme's `double_click` (0.3 s) is a double click too. For a widget that senses drags (its record has `DRAG`), moving past the theme's `drag_threshold` (4 UI units) from the press starts a drag (`drag_started`, then `dragging` and `drag_delta`, then `drag_released`), which cancels the click. A click-only widget is never dragged: it clicks when released over itself however far the pointer moved within it, and only leaving it cancels the click. An active widget gone from last frame's records, or a release that was missed (the button no longer down), clears it. One-frame results last until the next resolve.
- **`Sense`** masks the response: a widget reports only the clicks or drags it senses, and `hovered()` whatever it senses. Its record carries `CLICK`/`DRAG` to match, or `HOVER` for `Sense::hover()` (`ui.custom`'s default).
- **Presses over the UI are captured.** A press over any candidate is consumed in the UI's input snapshot before the context is built, so the existing consumption (`apply_consumed`, `ui_mouse_capture`) keeps the press, its held frames and its release from gameplay. `ui.wants_pointer()` is `over_ui || active != NONE`.
- **Widgets** (`widgets/`) are builders that run on `show()`, a shorthand such as `clicked()`, or drop: `run` takes the context out of an `Option`, so it records once. `widget_builders!` (`widgets/common.rs`) gives every widget `id`, `enabled`, `at`, `width`, `height`, `fill_width`, `margin`, `anchor`, `offset`, `grow`, `min_width` and `max_width`, and the focus options `default_focus`, `nav_up`/`nav_down`/`nav_left`/`nav_right`, `nav_skip` and `focusable` (`WidgetOpts::flags` turns them into record flags). The button is a leaf of fixed size (label plus its look's padding, else `Sizes::button_padding`, at least `button_min_height` tall) with its look's fill and a centred label (and an icon left of it, centred with it); `ui.custom(w, h)` is a fixed leaf whose `Painter` draws `DrawKind::Local` commands in the widget's own units, placed when its subtree is laid out.
- **Value widgets** (`checkbox`, `toggle`, `radio`, `slider`) write the caller's data and report `Response::changed()`. Checkbox, toggle and radio share `mark_row` (`widgets/mark_row.rs`): a row recording `CLICK | FOCUSABLE` around a mark leaf and a body-text label, so a click anywhere on the row or Confirm flips it; checked uses `palette.accent`, with a check drawn as two `Local` lines, a toggle knob moved right or a radio dot. A slider is just its track leaf (`Sizes::slider` wide, at least `slider_handle` tall) recording `CLICK | DRAG | FOCUSABLE | TAKES_HORIZONTAL`; with a label or `show_value` it is a row around the track, which keeps the id and the record. The pointer sets the value from last frame's track rect while the track is active; Left and Right (`nav_step_for`) move it by the step (a twentieth of the range by default), and an explicit `.step` also snaps. The groove, a `DrawKind::Fraction` filled part and the handle are the track's draws. `progress` is a leaf with a `Fill` and a `Fraction`, and `image` a leaf with a `Sprite` draw that takes a `Filter`; both record `HOVER` only when they have a tooltip. `separator` runs across the open container's cross axis (`open_flow`), `spacer` grows. `.at(rect)` places a widget or container at that rect out of its parent's flow: inside a container the node is `UiStyle::absolute` (Taffy `Position::Absolute`, sized to the rect, taking no room and moving no sibling), and `tree::resolve` puts its absolute origin at `rect.min` in UI units, its descendants placed relative to it. It keeps its parent for ids, focus scope and clip.
- **The text field** (`widgets/text_input.rs`) edits the caller's `String`; its caret, selection anchor, horizontal scroll, blink (1 Hz) and paste guard are a `TextEdit` (`widgets/text_edit.rs`) in `UiMemory` under its id. It records `CLICK | DRAG | FOCUSABLE | TEXT_FIELD | TAKES_HORIZONTAL`, plus `USES_BACK` while focused, at `Sizes::text_input` unless `.width`/`.height` say otherwise. A press focuses it (outside a scope too) and puts the caret under the pointer, a held press selects; navigation (or a request) puts the caret at the end. While it is focused it calls `TextEdit::handle_input` on the caller's string (typing and the IME's commits, the arrows, Home, End, Backspace, Delete, Ctrl or Cmd with A, C, X, V; `max_len` cuts insertions to the characters left), Enter marks it `submitted()`, Escape or a pad's Back (`Interaction::back_used`, since the field records `USES_BACK`) releases the focus (`release_focus`) and is taken from the scene, and it consumes the whole keyboard (`consume_keyboard`); Tab is navigation's. It draws a box with its look (the focused look while focused), then, in a child node that fills its content box (inside the padding) and clips to it, the selection (`palette.accent` at 100 alpha), the text (or the placeholder in `palette.muted` while empty and unfocused) scrolled by the edit, the IME's composition underlined at the caret, and the caret (1.5 wide). `.password()` draws a bullet (U+2022) per character, so carets and clicks map by character index. `wants_keyboard()` is true while the focus is on a `TEXT_FIELD` record of the top scene (`Interaction::nav_scene`), or while an open list or popup traps the focus (Popups and dialogs).
- **Tooltips.** `.tooltip(text)` is in `widget_builders!`; each widget calls `tooltip_tick` with its response. The timer (`TooltipTimer`, widget state under an id derived from the widget's) counts `dt` while the widget is hovered, or focused with the ring showing, and not pressed; at `Metrics::tooltip_delay` it sets `UiContext::pending_tooltip` to the text and the widget's rect. `end_scene` draws the last one of the top scene on the popup layer as its own subtree (`flush_tooltip`), after the scene's popups, so it shows over them: the tooltip look and caption text, wrapped at 280 units, below the widget (6 units) or above it near the UI's bottom, shifted left to stay on screen.
- **Tests** drive several frames without a GPU with `test_util::UiDriver` (scripted pointer, keys, typed text, Shift and IME composition, resolved before each frame as the engine does; the context's `UiInput` is `UiInput::from_view` of them, a press over the UI consumed as in the engine). A widget keeps its id only from one call site, so a test draws it from one closure.

## Scrolling

`ui.scroll()` (`widgets/scroll.rs`) is a container whose children are translated by its offset and clipped to its rect, for hits as well as drawing; `finish_subtree`'s resolution subtracts the scroll node's `ScrollState::offset` from every descendant and the clip is the node's rect. Its record has `SCROLLABLE | DRAG`; a `ScrollState` (offset, target, content, view) lives in `UiMemory` under its id.

- **The wheel** is routed once a frame, right after the pointer resolve (`interact::route_wheel`, called from `Engine::resolve_pointer`). The topmost record under the pointer decides, by the hit test's rule (top scene, inside its clip, layer then order, ties by depth and id), so a blocking panel or a popup over a scroll area keeps the wheel from it, and a popup list beats a deeper page list. Its scroll chain takes the wheel in turn: the record itself if it is a scroll area, then each `Record::scroll` upward, innermost first. Each area that can still move toward the wheel takes it, per axis, moving its `target` by `Metrics::scroll_line` (40) units a line; one at its edge, or whose contents fit, passes the wheel outward along the chain. A topmost record with no scroll chain leaves the wheel to the game. Shift turns a vertical wheel sideways. When anything took it the snapshot's wheel is consumed, so gameplay never sees it. Not routed under the console.
- **Offsets ease.** Each frame the area's `offset` moves toward `target` by `1 - exp(-dt / scroll_smoothing)` (0.08 s) (snapping within 0.5); both are clamped to `content - view` once the area has been laid out. `content` and `view` are written when its subtree is laid out (an axis it does not scroll counts as fitting), so clamping, the scrollbar and the wheel use the previous frame's sizes.
- **The scrollbar** is drawn over the area's right (or bottom) edge when the contents do not fit, and takes its width as padding so contents never lie under it. A press on its column makes the area active (the contents are above everything else) and the target follows the pointer; a press on the contents does nothing, because contents are never dragged.
- **`scroll_to(id)`** stores a request in `UiMemory`; the next resolve (`interact::apply_scroll_requests`) finds the widget's record and its scroll ancestor and moves that area's `target` the least that brings the rect into view. `scroll_offset` reads and `set_scroll_offset` sets (no easing) an area's offset by the `Response::id` of its `show`.
- **Tests** read an offset in a frame that draws nothing; `UiDriver` leaves the last drawn frame's records and state as they were for such a frame.

## Focus and navigation

The keyboard and gamepad focus is resolved once per engine frame, after the pointer and the wheel (`nav::resolve_focus`, called by `Engine::resolve_navigation` on the first UI pass), against last frame's records of the top scene. It lives in `Interaction` (`focused`, one-frame `gained`/`lost`/`activated`/`nav_step`, Back and tab-switch state); `UiMemory` keeps the pending `request_focus`, the scopes seen last frame (`known_scopes`) and the open modals (`modal_stack`, each with the focus to give back).

- **Scopes.** Only explicit scopes take part: containers marked `.focus_scope()`, popups (dropdown lists, `ui.popup`) and modals. Panels are not scopes and the scene root never is, so a HUD button outside any scope is mouse-only and never takes the arrows, Space or A from gameplay; a text field outside a scope still takes focus by click. A record's `scope` is its nearest open scope node, or the scope its subtree started in; a scope's own `scope` is the one around it, which gives the chain. When a scope appears and nothing is focused, focus goes to its default: its remembered focus, else its `.default_focus()` member, else its first member by order. A `.trap()` (or modal) scope always takes focus when it appears, saving the old focus on `modal_stack` and giving it back when it closes; it opens on its `.default_focus()` member first, then its remembered focus, then its first member (`trap_default_in`), so a dialog opens on its default and a list on its selection whatever had the focus when it last closed. One with nothing focusable keeps focus empty, never on the page under it. While one is open, no request, pointer-follow or press moves the focus outside the innermost (`modal_stack`'s last). Focus memory is per scope, remembered on each change for the scene's lifetime (`UiMemory::forget_scene` drops it). Focus on a record that is gone, disabled or clipped out is lost.
- **Movement.** Focusables are `FOCUSABLE`, enabled records whose rect shows inside their clip; a record in a scroll area counts as shown when its area does, so the pad walks a long list and the move scrolls it into view (`scroll_to`). Rows scrolled out of view are candidates only from inside their own scroll area: from outside, a row counts by the part of it that shows, so a move never jumps back into a list (or past its end) to a row the player cannot see. A direction fires on press, then after `repeat_delay` (0.35 s) held and every `repeat_rate` (0.1 s). A press the UI uses captures its direction until release (`Interaction::repeat` is `Some`): every held frame counts as used, so gameplay never sees it between repeats. A direction held from before (gameplay's press) is never captured and never repeats, and a change of top scene drops every capture. It goes to the record's explicit `nav_*` neighbour, else the best `spatial` candidate among its scope's members (not `NAV_SKIP`): the candidate beyond the centre with the lowest `p + 2s + 0.1c` (gap along, gap across, centre distance across), aligned ones first, ties to the lower id. Then a `.wrap_focus()` scope wraps (`wrap_target`), and an untrapped scope hands the search to the scope around it, up to every focusable of the scene. With nothing focused, a direction focuses the innermost trapping scope's default (default member first), or the first scope's. Tab moves through every focusable by order (Shift back), wrapping, inside the innermost trapping scope while one is open. A text field outside any scope (focused by a click) has no neighbours and no tab order: directions and Tab leave it focused, and Tab is not used.
- **Pointer.** Focus follows the pointer (a frame where it moved onto a focusable `hot` widget), but never onto or away from a text field: a field takes the keys only by a press, the keys or the pad, and a player typing keeps it when the mouse brushes a button; a press focuses what it lands on, and a press elsewhere leaves a focused text field. Neither the pointer nor a press takes the focus out of an open trapping scope (Scopes). The ring (`UiContext::focus_ring`, from `Metrics::focus_ring`: 2 units wide, 2 outside the widget) and `focus_visible()` show only when the last device is the keyboard or a gamepad.
- **Actions.** Directions, Tab, Confirm and Back come from the `ui.*` actions. A focused record with `TAKES_HORIZONTAL`/`TAKES_VERTICAL` takes those directions as `nav_step` (read with `nav_step_for`) instead of moving. Confirm activates the focused widget, which reports `clicked()`; on a focused text field it is typing (a space, Enter's own submit), so it activates nothing but is still used. Back is offered to the focused widget first (`USES_BACK`); otherwise `ui.back()` returns it to its first caller only, setting `back_taken`, so a scene brought up by a rerun pass (the popped scene's action) does not pop as well. `tab_step` comes from `ui.tab_next`/`ui.tab_prev` while a scope is shown and no text field has the focus (E and Q type), for the first tabs widget to take (`take_tab_step`, which sets `tab_taken`). The right stick scrolls the focused widget's scroll area. The engine hides from gameplay the bindings of every action the resolve used (a captured direction or Tab while something is focused or a scope is shown, Confirm with a focus, Back a widget used), and after the pass those of `ui.back` when `back_taken` and of the tab actions when `tab_taken`; with no scope on screen the arrows, Space and A stay the game's. Each of those bindings that is down joins `Engine::ui_binding_capture` and stays hidden from gameplay until it is released (`Input::binding_down_raw`), like `ui_mouse_capture` for a press: a Confirm held after Resume closed the menu, or a direction held as a menu closes, never reaches gameplay as held. The UI pass still reads them (its snapshot is taken first), so a field's held arrow repeats.
- **Tests** script navigation through `UiDriver` (`nav`, `hold`, `release_nav`, `confirm`, `back`, `tab`, `tab_next`, `stick`, `device`, `set_scene`); `last_outcome()` is the outcome of the last frame that had navigation input.

## Popups and dialogs

`popup.rs` and `widgets/{dropdown,tabs,choice_list,modal}.rs`.

- **Built where they are called, drawn at the scene's end, above its page.** `begin_popup(anchor, modal)` sets the subtree being built (and its open node) aside on `UiContext::subtree_stack` and starts the popup's own, under no clip and in the focus scope it was opened in (`focus_scope_here` before the swap, kept as `Subtree::scope`); widgets record into it until `end_popup` queues it (`UiContext::popups`) and brings the set-aside subtree back. Closing a popup's root does not lay it out. `end_scene` flushes the queue in the order the popups were begun (one opened inside another is queued after it, so it draws over it), then the tooltip: each popup's nodes and draws take fresh `next_order()` values, keeping their order among themselves, so they follow everything the scene drew, on `POPUP_LAYER` for the top scene or `PAGE_LAYER` for a lower one (the scenes above still cover it); then it is laid out like any subtree. Its records, at that layer and order, win next frame's hit tests and the wheel over the page.
- **Placement** (`popup::below`, `Subtree::below`). A modal covers the UI (its subtree's `at`). An anchored popup goes 2 units below its anchor's rect, or above it when only that fits (when neither does, on the roomier side, moved to stay inside), moved left to stay inside, and is at least as wide as the anchor. Without an anchor it is centred.
- **Ids** inside a popup are scoped under its owner: a dropdown's list is an id derived from the trigger's, and its options are keyed under the list, so they belong to that dropdown.
- **Dropdown lists trap focus and use Back.** `ui.dropdown(&mut usize, &[&str])`: the trigger is a row with the dropdown look, the selected label (one line, ellipsis) and a chevron (`Local` lines), recording `CLICK | FOCUSABLE`, plus `USES_BACK` while open. `DropdownState { open }` lives in memory under its id; a click or Confirm toggles it. While open, its list is a popup below the trigger: a column in the dropdown's normal look (opaque in the built-ins, so the page does not show through) recording `FOCUS_SCOPE | TRAP | BLOCKING | POPUP`, with one Choice-look option per entry recording `USES_BACK`, the selected one `default_focus` and labelled in `palette.accent`. A click or Confirm on an option sets the value, closes the list (drawn that frame, gone the next) and marks `changed`. Back while the focus is the dropdown's (`back_used`) closes it, so `ui.back()` is false; so does a press whose `Interaction::press_target` (the topmost record the press landed on, hot or not) is neither the trigger, the list nor an option. The list is built before the trigger, so the trigger shows a pick the frame it is made. While it is open the pointer cannot take the focus out of it, so Back always reaches it. It reopens on its selection. When the list goes, `modal_stack` gives the focus back to the trigger. A value out of range is clamped on draw; no options draws "-" and never opens.
- **Tabs follow the shoulder buttons.** `ui.tabs(&mut usize, &[&str])`: a row of Tab-look buttons that share its width (`Length::Fill`), the selected one in the theme's `selected` variant. A click or Confirm selects one. The first tabs drawn in the top scene take `tab_step` (`take_tab_step`: `ui.tab_next`/`ui.tab_prev`, the shoulder buttons and E/Q), wrapping, and request the focus for the newly selected tab, so the bumpers leave it on the tab bar; only when no trapping scope is open or the tabs are inside the innermost (`UiContext::shortcuts_reach_here`), so tabs under a modal or an open list ignore them and tabs in a dialog keep them. `changed` when the selection moves. A tab, like any button that fills its parent's width, is at least as wide as its label.
- **Choice lists take number keys.** `ui.choice_list(&[&str]).show() -> Option<usize>`: a `FOCUS_SCOPE` column of Choice-look buttons, the first (or `.default(i)`'s) `default_focus`. A click or Confirm picks one; in the top scene, unless the keyboard is wanted or a trapping scope it is not in is open (`shortcuts_reach_here`), `Digit1`-`Digit9` and `Numpad1`-`Numpad9` pick choice `n - 1` when it exists, and that key is consumed.
- **Modals block and trap, and return focus.** `ui.modal().show(..)` (`Modal` is a `Container`): a popup whose root is a `Flow::Stack` dim over the UI (the Modal look's fill, `rgba(0, 0, 0, 160)` in the built-ins) recording `BLOCKING`, so nothing under it is hot, with the dialog in it: a column with the panel look, `FOCUS_SCOPE | TRAP | MODAL | BLOCKING`, anchored at the centre. Focus moves in when it appears and returns when it goes (`modal_stack`). It never closes itself: the game does, on `ui.back()` or a button.
- **`ui.confirm(title, message)`** (and `confirm_with(.., yes, no)`): a modal with the title (heading role), the message (body role, wrapped at 320) and a row of two buttons, No the default focus. `Some(true)` or `Some(false)` when one is chosen, `Some(false)` on Back, else `None`. Its ids come from its texts (the modal is keyed by title, message, yes and no; it is not `#[track_caller]`): one dialog wherever it is called from, and a different question is a new one that opens on No.
- **`ui.popup(anchor_id)`**: a panel column below the anchor's rect (this frame's, else last frame's; centred when unknown) recording `FOCUS_SCOPE | TRAP | BLOCKING | POPUP`, for context menus. The game decides when it shows.
- **`wants_keyboard()`** is also true while the top scene has an open list or popup: an entry on `modal_stack` whose scope record is a popup root (`POPUP`, which lists and `ui.popup` record) and traps, or a popup that is not a modal queued this pass (so from the frame it opens; it stays true one frame after it closes). A modal does not count, since the game closes it, nor does a page column marked `.trap()`; a page that shows one and wants Escape for it says so (demo-kit's `wants_escape`).
- **Back closes the innermost first.** An open list holds the focus and its options use Back; once it is gone, Back is the game's (`ui.back()`), to close the modal around it.

## Theme

`theme/` (`mod.rs`, `look.rs`, `builtin.rs`, `file.rs`). The spec is `docs/specs/2026-10-16-ui-interaction-design.md`.

- **`UiTheme` is a world resource** holding an `Arc<Theme>` (`get`, `set`, `modify`; `ctx.ui_theme()`, `EngineBuilder::ui_theme`). `Engine::draw_ui` takes the `Arc` once per pass (`refresh_ui_theme`) and gives it to the `UiContext` (`ui.theme()`), so a change applies from the next frame. The interaction resolves read the same theme's metrics (drag threshold, double click, wheel line, repeat delay and rate) through `PointerInput::double_click`, the `resolve_pointer` and `route_wheel` arguments and `NavInput::repeat_*`.
- **Looks.** A `Theme` has a `Palette`, `Metrics` (radius, timings, `FocusRing`, `Sizes`), `TextRoles` (`TextLook`: size, colour, font, bold, which a RON file can state), a `Looks` per `WidgetKind` and named `Variant`s. `Looks::resolve(state)` starts from `normal` and applies the state's `LookPatch` (`Some` replaces): `Pressed` applies `hovered` first, `Focused` only its own patch. `Theme::look(kind, variant, state)` then applies the variant's `normal` and state patches, and `.style(patch)` on the widget applies last, in every state (`UiContext::look_of`). An unknown variant or skin name warns once and draws the plain look. `UiContext::widget_state` picks the state: disabled, pressed, hovered, focused with the ring visible, else normal.
- **Padding and sizes.** A look's `padding` is used when it is not zero; otherwise the widget takes its size from `Metrics::sizes` (the button's padding, the panel's). The scrollbar's look is its colours: `fill` is the track, `border` the thumb, and its hovered and pressed patches the thumb's states. The slider and progress looks use `fill` for the track and `border` for the filled part; the slider's `text` is its handle.
- **Skins.** A look with `skin: Some(name)` draws that skin's sprite as `DrawKind::NineSlice` (corners of `insets` sprite pixels drawn at that size in UI units, pieces snapped to render pixels), the look's `fill` tinting it; without a sprite it draws the plain look. The engine loads skin `path`s through `AssetManager::load_sprite` when the theme's generation changes (`UiTheme::load_skins`). The skin's `filter` is carried by `DrawKind::NineSlice` and `UiCommand::Sprite` to the draw.
- **Files.** `Theme::load`/`save` are RON, read with the `implicit_some` extension. `load` parses the file as plain data (`serde_json::Value`) and merges it over `Theme::dark()` serialised the same way, map by map (so a nested partial struct, or a `variants` map that adds one variant, keeps dark's other fields and entries; lists and options replace), then deserialises the result. RON loses the names of bare unit variants in plain data, so `Variant::base`, `TextLook::font` and `Skin::filter` are strings in files (`base: "Button"`, `font: "Pixel"`, `filter: "Nearest"`, field-level `serde(with = "names")`); an unknown name is a `ThemeError::Parse` naming the path, the type and the name. `load` stores the path as the theme's `source`. In debug builds the engine polls a `ThemeWatch` each frame: at most once a second it compares the source file's modification time, reloads and `set`s on a change, and on a load error warns once per change and keeps the old theme.
- **Built-ins** (`builtin.rs`): `dark` (today's colours), `light`, and `pixel` (the pixel font at 16, square corners, button and panel skins drawn in code). All carry the `danger`, `accent` and `tab` button variants and the `selected` tab variant. Their Choice looks are plain rows filled on hover, press and focus; their Modal look is the dim behind a modal.

## Drawing on the GPU

- **Recording.** `UiContext` draws nothing itself: every primitive records a `UiCommand` (`Rect`, `Sprite`, `Line`, `Text`) in UI units into the engine's `UiCommands`. The commands, clips, text, fades, the typewriter and popups are described in `immediate/AGENTS.md`.
- **The UI pass.** At present time `render::ui::emit_ui` lays the commands into the 2D batch for the UI camera (`UI_CAMERA`, `CameraDraw::ui`): one z per command (layer, then the order it was recorded in), so the painter's order holds. The `ui` render pass draws that camera into the UI image: `Rgba8Unorm`, gamma-encoded colour premultiplied by alpha (`UI_FORMAT`, the `UI_GAMMA` override). The composite blends it over the frame in sRGB space, so a 50% black panel over white is 128, as on the web. Rects are analytic (`BatchShader::UiRect`: rounded corners, inner border, anti-aliased edges). Frame steps and shaders are in `src/core/render/AGENTS.md`.
- **UI units and scale** (`render/ui.rs`, `UiSpace`). With the automatic scale (`ui_scale: None`, the default) UI units are screen units at any display scale; text is laid out at render pixels, so it is sharp on HiDPI displays. `EngineBuilder::ui_scale(Some(s))` / `ctx.request_ui_scale` make it `s` render pixels per UI unit, rects and text alike; mouse positions are converted to UI units (`UiInput::with_mouse_scale`). `UiResolution::Render` (default) draws the UI at the render size (pixel art: the low-res target, snapped like the world); `Window` draws it at window resolution.
- **Clipping** is a scissor per command (the clip in image pixels, rounded outward); the stack has no depth limit.
- **Text** goes through the text engine (`src/core/text/AGENTS.md`): measured, wrapped and laid out at the UI scale. Fonts are the `Fonts` resource; the UI uses `FontRole::Ui`, and the console and overlays `FontRole::Mono`.

## Notes for AI Agents

1. **State ownership**: the game's values (a selection, a volume, a name) are the caller's; what a widget remembers of itself (an open list, a caret) is in `UiMemory`, dropped when the widget is not drawn for a frame.
2. **UI units**: all coordinates are UI units (screen units with the automatic scale), never render pixels.
3. **Alpha blending**: colours with alpha < 255 blend with what is below in sRGB space, as designers expect.
4. **The UI is never lit** and never post-processed.
5. **Fade text through opacity**, never through a style's colour: colour is in the layout cache key, so a colour fade lays the text out again every frame (`ui.text(..).opacity(a)`).
