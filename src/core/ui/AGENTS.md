# AGENTS.md - UI Module

## Architecture

The UI is built every frame in `Scene::ui` through `UiContext` (`immediate/context.rs`):

- **Absolute drawing** (`draw_*`, `ui.text(..).at(..)`) records at once: HUDs, debug overlays.
- **Widgets and containers** (`widgets/`, `containers.rs`) are laid out by the layout engine and report what the pointer, keyboard and pad did through a `Response` (`ui.button("Go").clicked()`), resolved before the scenes against last frame's layout (see Interaction).
- **Game data stays with the game**: widgets take `&mut bool`, `&mut f32`, `&mut usize` or `&mut String`. What a widget remembers itself (an open list, a caret, a scroll offset) lives in `UiMemory` under its id.
- **Popups** (`popup.rs`) are built where they are called and drawn when their scene's UI ends (see Popups and dialogs).
- **Node trees** (`nodes/`) are UI described once as `UiNode` values and spawned as entities. Each frame the walk draws them through the same builders, before the scene's `ui` (see Nodes); a node that did not change replays what its builder pushed last time instead (see Cached node trees).
- **Virtual lists** (`widgets/list.rs`, `nodes/list.rs`) build only the rows in view, in both styles: a closure `ui.list` and a node `List` whose few pooled rows are reused (see Virtual lists).

## Integration Point

`Scene::ui(&mut self, ui: &mut UiContext, ctx: &mut SceneContext) -> SceneAction` runs once per frame for the visible scenes, bottom-up, **before** the fixed steps (`Engine::ui_pass`, `engine/frame.rs`). Engine stats/FPS overlays and the dev console are drawn into the same `UiContext` after the scenes, on the overlay layer, so they appear on top of the scenes' pages and popups alike.

- **Input**: `UiContext` reads a `UiInput` snapshot of `Input` (blocks and consumption carried over). What the UI consumes (`consume_key`, `consume_scroll`, widget responses, the wheel over the UI, typed text and the actions navigation used) is applied to `Input` after the pass, so `update` and systems never see it: gameplay keys belong in `update` (`ctx.input`), keys the UI acts on in `ui` (`ui.input()`).
- **Time**: `ui.dt()` is real time, so UI animation runs through pause and slow motion.
- **Scene actions**: only the top scene's returned action counts (scenes below a transparent one draw, but their actions are dropped). It applies at once, before the fixed steps. If it brings a different scene to the top, the UI pass runs once more so the new scene's UI shows this frame. While a scene transition runs, a scene change from `ui` is ignored (`SceneManager::ui_pass`; only `Quit` applies): the UI still draws during a fade, and a second click must not restart it with another change.

API usage is covered by the `ryo-ui` skill.

## Layout and ids

Containers (`containers.rs`: `column`, `row`, `grid`, `stack`, `panel`) are laid out by the layout engine (`layout/`, the only code that names Taffy); `tree.rs` holds the subtree being built and its resolution.

- **Ids** (`id.rs`) come from call sites: a hash of the enclosing scope, the builder's `#[track_caller]` site and how often that site ran in the scope this frame. A helper called in a loop gets one id per call, and skipping an earlier call shifts the later ones; lists that reorder or filter use `.id(key)`, which replaces the count with the key. A container's id is the scope of what it contains, and `ui.scope(key, |ui| ..)` adds a keyed scope with no node, so a game's component salts its widgets' ids without touching layout. The id hash is the fast word-wise one: `mix` folds each word in with a 128-bit multiply, `.id(key)` keys hash through `FastHasher` (`core::hash`, the same fold, never SipHash; see Frame cost), and the per-frame `counts` and `used` maps hash with it too. Ids live only in memory, so their values may change between versions; a duplicate explicit key is still caught by `used`, suffixed and warned once.
- **Scenes are root scopes.** `SceneManager::ui_pass` brackets each scene's `ui` with `begin_scene(scope_id, is_top)` and `end_scene`; the overlays and the console are scene 0. The same code in two scenes makes two ids, and a scene's records and state carry its scope id, so they are forgotten when it exits (`SceneManager::take_exited`, drained by `Engine::draw_ui` into `UiMemory::forget_scene`).
- **Each top-level container lays out when its `.show()` returns.** Opening a container with none open starts a subtree (remembering its `at` rect and the clip in force); nested containers and leaves join it, and closing its root lays it out, places it by its anchor and offset in the UI (or at its `at` rect), snaps every rect to render pixels (`render::ui::snap_rect`) and resolves its draws. A leaf outside any container (`ui.text("..")` without `.at`) is a subtree of its own, laid out at once. So a top-level container's `Response` has this frame's rect; one inside another container has last frame's.
- **A fixed-size leaf that fills keeps its size as a floor.** A `Measure::Fixed` node (a button, a slider, a slot) whose width or height is `Length::Fill` has no size of its own on that axis, so a column sized to its contents would make it zero; `to_taffy` gives it a min size of its fixed size there, or of its `max_width`/`max_height` when that is smaller: a cap the caller asked for must hold (a min above it would beat it), and the widget never collapses below it.
- **Text leaves** are measured by the text engine through the layout's measure callback, wrapped to the width they get (left-aligned when measured, so a centred text does not claim the whole row) and drawn at their unsnapped width, so snapping never wraps them. `UiText` draws itself when dropped: `ui.text("Hi");` is a statement.
- **Draws keep submission order through `order`.** Every draw takes `UiContext::next_order()` when it is recorded, inside a container or not; a container's draws reach `UiCommands` only when it is laid out, after absolute draws recorded later, and `emit_ui` orders by `ui_z(layer, order)`, never by position in the list.
- **Records are written for next frame's hit tests.** Each container writes a `Record` (rect, clip, layer, order, depth, scene, flags, focus scope, scroll ancestor, content size, the payload type a drop target accepts) into `UiMemory` when its subtree is laid out. Hit testing and navigation read last frame's records (`UiMemory::prev`), so input lands on what was drawn. The memory and layout engine keep one frame per engine frame: a rerun UI pass (a scene switched from `ui`) discards the first pass's records and ids with `UiMemory::restart_pass`.
- A container still open when a scene's `ui` ends (its contents panicked) is laid out by `end_scene`, warned once.

## Interaction

The pointer is resolved once per engine frame, before any scene's `ui` (`interact::resolve_pointer`, called by `Engine::draw_ui` on the frame's first UI pass, never on a rerun), against **last frame's records**: a click lands on what the player saw under the pointer, even if the widget moves or disappears this frame. The result is `UiMemory::interact` (`Interaction`); widgets read it through `UiContext::response(id, sense, disabled)`.

- **Topmost wins.** The candidates are the top scene's records under the pointer, inside their clip, with `CLICK`, `DRAG`, `BLOCKING`, `SCROLLABLE` or `DROP_TARGET`; the highest by layer, then order, decides. If it senses (`CLICK`/`DRAG`) and is not `DISABLED` it is hot; otherwise nothing is: a panel, a scroll area or a disabled widget blocks what is under it. The console window (while shown) is a blocker rect: the pointer there is nobody's and is not counted as over the UI.
- **Hovered is the topmost of everything.** `hovered` is the topmost record under the pointer among the candidates and the `HOVER` records (hover-only widgets, `Sense::hover()`), by the same clip and top-scene rules; `Response::hovered()` reads it. Hover-only records never become hot or active, block nothing, and count neither for `over_ui` nor for press consumption, so a hover-only widget drawn over a button reports `hovered()` while the button still takes the click (and is then not `hovered()` itself).
- **Only the top scene.** Lower scenes' records are never candidates, and `response` reports nothing for a scene that is not the top one or for a disabled widget.
- **Click on release.** A left or right press on the hot widget makes it active. Released over it (still hot, not dragged) the left button clicks (`clicked`), the right one `secondary_clicked`; a second left click on the same widget within the theme's `double_click` (0.3 s) is a double click too. For a widget that senses drags (its record has `DRAG`), moving past the theme's `drag_threshold` (4 UI units) from the press starts a drag (`drag_started`, then `dragging` and `drag_delta`, then `drag_released`), which cancels the click. A click-only widget is never dragged: it clicks when released over itself however far the pointer moved within it, and only leaving it cancels the click. An active widget gone from last frame's records, or a release that was missed (the button no longer down), clears it. One-frame results last until the next resolve.
- **`Sense`** masks the response: a widget reports only the clicks or drags it senses, and `hovered()` whatever it senses. Its record carries `CLICK`/`DRAG` to match, or `HOVER` for `Sense::hover()` (`ui.custom`'s default).
- **Presses over the UI are captured.** A press over any candidate is consumed in the UI's input snapshot before the context is built, so the existing consumption (`apply_consumed`, `ui_mouse_capture`) keeps the press, its held frames and its release from gameplay. `ui.wants_pointer()` is `over_ui || active != NONE`.
- **Widgets** (`widgets/`) are builders that run on `show()`, a shorthand such as `clicked()`, or drop: `run` takes the context out of an `Option`, so it records once. `widget_builders!` (`widgets/common.rs`) gives every widget `id`, `enabled`, `at`, `width`, `height`, `fill_width`, `margin`, `anchor`, `offset`, `grow`, `min_width` and `max_width`, and the focus options `default_focus`, `nav_up`/`nav_down`/`nav_left`/`nav_right`, `nav_skip` and `focusable` (`WidgetOpts::flags` turns them into record flags), and `drag_source`, `drop_target` and `drag_ghost` (Drag and drop). The button is a leaf of fixed size (label plus its look's padding, else `Sizes::button_padding`, at least `button_min_height` tall) with its look's fill and a centred label (and an icon left of it, centred with it); `ui.custom(w, h)` is a fixed leaf whose `Painter` draws `DrawKind::Local` commands in the widget's own units, placed when its subtree is laid out; `.takes_horizontal()`/`.takes_vertical()` add `TAKES_HORIZONTAL`/`TAKES_VERTICAL` to its record (read with the public `ui.nav_step(id)`, which is `nav_step_for`), and `.takes_confirm(false)` adds `NO_CONFIRM` (Focus and navigation, Actions). demo-kit's settings panel is one such widget.
- **Value widgets** (`checkbox`, `toggle`, `radio`, `slider`) write the caller's data and report `Response::changed()`. Checkbox, toggle and radio share `mark_row` (`widgets/mark_row.rs`): a row recording `CLICK | FOCUSABLE` around a mark leaf and a body-text label, so a click anywhere on the row or Confirm flips it; checked uses `palette.accent`, with a check drawn as two `Local` lines, a toggle knob moved right or a radio dot. A slider is just its track leaf (`Sizes::slider` wide, at least `slider_handle` tall) recording `CLICK | DRAG | FOCUSABLE | TAKES_HORIZONTAL`; with a label or `show_value` it is a row around the track, which keeps the id and the record. The pointer sets the value from last frame's track rect while the track is active; Left and Right (`nav_step_for`) move it by the step (a twentieth of the range by default), and an explicit `.step` also snaps. The groove, a `DrawKind::Fraction` filled part and the handle are the track's draws. `progress` is a leaf with a `Fill` and a `Fraction`, and `image` a leaf with a `Sprite` draw that takes a `Filter`; both record `HOVER` only when they have a tooltip. `separator` runs across the open container's cross axis (`open_flow`), `spacer` grows. `.at(rect)` places a widget or container at that rect out of its parent's flow: inside a container the node is `UiStyle::absolute` (Taffy `Position::Absolute`, sized to the rect, taking no room and moving no sibling), and `tree::resolve` puts its absolute origin at `rect.min` in UI units, its descendants placed relative to it. It keeps its parent for ids, focus scope and clip.
- **The text field** (`widgets/text_input.rs`) edits the caller's `String`; its caret, selection anchor, horizontal scroll, blink (1 Hz) and paste guard are a `TextEdit` (`widgets/text_edit.rs`) in `UiMemory` under its id. It records `CLICK | DRAG | FOCUSABLE | TEXT_FIELD | TAKES_HORIZONTAL`, plus `USES_BACK` while focused, at `Sizes::text_input` unless `.width`/`.height` say otherwise. A press focuses it (outside a scope too) and puts the caret under the pointer, a held press selects; navigation (or a request) puts the caret at the end. While it is focused it calls `TextEdit::handle_input` on the caller's string (typing and the IME's commits, the arrows, Home, End, Backspace, Delete, Ctrl or Cmd with A, C, X, V; `max_len` cuts insertions to the characters left), Enter marks it `submitted()`, Escape or a pad's Back (`Interaction::back_used`, since the field records `USES_BACK`) releases the focus (`release_focus`) and is taken from the scene, and it consumes the whole keyboard (`consume_keyboard`); Tab is navigation's. It draws a box with its look (the focused look while focused), then, in a child node that fills its content box (inside the padding) and clips to it, the selection (`palette.accent` at 100 alpha), the text (or the placeholder in `palette.muted` while empty and unfocused) scrolled by the edit, the IME's composition underlined at the caret, and the caret (1.5 wide). `.password()` draws a bullet (U+2022) per character, so carets and clicks map by character index. `wants_keyboard()` is true while the focus is on a `TEXT_FIELD` record of the top scene (`Interaction::nav_scene`), or while an open list or popup traps the focus (Popups and dialogs).
- **Tooltips.** `.tooltip(text)` is in `widget_builders!`; each widget calls `tooltip_tick` with its response. The timer (`TooltipTimer`, widget state under an id derived from the widget's) counts `dt` while the widget is hovered, or focused with the ring showing, and not pressed; at `Metrics::tooltip_delay` it sets `UiContext::pending_tooltip` to the text and the widget's rect. `end_scene` draws the last one of the top scene on the popup layer as its own subtree (`flush_tooltip`), after the scene's popups, so it shows over them: the tooltip look and caption text, wrapped at 280 units, below the widget (6 units) or above it near the UI's bottom, shifted left to stay on screen.
- **Tests** drive several frames without a GPU with `test_util::UiDriver`, which wraps the public `UiHarness` (`src/core/testing/ui.rs`, see Testing) and derefs to it: scripted pointer, keys, typed text, Shift and IME composition, resolved before each frame as the engine does; the context's `UiInput` is `UiInput::from_view` of them, a press over the UI consumed as in the engine. A widget keeps its id only from one call site, so a test draws it from one closure.

## Scrolling

`ui.scroll()` (`widgets/scroll.rs`) is a container whose children are translated by its offset and clipped to its rect, for hits as well as drawing; `finish_subtree`'s resolution subtracts the scroll node's `ScrollState::offset` from every descendant and the clip is the node's rect. Its record has `SCROLLABLE | DRAG`; a `ScrollState` (offset, target, content, view) lives in `UiMemory` under its id.

- **The wheel** is routed once a frame, right after the pointer resolve (`interact::route_wheel`, called from `Engine::resolve_pointer`). The topmost record under the pointer decides, by the hit test's rule (top scene, inside its clip, layer then order, ties by depth and id), so a blocking panel or a popup over a scroll area keeps the wheel from it, and a popup list beats a deeper page list. Its scroll chain takes the wheel in turn: the record itself if it is a scroll area, then each `Record::scroll` upward, innermost first. Each area that can still move toward the wheel takes it, per axis, moving its `target` by `Metrics::scroll_line` (40) units a line; one at its edge, or whose contents fit, passes the wheel outward along the chain; a topmost record with no scroll chain moves nothing. A trackpad's pixels (`UiInput::scroll_pixels`, logical pixels) are converted to UI units by the pointer's scales with no offset (`Engine::logical_to_screen` times `UiSpace::mouse_scale`) and take the same chain per axis, but move `target` and `offset` together, clamped, at once with no easing (the OS supplies the momentum); an area passes on the pixels it cannot use. Pixels start from the offset (clamped to the content), not the target: a gesture interrupts an ease in flight (`target = offset`), and the remainder passed outward is exactly `raw - clamped`. Lists scroll through the same state; a node list, whose rows draw a frame after they are bound, pools its rows ahead of an offset that moves at once by the recent step (`UiList::ahead`: the largest recent step, never below the current one, held for 2 still frames and then decaying by a quarter a frame, at most a view, none for a jump of more than a view), so a flick stays drawn up to about that speed, uneven frame cadences included (`.overscan(n)` for faster). Shift turns a vertical wheel or trackpad sideways. The wheel over the top scene's UI is the UI's whether anything moved or not, by the rule for presses (`over_ui`, `PointerOutcome::consume_wheel` from `resolve_pointer`, or'd with what `route_wheel` took): the snapshot's wheel is consumed, so a game's wheel zoom never fires behind a panel, a modal's dim, an open list or a list at its edge. Over nothing it is the game's. Not routed under the console, where it is the console's.
- **Offsets ease.** Each frame the area's `offset` moves toward `target` by `1 - exp(-dt / scroll_smoothing)` (0.08 s) (snapping within 0.5, and to the target once an `f32` step can no longer move the offset, far down a long list); both are clamped to `content - view` once the area has been laid out. `content` and `view` are written when its subtree is laid out (an axis it does not scroll counts as fitting), so clamping, the scrollbar and the wheel use the previous frame's sizes. `view` is the snapped rect and `content` is moved by the same snapping (`tree.rs`), so an area that grows to a fractional height and is snapped a little shorter still fits contents that fit its layout, and shows no scrollbar.
- **A known content height.** `Scroll::content_height(h)` (crate) makes an area's contents `h` tall inside its padding whatever they measure: a list knows its length before it builds its rows. It is applied before the ease, so the offset, the clamp and the thumb take a list that got shorter this frame, not last frame's layout.
- **The scrollbar** is drawn over the area's right (or bottom) edge when the contents do not fit, and takes its width as padding so contents never lie under it. A press on its column makes the area active (the contents are above everything else) and the target follows the pointer; a press on the contents does nothing, because contents are never dragged.
- **`scroll_to(id)`** stores a request in `UiMemory`; the next resolve (`interact::apply_scroll_requests`) finds the widget's record and walks its scroll chain, innermost first, moving each area's `target` the least that brings the rect into view, the rect moved by what the areas inside will scroll: a card in a strip in a list comes into view in the strip and in the list. `scroll_offset` reads and `set_scroll_offset` sets (no easing) an area's offset by the `Response::id` of its `show`.
- **Tests** read an offset in a frame that draws nothing; `UiDriver` leaves the last drawn frame's records and state as they were for such a frame.

## Focus and navigation

The keyboard and gamepad focus is resolved once per engine frame, after the pointer and the wheel (`nav::resolve_focus`, called by `Engine::resolve_navigation` on the first UI pass), against last frame's records of the top scene. It lives in `Interaction` (`focused`, one-frame `gained`/`lost`/`activated`/`nav_step`, Back and tab-switch state); `UiMemory` keeps the pending `request_focus`, the scopes seen last frame (`known_scopes`) and the open modals (`modal_stack`, each with the focus to give back).

- **Scopes.** Only explicit scopes take part: containers marked `.focus_scope()` (`.trap()` and `.wrap_focus()` make one too, since either means nothing outside a scope), popups (dropdown lists, `ui.popup`) and modals. Panels are not scopes and the scene root never is, so a HUD button outside any scope is mouse-only and never takes the arrows, Space or A from gameplay; a text field outside a scope still takes focus by click. A record's `scope` is its nearest open scope node, or the scope its subtree started in; a scope's own `scope` is the one around it, which gives the chain. When a scope appears and nothing is focused, focus goes to its default (its remembered focus, else its `.default_focus()` member, else its first member by order), provided no trapping scope is open or the scope lies inside the innermost one (`modal_stack`'s last). So under an open modal holding only text a page scope that appears takes nothing, and Confirm and the directions never act on the page under it, while the modal's own choices take the focus when they appear (a dialogue shows its text, then its `choice_list`). A `.trap()` (or modal) scope always takes focus when it appears, saving the old focus on `modal_stack` and giving it back when it closes; it opens on its `.default_focus()` member first, then its remembered focus, then its first member (`trap_default_in`), so a dialog opens on its default and a list on its selection whatever had the focus when it last closed. One with nothing focusable keeps focus empty, never on the page under it. While one is open, no request, pointer-follow or press moves the focus outside the innermost (`modal_stack`'s last). Closures are taken before appearances: every `modal_stack` entry whose scope the top scene no longer shows is dropped (one another scene left open too: a dialog whose answer switched scenes, or a confirm scene that popped), and the innermost of them whose saved focus can still take it (inside the innermost trap left open) gives it back; only then do the scopes that appeared take the focus, so the page a dialog's answer shows, or the menu a popped dialog scene uncovers, takes its remembered focus or its default. Focus memory is per scope, remembered on each change for the scene's lifetime (`UiMemory::forget_scene` drops it) in the focused record's scope and each scope around it out to the first trapping one (`Nav::remembering`): nested scopes reopen where they were, and the page outside a modal or list keeps the focus it is given back. Focus on a record that is gone, disabled or clipped out is lost.
- **Movement.** Focusables are `FOCUSABLE`, enabled records whose rect shows inside their clip; a record in a scroll area counts as shown when its area does, by the same rule at every depth (`Nav::shows`), so the pad walks a long list, and a strip nested in it that the list has scrolled out of view, and the move scrolls it into view (`scroll_to`, in every area around it). A candidate sharing a scroll area with the focused record (anywhere along both scroll chains) is inside that list: it counts whole, clipped only by the areas nested inside the shared one (a card in a strip, by the strip's view; `Nav::seen_from`). From outside every area it is in, a row counts by the part of it that shows, so a move never jumps back into a list (or past its end) to a row the player cannot see. A direction fires on press, then after `repeat_delay` (0.35 s) held and every `repeat_rate` (0.1 s). A press the UI uses captures its direction until release (`Interaction::repeat` is `Some`): every held frame counts as used, so gameplay never sees it between repeats. A direction held from before (gameplay's press) is never captured and never repeats, and a change of top scene drops every capture. It goes to the record's explicit `nav_*` neighbour, else the best `spatial` candidate among its scope's members that are navigation's targets (`Nav::targets`: not `NAV_SKIP`, inside the innermost open trap; `nav_targets` lists the same for the headless engine): the candidate beyond the centre with the lowest `p + 2s + 0.1c` (gap along, gap across, centre distance across), aligned ones first, ties to the lower id. Then a `.wrap_focus()` scope wraps (`wrap_target`), and an untrapped scope hands the search to the scope around it, up to every focusable of the scene. With nothing focused, a direction focuses the innermost trapping scope's default (default member first), or the first scope's. Tab moves through every focusable by order (Shift back), wrapping, inside the innermost trapping scope while one is open. A text field outside any scope (focused by a click) has no neighbours and no tab order: directions and Tab leave it focused, and Tab is not used.
- **Pointer.** Focus follows the pointer (a frame where it moved onto a focusable `hot` widget), but never onto or away from a text field: a field takes the keys only by a press, the keys or the pad, and a player typing keeps it when the mouse brushes a button; a press focuses what it lands on, and a press elsewhere leaves a focused text field. Neither the pointer nor a press takes the focus out of an open trapping scope (Scopes). The ring (`UiContext::focus_ring`, from `Metrics::focus_ring`: 2 units wide, 2 outside the widget) and `focus_visible()` show only when the last device is the keyboard or a gamepad.
- **Actions.** Directions, Tab, Confirm and Back come from the `ui.*` actions. A focused record with `TAKES_HORIZONTAL`/`TAKES_VERTICAL` takes those directions as `nav_step` (read with `nav_step_for`, or `ui.nav_step` for a game's custom widget) instead of moving. Confirm activates the focused widget, which reports `clicked()`; on a focused text field it is typing (a space, Enter's own submit), so it activates nothing but is still used. A focused `NO_CONFIRM` record (`Custom::takes_confirm(false)`) declines it: nothing activates and `ui.confirm` is not used, so Space, Enter and A stay gameplay's while it has the focus (demo-kit's settings panel, which only takes directions). While a drag payload is held Confirm activates nothing and only puts a pad's payload down, and Back cancels the drag (Drag and drop). Back is offered to the focused widget first (`USES_BACK`); otherwise `ui.back()` returns it to its first caller only, setting `back_taken`, so a scene brought up by a rerun pass (the popped scene's action) does not pop as well. `tab_step` comes from `ui.tab_next`/`ui.tab_prev` while a scope is shown and no text field has the focus (E and Q type), for the first tabs widget to take (`take_tab_step`, which sets `tab_taken`). The right stick scrolls the focused widget's scroll area; a focused widget in none (a dialog's Close under its scrolling text) scrolls the first scroll area by order inside its own focus scope (`Nav::first_scroll_in`), never one outside that scope, and so never one outside the innermost trap. The engine hides from gameplay the bindings of every action the resolve used (a captured direction or Tab while something is focused or a scope is shown, Confirm with a focus, Back a widget used), and after the pass those of `ui.back` when `back_taken` and of the tab actions when `tab_taken`; with no scope on screen the arrows, Space and A stay the game's. Each of those bindings that is down joins `Engine::ui_binding_capture` and stays hidden from gameplay until it is released (`Input::binding_down_raw`), like `ui_mouse_capture` for a press: a Confirm held after Resume closed the menu, or a direction held as a menu closes, never reaches gameplay as held. The UI pass still reads them (its snapshot is taken first), so a field's held arrow repeats.
- **Tests** script navigation through `UiDriver` (`nav`, `hold`, `release_nav`, `confirm`, `back`, `tab`, `tab_next`, `stick`, `device`, `set_scene`); `last_outcome()` is the outcome of the last frame that had navigation input.

## Popups and dialogs

`popup.rs` and `widgets/{dropdown,tabs,choice_list,modal}.rs`.

- **Built where they are called, drawn at the scene's end, above its page.** `begin_popup(anchor, modal)` sets the subtree being built (and its open node) aside on `UiContext::subtree_stack` and starts the popup's own, under no clip and in the focus scope it was opened in (`focus_scope_here` before the swap, kept as `Subtree::scope`); widgets record into it until `end_popup` queues it (`UiContext::popups`) and brings the set-aside subtree back. Closing a popup's root does not lay it out. `end_scene` flushes the queue in the order the popups were begun (one opened inside another is queued after it, so it draws over it), then the tooltip: each popup's nodes and draws take fresh `next_order()` values, keeping their order among themselves, so they follow everything the scene drew, on `POPUP_LAYER` for the top scene or `PAGE_LAYER` for a lower one (the scenes above still cover it); then it is laid out like any subtree. Its records, at that layer and order, win next frame's hit tests and the wheel over the page.
- **Placement** (`popup::below`, `Subtree::below`). A modal covers the UI (its subtree's `at`). An anchored popup goes 2 units below its anchor's rect, or above it when only that fits (when neither does, on the roomier side, moved to stay inside), moved left to stay inside, and is at least as wide as the anchor. Without an anchor it is centred.
- **Ids** inside a popup are scoped under its owner: a dropdown's list is an id derived from the trigger's, and its options are keyed under the list, so they belong to that dropdown.
- **Dropdown lists trap focus and use Back.** `ui.dropdown(&mut usize, &[&str])`: the trigger is a row with the dropdown look, the selected label (one line, ellipsis) and a chevron (`Local` lines), recording `CLICK | FOCUSABLE`, plus `USES_BACK` while open. `DropdownMemory { open }` lives in memory under its id; a click or Confirm toggles it. While open, its list is a popup below the trigger: a column in the dropdown's normal look (opaque in the built-ins, so the page does not show through) recording `FOCUS_SCOPE | TRAP | BLOCKING | POPUP`, with one Choice-look option per entry recording `USES_BACK`, the selected one `default_focus` and labelled in `palette.accent`. The options are in a `ui.scroll()` whose `max_height` is the room on the side the list opens on, less the list's padding (`popup::room`: the roomier of below and above the trigger, so `popup::below` still puts the list below or above it whenever it fits there), so a long list stays inside the UI, and the wheel and navigation's `scroll_to` scroll it. A click or Confirm on an option sets the value, closes the list (drawn that frame, gone the next) and marks `changed`. Back while the focus is the dropdown's (`back_used`) closes it, so `ui.back()` is false; so does a press whose `Interaction::press_target` (the topmost record the press landed on, hot or not) is neither the trigger, the list nor an option. The list is built before the trigger, so the trigger shows a pick the frame it is made. While it is open the pointer cannot take the focus out of it, so Back always reaches it. It reopens on its selection. When the list goes, `modal_stack` gives the focus back to the trigger. A value out of range is clamped on draw; no options draws "-" and never opens.
- **Tabs follow the shoulder buttons.** `ui.tabs(&mut usize, &[&str])`: a row of Tab-look buttons that share its width (`Length::Fill`), the selected one in the theme's `selected` variant. A click or Confirm selects one. The first tabs drawn in the top scene take `tab_step` (`take_tab_step`: `ui.tab_next`/`ui.tab_prev`, the shoulder buttons and E/Q), wrapping, and request the focus for the newly selected tab, so the bumpers leave it on the tab bar; only when no trapping scope is open or the tabs are inside the innermost (`UiContext::shortcuts_reach_here`), so tabs under a modal or an open list ignore them and tabs in a dialog keep them. `changed` when the selection moves. A tab, like any fixed-size widget that fills its parent's width, is at least as wide as its label (Layout and ids).
- **Choice lists take number keys.** `ui.choice_list(&[&str]).show() -> Option<usize>`: a `FOCUS_SCOPE` column of Choice-look buttons, the first (or `.default(i)`'s) `default_focus`. A click or Confirm picks one; in the top scene, unless the keyboard is wanted or a trapping scope it is not in is open (`shortcuts_reach_here`), `Digit1`-`Digit9` and `Numpad1`-`Numpad9` pick choice `n - 1` when it exists, and that key is consumed.
- **Modals block and trap, and return focus.** `ui.modal().show(..)` (`Modal` is a `Container`): a popup whose root is a `Flow::Stack` dim over the UI (the Modal look's fill, `rgba(0, 0, 0, 160)` in the built-ins) recording `BLOCKING`, so nothing under it is hot, with the dialog in it: a column with the panel look, its fill made opaque (`Backing::Dialog`; a page panel keeps the theme's translucency, but nothing under a dialog shows through it), `FOCUS_SCOPE | TRAP | MODAL | BLOCKING`, anchored at the centre. Focus moves in when it appears and returns when it goes (`modal_stack`). It never closes itself: the game does, on `ui.back()` or a button.
- **`ui.confirm(title, message)`** (and `confirm_with(.., yes, no)`): a modal with the title (heading role), the message (body role, wrapped at 320; left out when empty, so the buttons sit under the title) and a row of two buttons, No the default focus. `Some(true)` or `Some(false)` when one is chosen, `Some(false)` on Back, else `None`. Its ids come from its texts (the modal is keyed by title, message, yes and no; it is not `#[track_caller]`): one dialog wherever it is called from, and a different question is a new one that opens on No.
- **`ui.popup(anchor_id)`**: a panel column below the anchor's rect (this frame's, else last frame's; centred when unknown) recording `FOCUS_SCOPE | TRAP | BLOCKING | POPUP`, for context menus. The game decides when it shows.
- **`wants_keyboard()`** is also true while the top scene has an open list or popup: an entry on `modal_stack` whose scope record is a popup root (`POPUP`, which lists and `ui.popup` record) and traps, or a popup that is not a modal queued this pass (so from the frame it opens; it stays true one frame after it closes). A modal does not count, since the game closes it, nor does a page column marked `.trap()`; a page that shows one and wants Escape for it says so (demo-kit's `wants_escape`).
- **Back closes the innermost first.** An open list holds the focus and its options use Back; once it is gone, Back is the game's (`ui.back()`), to close the modal around it.

## Drag and drop

`widgets/drag.rs` (the drag state, the ghost and the shared builder methods) and `widgets/slot.rs`. The payloads are typed and the game decides what a drop means (a move, a swap, a merge): the UI only carries a clone of the source's payload to the target's `Response::dropped::<T>()`.

- **Sources and targets on any widget or container.** `drag_builders!` (`drag_source::<P>(payload)`, `drop_target::<P>()`, `drag_ghost(&sprite)`) is part of `widget_builders!` and is on `Container` and `Scroll` too; they fill a `DragOpts`. A source's record has `DRAG_SOURCE | DRAG` (so the pointer drags it), a target's `DROP_TARGET` and `Record::accepts = Some(TypeId::of::<P>())` (`WidgetOpts::record`, `RecordSpec::accepts`). Widgets take their response through `widget_response`, which senses drags for a source and runs `drag_tick` before the widget reads its clicks; containers, tabs and choice lists run `drag_tick` on the response of their node.
- **The state** is `Interaction::drag: Option<DragState>` (source, payload `Arc<dyn Any + Send + Sync>`, type, `Ghost`, `pad`, `grab`, size), this frame's `dropped: Option<(target, payload)>` (cleared by the next pointer resolve) and `drop_hover`, the target a mouse drag would land on now. The `Arc` makes `Interaction` `Clone` but not `Copy`: the resolves work on a clone. A drag whose source is not in last frame's records of the top scene ends with no drop, so nothing is held after its source goes (the pointer resolve).
- **The mouse.** `drag_tick` picks a source up when its drag starts (`Interaction::drag_started`, left button, nothing held): `grab` is where it was pressed in its rect, `size` its rect's size. While the left button stays down the pointer resolve keeps `drop_hover`; on its release `dropped` is the target under the pointer and the drag ends either way (a missed release ends it too). The target (`drop_target_at`) is the topmost top-scene record under the pointer, inside its clip, that is an enabled `DROP_TARGET` accepting the payload's type, unless a `BLOCKING` record that does not accept it lies over it there: a modal's dim or a panel over the target keeps the drop from it, while a button or label inside a target panel lets it through. The source reports `drag_released`, never `clicked`.
- **The pad.** With nothing held, Confirm on a focused source is delivered as `activated`, and `drag_tick` turns it into a pick-up (`pad: true`): the source reports `drag_started_here()`, not `clicked()`. While a payload is held Confirm activates nothing; when it is a pad drag and the focused record accepts its type, Confirm sets `dropped` to the focused target and ends the drag. Back while anything is held cancels it and is `back_used`, so `ui.back()` is false.
- **Responses.** `dropped::<T>()` is the payload when this frame's drop is on this target and downcasts to `T`; `drag_hover::<T>()` is true while a `T` is held over this target: `drop_hover` for the mouse (so a target panel sees it through the widgets in it), the focus for the pad; `drag_started_here()` is the frame of the pick-up. `ui.held::<P>()` is the payload held now, when it is a `P`, in the top scene (from the pick-up, so a call after the source's widget sees that frame's pick-up, until the drop, Back or a release over nothing): a game shows what is carried from it, and knows Back is the drag's while it is `Some`.
- **The ghost.** `end_scene` of the top scene draws it after the popups and the tooltip (`flush_ghost`), while a payload is held and its source was drawn by the scene this pass: on `POPUP_LAYER` at 80% opacity (alpha 204), the source's size, at `pointer - grab` for the mouse or 8 units up and left of the focused record for the pad. `Ghost::Sprite` is the `drag_ghost` sprite, else a slot's icon, sampled with a slot's filter (`Filter::Default` for other widgets); `Ghost::Box` is a rect in `palette.accent` with the theme's radius. It is a node with no record, so it never takes the pointer.
- **The slot** (`ui.slot()`): a `Sizes::slot` square leaf recording `CLICK | FOCUSABLE`, drawn with the slot looks (`.selected(true)` borders it 2 units in `palette.accent`), its `.icon` a `Sprite` inset 6 with its `.filter` (default `Filter::Default`), and a `.count` above 1 in the caption role at the bottom-right, inset 3 (the node's padding). A slot with no icon is empty.

## Prompts and rebinding

`widgets/prompt.rs` and `widgets/rebind.rs`; the labels are `input/labels.rs`.

- **Prompts follow the last device and the pad family.** `UiContext` holds a `PromptContext` (`immediate/context.rs`: `device`, `family`, every action's `bindings`, a `TextIcons` copy). `Engine::refresh_prompts` brings it up to date before each UI pass (the device and family every frame, the bindings when they differ from `Actions`, the icons when `TextIcons` changed by its change tick) and hands it over with `set_prompts`; tests use `UiDriver::prompts(prompts_with(device, &[..]))`. `binding_for_device` picks the first key or mouse binding on the keyboard or mouse, the first pad or stick binding on a gamepad, else the first binding; `Binding::label(family)` labels it ("A" on Xbox, "×" on PlayStation, "B" on Nintendo for South).
- **Registered glyphs replace chips.** `ui.prompt(action)` is a leaf: when `PromptContext::icons` has the binding's `glyph_name` (`prompt.key.Space`, `prompt.pad.xbox.South`, `prompt.stick.LeftUp`), it draws that sprite (or region) a caption line high, keeping its aspect; otherwise a chip: the Prompt look's box (its padding, else 4 x 1) around the label in the caption role in the look's text colour. An action with no binding shows "?" and warns once per action. `prompt_chip` draws one chip for a binding; the rebinding row uses it.
- **Markup prompts are resolved before layout.** `[prompt=jump]` (and `RichText::prompt`) is a `PromptMark` at its byte (`RichText::prompts`, hashed by `hash_into`; at one byte, icons come before prompts) carrying the markup span it was written in, since a span never covers the empty prompt at its edges. `resolve_prompts` replaces each with an inline `Icon::Named(glyph_name)` when the glyph is registered, else inserts `[label]` bold in `palette.accent` over that span's style (so `[size=32]Press [prompt=start][/size]` labels at 32, and `[wave][prompt=x][/wave]` waves), with `RichText::insert_text`, which moves the marks after it and splits a span around it; text without prompts is borrowed unchanged. The UI resolves at every entry point before measuring or laying out: `UiText::record`, `text_leaf`, `push_draw` of a `DrawKind::Text`, `record_text` (`draw_text*`), `measure_text`, a widget's `leaf_of` and `Painter::text`, so a leaf is measured as it is drawn and its content key and seed come from the resolved text (a device change lays it out again). World text resolves the same way in `render::text::layout_world_text`, against the engine's `PromptContext` and the `UiTheme` accent; its layout key hashes the resolved text, while a reveal restarts only for a new unresolved text.
- **Rebinding rows capture the next key or pad button.** `ui.rebind(action)` (`.label`, default the action's name; `.slot`, default 0) is a column holding a row and, for 2 s after a swap, a caption note under it. The row has the Rebind look (Pressed while capturing), the button padding and minimum height, the label (body role) in a `grow` box, then a prompt chip per binding, or "Press a key or button…" (caption) while capturing; it records `CLICK | FOCUSABLE`, plus `CAPTURING | USES_BACK` while capturing. `RebindState { capturing, since, note }` is in memory under its id, timed by `Interaction::now` (the real time `resolve_pointer` saw). A click or Confirm starts a capture; from the next frame (never the press that started it) Escape cancels (consumed), any other key (`UiInput::key_pressed_any`, the first in `KEY_NAMES` order) or any pad button, East included (`gamepad_pressed_any`), that `is_saveable` is consumed and pushed as a `PendingRebind` (id, scene, action, slot, binding), and the row reports `changed()`. Mouse buttons are not captured. A capture cancels after 5 s, on another click, when the row loses the focus, is disabled or is not in the top scene. A row for an action missing from `PromptContext::bindings` (never bound) warns once, naming it, shows "?" and never captures.
- **Navigation stands aside while capturing.** When the focused record has `CAPTURING`, `resolve_focus` moves nothing and marks nothing used for the directions (their repeats drop), Tab, Confirm, a tab switch or Back; Back still counts as the row's (`back_used`, so `ui.back()` is false), and the pointer passing over another widget does not take the focus (a press elsewhere does, which cancels). `wants_keyboard()` is true while a capturing row has the focus.
- **A collision swaps.** After the pass the engine applies each `PendingRebind` with `actions_mut().rebind(..)` (which swaps inside the group; the bindings' dirty flag saves it), hides the captured binding from gameplay and adds it to `ui_binding_capture` until released, so the press never acts as a UI action or reaches gameplay. When `rebind` returns another action's name, `note_swap` puts "Swapped with <name>" on the row's state.
- **Tests** drive pad presses with `UiDriver::pad(button)` and read `pending_rebinds()` (action, slot, binding) or `rebinds()` (whole) of the last frame.

## Nodes

`nodes/` (`node.rs` the `UiNode` value, `spawn.rs` the entities a tree becomes, `components.rs` the public state components and the `UiNodes` resource, `draw.rs` the walk, `events.rs` `UiEvent` and `UiListBind`, `list.rs` the pooled list: Virtual lists, below; `cache.rs` the records and the dirty set: Cached node trees, below). The spec is `docs/specs/2026-10-17-ui-nodes-design.md`.

- **The walk.** `draw_nodes(world, ui, scene)` runs in `SceneManager::ui_pass` between `begin_scene` and the scene's `ui`, and in `UiHarness::frame` before its closure. It walks the scene's roots in spawn order and draws each node through the builder a closure would call, given `.id(entity)`; text, separators and spacers are drawn in `ui.scope(entity, ..)`. So a node's id is its entity under its parent's id, its widget state follows it through sibling changes, and it is forgotten on despawn. With the cache on, a clean node replays its record instead of calling the builder.
  - A container's builder is configured from its `UiNodeKind`, then its `.show` walks the children with the world free. The children list is copied once onto the walk's stack.
  - A widget reads its state components through shared gets from one entity lookup. A value the player changed is written back after the builder returns.
  - The text field reads its tuple mutably, since it edits `UiTextValue`'s `String` in place.
  - Each response's id, hover and focus go into the node's `UiInteraction`, written only when they differ.
  - A modal root opens centred, as `ui.modal()` does, unless it was given an anchor.
- **Nodes never write records themselves.** Records, layout, focus, hit tests, popups and drag and drop all come from the builders, so a node behaves exactly as the equivalent closure widget. A builder option a node cannot express is a missing `UiNode` option, never a second path.
- **Ownership.** `UiNodes::roots` lists `(scene scope, root)` in spawn order, and `UiRoot` holds the owning scene. Only the owning scene's pass draws a root, under the top-scene rule, so a lower scene's nodes draw and take no input. `Engine::draw_ui` drains `take_exited` into `UiMemory::forget_scene` and `despawn_scene_roots`, so a popped scene's trees go with it.
- **Components flow both ways.** The game writes a component and the next pass draws it. The walk writes a value component only when the player changed it, so `Changed<..>` filters see real changes. A value set out of a widget's range is drawn clamped and kept. `UiHidden` skips a subtree, so it records nothing and leaves the focus chain. `UiDisabled` draws a widget with `enabled(false)` and is warned once on a container.
- **Events.** The walk collects `UiEvent`s in walk order, each after its component write. `events::deliver` writes them as messages and triggers each on its node. A scene's tree events are delivered right after its walk, before its `ui`. An embedded tree's (`ui.node`) go to `UiNodes::pending` and are delivered by `deliver_pending` after the scene's `ui` returns. `ctx.ui_events()` filters by scene and shares `messages::<UiEvent>()`'s cursor.
- **Observers run inside `ui_pass`,** while the scene host is out of the world. An observer on a node must not try to change scenes: it sends a message or sets state for the scene's `update` or `ui` to act on.
- **Back.** The walk remembers the last modal or popup node drawn (`Walk::back`), the innermost. After the scene's trees, `Walk::finish` calls `ui.back()` once. A confirm (its `BackAnswer` names the No button) gets a `Clicked` from No; any other dialog gets a `Back` event on itself. Node dialogs therefore answer Back before the scene's closure. So a closure modal drawn above a node dialog in the same scene does not get Back first: don't mix them in one scene, or close the node dialog from the closure explicitly. A modal inside an embedded tree takes Back only through the closure's own `ui.back()`.
- **Focus.** `ctx.focus_ui(node)` waits in `UiNodes::pending_focus` until the node is drawn. A focused node that is despawned leaves the focus at `None`, and the next navigation lands on its scope's default, as for a closure widget that stops being drawn.
- **Spawn checks.** Each is warned once:
  - an option the kind does not take (`Kind::takes`), including children given to a widget;
  - `.embedded()` on a child;
  - an unknown `nav_*` or popup name (names resolve within the root at spawn);
  - a name used twice.

## Files

`file/` (`reader.rs` RON text into positioned values, `vocab.rs` the kinds and options, `build.rs` templates and the `UiNode` they make, `document.rs` `UiFile`, `UiArgs` and the load checks, `error.rs` `UiFileError`, `check.rs` `ryo2d check-ui`) with the reconcile (`nodes/reconcile.rs`) and bindings (`nodes/bindings.rs`) in `nodes/`. The spec is `docs/specs/2026-10-17-ui-files-design.md`; where it and the code differ, the code is current.

- **The reader is ours.** `ron::Value` drops names (`Button(..)` becomes a nameless map), typed serde structs fight template parameters in any value position and a serde schema would repeat `UiNode`'s option list. Ours keeps every value's line and column, which every error uses. It takes a subset of RON; every UI file in the repo is also parsed by the `ron` crate in a test, so the files stay valid RON. A new RON form the reader refuses gets an error that says so, never a silent skip.
- **One vocabulary.** `vocab.rs` holds `KINDS` (a `KindSpec` per kind: its main value for the short form, its constructor arguments, the `UiNode` constructor it calls) and `OPTIONS` (an `OptionSpec` per option: its name, a function that reads the value form and calls the `UiNode` method). Checking and building both read them, so a file cannot say what `UiNode` cannot. To add an option:
  - add the `UiNode` method first (it records itself with `given(..)` so spawn can warn);
  - add one `option!` line to `OPTIONS` (a form already there, or a new reader on `BuildCx`);
  - list it in `Kind::takes` (`nodes/node.rs`) for the kinds that use it. A file option a kind does not take is an error by that same list, the one spawn warns with in code trees;
  - add the option to the `ryo-ui` Files tables and a test that the file form builds what the method builds.
  To add a kind, add the constructor and a `KindSpec`; a template may not share a kind's name.
- **Errors collect.** A load reports every mistake in a file at once, each with the file, line and column of the offending value (a template's error in the file that defines it). Unknown names get `nearest(..)` suggestions. Keep messages in the form "what is wrong; did you mean ..".
- **Templates expand at build time.** `substitute` replaces a bare lowercase parameter name with the argument and fills `{param}` holes in strings. A hole that is not a parameter, and `{{`/`}}`, are left for the binding pattern parser, which is why a binding pattern cannot be built from a parameter. A built node carries its source (`TreeSource`: the file, the root or template, the arguments, an instance number), so a reload can build it again.
- **Keys.** `UiTreeNode { key, instance }` is on every spawned node: the key (`key`, else `name`, else kind and index among the unnamed siblings of that kind) is what a reconcile matches by, and the instance says which file instance of a repeated template the node came from.
- **The reconcile** (`reconcile.rs`) is one walk over the tree being applied and the spawned children:
  - same key and kind: updated in place; same key, other kind: despawned and spawned again in the same place; new keys spawn; missing keys despawn with their subtree;
  - **ownership.** `UiAdded` marks the top of a `spawn_ui_in` subtree, which the reconcile never touches (it stays after the tree sibling it followed). A reload (`Mode::Reload { instance }`) updates only the children of its own file instance, so a `.child(..)` the game put into a file-built tree is left alone like an added subtree; `ctx.update_ui` (`Mode::Update`) replaces everything else. `update_ui` on a node that is not a root keeps that node's stored `instance` (`reconcile` gives it to the tree's top): its parent still owns the node it placed, so a file's placeholder whose contents code rebuilt stays the file's, while the code-built children under it are code's (instance 0) and a reload leaves them;
  - **the three-way rule.** `UiApplied` holds what the tree last gave each node (state, tooltip, hidden, disabled, a root's placement). A state component is written only when the tree's value differs from the applied one; then it wins. When it does not differ the live value stays, whoever wrote it. The tree's own settings (layout, flags, variant, action, name, key, neighbours, `bind`) are rewritten;
  - **a bound widget's value** is never written by the reconcile: the tree's value only seeds the name;
  - writes only on a real change (change detection stays truthful), and no `UiEvent` is sent;
  - keys that repeat among siblings warn in code trees and match in order.
- **Bindings** (`bindings.rs`). The bound components stay the truth; the per-root `UiBindings` values (per row, in a list's row) hold what patterns format and `ui_get` reads. Sync points:
  - `set` (`ctx.ui_set`) stores the value and, only when it changed (`store` says), writes every bound widget and formats every pattern that uses the name, so a game setting a value every frame costs a compare. A widget the game wrote directly keeps that value and sets the name at `sync_root`;
  - `sync_root` runs before a root is drawn: a bound widget a game changed (`UiValue` written directly) sets its name;
  - `widget_wrote` runs right after a bound widget is drawn: the player's change sets the name, so a pattern drawn after the widget shows it the same frame and one drawn before it the next;
  - `seed` applies starting values only to names with no value yet, so a reload never resets a score; `apply_subtree` formats a freshly spawned subtree.
  A per-root index of bound widgets and patterns is built lazily and dropped by `invalidate` when the tree's shape changes. A name used in a pattern and never set warns once.
- **Reloads.** `UiFile` is a cheap handle over a shared document and an atomic `generation`; the asset manager replaces the document in place on a reload. Every tree built from a file holds a `UiSource` with the generation it was built at (`TreeSource::generation`, read when the tree is built, so a tree built before a reload and spawned after it reloads too). `reload_trees` (called by `Engine::draw_ui` before the UI pass, and by `UiHarness::frame`) finds the sources whose file's generation moved, builds each again, outer trees first, reconciles it, and sends `UiReloaded` once per root, with `replaced` the old root when the reload respawned it (a new kind). A template instance built from code (`ctx.ui_template`) holds its own `UiSource`, so it reloads on its own wherever it was spawned, and a reload of its parent tree leaves it to that. A tree that cannot be rebuilt (a missing image, a template that went) is kept as it was and warned about once. The query is kept between frames in a `SourceQuery` that the engine and `UiHarness` own, outside the world, and is made once `UiSource` is registered. It is not a resource: a resource is an entity in bevy 0.20, and a UI pass that spawned one would shift the game's entity and archetype ids (what a game prints or draws in query order). With no source in the world it is one check. Keep it before the walk, never inside it.

## Virtual lists

`widgets/list.rs` (the closure `ui.list`, and what both kinds share) and `nodes/list.rs` (the pooled node `List`). The spec is `docs/specs/2026-10-18-ui-fast-design.md`.

- **One shape for both.** `Shape::new` cleans a list's options once a frame: a row height that is not finite and above 0, or a row height and gap not finite together, warns once and the list draws empty; overscan is kept to 1..=64, columns to 1..=256, the gap and top padding cleaned as the layout cleans them. `Shape::length` is the exact content height, `rows × stride − gap` in `f64`, which the list gives its scroll area with `Scroll::content_height`, so the scroll length never depends on what the rows measure: row contents taller than the row draw over the next one.
- **Built rows.** `built_rows` and `Shape::built` pick the rows covering the view at the offset the frame is drawn at (the area eases before its contents are built), plus the overscan, in `f64` with saturating casts, and at most `BUILT_ITEMS` (4,096) items a frame (the rows in view first; warned once per list). However far the area is heading, a frame builds a view's worth.
- **The part that shows.** `seen` gives the part of the view the rows must cover: a view no taller than the screen is taken whole, a screenful at most. A taller one (a list given no height grows to its whole length, `Fit` around its spacers) takes only where last frame's record meets the screen and the record's clip, so a list nested in an outer scroll area builds what that area shows; before the first layout the screen's height stands in. Lists that fit the screen keep their whole view so an outer area that scrolls them past its edge never shows a band of rows not built yet. A list whose laid-out view holds its whole length and is taller than the screen warns once (`warn_grown`: "give the list a height ..") instead of the cap message.
- **Placement.** `place` builds the runs of rows in order inside the scroll area: each item in a container keyed by its index at one call site (`item_site`), a grid row as a `Flow::Row` container keyed by its row with equal `Fill` cells (`min_width` 0) and blanks finishing the last row, and between the runs spacers (`blank`) that record nothing, a gap short of the rows they stand for (the area's gap is the list's). Both kinds place their rows through it, behind the `Fill` trait (`opening`, `contents`, `closed`).
- **Ids by index.** An item's widgets are keyed under its container, so hover, focus and memory follow the index, and a reused node row is drawn in its new item's container with new ids. A row that leaves the built rows loses its widgets' memory, as any widget not drawn does.
- **Focus.** `ListState` (under `state_id(list)`, apart from the area's `ScrollState`) keeps the shape for the jump calls and the focus. `FocusWatch` finds the item that made the focused widget; its row and one row each side are built as extra runs wherever the list scrolls (with the row alone, a direction from an out-of-view row would land on the view's overscan row, not the next item). `list_focus` pends an item: its row is built and its ids captured (`IdScopes::start_capture`), the first that can take the focus is asked for the next frame, and the pending focus ends the frame after. A count that shrinks under the focus pends the new last item while the focus is still on the widget the old item made.
- **Jumps.** `list_scroll_to` sets the area's target and `ListState::jump`; the list's next build calls `ScrollState::approach(1, view)` before it picks rows, bringing the offset to one view short of the target, so the ease covers only the last view and the rows between are never built (and a call after the list in its container draws no empty frame).
- **Far targets.** Any target further than two views from the offset (`far`: scroll-into-view from a focused row the wheel left far behind, a big wheel spin) gets the same `approach` before rows are chosen, in both kinds: the closure list never sweeps, and the node pool, which holds the rows at the offset and at the target, covers every offset the ease draws.
- **The node pool.** `UiNode::list` is `Kind::List(ListOpts)`; its count is state (`NodeState::list_count` into `UiList::count`, as `UiValue` is) and its row shape a `UiListShape` component (`RowShape::Code`, or `RowShape::File`: the file's value, built for each row in the file it was written in, as that file was when the list's tree was built). `update_lists` brings every pool in line once a frame, in `Engine::draw_ui` (and `UiHarness::frame`) after the resolve and before any tree is drawn. A pool holds a row for each item it needs: the part of the view that shows (`seen`) at the area's offset and at its target (and every row between when the two are within two views and fit the cap; a target further away is first brought within a view, Far targets), the overscan, the focused row and one each side, a jump's row and a pending focus's row. Rows of items no longer needed are given the items that have none; the difference is spawned from the shape (`spawn_list_row`) or despawned; each row given an item sends `UiListBind`, written as a message and triggered on the row.
- **Drawn from the next frame.** `UiListRow::bound_frame` is the frame a row was given its item, and `draw_list` draws it only from the frame after (until then its container is drawn empty, at full size), so a scene binds it in its `ui` in between. A refresh (`Rebind`) sends binds without hiding the rows, since they keep their items. A scroll the wheel or navigation moves is pooled in that frame's update: within two views the pool holds every row the ease passes, so from the next frame each is drawn bound; a trackpad (offset == target) is looked ahead by its last step; a farther one is pre-moved first (Far targets), so the view it lands in is drawn empty for that one frame. A jump a `ui` asks for is pooled at the next update. Before a list is first drawn its view is unknown and the screen's height stands in.
- **A new list's first focus.** A node list's rows show from its second frame, so the scope's default focus goes to another focusable in it when there is one. `FirstFocus` gives the first rows the default (a row node marked `.default_focus()`, else the first focusable) only when the list's scope appeared with it and nothing else took the focus. A game starts on a row with `ctx.ui_list_focus(list, 0)`. Closure lists pick their first row in order, as any widget.
- **Rows are scopes.** A row is its own binding scope and naming scope (`spawn::scope_of` stops at a `UiListRow`, and `find_ui_in` does not descend into rows), so the rows from one shape hold their own values and their names never clash ("named twice"). A reconcile never matches the rows against a tree's children: they are the list's.
- **A new row shape.** A reconcile puts the tree's shape in `UiListShape::next`. The next update builds it and sets it against a kept copy of the row as the pool was built (`same_tree`): another row brings every pooled row in line in place (`reconcile`, `Mode::Update`), hidden and bound again (`Renew::Rebind`); the same row holding a list is brought in line for that list's own shape (`Renew::InPlace`); else nothing changes, so an `update_ui` every frame never keeps the list hidden. A row whose top is of another kind is spawned again in its place, hidden, and bound whatever the mode. A shape taken away and given back before the update (`UiListShape::given`) is taken up as a new one, so rows built from the old shape come in line. A shape that fails to build keeps the old shape and rows, warned once per list and mistake; a row that builds afterwards bumps `UiListShape::generation`, so the same mistake made again warns again.
- **A world with no list is left alone.** `update_lists` returns before touching anything when `UiNodes::lists` is empty (Notes for AI Agents, 6).

## Cached node trees

`tape.rs` (what a build pushed, and its replay), `nodes/cache.rs` (the records and the dirty set), the walk in `nodes/draw.rs`, and the oracle (`nodes/oracle.rs`, `nodes/oracle_tests.rs`). The spec is `docs/specs/2026-10-18-ui-cache-design.md`; where it and the code differ, the code is current. Only node trees are cached: closure UI is immediate by design.

- **Caching is not observable.** With the cache on and off, every frame's draw commands, records, focus and navigation results, `UiEvent`s and component writes are identical. Every rule below serves that, and the oracle tests it.
- **The tape** (`Tape`) is what one node's builder pushed into the open subtree:
  - `ops` in push order: `Op::Node { node, at }` (the k-th of `Tape::nodes`, kept as given to `push_node`, before stamping), `Draw { node, kind }` (prompts already resolved), `Close(node)`, `PopupBegin { anchor, modal }` and `PopupEnd` (a replay looks the anchor's rect up again, so the popup follows its widget), and `Child(entity)`, the slot a child's output goes in;
  - `ids`, the ids its own builder made; `states`, the widget states it touched; `reads` (below); and `replayable`.
- **Child slots pause it.** `begin_child` notes `Op::Child` and pauses the open tape until `end_child`: what the child pushes, makes and touches belongs to the child's own tape or replay, so a child changes alone. The id and state logs (`IdScopes::log` and `UiMemory::touched`, each a `TapeLog`) note only while a tape records unpaused (`sync_logs`). Nested tapes share them and `Scratch::places`, each taking what came after its mark, so recording allocates nothing once warm.
- **A replay equals a build.** `replay` pushes the tape's nodes through `push_stamped` (`push_node_copy`), the one function that stamps a pushed node (layer, order, focus scope, parent, depth, scroll area, `at`) from where it lands, as `push_node` and `push_text_node` do, and its draws as `push_draw` does (`push_draw_copy`: order and layer). So every stamp, `next_order` included, is a build's. It registers the recorded ids before the nodes (`IdScopes::replay_id`: `used`, and a list's capture), as a build makes a node's ids before its children's, and touches its states so `end_frame` keeps them. Its preconditions (its rustdoc): it replays in the id scope it was built in, since its ids are kept, not made; no own id is made after a child slot; and it does not advance the per-site counts unkeyed ids come from. Node trees key every node by its entity, so neither of the last two arises there.
- **Reads go up.** A build that bakes in something from outside its node notes a `Read` (`note_read`, `note_sprite`) in the open tape and every tape around it, and a replay inside a recording tape adds its reads to them. So a record carries its whole subtree's reads, and a parent replays only while all of them hold: a replay never asks its children (it never builds them).
  - `Read::Id`, another node's response id: a `nav_*` neighbour, a popup node's anchor (`read_id`, `draw.rs`).
  - `Read::Rect`, where a widget was: an open dropdown sizes its list by the room beside its own rect (`placed_by`); a text field that fills is sized by its own last rect.
  - `Read::Sprite`, a sprite's version: an image without a size and a prompt's glyph are sized by the sprite, and a hot reload replaces it in place, perhaps at another size, while no component changes.
- **Taint: a build with a side effect is never replayed.** A replay pushes only nodes and draws, so a build that does anything else calls `taint`, which makes the open tape and every tape around it unreplayable. The sites: `request_focus` and `release_focus`, sounds (`play`, `play_tick`), `back`, `take_tab_step`, the `consume_*` calls, absolute drawing (`record_rect`, `record_layout`, `record_sprite`, `draw_line`: outside the subtree), a tooltip showing, a drag pick-up, a captured rebinding, `scroll_to`, `set_scroll_offset`, `list_scroll_to`, `list_focus`, a node event (`push_event`), a bound widget writing other nodes (`wrote`), a miss (below), a tape started or a replay made while a tape records outside a child slot (it would miss what they push), and a draw or close on a node the tape did not push. Most of these come with an interaction role anyway, so taint is also defence in depth.
- **The record** (`NodeRecord`): the tape, the scene that drew it and whether it was on top, the `UiEnv` it was built in, the memory frame it was last drawn in, its response id (what a replay answers with), whether it is a modal or popup (the walk's Back target, restored on replay) and the id scope it was built in. The scope is its parent's id: a node reparented, or a parent given another id, builds again, and so does a list row given another item (it lands in another index-keyed container).
  - **Records live in `UiNodes` (`UiCache`), not in components:** a component on each node would change the game's archetypes, and with them the order its queries see (Notes for AI Agents, 6).
  - **`Arc<Tape>`.** A replay clones the `Arc`; a build takes the tape out of its unique `Arc` (`take_for_build`), records into its cleared buffers (`start_tape_in`) and puts it back, so a record built again allocates nothing.
  - `by_id` maps every id a stored tape pushed to its node: who holds a role. Records not drawn in a memory frame (despawned, hidden, of a scene not drawn) drop at its end (`nodes::end_frame`), with their `by_id` entries and live-set places, as widget state does. A frame that draws nothing (the harness's rewound frame) keeps them.
- **Dirtiness** (`UiCache::dirty`). The invariant: **every dirty node's ancestors are dirty.** `mark` climbs `ChildOf` to the root, stopping at a dirty node (its ancestors are); the walk clears a node only as it builds it, before its children, and `forget` takes a node it does not draw out with its subtree, dropping their records at once (a rerun pass may show the branch again before the frame ends, and a changed record must not replay). Dirtiness goes up, never across: an ancestor of a dirty node re-runs its own builder call (cheap) and replays its clean children, so a replay never resumes inside a half-open builder. The sources:
  - **Component changes.** `refresh`, before each scene's walk, marks the nodes whose tracked components (`tracked!`: what `NodeRead` and each kind's draw read, the row index, binding patterns, `Children`, `ChildOf`) changed since `checked`, and those a tracked component was removed from (one removal cursor per component; removals missed for two tracker clears drop every record, since who they touched is unknown). The query has `Allow<Disabled>`: the walk draws a node carrying bevy's `Disabled`. The cache keeps its own tick because the engine clears its trackers in `Last`, after the UI pass, so the world's would miss the previous frame's `update`. It moves with `increment_change_tick` after each check and each scene's walk (`walked`), so later writes are newer than it. Each record also keeps the tick it was built at (`NodeRecord::tick`), and a change counts only when newer than both: an embedded tree is drawn after the check, and its own writes are not changes. Both are clamped on `CheckChangeTicks` (`check_cache_ticks`; `src/core/AGENTS.md`, Change Ticks). Hence the rule for games: a write through `bypass_change_detection` is invisible to the cache, as to any `Changed` query.
  - **Roles** (`mark_live`, before each walk): the holders of an interaction role (`Interaction::roles`: hot, hovered, pressed, clicked, dragged, focused, gained, lost, activated, stepped, dropped on or over, the held payload's source) this frame or the last, found through `by_id`, since a widget draws its state and its exit from it; and the pending focus node, which only a build asks the focus for (`Walk::ask_focus` marks a list row's first focus asked for mid-walk).
  - **Live sets**, kept by kind as records are stored (`LiveKinds`): scroll areas and lists every frame (their own node: what they hold replays, since the scroll shift is applied at resolve); unfinished typewriters; and nodes that read input or time without holding a role, while it moves: tabs while a tab switch is pressed and choice lists while a number key is (`choice_key_pressed`), in the top scene, drop targets while a drag is held, rebinding rows while they capture or show a swap note. A builder that reads input or time another way needs a rule here.
  - **Reads**, checked when the record is asked (`replays_here`, `holds`).
  - **The environment**: `UiEnv` (`env.rs`: the theme's generation, taken from one process-wide counter by every change and by loading skins, so a theme put in place of the `UiTheme` resource never shares one with the theme it replaced; the fonts', the prompts' (device, pad family, bindings, text icons), the UI scale and size) and the record's scene and top flag. A change rebuilds every tree once: rare, and plainly correct.
  - A node without a record of this scene is never marked: it is built anyway, and marking it would dirty its ancestors (a hidden branch's typewriter would rebuild the path above it every frame).
- **Splice or build** (`draw_node`). A clean node (caching on; not dirty; a replayable record built in this scene, top flag, environment and id scope; every read holding: `take_clean`) replays (`replay_taken`), each child slot filled by the child's replay (`replay_child`). Any other node is built into a new tape and stored, each child in a slot (`draw_child`).
  - **Never build a child inside a replay.** A replay does not push its node's id scope, so a child built there would make other ids and lose its state and focus. There the scope check is skipped (`None`): by induction a child's recorded scope is the one its parent's build gave it.
  - **A miss is a bug.** A child found unclean in a replay breaks the invariant. It is counted (`CacheStats::missed`), warned once, taints, is marked anew with its ancestors (`mark_anew`, so a stale entry cannot stop the mark) and drawn from its old record; it builds next frame. A hidden or despawned child draws nothing and is forgotten.
  - **Off** (`UiCache::enabled`, copied from `DebugConfig::ui_cache` each pass; `UiHarness::set_ui_cache`), every node builds and nothing is recorded; the records left drop at the frame's end.
- **Writes during the walk.** A node's writes to itself (a value written back, `UiInteraction`, a text field's `UiTextValue`, a typewriter's advance) come from a node built that frame, whose new record shows them: they are not marked. A scene's `walked` moves `checked` past them; an embedded tree's records keep the tick its walk wrote at. A write to another node (a bound widget's change setting a pattern elsewhere, `bindings::widget_wrote`) marks that node at once and taints (`wrote`), so one drawn later this frame builds with the new value and one drawn earlier builds next frame, as without caching.
- **Embedded trees** (`ui.node`) take the cache out as `draw_nodes` does and check their own tree only (`check_tree`): one walk of the tree's nodes marks each whose tracked components changed since `checked` (a write the closure made before the call is drawn this frame) or that is live, then the removals and the roles inside the tree. A closure drawing many trees so pays for each tree once, never for every node in the world per tree. `checked` stays: what the closure wrote to other trees is seen by their own check (a later `ui.node`, the next scene's or frame's `refresh`), and marking the scene's trees' roles again would rebuild them a frame too long. The tick moves before the tree's walk (its writes get a tick of their own, which its records keep) and after it (later writes are newer).
- **List rows** replay or build like children; the `List` node is live. `Walk::sync_row` marks what a row's binding sync wrote before the row draws (a mid-walk refresh would see the walk's own writes too), and `skip_row` forgets a row given its item this frame, which is not drawn and must not stay dirty under a list just built.
- **The spot check** (debug builds; `SpotCheck`, `spot_check`). Each frame one clean record, taken in turn by entity, is built in place of its replay, with the clean ancestors above it (only a build reaches a child), and each build is compared with its record op by op (`Tape::first_difference`). A difference is an input the cache does not track: it warns once per node ("the cached UI node .. does not build as it was recorded"), and the build becomes the record. On in the engine's debug builds, off in `UiHarness` until `set_ui_spot_check(true)`. Spot builds are counted apart (`spot_built`, `spot_checked`), not in `built`, so `debug:ui-rebuilds` does not outline them; debug builds report fewer replays than release ones.
- **`debug:ui-rebuilds`** (`RebuildsOverlay`, `debug.rs`) outlines each node in the last pass's `rebuilt` that has a response id (widgets and containers: a text, separator or spacer shows only as its container's outline), fading over 0.5 s, with the counter "rebuilt N / replayed M nodes (spot check K)" and the render line as the engine overlays' mono panels in the bottom-left stack, above whichever of stats, FPS and frame timing are shown (`overlay_stack_top`). The counter and the render line come from `OverlayTally` and refresh once a second (the counter shows the frame at which it refreshes, K totals the second), so the overlay does not keep an idle UI redrawing; the outlines stay per frame; `ui:cache on|off` sets `DebugConfig::ui_cache`, as `EngineBuilder::ui_cache` does.
- **The oracle is the test of record.** `oracle` runs a scenario in two harnesses, the cache on and off, and after every frame asserts equal `frame_snapshot`s (commands, records, focus, events, the interaction, widget states with their values, modals, consumed input, every node's components), no miss and the invariant. Its scenarios (two of them seeded random runs) give each dirtiness source a case it alone decides, and they run again with the spot check on. A new dirtiness source, read or replay duty gets a scenario that fails without it. At the engine level, the ui demo's and breakout's `tests/cache.rs` compare a `HeadlessEngine` built with `ui_cache(false)` against a cached one frame by frame (`ui_snapshot`), and `tests/e2e/ui_cache.rs` pushes and pops a scene whose lower scene writes the overlay's label.
- **Four checks are kept as defence in depth**, though no scenario can make them fail (each was mutated; nothing caught it):
  - the record's top flag: builders read `top` only through responses, shortcuts, flushes and capture cancelling, which come with a role, a live rule or an untaped flush; kept so a builder that reads it another way never replays stale across a scene change;
  - the drop-target live rule: a target draws its drag-over look only while it is `drop_hover` or focused, both roles; kept for a look that answers any held payload;
  - `draw_node` refusing to replay the pending-focus node: `mark_live` and `ask_focus` mark it already; kept because only a build asks for the focus, so a replayed node would leave the request waiting;
  - a replay registering its ids (`replay_id`): `made` is read only for the focused widget (always built) and a list's pending row (marked, so built); kept so a replayed id is never free for a duplicate or missing from a list's capture.

## Theme

`theme/` (`mod.rs`, `look.rs`, `builtin.rs`, `file.rs`). The spec is `docs/specs/2026-10-16-ui-interaction-design.md`.

- **`UiTheme` is a world resource** holding an `Arc<Theme>` (`get`, `set`, `modify`; `ctx.ui_theme()`, `EngineBuilder::ui_theme`). `Engine::draw_ui` takes the `Arc` once per pass (`refresh_ui_theme`) and gives it to the `UiContext` (`ui.theme()`), so a change applies from the next frame. The interaction resolves read the same theme's metrics (drag threshold, double click, wheel line, repeat delay and rate) through `PointerInput::double_click`, the `resolve_pointer` and `route_wheel` arguments and `NavInput::repeat_*`.
- **Looks.** A `Theme` has a `Palette`, `Metrics` (radius, timings, `FocusRing`, `Sizes`), `TextRoles` (`TextLook`: size, colour, font, bold, which a RON file can state), a `Looks` per `WidgetKind` and named `Variant`s. `Looks::resolve(state)` starts from `normal` and applies the state's `LookPatch` (`Some` replaces): `Pressed` applies `hovered` first, `Focused` only its own patch. `Theme::look(kind, variant, state)` then applies the variant's `normal` and state patches, and `.style(patch)` on the widget applies last, in every state (`UiContext::look_of`). An unknown variant or skin name warns once and draws the plain look. `UiContext::widget_state` picks the state: disabled, pressed, hovered, focused with the ring visible, else normal.
- **Padding and sizes.** A look's `padding` is used when it is not zero; otherwise the widget takes its size from `Metrics::sizes` (the button's padding, the panel's). The scrollbar's look is its colours: `fill` is the track, `border` the thumb, and its hovered and pressed patches the thumb's states. The slider and progress looks use `fill` for the track and `border` for the filled part; the slider's `text` is its handle.
- **Skins.** A look with `skin: Some(name)` draws that skin's sprite as `DrawKind::NineSlice` (corners of `insets` sprite pixels drawn at that size in UI units, pieces snapped to render pixels), the look's `fill` tinting it; without a sprite it draws the plain look. The engine loads skin `path`s through `AssetManager::load_sprite` when the theme's generation changes (`UiTheme::load_skins`). The skin's `filter` is carried by `DrawKind::NineSlice` and `UiCommand::Sprite` to the draw.
- **Files.** `Theme::load`/`save` are RON, read with the `implicit_some` extension. `load` parses the file as plain data (`serde_json::Value`) and merges it over `Theme::dark()` serialised the same way, map by map (so a nested partial struct, or a `variants` map that adds one variant, keeps dark's other fields and entries; lists and options replace), then deserialises the result. RON loses the names of bare unit variants in plain data, so `Variant::base`, `TextLook::font` and `Skin::filter` are strings in files (`base: "Button"`, `font: "Pixel"`, `filter: "Nearest"`, field-level `serde(with = "names")`); an unknown name is a `ThemeError::Parse` naming the path, the type and the name. `load` stores the path as the theme's `source`. In debug builds the engine polls a `ThemeWatch` each frame: at most once a second it compares the source file's modification time, reloads and `set`s on a change, and on a load error warns once per change and keeps the old theme.
- **Built-ins** (`builtin.rs`): `dark` (today's colours), `light`, and `pixel` (the pixel font at 16, square corners, button and panel skins drawn in code). All carry the `danger`, `accent` and `tab` button variants and the `selected` tab variant. Their Choice looks are plain rows filled on hover, press and focus; their Modal look is the dim behind a modal.

## Frame cost

The UI is built every frame, so the shared pipeline does per frame only what changed. The profile and the decisions behind this are in `docs/specs/2026-10-18-ui-fast-design.md`; `benches/ui.rs`, `tests/ui_alloc.rs` and `tests/ui_list_alloc.rs` guard them (Testing and performance).

- **One fast hasher.** `core::hash` (`FastHasher`, `FastMap`, `FastSet`, `fast_hash`, `fold`) folds a word at a time with a 128-bit multiply. Every engine-keyed map in the UI and the text engine uses it: ids and their per-frame maps, `UiMemory`'s records, states and focus memory, the layout engine's entries and index, the text caches. SipHash (`std`'s default) cost about 40% of a frame, and its resistance to crafted collisions buys nothing for keys the engine makes from its own data, never from player input. Hash values may change between versions: never save them.
- **Text hashed once.** A text leaf (`TextLeaf`, `tree.rs`) carries a `TextKey` (`text/key.rs`): its text, style shape, colours and options, each hashed once when the leaf is made (and made again when any of them changes), passed to the text engine's keyed calls for measuring and drawing. A cache hit is confirmed against the stored source, so a collision is a miss, never another text's layout (`src/core/text/AGENTS.md`).
- **Kept buffers.** `UiMemory::scratch` (`Scratch`) keeps the subtrees' node, draw and text leaf lists (`take_subtree`, `give_subtree`) and tree resolve's vectors (the layout descriptions, the floating styles of the nodes with an `at` rect, each node's children run by run, shifts, rects and clips); the layout engine keeps its own (`Buffers`). Each is cleared at its use, its capacity kept. A `Node` holds no child list: `child_runs` builds the runs into scratch at each resolve. `tests/ui_alloc.rs` counts an unchanged settings frame's allocations (under 220), `tests/ui_list_alloc.rs` that an unchanged frame of a 10,000-row closure list allocates as much as a 100-row one, and `tests/ui_cache_alloc.rs` that an unchanged cached node frame allocates no more than an uncached one and the same every frame, at most 30; each binary holds that one test, because the counting allocator is global.
- **A node is small.** A built text node's `TextLeaf` goes into its subtree's `leaves` and the node holds `Leaf::Owned(index)` (`push_text_node`), so a `Node` is about 300 bytes to push, clone and resolve; a taped node holds `Leaf::Shared(Arc<TextLeaf>)`, which a replay shares. `Leaf::get(leaves)` reads either.
- **The layout diff by hash.** A layout entry keeps one hash of its raw style (`UiStyle::shape_hash`), its parent's flow and its measure kind. Only a node whose hash changed is cleaned and converted for Taffy, and only a changed child list is sent. A field added to `UiStyle` must be added to `UiStyle::hash_into`, or a change to it alone is never laid out.
- **The kept shape hash.** `Node::shape` holds the style's `shape_hash` (0: not known); `tape_node` fills it, so a replayed node is not hashed again. **Anything that restyles a node in place after pushing it must reset `node.shape` to 0** (`flush_popups` does, for a popup root's `min_width` and `anchor`); a debug assert in the layout (`node_hash`) catches a miss anywhere in the test suite.
- **Lines placed by offset.** `UiCommand::Line` carries `at`, added to each point where it is emitted (`render::ui::emit_ui`), so placing a node's local line (a check mark, a chevron) shares its `Arc<[Vec2]>` instead of copying the points.
- **The layout's sweep.** `LayoutEngine::end_frame` removes the entries not laid out this frame only when `laid` (the entries laid out since `begin_frame`) falls short of the entry count.
- **Looks borrowed.** Widgets read their look from the theme by reference, and `Look::skin` is an `Option<Arc<str>>`, so resolving a look copies no string.
- **The node walk** reads a node's hidden flag, kind, binding, disabled flag and tooltip in one entity lookup (`NodeRead`, `draw.rs`), then dispatches on the kind.
- **Nothing added to the world that the game did not ask for.** A UI pass adds no resource and no bookkeeping entity, and avoids adding archetypes (Notes for AI Agents, 6).

## Testing and performance

- **`UiHarness`** (`ryo2d::testing`, `src/core/testing/ui.rs`) is the engine's UI frame without a window or GPU: it owns a `UiMemory`, a `LayoutEngine`, a `TextEngine` over the built-in fonts and the `UiCommands`, and each `frame` runs the engine's order (`reload_trees`, `begin_frame`, `resolve_pointer`, `apply_scroll_requests`, `route_wheel`, `resolve_focus`, `update_lists`, the node trees and then the closure as the top scene between `begin_scene` and `end_scene`, `end_frame`), 1/60 s apart. Its public script is the pointer, the left button, the wheel and the nine `ui.*` actions (`action(name)`; another name warns once). A frame that records nothing rewinds the memory (`UiMemory::rewind_frame`), so a read such as `scroll_offset` leaves the UI as the last drawn frame left it. `set_ui_cache`, `set_ui_spot_check` and `ui_cache_stats` reach the node cache, and the doc-hidden `frame_snapshot` is everything a frame shows, for comparing two runs (`src/core/testing/AGENTS.md`).
- **`test_util::UiDriver`** adds the crate's scripting on top: keys, typed text, IME composition, Shift, pad buttons, held directions, the right stick, the device, the scene, prompts and the theme, and reads of the memory, commands, sounds, outcomes and captured rebinds.
- **Benchmarks** (`benches/ui.rs`, on `UiHarness`): a 200-widget settings screen (a focus-scoped panel that wraps, of tabs and a scroll area of 50 rows, a `ui.down` every 10th frame, so every step moves the focus and scrolls) must stay under 60 µs; a 1,000-row scroll list scrolled to its middle; an empty frame. ## Drawing on the GPU

- **Recording.** `UiContext` draws nothing itself: every primitive records a `UiCommand` (`Rect`, `Sprite`, `Line`, `Text`) in UI units into the engine's `UiCommands`. The commands, clips, text, fades, the typewriter and popups are described in `immediate/AGENTS.md`.
- **The UI pass.** At present time `render::ui::emit_ui` lays the commands into the 2D batch for the UI camera (`UI_CAMERA`, `CameraDraw::ui`): one z per command (layer, then the order it was recorded in), so the painter's order holds. The `ui` render pass draws that camera into the UI image: `Rgba8Unorm`, gamma-encoded colour premultiplied by alpha (`UI_FORMAT`, the `UI_GAMMA` override). The composite blends it over the frame in sRGB space, so a 50% black panel over white is 128, as on the web. Rects are analytic (`BatchShader::UiRect`: rounded corners, inner border, anti-aliased edges). Frame steps and shaders are in `src/core/render/AGENTS.md`.
- **UI units and scale** (`render/ui.rs`, `UiSpace`). With the automatic scale (`ui_scale: None`, the default) UI units are screen units at any display scale; text is laid out at render pixels, so it is sharp on HiDPI displays. `EngineBuilder::ui_scale(Some(s))` / `ctx.request_ui_scale` make it `s` render pixels per UI unit, rects and text alike; mouse positions are converted to UI units (`UiInput::with_mouse_scale`). `UiResolution::Render` (default) draws the UI at the render size (pixel art: the low-res target, snapped like the world); `Window` draws it at window resolution.
- **Clipping** is a scissor per command (the clip in image pixels, rounded outward); the stack has no depth limit.
- **Text** goes through the text engine (`src/core/text/AGENTS.md`): measured, wrapped and laid out at the UI scale. Fonts are the `Fonts` resource; the UI uses `FontRole::Ui`, and the console and overlays `FontRole::Mono`.

## Notes for AI Agents

1. **State ownership**: the game's values (a selection, a volume, a name) are the caller's; what a widget remembers of itself (an open list, a caret) is in `UiMemory`, dropped when the widget is not drawn for a frame.
2. **UI units**: all coordinates are UI units (screen units with the automatic scale), never render pixels.
3. **Alpha blending**: colours with alpha < 255 blend with what is below in sRGB space, as designers expect.
4. **The UI is never lit** and never post-processed.
5. **Fade text through opacity**, never through a style's colour: colour is in the layout cache key, so a colour fade lays the text out again every frame (`ui.text(..).opacity(a)`).
6. **A UI pass adds nothing to a world the game did not ask for, and avoids adding archetypes.** No resource and no bookkeeping entity: the only entities it spawns are a list node's pooled rows, which the game's list asked for. In bevy 0.20 a resource is an entity: when the reload check kept its query as a resource, every later entity id shifted, and so did the archetype order a fresh query sees, which changed what a game printed and drew. Keep per-world UI state outside the world (the reload query is owned by `Engine` and `UiHarness`, keyed by `WorldId`), and return early when there is nothing to do (`update_lists` in a world with no list). One known archetype remains: `draw_nodes` takes `UiNodes` out with `try_resource_scope`, which adds one archetype in a world with node trees.
