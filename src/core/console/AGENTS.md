# AGENTS.md - The developer console

The console window (`mod.rs`, the `Console` world resource) and the commands typed into it. Design: `docs/specs/2026-11-09-dev-tools-design.md` ("The console").

| File | What |
|------|------|
| `mod.rs` | `Console` (dev tools only): the window, input line, history, output (1,000 lines), scrolling, mouse, Tab completion and the log mirror; `log_show`, the lowest log level the console shows (`log:show`, default `warn`) |
| `view.rs` | Drawing (dev tools only): the window, the input line and the output, each line wrapped once for its width |
| `tests.rs` | The console's own tests (the view's are in `view.rs`, and use its `scrolling_console`, `console_frame` and `scrolled_units`) |
| `command.rs` | `CommandSpec` (name, description, usage, help) and `Command` (what a handler gets: arguments, typed `arg`, printing, `act`, `quit`); `split`, the line's words (double quotes keep a phrase) |
| `scope.rs` | `ConsoleScope`, what `ctx.console()` returns: `command`, `remove`, `print`, `print_colored` |
| `registry.rs` | `ConsoleCommands` (dev tools only): per name, a stack of entries; `Handler`; `erase`; `EngineHooks`; `valid_name` |
| `dispatch.rs` | `run_line` (dev tools only): how a line runs |
| `builtins.rs` | The built-in commands (dev tools only) |

## Three kinds of handler

- **Built-in** (`Handler::Builtin`): the world and `EngineHooks`, the engine's own state: its `DebugConfig`, the overlay mode F1 cycles (so `debug:stats` and F1 agree), the frame capture, quit, and the game's name and version. Game code never sees the hooks.
- **Builder** (`Handler::World`, `EngineBuilder::console_command`): the world, for the whole run.
- **Scene** (`Handler::Scene`, `ctx.console().command::<S>`): the scene itself (`&mut S`, downcast from `&mut dyn Scene` by `erase`; a scene of another type is refused with an error) and the `SceneContext` `update` gets. It runs through the scene host as `update` is, inside the scene's scope (`SceneManager::call_scope` calls the slot), so the sounds and particle effects it starts are that scene's.

## A name's stack

Names are lower-cased when added and when looked up. A name has at most one run-long entry (a built-in or a builder command) at the bottom, then the scenes' entries by scope id; scope ids grow with each scene made, so the uppermost scene's entry answers whatever order they registered in, and the one below answers again when it leaves. A scope re-adding its own name replaces its entry, and a second run-long entry replaces the first: the engine adds the built-ins first, then applies the builder's `console_command` and `remove_console_command` calls in the order made, so a builder `help` replaces the built-in. `remove` (the builder's, or `ConsoleScope::remove`) takes every entry of the name. A name that is empty or has whitespace is refused with one warning naming it.

A scene's entries go when its slot leaves the stack (pop, switch, reset, clear): `release_scope` (`scene/manager.rs`) calls `ConsoleCommands::clear_scope`, beside the audio and particle releases.

## How a line runs (`dispatch::run_line`)

1. `Console::handle_input` echoes the submitted line (`> line`, light blue); `console_tick` (`engine/frame.rs`) passes it to `Engine::run_console_line`, which builds the hooks from the engine's fields.
2. The line is split; the first word, lower-cased, is the name. An empty line (or `""`) does nothing; an unknown name prints `Unknown command: <name>. Type 'help'.` in red.
3. `find` clones the spec and the handler (`Arc`s) out, so nothing of the registry is borrowed while the handler runs: a handler may add or remove commands, or pop its own scene.
4. The handler runs (above). A scene entry whose scope has no slot prints an error and its scope's entries are removed.
5. Its printed lines go to the console, then an `Err` text in red. A line the handler prints through `ctx.console().print` goes in at once, so it comes before the command's own lines, which are buffered in `Command` until the handler returns.
6. A scene action it asked for goes through `SceneManager::handle_action` and `sync_pauses`, as `update`'s does: a builder's or a built-in's always, a scene's only from the top scene (a lower scene's is dropped with a red line, as `update` drops one). During a transition only `Quit` applies; a scene change asked for then is dropped with a red line. A stack left empty, or `cmd.quit()`, asks the engine to quit (`run_console_line` inserts `QuitRequested`, as a scene's quit does).

The console runs once a frame in `console_tick`, after `PreUpdate` and before the UI pass, on real time, so commands work while the game is paused. A closed console does no work a frame: `console_tick` and the UI pass only read it, so the resource is neither changed nor taken out of the world (`a_closed_console_does_no_per_frame_work`); its clock and scroll ease stand still until it opens.

`log:level`: it calls `logging::set_level`/`level` as they are, where `game`, `engine` (every `ryo2d…` and `ryo2d_…` target) and `library` name the three origin defaults, as everywhere a level is set (`RYO_LOG` included; logging module notes, Levels); any other word is a target prefix with an override. The listing shows a `defaults:` block and an `overrides:` block.

## The window

- **Wrapping.** Each `ConsoleLine` keeps its wrapped `rows`; the console keeps the width (and UI scale) they were wrapped at (`wrap_width`), how many lines from the oldest are wrapped (`wrapped_lines`) and their rows altogether (`wrapped_row_count`). A render wraps only the lines printed since the last one, or every line when the width or the scale changed (a resize, the scrollbar appearing or going). The text is wrapped at the full width, and at the narrower one while the rows overflow the view; it goes back to the full width once the narrower rows fit (so a view whose rows overflow only when narrow keeps the scrollbar). `total_rows` counts the wrapped rows plus one per line not yet wrapped, so scrolling between renders reads the current count, not last frame's. A held-open console with 1,000 lines wraps each once (twice when the scrollbar came; `a_held_open_console_wraps_each_line_once` counts calls with a test-only counter, `wrap_calls`). An empty line is one row.
- **Completion.** Tab on the first word (no whitespace in the line yet) completes it from `ConsoleCommands::completions`: one match becomes the name and a space (so a second Tab, now after the first word, does nothing); several are completed to their longest common start, and a Tab that finds the line as the last Tab left it lists them on one line (grey, two spaces apart); any edit of the line (typing, Backspace, Delete, history, Enter) forgets the last Tab (`line_edited`). `handle_input` only notes the Tab (`take_tab`); `console_tick` completes with the registry (dev tools only).
- **The log in the console** (`mirror_log`, dev tools only). Run by `console_tick` when the console opens and each frame while it is open (a closed console does nothing a frame): it appends the ring's records after the last sequence it read (`log_seq`), of the engine's log scope (`Engine::log_scope`: in a test process each engine shows only its own), at or above `log_show`, as `target: message`: warnings in yellow (`colors::WARNING`), errors in red, info white, debug and trace grey. It starts just before the ring's oldest record when `Engine::new` runs (`logging::mirror_start`), so the builder's warnings (Ryo.toml, the save folder, the settings file) and the game's `main`'s are shown, and nothing counts as lost at the start. What was logged while it was closed is there when it opens; the catch-up keeps the newest 1,000, and the scope's warnings and errors it cannot show, those the ring dropped since its last read and those past the cap, are counted in one grey line, `N earlier warnings and errors are no longer shown` (none when N is 0). The ring keeps those counts per scope (`log_mark` is the scope's warnings given at the last read). With nothing logged anywhere since its last read it takes no lock: one atomic load of the next sequence number (`logging::records_may_follow`; `an_open_console_with_nothing_new_takes_no_lock`). `log:show off` reads nothing and moves past what was logged meanwhile. No loop: printing logs nothing (a line is pushed, and wrapped when drawn), so no record of the console's own making reaches the mirror.
- **The mouse.** The pointer is converted to UI units (`set_mouse_scale`, the UI pass's `UiSpace::mouse_scale`) before every hit test and the cursor check, so they match the drawing under an explicit `ui_scale`. `render` writes its clamped position back, so after the game window shrinks the window is hit where it is drawn. In the UI pass, every mouse button pressed over the window is consumed before the scenes' UI (`UiInput::consume_mouse_presses`), and a press taken there stays hidden from gameplay through its holds and release, wherever the pointer goes (`ui_mouse_capture`). Only presses: a drag the game began keeps its holds and release over the console.
- **Typing.** The console key (`KeyCode::Backquote`, the physical key, whatever character the layout gives it) opens the console, and closes it while the input line is empty; with text in a focused console's line it types its character (`handle_debug_keys`). The press that toggled it is the console's until that key is released (`Console::key_held`): its text and its auto-repeats' are taken (`Input::consume_text`), so a held key neither types nor toggles again. Escape and the close button always close it. Control characters (a Tab's) are not typed.

Tests drive it through `HeadlessEngine::console_run` (doc-hidden, dev tools): the line is echoed, run, and the lines printed after the echo are returned (`Console::capture`/`take_captured`). `console_fill` and `console_open` (doc-hidden, dev tools) are the bench's.

## A build without the tools

The console is a developer tool: everything here but `command.rs` and the `ConsoleScope` front is `#[cfg(dev_tools)]` (the `Console` resource and its window, `view.rs`, `registry.rs`, `dispatch.rs`, `builtins.rs`, the tests). A build without the tools has no `Console` or `ConsoleCommands` resource, no dispatch and no built-ins, so its binary holds none of their names (`system:timescale`, `log:level`). What a game writes still compiles there: `ctx.console()` gives a `ConsoleScope` that holds no world (`command` and `print` drop their arguments, `remove` returns false), `Command` and `CommandSpec` exist (their crate-internal constructor and readers only with the tools, or in tests), and `EngineBuilder::console_command` and `remove_console_command` drop their arguments. The engine's own call sites have a counterpart without the tools where both builds need one (`Engine::console_rect`, `Engine::console_cursor`: none), and gate the rest (`console_tick`, the console key, the console's UI pass, the capture lines it prints).

No file here names `std::net` (`the_console_names_no_network_code`).
