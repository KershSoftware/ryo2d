# Skeleton module notes

Skeletal animation is being rebuilt from scratch. The design and its decisions are in `docs/specs/2026-11-12-skeleton-design.md`.

## Data (`data.rs`, `attachment.rs`, `skin.rs`, `curve.rs`, `animation.rs`)

- `SkeletonData` is immutable once built. Everything goes through `SkeletonDataBuilder` (`builder.rs`), which checks it in `build` (`validate.rs`); the loader builds through it too.
- The builder refers to bones, slots and skins by name. Animations hold `BoneId`/`SlotId` and event indices, and region attachments hold region indices: places in the order added, which `bone_id`, `slot_id`, `region_index` and `event_index` look up.
- `SkeletonError { item, problem }` names the item as `bone "arm"`, `slot "head"`, `region "torso"`, `event "step"`, `skin "red"`, `skin "red" slot "head" attachment "hat"`, `animation "walk"`, `animation "walk" timeline 2 (rotate)`, `mix "idle" to "run"` or `default mix`. The first problem found is reported.
- In the prelude, the module's generic names are prefixed (aliases; the types keep their short names in `ryo2d::core::skeleton`): `SkeletonClip` (`Animation`), `SkeletonCurve`, `SkeletonSkin`, `SkeletonTimeline`, `SkeletonAttachment`, `SkeletonRegion`, `SkeletonEventData`, `SkeletonEventValues`, `SkeletonEventAudio` and `BoneInherit` (`Inherit`).
- Bone timelines key rotate, and translate, scale and shear either combined (`Vec2` keys) or per axis (`TranslateX` … `ShearY`, `f32` keys).
- Colours (`SlotData::color`, `RegionAttachment::color`, colour keys) are 8-bit sRGB `Color`s. The pose keeps each slot's colour in float (`Vec4`, sRGB with alpha, 0 to 1), so blends never round; drawing clamps it and converts it to 8 bits.

## The file (`src/core/asset/loaders/skeleton.rs`)

- `SkeletonLoader` reads `.skeleton.ron`; its rustdoc holds the whole format as a commented example, which a test loads (`the_documented_example_loads`). Everything the data holds is expressible: every bone field and inherit mode, slot colour and blend, regions on several images, region, point and bounding-box attachments, several skins, events with default values and audio, combined and per-axis bone timelines, attachment, colour, draw-order and event keys (with value overrides), a curve on every value key, and the mixes.
- Choices where the brief was silent: images are named in `images` and regions refer to them by name, their paths from the asset root; a region attachment's size is its region's unless written; a key is `(time, value)` or `(time, value, curve)`, the curve `Linear` when left out; a draw-order key lists every slot by name (`(0.25, ["head", "torso"])`, or `None` for the setup order); an event key is `(time, "event")` or `(time, "event", (int: 9, volume: 0.3))`; the mixes are a map, `{ default: 0.1, pairs: [("a", "b", 0.2)] }`.
- Timelines come out in a fixed order: each bone in file order (rotate, translate, scale, shear, then translate x, translate y, scale x, scale y, shear x, shear y), each slot (attachment, colour), then draw order and events, so a validation error's `timeline N` follows the file.
- Names the file uses that nothing declares (an animation's bone, slot or event, a region's image, an attachment's region) fail as a `SkeletonError` naming the animation, region or `skin .. slot .. attachment ..` and the name.

## Validation rules

Every rule below has its own test in `validate.rs`, which asserts the error's full item and that the problem names the reason.

- Names are unique per kind (bones, slots, regions, events, skins, animations), and so is an attachment name within a skin's slot, and a mix pair.
- Parents come before children. At most 255 bones and 255 slots (`bone_id` and `slot_id` give `None` past the 255th).
- References resolve: parents, slots' bones, attachments' skins, slots and regions, timelines' bones and slots, event keys' events, mixes' animations.
- Values are finite: bone setups, attachments, event defaults and overrides, key times and values, curves, durations and mixes. Durations and mixes are not negative.
- Rules we chose where Spine's docs are silent:
  - The default skin (`SkeletonData::DEFAULT_SKIN`, "default") always exists, first in `skins()`, and may be declared once without being a duplicate.
  - Every timeline has at least one key. Key times run from 0 to the animation's duration, strictly increasing, except event keys, which may share a time (several events at one moment).
  - An animation has at most one timeline per property of a bone or slot: two rotate timelines on one bone fail, and so do a combined translate and a translate x on one bone (the combined one keys both axes); translate x and translate y together are fine. At most one draw-order and one event timeline an animation.
  - A bezier's x controls lie in 0..=1, so its time never runs backwards.
  - A draw-order key lists every slot exactly once (or is `None`, the setup order).
  - A region is not empty; a bounding box has at least three vertices.
  - No animation is named `<empty>`: that is the animation state's empty animation (`SkeletonAnimation::EMPTY`), and a track event's animation name must tell the two apart.
- Not checked: slots' setup attachments and attachment keys are names looked up in the skin at run time, so a name no skin has is allowed (it shows nothing).

## Pose and world transforms (`pose.rs`)

- `BonePose` is a bone's local transform (setup, or as animations leave it); the crate-internal `Pose` holds one per bone, the world transforms, and each slot's colour (float sRGB, `pose::srgb` of the setup colour) and attachment and the draw order, all set from the setup by `Pose::setup`. `Pose::reset` puts the local transforms, colours, attachments and draw order back to the setup without allocating, and leaves the world transforms as last computed (`reset_puts_a_changed_pose_back_to_setup`); the animation state calls it at the start of every step's apply.
- A bone's local linear part: x axis `scale_x * (cos(rotation + shear_x), sin(rotation + shear_x))`, y axis `scale_y * (-sin(rotation + shear_y), cos(rotation + shear_y))`. With y down this turns clockwise, as the engine does.
- `compute_world` is one pass over the parent-first bones. A child's origin is always its parent's full world transform applied to `(x, y)`: translation is inherited in every mode. Its linear part is `M * L`, where `L` is its local linear part and `M` comes from the parent's world linear part `P` (axes `p_x`, `p_y`) by mode:
  - Normal: `M = P`.
  - Only translation: `M = I`.
  - No rotation or reflection: `M = R(θ) * diag(s, u) * R(-θ)`, where `θ` is the parent bone's direction (the angle of `p_x`), `s = |p_x|` its length scale along itself and `u = |det(P)| / s` its area per unit length across itself. The child keeps its own world angle and is stretched along the parent bone's own axes, wherever the parent points: a parent turned 90 degrees and scaled (2, 1) stretches the child vertically. The parent's shear is dropped: written as `P * R(-θ)` it would skew the child's axes, which is a rotation the mode removes, and a mirrored parent's shear has no single unmirrored form. The absolute determinant takes out reflection and keeps the parent's area. If `p_x` has collapsed (under 1e-6), `θ` comes from `p_y` turned back a quarter, with `s = 0` and `u = |p_y|`, the limit of the normal path; with both axes collapsed `M` is zero.
  - No scale: the child is rigid, pointing where normal inheritance points it. Its world x direction is `d = normalise(P * (cos(r + shear_x), sin(r + shear_x)))`, its y direction `d.perp()` (a quarter turn clockwise), negated when `det(P) < 0` so the parent's mirroring stays. Then the child's own scale and shear apply in that frame (its linear part with the rotation taken as `-shear_x`). Taking the direction from `P` applied to the child's own direction, not from `p_x`, makes it match normal inheritance exactly under a skewed parent (a chain of turns under non-uniform scale), and the perpendicular unit frame takes out every scale and skew. If `P` squashes that direction flat (a zero-scale parent), the child is turned by the parent's rotation (from `p_x`, else from `p_y` turned back a quarter) at full size; with both axes zero it keeps its own axes.
  - No scale or reflection: as no scale, but the y direction is always `d.perp()`, so a mirrored parent leaves the child pointing as normal inheritance does but unmirrored.
- Rule we chose: the inherit modes act in skeleton space. `root` (the entity's transform) is applied to every bone after the pass, whatever its mode, so turning, scaling or flipping the entity turns, scales or flips an only-translation or no-rotation bone too (Spine's own flip flips every bone).

## Curves, applying an animation and events (`curve.rs`, `apply.rs`)

- `Curve::value(t)` eases a fraction of the span between two keys. The ends are exact (0 gives 0, 1 gives 1), so every key's value is hit exactly. Stepped gives 0 until 1. A bezier is solved for the parameter whose x is `t` (Newton's method kept inside a shrinking bracket, bisecting where a step would leave it or the slope is flat; it stops at an x error under 2e-7 or a bracket under 1e-7 wide), then its y is taken; the x controls lie in 0..=1, so x is monotonic and the answer unique.
- `apply(animation, data, pose, time, alpha, blend, direction)` blends one animation into the pose. `time` is the animation's own time; the caller wraps a looping track. Rules we chose where Spine's docs are silent or where we keep only part of Spine's model:
  - Before a timeline's first key it leaves the pose alone, whatever the blend; after its last key the last value holds. Between keys the value is the first key's plus the change times the first key's curve value.
  - Bone keys are relative to the setup pose: rotate, translate and shear add to the setup value, scale multiplies it. Call that the target.
  - Replace moves each bone property toward the target by alpha (`value += (target - value) * alpha`). Rotation goes the short way round: the difference is wrapped to -180..=180 degrees first. Keys themselves interpolate as written, so keys 0 and 360 make a full turn; the wrap applies only to blending toward the pose. Shear blends without wrapping.
  - Add adds the target's change from setup times alpha (`value += (target - setup) * alpha`): the key for rotate, translate and shear, and `setup * (key - 1)` for scale.
  - Colour keys are absolute. Components are interpolated in float, in sRGB (not linear light), and both blends move the slot's colour toward the key by alpha: colours do not add. Nothing is clamped or rounded in the pose (a bezier can overshoot); drawing clamps.
  - Attachment and draw-order keys are stepped and apply only when `direction` is `In`, whatever the alpha or blend: a step cannot be part-applied. The animation state passes `In` to at most one entry of a track, the one that owns the stepped keys (see "Stepped keys" below), and `Out` to the rest. A `None` attachment key hides the slot; a `None` draw-order key restores the setup order. Bone and colour timelines ignore the direction.
  - Event timelines do nothing in `apply`.
- `MixBlend` (`Replace`, `Add`) is public, for tracks. `MixDirection` (`In`, `Out`) is crate-internal.
- `events_between(animation, last, now, looping, out)` pushes the event keys in (`last`, `now`] onto `out`, in time order, as (unwrapped time, event index, values). Times are the track's unwrapped time: a looping animation's keys repeat every duration from 0, so a span over several loops fires each loop's keys once, and contiguous spans never fire a key twice. Rules we chose:
  - The first step passes a negative `last`, so a key at 0 fires on it, and on each later loop (at 1 x duration, 2 x duration, ...).
  - Not looping, only the animation's own keys fire. A zero-length looping animation fires its keys once, as if not looping.
  - Nothing fires when `now <= last` (or either is NaN). Reverse playback is the animation state's to mirror into forward times.
  - A loop boundary is never missed: dividing a time by the duration can round across a boundary in f32 (2.7 / 0.9 is just under 3), so the search visits one loop more on each side than division gives, and the (last, now] test drops the extras. Each key's unwrapped time (`loop * duration + key`) is computed the same way every step, so contiguous steps fire it exactly once. A key at the duration and the next loop's key at 0 can come out one ulp apart in either order; a stable insertion pass keeps the output in time order without allocating.
  - One span fires the keys of at most the last 1,000 loops (`MAX_LOOPS`), those ending at the one holding `now` (1,001 when `now` sits on a boundary that division rounds under); the skipped loops' keys are not fired. The loop over them is also bounded by its length (`take(MAX_LOOPS + 2)`), so a mistake in the arithmetic fails a test and cannot run on or grow memory.
- `apply_layer` is `apply` with a fade per timeline (a factor on the alpha) and a turn memory per rotate timeline: given one, a Replace rotation blends by the turn nearest the one it took last step (the short way on the first), so a turn that would cross half a circle mid-mix keeps going the way it started. Without one (`apply`, and an entry alone on its track at full strength) it blends the short way each step.
- `events_crossed` is `events_between` playing backward when asked: a key at `k` is crossed `duration - k` into each loop. Each crossed key carries its own time in the animation too. Float-to-int casts and the loop sums saturate, so an infinite or huge `now` neither overflows nor runs past the 1,000-loop cap (`an_infinite_or_huge_span_neither_overflows_nor_runs_long`).
- The animation state calls `apply_layer` and `events_crossed`. `apply` and `events_between` are their plain forms (no fades, no turn memory, forward only), compiled for tests only: the tests of the rules above go through them.

## The animation state (`state.rs`)

`SkeletonAnimation` (a component) holds tracks numbered 0 to 63 (`MAX_TRACKS`; a higher number warns once per skeleton and does nothing: `a_track_past_the_last_warns_once_and_does_nothing`). A track is a chain, the current entry last after the entries it is mixing from (oldest first, at most 16 in all), and a queue. `TrackEntryId` finds an entry (playing, mixing out, queued or kept) until its `Dispose`. Rules, each pinned by the test named:

- **Each step** (`advance_and_apply`, crate-internal, called by the skeleton step): take up the data (below), advance every track, start the queued entries that are due, push the event keys and track events, end finished mixes, then reset the pose to the setup pose and apply the tracks from the lowest up. The reset makes every step a pure function of the tracks: nothing an animation set last step lingers when no entry keys it now (`attachments_belong_to_the_entry_mixing_in`). So whatever else writes the pose (a game's attachment or bone override) must write it after this call, every step.
- **Time** (`an_entry_s_speed_scales_its_time_but_not_its_mix`, `zero_length_animations_and_zero_mixes_are_finite`): an entry's track time advances by `dt × time_scale × the entry's speed`. A negative or non-finite `dt`, `time_scale` or speed counts as 0, and track times stay finite (an overflow holds at the largest float), so no non-finite time reaches `apply_layer` or `events_crossed`. `is_complete` is true once a started entry's track time has reached its duration; an entry that has not started (queued, or kept until the data lands) is not complete. It reads the time alone, so it also turns true for an entry that passes its end while mixing out, which sends no `Complete`.
- **Limit of track time** (`a_looping_entry_s_time_steps_coarser_after_days`): it is an `f32` that counts every loop, so a looping entry left playing for days moves in coarser steps: 2 ms after 4.6 hours (2^14 s), 8 ms after 18 hours (2^16 s), and 31 ms after 3 days (2^18 s), where a 60 Hz step rounds up to one and the animation runs near twice as fast. After 6 days (2^19 s) a 60 Hz step no longer moves it and the entry stops. Setting the animation again starts its time from 0.
- **Layers:** track 0 applies over the setup pose; a higher track over the tracks below, by its alpha (clamped to 0..=1, NaN is 0) and blend. An `Add` entry adds its change from setup times its alpha (`a_higher_track_at_half_alpha_blends_half`, `an_additive_track_adds_over_track_zero`).
- **Starting:** `set_animation` makes the entry current at once, disposes the queue (`set_animation_and_clear_drop_what_is_queued`), and the old current mixes out over the new entry's `mix_duration`: the data's mix for the pair, else its default mix (`an_entry_mixes_in_over_the_data_s_mix_for_its_pair`); the field can be changed until the mix ends. The first entry on an empty track has nothing to mix from and shows at once at its alpha (`a_layer_fades_in_after_set_empty`). An entry replaced before it was ever applied (two calls in one frame) is dropped, not mixed from: it gets its `Interrupt`, `End` and `Dispose`, and the new entry mixes from the one before it. The empty animation is the exception: it stays, so `set_empty` and `set_animation` in one frame mix the new entry in from nothing (`an_entry_replaced_before_it_shows_is_dropped`).
- **Chain length** (`a_track_mixes_from_at_most_fifteen_entries`): a chain holds at most 16 entries (`MAX_CHAIN`): the current one and the fifteen it is mixing from. When a seventeenth joins, the oldest ends (`End`, `Dispose`), whatever weight it has left: at once when a call adds it, and at the end of the step when a queued entry that starts in the step does, so the oldest still fires the event keys it crossed in that step (`an_entry_the_cap_ends_in_a_step_still_fires_that_step_s_keys`). Why 16: a chain fills only while new entries join faster than mixes finish, and the worst ordinary case is a state machine that flickers, setting a new animation every step. Measured at 60 Hz (`the_entry_the_cap_ends_has_little_weight_left`), the entry the cap then ends weighs 0.7% under a 0.5 s mix and less under a shorter one (a mix shorter than 0.25 s is over before the chain fills), so nothing shows; under a 1 s mix it weighs about 11%. A cap of 8 would end an entry weighing 36% under a 0.5 s mix. The cap also bounds a step's work, and a chain whose mixes cannot finish. That last case is a skeleton whose clock is stopped: there the oldest entry has all the weight, and the pose jumps to the next oldest.
- **Mixing** (`a_crossfade_is_half_way_at_half_its_mix`, `a_crossfade_does_not_dip_toward_what_is_under_it`): the mix fraction `m` is the incoming entry's mix time over its mix duration, its mix time counting skeleton time (`dt × time_scale`, not its own speed). The incoming entry applies at `alpha × m`. Rule we chose, from first principles: each entry mixing out applies, per timeline, at the alpha that makes its weight in the result fall from its own to 0 linearly with `m`, whatever the incoming entry keys. When the incoming entry (Replace) keys all the timeline's properties at applied alpha `y`, the outgoing timeline applies at `alpha × (1 - m) / (1 - y)`, so after the incoming lerp it weighs exactly `alpha × (1 - m)`; at alpha 1 that is full strength and the crossfade is a plain lerp, with no dip toward the tracks below. When the incoming entry does not key it (or adds), it applies at `alpha × (1 - m)` and fades to what is under the track: the setup pose on track 0, the tracks below on a higher one. Down a chain the factors multiply: with mixes `b` then `c` over entries that all key a property, the three weigh `(1 - b)(1 - c)`, `b(1 - c)` and `c`. "Keys" means one timeline of the incoming animation keys every property the outgoing timeline keys (a combined translate is not covered by a translate x alone; that case dips a little). Before its first key that timeline applies nothing, so until then it replaces nothing of the outgoing timeline, which applies at `alpha × (1 - m)` and fades toward what is under the track; when the key comes, the pose takes the key's value at the incoming entry's weight, which is the animation's own step, weighted by the mix (`a_timeline_before_its_first_key_does_not_hold_the_outgoing_entry_up`). In a longer chain, the entries newer than the incoming one fade the outgoing timeline as they fade the incoming one's, before that key and after it, so the outgoing weight is the same on both sides of the key (`an_outgoing_weight_holds_when_a_middle_entry_reaches_its_first_key`: of three entries with both mixes half done, the oldest weighs 0.25 before the middle one's first key and after). In a chain of three or more, past a newer entry that does not key the property (or that adds), the older ones assume nothing newer keys it, so they fade a little faster there: a small dip. What is promised: an outgoing timeline's weight in the result is at most its applied alpha times the product of `(1 - m)` over the mixes of the entries newer than it, and is 0 when its mix ends, so ending the entry changes nothing in the pose. Where every newer entry keys the property and replaces, the weight is exactly that product, whether or not their timelines have reached their first keys, so it never rises while the mixes run. Past a newer entry that does not key the property it is lower (the dip), and how it moves under that bound is not promised: it can creep up a little while an entry above mixes in at partial alpha. `a_crossfade_does_not_dip_toward_what_is_under_it` works an example of each case, the two dips included.
- **The previous entry's time:** it keeps advancing while it mixes out, as Spine's default is; with the incoming entry's `hold_previous`, it holds its time (`a_mixing_out_entry_stops_firing_past_its_event_threshold`). The flag lives on the incoming entry, as its name says.
- **End of a mix:** once an entry has mixed in fully, every older entry ends (`End`, `Dispose`; `track_events_follow_start_interrupt_end_complete_dispose`).
- **Stepped keys** (attachments, draw order) belong to the newest entry of the chain whose applied alpha (`alpha × m`) is above 0, and no other entry applies them. So an entry mixing out keeps setting them until the entry replacing it has weight: at 0% of a mix (a queued entry that starts exactly on its delay, or a `set_animation` while the skeleton's clock is stopped) the outgoing entry's attachments and draw order still show, and from the first step with weight the incoming entry's do (`stepped_keys_stay_with_the_outgoing_entry_until_the_incoming_has_weight`). An entry whose own alpha is 0 never has weight, so a layer at alpha 0 forces nothing (`a_zero_alpha_layer_does_not_force_its_attachments`), and the entry it replaced keeps them while it lasts. When the outgoing animation keys a slot's attachment and the incoming one does not, then once the incoming entry has weight the slot shows what the tracks below set, else its setup attachment, for the rest of the mix and after (`attachments_belong_to_the_entry_mixing_in`). The empty animation is such an incoming entry: it keys nothing.
- **Rotation memory:** an entry keeps a turn per rotate timeline (see `apply_layer`) while it is in a mix or applies at less than full strength (`alpha × m < 1`). So a bone keeps turning one way through a mix (`a_crossfade_keeps_each_bone_turning_one_way`), and a layer at partial alpha does not jump by alpha × 360° on the step after its mix ends (`a_layer_at_partial_alpha_keeps_turning_one_way_after_its_mix`). An entry alone at full strength keeps none, since the way round makes no difference to where the bone ends up, so its next mix starts afresh, the short way. The memory is one of the entry's own buffers: no step allocates for it. Two limits of keeping it for as long as an entry applies at less than full strength. It winds: the remembered turn is the whole angle from the pose under the entry to its target, so under a layer whose target keeps going round it grows by 2π a revolution, and as an `f32` it steps coarser as it grows: after 2^14 revolutions (4.5 hours of one turn a second) it is near 103,000 radians, where an `f32` moves in steps of 0.45°, so the turn is up to 0.2° off and the layer's rotation moves in steps of 0.45° times its alpha. And a partial-alpha layer's resting angle depends on its history: it rests at the pose under it plus alpha times the remembered turn, and a turn that has wound k times round rests alpha × k × 360° from where a fresh entry showing the same key rests (the short way). Setting the animation again starts the memory afresh.
- **`set_empty(track, mix)`** plays the empty animation (`<empty>`, keying nothing) as the current entry with that mix: the old entry fades to the setup pose on track 0, or to the tracks below on a higher one. When the empty entry has mixed in and nothing is queued after it, the track clears (`set_empty_fades_a_layer_out_then_clears_it`). An entry queued after it mixes in from nothing: a layer fading in (`a_layer_fades_in_after_set_empty`). `current` does not report an empty entry.
- **`clear(track)`** ends what plays at once (`End`, `Dispose`, newest first) and disposes the queue (`set_animation_and_clear_drop_what_is_queued`). From the next step the track's properties are what is under it: nothing fades.
- **Queue** (`a_queued_entry_starts_after_its_delay`): an entry starts when the previous entry's track time reaches its `delay`. A `delay <= 0` is turned into the previous entry's end plus the delay (at least 0) when added, and the field holds the result. The end is the previous entry's duration, or for a looping entry the end of the loop it is in when the call is made (2.25 s into a 1 s loop, 3 s). On an empty track it starts after `delay` seconds of skeleton time, and with `delay <= 0` it is current at once, as if set. Its mix is the data's for the pair (the previous entry, it). A step past the start carries the rest into the new entry (track time and mix time), and several queued entries can start in one step (`several_queued_entries_can_start_in_one_step`).
- **Events** (`events_fire_once_across_loops_large_steps_and_time_scales`, `events_from_several_tracks_come_in_time_order`): each entry fires the keys its track time crossed this step (`events_crossed`, from before 0 on its first step), with the key's time in its animation. A stopped clock fires nothing, but for an entry's first step: that puts it at its time 0, so a key at 0 fires then, once, even with the clock stopped. The step's events are ordered by when in the step each was crossed, across tracks; ties keep track order.
- **Event threshold** (`a_mixing_out_entry_stops_firing_past_its_event_threshold`): an entry mixing out fires keys up to the track time at which the incoming mix reaches its `event_threshold` (`replaced_at + threshold × mix_duration × speed`), clipped exactly whatever the step size. At the default 0, nothing fires after it is replaced.
- **Reverse** (`reverse_plays_backward_and_fires_events_backward`): the animation's time is `duration - t` (wrapped when looping, held at the end otherwise), and events are mirrored the same way, so keys fire backward, each loop.
- **Track events** (`track_events_follow_start_interrupt_end_complete_dispose`), sent with the next step when a call causes them: `Start` when an entry becomes current; `Interrupt` when another entry replaces it as current (a call or a queued entry); `End` when it will never be applied again (cleared, replaced with no mix, or its mix-out over); `Dispose` right after `End`, or alone for an entry that never started (queued, or kept before the data landed and dropped); `Complete` each time a current looping entry passes a multiple of its duration (each one, even several in a step, at most 1,000 a step: `complete_tells_at_most_a_thousand_whatever_the_rounding`), and once for a non-looping or zero-length one. An entry mixing out completes no more (`an_entry_mixing_out_completes_no_more`).
- **The empty animation's entries** send `Start`, `Interrupt`, `End` and `Dispose`, and never `Complete` (`set_empty_fades_a_layer_out_then_clears_it`): a game that wants "the fade is over" listens for the `End`. Their events carry the name `<empty>`, which is the public `SkeletonAnimation::EMPTY`; validation keeps any animation in the data from taking it, so the name alone tells an empty entry apart. The constant is for reading events: a track is faded out with `set_empty`, and `set_animation(track, EMPTY, ..)` is an unknown name like any other. No handle to an empty entry is ever given out (`set_empty` returns none and `current` does not report it), so `TrackEntry` has no test for it.
- **Events from calls** wait for the next step in a list of at most 1,024 (`MAX_TOLD`). Past that the oldest are dropped, with one warning per skeleton (`track_events_from_calls_are_bounded_between_steps`): a skeleton that is not stepped while a game keeps calling it cannot grow without bound, and the newest events are the ones it hears when it steps again.
- **Unknown names and data that has not landed** (`an_unknown_name_warns_once_and_does_nothing`, `a_call_before_the_data_lands_is_kept`, `a_later_call_drops_the_calls_kept_for_its_track`): the state learns the data in its first step (the data's shared `AnimationCatalogue`: names, durations, mixes). Until then every call is kept, in order, and returns a handle whose entry can be changed meanwhile; `set_animation`, `set_empty` and `clear` drop the earlier kept calls for their track, but `set_animation` leaves a `set_empty` with nothing but queued entries after it (those it drops), as the empty animation stays on a track for the next entry to mix in from (`an_entry_replaced_before_it_shows_is_dropped`). The first step makes them. A name the data lacks warns once per skeleton per name and does nothing (`None` once the data is known). A kept entry whose mix is still 0 when it is made takes the data's mix, so a 0 set before the data lands counts as unset. At most 256 calls are kept (`MAX_KEPT`: room for a `set_empty`, a `set_animation` and two queued entries on every track); one more is ignored and returns `None`, with one warning per skeleton. A call that replaces kept calls on its own track (`set_animation`, `set_empty`) drops those first and so always fits; a call that is refused has dropped nothing (`kept_calls_are_capped_with_one_warning`). A kept entry that a later call drops, or whose name the data turns out to lack, is disposed: a `Dispose` alone, sent with the first step. So every handle's entry ends with a `Dispose`, unless the bounded list above dropped it.
- **Allocation** (`a_call_after_the_data_lands_takes_the_data_s_name_and_spare_buffers`, `spare_buffers_are_bounded`): a step allocates nothing in steady state, and once the data has landed a call allocates nothing either. The entry's name is the data's own `Arc<str>` (only a call kept before the data lands copies its name), and its per-timeline buffers (cover, fades, turns) are a set that a finished entry left with the state, which keeps at most 16 (`MAX_SPARE`). A steady stream of crossfades so allocates nothing after the first few; the chains, queues and event list keep their capacity.
- **New data** (`new_data_keeps_tracks_by_animation_name`): a step with another catalogue (a reload) finds each entry's animation by name and keeps its times. A track whose current animation is gone is cleared whole (the entry it was mixing from does not come back); a gone entry that is mixing out or queued is dropped and the track plays on; each gone name warns once per skeleton. Gone entries end newest first: a cleared track as `clear` ends it (its chain from the newest back, then its queue in order), and on a track that plays on, the gone entries mixing out from the newest back, then the gone queued ones from the last queued.
- **Known differences from Spine's documented behaviour** (its runtimes guide and API reference):
  - Spine documents that a crossfade on a higher track dips toward the tracks below, and offers `holdPrevious` (in the versions that have it) to keep the previous animation at full strength instead. Here the linear-weight rule above, written from first principles, has no dip where the incoming animation keys the property, and `hold_previous` instead holds the previous entry's time.
  - Spine turns `delay <= 0` into the previous duration (the next loop's end for a looping entry) minus the mix plus the delay, so the mix ends at the previous end; here the mix is not taken off, so the mix starts there.
  - Spine makes an entry queued on an empty track current at once, and its delay postpones its time; here it waits in the queue and becomes current (`Start`) when the delay has passed.
  - Spine's `complete` can fire for an entry that is mixing out; here an entry completes only while it is current.
  - Spine's `clearTrack` leaves the skeleton in its current pose; here every step starts from the setup pose, so a cleared track's properties go back to what is under it.
  - Spine applies attachment and draw-order keys of an entry mixing out below its mix thresholds (`mixAttachmentThreshold`, `mixDrawOrderThreshold`, default 0: not while mixing out); here an entry mixing out applies them only until the entry replacing it has weight.
  - Spine applies an entry's attachment timelines when its computed alpha (its alpha and its mix) is above `alphaAttachmentThreshold`, whose default of 0 its reference describes as always applied; here an entry with no weight applies no stepped keys, and the threshold is not offered.
  - Not offered: a track end time (`trackEnd`), queued empty animations (`addEmptyAnimation`), the attachment and draw-order thresholds above, and the rotation-direction calls (`shortestRotation`, `resetRotationDirections`): the rotation memory here is kept and reset as "Rotation memory" says.
