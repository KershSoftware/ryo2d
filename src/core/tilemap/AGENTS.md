# AGENTS.md - Tilemap Module

Tile maps from Tiled and LDtk (sub-project 6a, orthogonal maps; isometric, hexagonal and infinite maps are 6b, `docs/backlog/tilemap-features.md`). Design: `docs/specs/2026-10-29-tilemap-design.md`; using it from a game: the `ryo-tilemap` skill; what it costs: `docs/backlog/tilemap.md`. The module holds the data model, the Tiled (JSON and XML) and LDtk readers as registry loaders, maps spawned as entities (landing whole, worked out on a thread of their own), reading and editing them (`MapsView`, `ctx.maps()`) with Wang terrain, their collision and 2D shadows kept in step with their tiles, worlds of levels, hot reload, and the padded tilesets they draw from. Drawing is the render module's: tile layers from cached chunks (y-sorted ones row by row among the entities), image layers as one repeating quad per view, tile objects as sprites (`render/tiles.rs`; render module notes, Tile chunks, and Image layers and tile objects).

## Where it runs

- `PreUpdate`, chained after the asset pump (`register_engine_systems`): `spawn_maps` (world levels resolved; ready maps' landings sent to the `Worker`; landings that came back land whole, with `MapEvent::Spawned`; failures reported once) and `reload_maps` (spawned maps brought to saved files, `MapEvent::Reloaded`). So a map whose asset lands this frame starts landing this frame, and a save is followed in the frame it lands, before the scenes' update.
- `FixedSet::Movement`: `collision::sync_map_colliders`, before physics' `rebuild_tile_colliders`, so an edit made in `update` collides in that step. `PostUpdate`, before `PostUpdateSet::Transforms`: `occluders::sync_map_occluders`, so an edit casts its shadow that frame. Both from `register_tilemap_systems` (`mod.rs`).
- The render step: `render/tiles.rs`'s `TileDrawer` (engine-owned) pads each spawned map's tilesets (`PaddedCache`, a world resource the landings share), builds changed chunks into the batch's chunk store and gathers the visible ones.
- The map builder thread (`jobs.rs`, `ryo2d map builder`): each landing's colliders, shadows and missing paddings. Where there is no thread (the web) a landing is worked out in the frame it is sent.
- The world holds no map state of its own beyond the assets' stores, `Messages<MapEvent>`, `PaddedCache` and `WangWarned` (`wang.rs`): everything else is on the map's entities.

## What exists

- `tile.rs`: `Tile` (tileset index, id, `TileFlip`) and `TileFlip` (H, V, D bits as Tiled stores them; `rotated_cw` uses Tiled's table).
- `property.rs`: `PropertyValue` and `Properties` (insertion-ordered, typed getters; `int` accepts a whole float, `float` accepts an int).
- `tileset.rs`: `Tileset` (an `Asset`; atlas or collection; per-tile `TileData` with shapes, animation, probability; `WangSet`s) and `URect`, the engine's own texel rectangle (glam has none).
- `grid.rs`: `TileGrid`, a dense layer of 4-byte cells (0 empty; flips in bits 28..=31, tileset in 20..=27, id + 1 in 0..=19) cut into `CHUNK_SIZE` (32) chunks. Edits mark chunks dirty; `drain_dirty` hands each changed chunk out once in row order. A new grid has no dirty chunk. A tile that does not fit a cell (tileset over 255, id over 1,048,574) is refused by `set`. `assign` (crate) takes another grid's cells, moving on only the chunks whose cells differ (or that its caller names), as one change: what a reload uses, so only the chunks a save changed rebuild. `touch` (crate) moves on the chunks it is given, the cells as they are, for IntGrid edits.
- `map.rs`: `TileMap` (an `Asset`) of `MapLayer`s (`LayerInfo` plus a `LayerKind` of tiles, objects or an image) over `TilesetSource`s (asset handle or embedded `Arc`). `ImageLayer::image` is `None` for an image layer given no picture (Tiled saves a new one as `"image": ""`, or an `<imagelayer>` with no `<image>`), which loads and draws nothing (`an_image_layer_tiled_left_without_an_image_loads_empty`; it failed the whole map). `IntGrid::get` returns `None` for 0 as well as outside.
- `spawn.rs`: maps as entities. `MapRoot` (a `TileMap` handle, or an LDtk project and a level by identifier or iid; class tiles, IntGrid collision overrides, collision off, base z) on an entity whose `Transform` places the map's top-left corner. `spawn_maps` (`PreUpdate`, chained after the asset pump) lands each ready map whole (below), or sends `MapEvent::Failed` once per failure. `map_asset` resolves a root to its `TileMap`, `root_map` the same from the stores a system holds.
- **A map lands whole.** When a root's asset (and its tilesets) is ready, `spawn_maps` copies the asset's layers (each Tiled tile object given what its tile carries, `inherit_tile_data`: with no class of its own it takes its tile's, and its properties lie over its tile's, which hold the tile class's defaults; an object with a class of its own keeps the tile class's defaults under its own, where Tiled keeps only what the tile wrote; LDtk entities take nothing; done here because a map's external tilesets are not loaded while it loads, `a_tile_object_takes_its_tile_s_class_and_properties`, asserted against Tiled's own resolution), the root's settings, the class-tile table and the tilesets' `ShapeSource`s and stamps into a `LandingJob` for its `Worker`, and marks the root `MapLanding { job }`. The job takes the class tiles out of the grids' copies (marking every chunk dirty), and works out the colliders (`collision::prepare`: every grid classified, traced and packed, the packs' Rapier shapes built) and the shadows (`occluders::prepare`: every chunk's chains) for the layers as they will spawn, layers named by their place (entities are stand-ins until they spawn). When it comes back (polled every `spawn_maps`), `land` spawns the layers and the objects' entities, inserts `MapIds` and `MapLayers`, puts the colliders (with their `Traced`) and the shadows on (`collision::land`, `occluders::land`: entities relinked by place), then gives the objects their components (observers run), spawns the class tiles, and sends `MapEvent::Spawned`: all in one frame, and the fixed step that frame (or the next) builds the parts from the traces before physics steps, so a body an object observer or a `Spawned` reader puts on the map lands on its ground (`a_body_on_a_map_reported_ready_never_falls_through`). Until then nothing of the map is in the world but its root, and `MapsView` reads nothing. A root disabled, despawned or given another root while its landing is out drops the result (`root_discarded` takes `MapLanding` too). The arrival looks roots up with `Allow<Disabled>`, so a disabled one loses its `MapLanding` and is worked out again once enabled (`a_root_disabled_while_its_landing_is_out_lands_once_enabled`; looked up with the default filter, its result was dropped with `MapLanding` left on, and it never landed). A job that panicked is logged and worked out on the main thread. If that panics too, the root gets `MapFailed` holding `landing_stamp` (the versions of its map or LDtk project and of each tileset asset the map uses) and `MapEvent::Failed` is sent once; it is not tried again until one of those versions changes (`a_landing_that_always_panics_is_reported_once_and_not_retried`; before, it was sent again every couple of frames). A test's map makes its landing panic with the `PANICKING_LANDING` property (test builds only). A landing records the loads of the files it was worked out from (`reload::content_stamp`); one that comes back after a load of one of them landed (a save while it was out) is dropped and worked out again from the files as they are, so the map lands as saved, with one `Spawned` (`a_save_while_a_map_lands_lands_the_saved_map_once`; before, it landed the old map and never followed the save). It lands with a `MapApplied` (below). On the web (no threads) the job runs where it is sent, so the map lands in the frame its asset is ready. Layer flags set on layer entities (`collides`, `occludes`, properties) can only change after the landing, through the systems' rebuild path.
- `kinds.rs`: what a cell is, for collision or light, pure so a landing job runs it off the main thread: `ShapeSource` (a tileset's tiles with shapes, read once: each tile's drawn size and shapes, the tileset's offset; `sources` for a map's tilesets), `placed`, `classify` and `tile_kind` (by `Purpose`), `intgrid_table`, the ranked union `over`, `Tracked` (a group layer's last-read chunk versions and IntGrid kinds) with `changed_chunks`, `TilesetStamp`, and the `Layers` and `Stores` query aliases both systems use.
- `jobs.rs`: `Worker`, one thread for `spawn_maps`' landings (started with its first job, named `ryo2d map builder`) taking boxed jobs and handing back each one's id and result (`None` for a job that panicked); where no thread starts (the web) a job runs where it is sent.
- `collision.rs`: `sync_map_colliders` (`FixedSet::Movement`, before physics' `rebuild_tile_colliders`, so an edit made in `update` collides in that step; `register_tilemap_systems` in `mod.rs`) keeps each spawned map's colliding tile layers in a `TileColliders`, with the crate's `MapCollision` on the map entity. Colliding layers (`LayerInfo::collides` on a root with collision) group by cell size, offset and collision material: the group of the map's `tile_size`, no offset and the map's material unions into one `TileColliders` on the map entity, any other gets its own on its first layer's entity (whose `Transform` carries the offset), so two colliding layers meet without a seam unless they differ in one of the three. A cell takes the strongest kind across its group (`Solid` > `Shape` > `Slope` > `OneWay`); on a tie (two shapes, two slopes) the upper layer's wins. An IntGrid layer collides by its values (`intgrid_table`: an override by value, else by name, else the default names `solid`, `one_way`, `slope_*`, all ignoring ASCII case; an override to `TileCell::Shape` names no shape and collides as nothing, which `plan` warns once a map, `an_int_grid_shape_override_collides_as_nothing_and_warns_once`), any other by its tiles' shapes not marked `occluder`, placed where the tile draws (`placed`, the drawing's rules: a tile stands on its cell's bottom edge from the left, `tile_offset` moves it, flips turn it: diagonal, then horizontal, then vertical) and classified (`classify`): a full-cell rectangle `Solid` (`OneWay` if one-way), three cell corners `Slope` (the right angle opposite the corner left out), anything else a `Shape` added once per distinct geometry (`ShapeKey`, points on a 1/46,080 tile grid). A tile with solid and one-way shapes collides with its solid ones only (`CellShape` has one `one_way`). A colliding layer with parallax other than 1 collides where it would draw without it (parallax is a rendering effect, as in Tiled, and a collider moving with the camera is not a body physics can hold) and the dev log warns once a map per layer (`a_colliding_layer_with_parallax_collides_where_it_is_and_warns_once`). Each tile's kind is worked out once per group (`kinds`), from the map's `ShapeSource`s. Material: the properties `collision_layer`, `collision_mask` (a 32-bit int: -1 is every bit), `friction` and `restitution`, a layer's over its map's over `TileColliders`' defaults (an ice layer saying `friction` 0 is a grid of its own); a wrong type warns once a map per layer and property, and what is under it counts.
  - **The first build** comes with the map's landing (`prepare`, `land`; see `spawn.rs` above): every grid on its target with its `Traced`, so physics only spawns the parts and inserts their shapes as built. Physics packs a grid's outlines by chunk (a part for the loops starting in each 32-cell chunk; physics module notes, Packing), so a map's part count follows its area, not its islands. Whatever builds the grids again after that (enabled again, a layer's flags, the tilesets or the overrides changed) builds at once on the main thread. The landing frame of a 256 x 256 four-layer map adds about 0.03 ms for terrain and about 0.2 ms for 1,024 separate islands in 64 parts (`spawning_a_256_map_adds_under_half_a_millisecond_to_any_frame`, ignored, release, timed after a warm-up since a process's first second runs slow; a part per island took about 1 ms, nearly all of it Rapier taking in the colliders).
  - **What changed:** every step the group's layers' `TileGrid::version` is compared with the last seen (never `drain_dirty`, which one consumer would empty for the others); for a layer that moved, each chunk whose `chunk_version` moved is classified again across the group and `TileColliders::set` is called only for cells whose kind changed, so physics' loop-local rebuild stays local. An IntGrid layer whose names (seen when `TileLayerData` changes) now give other kinds re-reads all its chunks. A change of what the grids are built from (the colliding layers, their entities, cell sizes, offsets, materials and sizes, whether each has an IntGrid, the map's tile size, the overrides, a tileset's shapes) builds every group again (new `TileColliders`, which physics builds whole). A tileset whose content version or embedded `Arc` moved is read again (`kinds::shapes_kept`), and only shapes that differ (`ShapeSource`) count: a tileset image's reload touches its tileset and map, and a tileset saved with other tile data, neither of which rebuilds anything (`saving_a_tileset_or_its_image_redraws_every_map_using_it`; before, an image save replaced every part). An idle step costs a look at each map's layers, tilesets and properties (about 0.1 µs a map in release); an edit's step about 18 µs for one chunk of four 1024-wide layers (`one_tile_edit_sync_timing`, ignored).
  - **Disabled, despawned, root gone:** `Disabled` does not reach the layers, so a disabled map's sync takes away every `TileColliders` it put on (the map's and its layers'), and enabling builds them all from the tiles as they then are, on the main thread (the cost: `docs/backlog/tilemap.md`, Limits). A despawned map takes its colliders with it (the map-level parts are its children, a layer-level grid's are its layer's). A map whose root is put over or taken away (no `MapLayers`, or no `MapRoot`) loses its grids and `MapCollision`. A disabled layer entity does not collide. A map with collision owns the `TileColliders` on its entity: one a game put there is replaced.
  - A layer's visibility does not matter: a hidden layer (a common collision-only layer) collides, and occludes as its flags say.
  - **Too large:** a group over 8192 cells a side (the loaders take up to 2^26 cells a layer) gets no `TileColliders`, and the map warns once naming its layers. Physics capped by area (2^26 cells) before this sub-project, so a 10,000 x 64 level collided then and does not now (`docs/backlog/tilemap.md`, Limits, with the route).
  - IntGrid values are followed through their layer's grid versions. `MapsView::set_intgrid` and `fill_intgrid` (`edit::fill_intgrid`) write the values and move on only the chunks whose values changed (`TileGrid::touch`, crate: the versions of the chunks named, the cells as they are), so only those chunks collide, occlude and redraw again (`an_int_grid_edit_re_collides_only_its_chunk`); before them a game wrote `TileLayerData::intgrid` and called `grid.mark_all_dirty()`, which rebuilt the whole layer. A value written by hand is seen once its chunk's version moves. LDtk's auto-layer rules are not run: the art changes through `set_tile`.
- `occluders.rs`: `sync_map_occluders` (`PostUpdate`, before `PostUpdateSet::Transforms`) keeps each map's shadows, with the crate's `MapShadows` on the map entity. A layer occludes as `LayerInfo::occludes` says, else as it `collides` (the root's `without_collision` does not change it); occluding layers sharing a cell size and offset occlude as one, each cell the strongest kind across them (collision's `over`). A tile occludes with its shapes marked `occluder`, else its collision shapes (one-way ones too), as one solid shape placed as collision places it (`Purpose::Occlusion` in `kinds.rs`); an IntGrid's `Solid` cells whole and its slopes as their half cell (a one-way cell has no area to occlude with).
  - **Boundary chains, not rectangles:** an occluder whose edge touches another's casts that edge's shadow through the other's lit art (a black wedge at full strength, measured headless), so the occluders are the boundary of what occludes: `physics::Boundary` reads the tile colliders' outline units (each cell's inside, the borders left of and above it; shapes fitted to their cells on the outline grid; edges two cells share cancel, partial overlaps too), reversed to lighting's winding. Each chunk owns the units of its cells and, where it reaches them, the grid's right and bottom borders, so the chunks' edges together are the boundary with nothing twice, and nothing at a chunk border. A chunk's edges are chained greedily (`chains`: from the points more edges leave than reach, then round the loops left; straight runs merged; each point's edges a run of the edges sorted by start, found through one map made at its full size: a list a point, maps grown from empty and a chain made for every start tried were half a dense chunk's rebuild) into `LightOccluder2D::chain`s, each a child of the group's first layer marked `MapOccluder { chunk }` (prelude), its entity at the centre of its corners' box (lighting's reach test reads the entity's translation less the chain's extent, so a small light at a chunk-long chain's end still reaches it), so a chain spans one chunk at most. Shapes are clipped to their cells, as collision clips them.
  - **The first build** comes with the map's landing: `prepare` works out every chunk's chains off the main thread, and `land` spawns them all (`World::spawn_batch`) as the layers spawn. After that a rebuild (enabled again: a disabled map keeps its `MapShadows`, emptied; its layers, tilesets or overrides changed) is at once on the main thread.
  - **Edits:** the group's layers' chunk versions, as collision's (`changed_chunks`); a moved chunk's chains are despawned and built again, every other chunk's kept. A chunk's borders read the column left of it and the row above, so each chunk keeps the kinds of its right column and bottom row (`Sides`): when they change, the chunk right of it or below it is built again too, row by row in the same pass. A disabled map or layer, a layer that stops occluding, a map whose root went, or a change of the layers, tilesets' shapes (`shapes_kept`, as collision) or overrides takes every chain down (built again when it applies).
- `edit.rs`: `LayerRef` (name or index), finding a layer entity, cell reads and edits (tiles and IntGrid values), world/cell conversions. `view.rs`: `MapsView` (`ctx.maps()`), the public face of `edit.rs`.
- `wang.rs`: `MapsView::set_terrain` (Wang auto-tiling, Tiled's terrain brush with corrections on) and `WangSet::best_tile` / `color_index` / `ANY` (public, for procgen). Each `WangTile` carries its tile's probability, copied at load (`build_tileset` builds the sets after the tiles; both readers share it), and `Tileset`/`WangSet` carry the tileset's `transformations` (hflip, vflip, rotate, preferuntransformed). The rules follow Tiled's observed results, never its source (GPL): a paint asks one colour of the kind's positions; the cells sharing one pick again, row by row, painted cell included, each from the candidates (every tile at every flip the transformations allow, turns before mirrors, plus the empty cell, which wins over a tile with no colour) that have the asked colour and what the cells that picked before it show; among those the closest to what the cell shows now (colour distances: steps through tiles holding both colours, 0 the empty colour; a colour no chain reaches rules a candidate out), then an untransformed tile if the set prefers, then probability times its colours' probabilities, drawn by a hash of the cell (Tiled draws at random, so ties cannot match it). A cell that picks a different tile passes the change to the neighbours across an edge whose colours disagree, first-in first-out, within a Chebyshev square around the painted cell as many cells out as the set's longest colour chain plus one (two colours sharing a tile: two cells; deep water, water, sand, grass: four; `Matcher::longest_chain`); one nothing fits keeps its tile and, if it holds a tile of the set or is the painted cell, the set warns once per tileset version (`WangWarned`). Cells read through their flips (D, then H, then V); class tiles are not touched. The pick's candidates, colour distances and tile-to-wangid index are built once per `WangSet`, on its first pick (`WangCache`, a `OnceLock`; a clone or a reloaded tileset builds its own), so `best_tile` costs a scan of the candidates (about 16 µs at 255 tiles with every flip, down from 60). A set is read-only once built, so the cache cannot go stale: its fields are `pub(crate)` and read through accessors (`name`, `kind`, `colors`, `tiles`, `transformations`), sets are made by `WangSet::new` or the loaders, and no mutator exists (a `compile_fail` doctest pins that a game cannot write a field, and a passing one beside it, the same code reading through an accessor, that nothing else fails it). Add a `&mut self` method only with a caller, and have it drop the cache. Limits: Tiled draws at random among equal fits, so a tie cannot match it (fixtures are built to have one fit); a class tile keeps its colours out of corrections, so painting beside one leaves a seam; an empty cell touched by a chain is judged by its zero colours; erasing in a set with no bare-corner tile warns once per set version. The test fixtures `wang-*` were painted by Tiled: `tests/fixtures/tilemap/tiled/scripts/paint-wang.js` (every job built to have one fit, since Tiled draws at random among equals).
- `reload.rs`: hot reload. `reload_maps` (`PreUpdate`, chained after `spawn_maps`, with `Allow<Disabled>` so a disabled map follows its files and is current once enabled) looks only in frames where a `TileMap`, `Tileset` or `LdtkProject` was added or changed (three `MessageCursor`s; never a store's change list). A spawned map follows its files: its map file or LDtk project with what their loaders read (templates, the Tiled project, LDtk level files: each a `cx.read`, so saving one runs the loader again), and its tileset files. `content_stamp` is their loads (`AssetServer::load_job`, which moves when a file's new value lands: not when a reload starts or fails, a dependency's reload checks it again, or code changes it); a map whose stamp differs from its `MapApplied` (crate, on the map entity: the stamp, each layer's editor id, shape and offset, each object's data and layer, and each class tile by layer editor id and cell, as the files had them) is brought to its asset by `apply_reload`, then `MapEvent::Reloaded` goes. So a tileset image's save, which only touches its tileset and maps, redraws (the padding is stamped by image versions) and reloads nothing; a failed save changes nothing and sends nothing (`a_broken_save_keeps_the_last_good_map`); a file several of a map's files read (the Tiled project: its map and its tilesets) loads each again, the loads landing in any order and frames apart, so the map follows each as it lands, one `Reloaded` a load, ending as saved (`a_project_save_whose_loads_land_apart_ends_with_the_new_defaults`; a test waiting for the first `Reloaded` after such a save saw the tileset's load alone now and then, and waits for every file's load: `until_reloaded_from_every_file`); a map whose asset keeps its last good value after a failed check (a tileset saved that the map no longer fits) waits for the next good load; an asset made in code (no `load_job`) never reloads, though its map follows its tilesets' files. An LDtk project saved without the map's level leaves the map as it is, warned once per load. A tileset file saved naming a larger image, and reloaded before that image, fails its check against the old image (too small) and keeps its last good value; the image's reload then only checks that old value again and never retries the failed load (a registry limit: asset module notes, Reloads), so the tileset stays old until it is saved again. Writing both at once (a `git pull`, a script) can hit it; a fix is the registry's.
  - **Layers** match by editor id (`LayerInfo::id`: Tiled's layer id, LDtk's layer definition uid, one instance a level). A layer the file still has, of the same kind and, for a tile layer, the same size, cell size and offset, keeps its entity: its `MapLayerRef` (index, name), `LayerInfo` and `ImageLayer` are put over only where they differ, an object or image layer whose offset changed moves (its `Transform`'s translation set to the new offset, so a Tiled group moved moves its layers, their objects keeping their entities and places in them: `kept_object_and_image_layers_move_with_a_saved_offset`), and its `TileLayerData` takes the file's cells through `TileGrid::assign`, the IntGrid's changed chunks named too (`values_differ`: collision reads IntGrid values through grid versions). So only the chunks a save changed draw, collide and occlude again, each the way an edit does: a chunk collider changes shape in place, keeping its entity and handle, so a character standing on ground the save did not change keeps its contacts and floor (`a_reload_keeps_the_ground_a_character_stands_on`, with chunk versions and shadows of the untouched chunks pinned). Any other layer (a new id, another kind, or a tile layer of another size, cell size or offset) spawns afresh (`spawn::spawn_layer`, shared with the landing), and a layer gone, or replaced, despawns after its objects moved out. There is no landing job for a reload: it runs on the main thread (a dev-time action; cost below).
  - **Objects** reconcile by id (`reconcile`, pure: `keep`, `update`, `spawn`, `despawn`), given their tiles' data first as at landing, so a tileset save that changes a tile's class or properties updates the tile objects taking them, in place (`a_tileset_save_reaches_the_tile_objects_that_take_its_tile_s_data`). Whether the file changed an object is judged against `MapApplied` (its data and layer then), never the entity's components, which the game may have moved. One unchanged keeps its entity untouched (its `Transform`, parent and components as the game has them); one changed takes a new `Transform` and `MapObject` (put over, so `Insert` observers run and `Add` ones do not, and the game's components stay), moving to its new layer's entity if its layer changed; an object the file added or changed with no live entity spawns as at landing (entities first, then `MapIds`, then the components, so observers resolve references); a removed id despawns. Ids are unique in files Tiled and LDtk write; a repeated id counts once on a reload (`MapApplied` notes the first, a landing's `MapIds` names the last spawned, so the first duplicate stays untracked). Class tiles reconcile by layer and cell (`reconcile_class_tiles`), judged against `MapApplied` too (never the live `MapTile`, which the game may change): one the file left as it was keeps its entity untouched (its `MapTile::layer` told a new index), one changed takes a new `MapTile` and `Transform`, and any other live one (a cell the file emptied, or one an edit placed) despawns. On a tile layer spawned afresh, the class tiles that lived on its old entity spawn again on the new one.
  - **What the game took away stays away** unless the save adds or changes it: an object or class tile the game despawned (a coin collected, an enemy killed), or a class tile a runtime `set_tile` replaced or cleared (its cell then takes the file's grid, which holds no tile there), is not spawned again while the file leaves it as it was (`new_and_removed_objects_spawn_and_despawn`, `class_tiles_reconcile_by_layer_and_cell`, `a_tile_layer_spawned_afresh_keeps_away_the_class_tiles_the_game_took`); a save that changes it spawns it. The file does win over the game's tile edits: a dug tile comes back.
  - **Limit, a tileset save that changes shapes:** collision builds every group again (new `TileColliders`), so the floor part under a character is replaced (a new entity and handle, `CharacterState::floor` names the new one, and `CollisionStopped` is sent), though nothing falls through and `on_floor` holds. Image saves and tileset saves that keep the shapes rebuild nothing. Follow-up: reclassify every chunk through `TileColliders::set` instead, as a map save does.
  - **Cost** (`reload_timing`, ignored, release, a 1024 x 1024 map of four layers, on the main thread): `apply_reload` costs about 1 ms per 4 M cells whatever the save changed, since it copies every grid out of the asset and compares it (1.0 ms with one tile changed, 1.4 ms with every chunk); only what follows is in proportion to the change: 40 to 80 µs for the next step's collision and `PostUpdate`'s shadows with one tile, about 80 ms with every chunk of every layer (as a first build on the main thread). Left out of the measure: the registry's main-thread `check` and insert of the new value as it lands, `take_class_tiles`' scan of every cell of each kept tile layer when the root registers classes (the timed map registers none), and the renderer's rebuild of the visible changed chunks. A dev-time hitch.
- `padded.rs`: each tileset's tiles copied into power-of-two cells of a padded `Image` of its own (edges extruded, so no filter or mip level reads a neighbour). A cell's side is `next_power_of_two(max(2 * T, T + 8))`, T the largest tile's longer side: mip level k samples only a tile's own cell while `2^k` is at most the cell's room past the tile, which is then at least T (every level a tile drawn a pixel wide or more uses) and at least 8 (every level of an atlas page). Power-of-two tiles from 8 px keep cells twice their side; tiles just under one (14, 15, 30 px) take the next power up, and tiles of 30 or 14 px read their neighbours zoomed out with the old `T + 2` rule (`no_seams_at_any_zoom_or_subpixel_camera`'s odd-size legs). The cells sit `margin` texels in from every side (`cell - 8`): with the 8 texel border a texture puts around an image (`atlas::BORDER`), every cell starts on a multiple of its side and the texture's sides are whole cells. A padded image over 256 px gets a texture of its own with every mip level, and the GPU sizes each level by rounding down and spreads it over the whole texture: without the margins its levels from the fifth (16 texels a texel) mixed neighbouring cells into a tile, and those of a texture whose side was not a multiple of the level's texel drifted off the full-size one (`no_seams_at_any_zoom_or_subpixel_camera`, zoom 0.1). Known limit: in a texture of its own, a tile drawn under a pixel wide reaches levels past the cell's room, and from one texel a cell the levels mix cells. `PaddedLayout` says where each tile and animation frame sits; `PaddedTilesets` makes one per tileset, again when the tileset or an image of it changes (in place, keeping the handle), and frees those no round of `get`s (one a frame) has asked for in `KEEP_ROUNDS` (120, as long as the batch keeps an undrawn chunk): a level despawned and another of the same tileset spawned soon after (restarted, or the next level) draws with the same padding, where padding again would cost its landing job the padding and its landing frame a new texture's first write (about 0.4 to 0.6 ms for the 256 x 256 map's tileset in `benches/tilemap.rs`; `a_padding_unasked_for_a_while_is_kept_and_then_freed`). The cost is memory: a padded image (up to 8,176 texels a side, 267 MB of RGBA, with its texture) outlives its last map by those 120 frames, so a level change between two big tilesets holds both for two seconds, about twice the peak. The cache is the world's (`PaddedCache`, a lock `init_world_resources` inserts and the drawer holds each frame, where taking a resource out and putting it back each frame would move an entity twice; inserted before the first scene enters, so a map spawned in its `on_enter` is padded off the frame too, `a_map_spawned_entering_the_first_scene_lands_with_its_tilesets_padded`): a map's landing job pads the tilesets it has no padding of yet and makes their textures' levels (`Image::prepare_upload`) on its thread (`to_pad`, `ToPad::pad`), and its landing hands them over (`adopt`), so its frame only writes them (`a_landing_pads_its_tilesets_off_the_frame_and_hands_them_over`); a tileset padded before and changed since is padded again by the drawer, at once and in place, as below. An inline tileset is known by its `Arc`'s address, so what is kept of one (its padding, a refusal) holds the allocation (a `Weak`) and no tileset made later can take the address and get its padding (`a_gone_embedded_tileset_s_address_is_held_while_its_padding_is_kept`). A tileset whose padded image would pass the device's largest texture side less the atlas's border on both sides draws nothing, and the dev log warns once per version of it, naming it (`a_tileset_too_big_to_pad_draws_nothing_and_warns_once`), or names its largest tile when even one cell would not fit; it is not padded again until it changes, and nothing of the oversized image is made. The limit is the cache's (`PaddedTilesets::set_texture_limit`, which `init_gpu` calls with the device's `max_texture_dimension_2d`; landing jobs carry it in `ToPad`): 8,176 texels under the `Limits::default()` the engine asks for, which the engine does not raise. A larger padded image was refused by the atlas (`atlas.rs`, `width + 2 * BORDER` past the limit) with no warning and drew nothing (`a_padded_image_past_the_device_s_texture_side_is_too_big`). Under it: about 3,800 tiles of 64 px (62 by 62 cells of 128 texels), 15,876 of 32 px, 64,516 of 16 px, and a collection whose largest image is 129 to 256 px holds 196 images, 257 to 512 px 36. Per-size-class cells, or several padded pages per tileset, would lift it. The module is public but doc-hidden, for `tests/tilemap_alloc.rs` (a cache hit allocates nothing) and `benches/tilemap.rs`. A padded image prepared ahead is a first upload, written at once; one padded again in place is made in code, written at once too (below). An animated tile's frames take consecutive cells after the static ones; unequal frame times repeat frames to a common beat (past 128 cells, the mean time). `render/tiles.rs` turns a chunk into instances in layer-local pixels (lane layout in its module docs), and its `TileDrawer` draws spawned maps' layers (an image layer as one quad per view, its image repeating across it; render module notes) and their tile layers: a map's tilesets padded each frame it exists (a disabled map's too, so its images stay; a disabled map draws nothing, `Disabled` not reaching its layers), hidden layers skipped, each visible chunk built once into the batch's chunk store and drawn at the layer's interpolated transform. A layer entity's own `RenderLayers` replace the map's for what it draws. Each padding gets a `serial` never given before, which the chunks' look stamp includes, so a tileset padded again rebuilds the chunks drawn from it. `TileGrid::chunk_version` and `version` stamp every change from one process-wide counter, so a version never repeats, across grids and clones too: a layer whose `TileLayerData::grid` is swapped for another, even one filled the same way, redraws. A fill or `mark_all_dirty` is one change, one version; consumers keep their last-seen versions. A padding made again in place is made in code, so its upload has nothing made ahead and the renderer writes it at once, never over frames (graphics module notes, Reloads): a re-padded tileset's texture and its chunks' new places change in the same frame (`a_tileset_padded_again_never_draws_its_old_image_with_new_places`, a 752 px padding whose places all move). A padding made again in place must never have its upload prepared ahead (`Image::prepare_upload`, as a landing's first padding has): a large new version would be written over frames while the old texture draws, and the chunks would need to keep the old layout until the new texture shows: with `prepare_upload` added that test fails at the fifth frame, a tile showing its neighbour.

## Speed

`benches/tilemap.rs` holds the spec's targets as guards (`static_frame`, `edit`, `load` with its landing), `tests/tilemap_alloc.rs` the allocation tests (a padded cache hit, and a frame drawing a static map under a shadowed light: no allocation of the engine's own beyond an empty frame's under the same light), and `docs/backlog/tilemap.md` the numbers measured and the limits. The `edit` guard times the systems an edit runs through on an engine's world, each in a schedule of its own (`edit_schedules`, doc-hidden): the collision sync, physics' tile collider rebuild with its collider sync, and the occluder sync.

## Gotchas

- `tiled/`: Tiled's formats as registry assets. `raw.rs` holds what a file says (serde structs named as Tiled's JSON names them; `xml.rs` fills the same ones from TMX, TSX and TX, so every non-zero default is an `Option` and `build.rs` owns the defaults), `data.rs` decodes gids and layer data (CSV, base64, gzip, zlib, zstd via `ruzstd`, all bounded by the layer's cell count: a small file of each compression inflating to 8 MiB fails, as does data cut short or corrupted, except that Tiled writes zstd frames without a checksum, so bytes changed inside one can decode to other tiles, never to more cells), `build.rs` turns raw into `TileMap` and `Tileset` and holds the checks, `json.rs` the `TiledMapLoader` (`.tmj`, `.tmx`) and `TiledTilesetLoader` (`.tsj`, `.tsx`), picking the reader by extension, `objects.rs` the objects of object layers and templates, `wang.rs` Wang sets, `project.rs` the Tiled project file and the property resolution (`Props::read`, `resolve_properties`).
- A path written in a file joins that file's folder; the registry normalises it and refuses one leaving the asset root. An inline tileset's paths resolve against the map's folder.
- **A dependency that fails is named where the file names it.** `load_dep` notes each dependency's normalised path and place (`DependencyPlaces`, crate-private on `TileMap`, `Tileset` and `LdtkProject`, its `Debug` only a count so the XML/JSON twins compare), and each loader's `dependency_failed` turns the server's `AssetError::Dependency` into `place: "path" did not load: why`, as `load_dep` does for one that fails under `load_now`: an inline or LDtk tileset's image names its tileset, an image layer's its layer, an external tileset's file its `tileset N` and that file's error its image (`a_tileset_image_that_does_not_load_fails_the_map_naming_it_and_the_tileset`, both ways, and the LDtk twin). A `.world`'s maps keep the server's error, which names the map.
- External tilesets are dependencies and are not loaded while the map loads, so a gid is matched to a tileset by `firstgid` alone. The ids each tile layer uses are noted in `TileMap::used_ids` and measured against the tilesets in the map's `check`; the atlas image against the declared tiles in the tileset's `check`.
- Group layers flatten: offset adds, opacity and tint multiply, parallax multiplies, visibility ands, a non-normal blend passes down. Layer ids stay as written; a layer without one gets the next free id.
- Limits, each a load error naming the place: 1<<26 cells a layer or map, 256 tilesets a map, 1,048,575 tiles a tileset. A map's tile layers hold at most 1<<27 cells together (`MAX_MAP_CELLS`, 512 MiB of cells: an 8192 x 8192 map of two layers, a 1024 x 1024 one of 128), counted from the layers' sizes before any is decoded or allocated (`tile_cells`, groups included), so a small file of many big layers (a 1 MB `.tmj` of 40 zstd layers once asked for 10 GiB) fails with `map: its layers hold N cells, past the M a map holds` (`a_map_whose_layers_hold_too_many_cells_together_is_refused_before_decoding_them`). An LDtk level counts its layers the same way (`level_cells`: every non-entity layer from `__cWid` and `__cHei`, empty ones too, an IntGrid layer twice for its tiles and its values), and the project's levels share the same cap, since a project holds all its levels at once (`a_level_whose_layers_hold_too_many_cells_together_is_refused_before_allocating`). Unsupported until 6b: isometric, staggered, hexagonal and oblique maps and infinite maps; layer blend modes other than normal, add, multiply and screen.
- A tileset's `tileoffset` is kept as `Tileset::tile_offset`.
- The map's `parallaxoriginx` and `parallaxoriginy` (TMX attributes, TMJ fields) are `TileMap::parallax_origin`, which the drawer measures parallax from (`render/tiles.rs`, `parallax`: a layer's offset is `(1 - factor) * (camera centre - origin)` in map space, so a camera centred on the origin shows every layer unmoved, as Tiled draws it; `a_parallax_layer_is_where_it_would_be_with_the_camera_on_the_map_s_parallax_origin`). LDtk has none: zero.
- Objects: `MapObjectData::position` is always the top-left corner of the object's rectangle in map pixels and `rotation` (radians, clockwise on screen) turns it about that corner. Tiled rotates about the object's own position, which for a tile object is the tileset's `objectalignment` point (bottom-left by default), so a tile object's position is moved to where its top-left corner ends up. A map cannot look inside an external tileset while it loads, so a map with tile objects `cx.read`s the `.tsj` or `.tsx` for its `objectalignment` (`objects.rs::read_alignment`). Ids are Tiled's, as strings; object-reference properties are `PropertyValue::Object(id)`. Fields of `RawObject` an instance of a template can override are `Option`s: the instance starts as the template's object, its own fields win and properties merge by name. A template tile's gid is relative to the template's tileset, matched to the map's by resolved path (a tileset the map lacks is a load error). Templates load from `.tj` and `.tx`. The XML reader (`roxmltree`) leaves an absent attribute `None` and never defaults it, writes class members and numbers as the JSON would hold them, and bounds group nesting by `build.rs`'s `MAX_DEPTH`; its errors read `line L, column C: what`. An XML fixture's properties must be in Tiled's JSON order (alphabetical) for the twin test, which compares every `xml/` fixture with its JSON export field by field.
- The Tiled project (`project.rs`): `[tilemap] tiled_project` in Ryo.toml, `EngineBuilder::tiled_project` over it, else `project.tiled-project` at the asset root if there is one (a configured file that is missing is a load error). The loaders are registered with the path (`with_project`) after `insert_registry`'s default ones. It is read with `cx.read`, so saving it loads the maps again. `Props::read(place, raw, class)` resolves a thing's properties: written values lie over the class member's default, members it omits take the default, nested classes layer (instance over the member's default over the nested class's own), enums read by name (flags as a `List`). Tiled 1.12's list properties (`"type": "list"` with an array of `{type, propertytype, value}` items in JSON, `<item>` elements in XML, which the XML reader turns into the JSON's items) read as a `PropertyValue::List` of their items, each converted by its own type (a class item resolved against its class, an enum by name, a list item recursively, an unset color left out), and so does a class member's list default, whose items name their custom type `propertyType` as the project file names a member's (Tiled reads them so; with `propertytype` it drops the type); a written list replaces the default whole. Without the project or the class, what is written is kept (a list member of an unknown class keeps its typed items) and `engine_warn!` names the class once per file. Classes holding several members of classes multiply, so a few classes can ask for billions of values: one thing's properties may take 65,536 values to resolve, and a file's things 4,194,304 together (`Budget`), past which the load fails naming the place (`classes_fanning_out_past_the_cap_fail_naming_the_cap`); nesting, lists included, stops at 16 deep.
- Wang sets load as written (`wangid` is clockwise from the top, 0 for no color); colors and tile ids are checked.
- `LayerInfo::occludes: None` means "as `collides`"; `lit` defaults to true.
- Spawned maps: the map entity gets a child per layer (`MapLayerRef`, the layer's `LayerInfo` as a component, a `Transform` at the layer's offset; `TileLayerData` for a tile layer, `ImageLayer` for an image layer), plus `MapIds` (objects by id) and the crate's `MapLayers` (layer entities by index). `TileLayerData` is the entity's own copy of the grid and IntGrid, with every chunk marked dirty at spawn (a new `TileGrid` has none) so the chunk renderer builds each once. Objects are children of their object layer: `MapObject` with a `Transform` at the centre of the object's rectangle (its point; a polygon's or polyline's origin, Tiled giving those no size), turned by its rotation, polygon points relative to it; a tile object keeps its `tile`, and a hidden object spawns with `visible: false` (games use hidden markers; drawing skips it). Tiles of a class the root registers are taken out of the copied grid and spawn as `MapTile` children of their layer at the cell's centre in the layer's cell size, listed by cell in the layer's `LayerTiles` (crate). The objects' entities are spawned and `MapIds` inserted before the `MapObject`s go on, so an `Add<MapObject>` observer can resolve references.
- Games name the lifecycle events (`Add`, `Insert`, `Remove`, public in `ecs/kernel.rs`), so the skill teaches three routes to an object's behaviour: an observer of `Add<MapObject>`, which runs as each object arrives (`a_game_s_observers_see_each_object_arrive_whole_and_go`: once per object, its fields filled and its references resolved, and `Remove` once per object as the map goes); `MapEvent::Spawned`; and a system over `Added<MapObject>`. The observer and the system also see the objects a reload spawns; one it updates in place fires `Insert` only. At observer time the map's layers, `MapIds`, colliders and shadows are in, and so is every object's entity, though objects later in the file lack their `MapObject` yet and class tiles come after; a body the observer puts down stands on the ground (`a_body_on_a_map_reported_ready_never_falls_through` spawns one from an `Add<MapObject>` observer), while physics queries see nothing of the map until the next step.
- Game observers run as each part arrives and may despawn the map, a layer or an object before its turn: the spawn checks each is alive (`get_entity_mut`, never `entity_mut`), skips what is gone, and stops (no `Spawned`) once the map is gone. Every child is spawned as `(Transform, ChildOf(parent))` first and its observed components inserted after (`child_of`): bevy runs `Add` observers before `ChildOf`'s insert hook, so an observer that despawned the parent of a child spawned whole would orphan it and fail the hook's queued `Children` update on the gone parent.
- Runtime edits place class tiles too: `set_tile`/`fill` with a tile whose class the root registers spawn a `MapTile` (the grid cell cleared) instead of writing the grid; a class tile on a cell any edit touches is despawned first (the same tile again changes nothing). A plain `fill` takes the class tiles in its region through `LayerTiles` and fills the grid in one go; a class-tile `fill` goes cell by cell. `tile()` reads the grid, so a cell holding a class tile reads `None`. `MapObject::reference` reads `PropertyValue::Object(id)`, treats Tiled's unset `"0"` (and an empty id) as none, and checks the entity is alive (no bookkeeping system: a despawned object just stops resolving).
- A map waits while its asset (or, for a map built in code, a tileset asset it names) loads; one despawned meanwhile (a scene's `SceneCleanup::WORLD`) or no longer a `MapRoot` is not in the query and spawns nothing; a disabled one waits until enabled. A failure is reported once per `Arc<AssetError>` (the registry shares one per failure), and a missing LDtk level once per project version; a failed map whose file is saved fixed spawns. `MapRoot`'s `on_discard` hook takes down a spawned map's layers (and `MapIds`, `MapLayers`, `MapApplied`, the reported failure) when the root is replaced or removed, so a new root spawns afresh.
- `MapsView` finds layers through `MapLayers` (by index, or the first by name), returns `None`/`false`/0 for a map not spawned, a missing layer, a non-tile layer or a cell outside, and marks `TileLayerData` changed only when an edit changed a cell. World/cell conversions take a layer (cell size is per layer) and walk the `Transform`s of the layer and its ancestors as they are now, not `GlobalTransform`, so a map moved this frame converts before propagation; `world_to_cell` gives cells outside the layer too, and `None` for a layer scaled to nothing.
- `ldtk/`: LDtk 1.5.x projects (`.ldtk`) as `LdtkProject` assets, one `LdtkLevel` per level with its `TileMap`. `raw.rs` holds what a file says (LDtk's JSON names), `build.rs` the conversion and the checks (reusing `tiled::build`'s `fail`, `join`, `load_dep`, `check_tileset`, `check_used_ids`), `mod.rs` the types and `LdtkLoader`. A newer `jsonVersion` than 1.5 is a load error naming both versions; older loads. Tilesets are shared: `LdtkProject::tilesets` in definition order, each level's map embeds them all (a tile's `tileset` is the definition's index). A tileset with no `relPath` (LDtk's built-in icons) is a `Collection` with nothing to draw. Its per-tile data reads as Tiled's tile classes and properties (`tile_data`): a tile's enum tags (`enumTags`, in the tag enum's order) give it its class, the first of them, and a bool property `true` a tag; its `customData` is the string property `custom_data`; a tag or data on a tile past the tileset's count fails naming the tileset (`tile_enum_tags_and_custom_data_read_as_class_and_properties`). `.ldtkl` levels are read with `cx.read` (saving one loads the project again); paths join the project's folder.
- LDtk levels: `layerInstances` list the top layer first, so layers are reversed (layer 0 draws first). `LayerKind::Tiles::cell_size` is a layer's cell in pixels: the map's `tile_size` for Tiled and for `add_tile_layer`, the layer's own `__gridSize` for LDtk, whose grid, int grid and cell counts follow it (`__cWid` and `__cHei` must match the level's pixels over the grid). The map's `tile_size` and `size` come from the bottom tile layer; a level with only entity layers uses `defaultGridSize`. Tiles whose cell is outside the level (auto-tiles of stamps reach past the edge) are dropped. **Stacked, offset and translucent tiles split a layer** (`plan_tiles`): LDtk saves a layer's tiles in display order (the first beneath the next), several in a cell where rules or stamps stack them, at a pixel offset into their cell where a rule moves them, and with an alpha `a` where a rule fades them (1.4 on). Each distinct (stack depth in the cell, offset in the cell, alpha) is a layer of its own (`SubKey`): the layer's own (depth 0, on the grid, opaque; always there, holding the IntGrid and `collides`), then its sub-layers by depth and, within a depth, as LDtk first lists them, each an ordinary tile layer named after the layer with `#1`, `#2`... at consecutive places in `MapLayers` (so consecutive z), its `LayerInfo::offset` the layer's plus its tiles' offset and its `opacity` the layer's times their alpha, `collides` false and `occludes` as collides, no IntGrid. Its `LayerInfo::id` is a hash of the layer's uid and its key with the top bit set (`sub_layer_id`, probed past a clash within the level), so a reload matches it to the sub-layer of the same tiles wherever a save moves it (`a_sub_layer_keeps_its_id_when_a_save_adds_another_before_it`). Past 16 a layer (`MAX_SUBLAYERS`: each is a level-sized grid and a draw a chunk, so 16 bounds a layer at 16 times a plain one's cells, a 1024 x 1024 layer's at 64 MiB) the keys holding the most tiles are kept and every other tile goes to the kept sub-layer whose cell is free and whose offset, then depth, then alpha are nearest, warned once per layer with the count. The sub-layers' cells count toward the level's cap. Measured on LDtk 1.5.3's bundled samples (read by hand, not committed: their art is third-party): every tile of every level now draws (WorldMap_Free_layout, with its `.aseprite` tileset swapped for a blank PNG, kept all 11,684 where 5,069 were lost; Typical_TopDown_example all 2,798, its 240 translucent and 150 offset tiles at their alpha and place), with up to 43 sub-layers a project, and the cap snaps at most 28 tiles of a layer (AutoLayers_6_OptionalRules' rule-heavy IntGrid layer, 44 keys) to a nearest sub-layer (`stacked_offset_and_translucent_tiles_load_as_sub_layers`, and the GPU test `an_ldtk_level_s_stacked_offset_and_translucent_tiles_draw_as_ldtk_shows_them` over `stacked.ldtk`). IntGrid layers hold their auto-tiles as `grid` and `collides` is true, every other layer's is false. Parallax is `1 - parallaxFactor`. Entity `position` is the top-left (`px` less pivot times size), rotation 0, `class` and `name` the entity identifier, `id` the iid. Field values by `__type`: Point is a `Class` "Point" with `cx` and `cy`, Tile a `Class` "Tile" with `tileset` (identifier), `x`, `y`, `w`, `h`, EntityRef `Object(iid)`, enums `Enum { ty, value }`, arrays `List`; an unset field (null value, or an unset reference) is left out, and null items of an array are skipped. Worlds: a single-world project has one `WorldLayout` named "World" and levels whose `world` is `None`; with multi-worlds each world has its name. A `Neighbour::level` indexes the same world's `WorldLayout::levels`. Linear layouts (`LinearHorizontal`, `LinearVertical`) write no positions, so levels follow one another from the origin, each after the last one's width (or height) plus LDtk's own spacing of 48 px (`World.reorganizeWorld` in LDtk's source; the JSON docs only say "one after the other"). Parallax `1 - factor` is what LDtk's editor shows (it shifts a layer by camera times factor); `parallaxScaling` has no counterpart and is ignored. Level backgrounds images are not loaded; `TileMap::background` is `__bgColor`, else the level's `bgColor`, else the project's `defaultLevelBgColor`.
- **Worlds** (`world.rs`, `tiled/world_file.rs`). `TileWorld` is a Tiled `.world` file: `layout: WorldLayout` plus a `Handle<TileMap>` per level (dependencies, so the world is ready when its maps are; a map that fails fails the world, naming it). An LDtk world is a `WorldLayout` of the project, named by `WorldRef::Ldtk { project, world }`. Tiled neighbours are computed from the rectangles (`direction`): touching along an edge is a cardinal, at a corner a diagonal, overlapping `Overlap`; levels are named by their `fileName` as written. A listed map without `width`/`height` has its size read from its file's header through `cx.read` (so a save of that map reloads the world too). Patterns: the registry cannot list a folder (the web has none), so a pattern is supported only as literal text (escaped punctuation allowed, optional `^`/`$`) with up to two `(\d+)`/`(-?\d+)` numbers; anything else is a load error naming the pattern and "not supported" (a bare `.` is a literal dot, as names are built, never matched; `.*` fails on the `*`; only an unescaped trailing `$` anchors). Placement uses checked i32 arithmetic: a multiplier or offset that overflows fails the load naming the `.world` and the pattern. A probe reads each map (size is width x tilewidth by height x tileheight), and the map then loads again as a dependency. Names are built by filling the numbers (one is x, two are x then y) and probed with `cx.read`: row by row from y = 0, x from 0 to the first missing file, stopping at the first row whose x = 0 file is missing, at most 1,024 probes. Maps sit at `(x * multiplierX + offsetX, y * multiplierY + offsetY)`. Numbers are written plainly (`to_string`), so zero-padded names (`room_01_02.tmx`) are never built (a literal `0` before a group reaches 00 to 09 only), and numbering from 1 finds nothing, as do negative indices and the maps past a gap (`a_pattern_finds_numbers_from_zero_written_plainly`); a pattern that finds no file fails the load; a world that needs more lists its maps. No regex crate on purpose.
- `MapRoot::world_level` / `ldtk_world_level` make a root with `MapSource::WorldLevel`, which stands for no map until its world loads: `resolve_world_levels` (first thing in `spawn_maps`) swaps the source for `MapSource::Map` or `MapSource::Ldtk`, so every other map system sees only those two (`root_map` reads `None` for an unresolved one). A level the world lacks, or a world that failed, fails the root once per world version. `MapsView::spawn_levels_in(world, area)` spawns a root, a `WorldLevelOf { world, level }` and a `Transform` at the level's position for each level at world depth 0 overlapping the area (`WorldLayout::levels_in(area, depth)`: touching an edge is not overlapping) that has no `WorldLevelOf` for the same world on any entity, disabled ones included (`Allow<Disabled>`: a game parks a level by disabling its root; looked up with the default filter, a parked level spawned again on top of itself), and returns only those entities; a despawned level spawns again. `spawn_levels_in_with(world, area, depth, configure)` streams the given depth and passes each bare root, with its `WorldLevel`, through the game's `configure` before it spawns; the source is put back afterwards, so only the root's settings are the game's and the map stays the level's. `WorldLevel::depth` (and `LdtkLevel::depth`) is LDtk's `worldDepth`, 0 for a Tiled world: streaming one depth keeps a floor above or below from stacking onto the one played (`an_ldtk_world_streams_one_depth_at_a_time`, over `worlds.ldtk`, whose `Upper` lies on depth 1 over `C`). Nothing spawns until the world's asset is loaded. Streaming (when to spawn and despawn) is the game's call. **Hot reload:** each spawned level is an ordinary map root, so saving its map reloads it; saving a `.world` reloads the `TileWorld` (and a level whose map file is read for its size), spawned levels stay where they are, and the next `spawn_levels_in` uses the new layout. Moving or respawning spawned levels on a world save is not done. `WorldLevelOf.level` is an index into the layout at spawn time, so a `.world` save that reorders levels can make `spawn_levels_in`'s dedupe mismatch until the game respawns its levels.
