# AGENTS.md - Tilemap Module

Tile maps from Tiled and LDtk (Tiled's files of every grid, orthogonal, isometric, staggered, hexagonal and oblique, and maps built in code on any of them, `TileMap::with_shape`: a map and its layers carry their grid, and its class tiles, picking and a stream's chunk requests go through it, while its drawing, collision and shadows still place cells as rectangles of the cell size, and hexagonal layers neither collide nor occlude; sparse, signed grids, so Tiled's infinite maps load and maps built in code with `TileMap::infinite` grow wherever a tile is written: `docs/backlog/tilemap-features.md`). Design: `docs/specs/2026-10-29-tilemap-design.md`; using it from a game: the `ryo-tilemap` skill; what it costs: `docs/backlog/tilemap.md`. The module holds the data model, the Tiled (JSON and XML) and LDtk readers as registry loaders, maps spawned as entities (landing whole, worked out on a thread of their own), reading and editing them (`MapsView`, `ctx.maps()`) with Wang terrain, their collision and 2D shadows kept in step with their tiles, infinite maps streamed from a game's generator round the cameras and anchors (`stream.rs`), worlds of levels, hot reload, and the padded tilesets they draw from. Drawing is the render module's: tile layers from cached chunks (y-sorted ones row by row among the entities), image layers as one repeating quad per view, tile objects as sprites (`render/tiles.rs`; render module notes, Tile chunks, and Image layers and tile objects).

## Where it runs

- `PreUpdate`, chained after the asset pump (`register_engine_systems`): `spawn_maps` (world levels resolved; ready maps' landings sent to the `Worker`; landings that came back land whole, with `MapEvent::Spawned`; failures reported once) and `reload_maps` (spawned maps brought to saved files, `MapEvent::Reloaded`), then `stream_maps` (streamed maps unload, ask for and land chunks round their anchors: `stream.rs` below), then `follow_chunk_swaps` (class tiles follow the chunks loaded and unloaded whole on unbounded layers: `spawn.rs` below). So a map whose asset lands this frame starts landing this frame, and starts streaming once it has landed, a save is followed in the frame it lands, and the class tiles of the chunks a stream landed or unloaded follow in that frame, all before the scenes' update.
- `FixedSet::Movement`: `collision::sync_map_colliders`, before physics' `rebuild_tile_colliders`, so an edit made in `update` collides in that step. `PostUpdate`, before `PostUpdateSet::Transforms`: `occluders::sync_map_occluders`, so an edit casts its shadow that frame. Both from `register_tilemap_systems` (`mod.rs`).
- The render step: `render/tiles.rs`'s `TileDrawer` (engine-owned) pads each spawned map's tilesets (`PaddedCache`, a world resource the landings share), builds changed chunks into the batch's chunk store and gathers the visible ones.
- The map builder thread (`jobs.rs`, `ryo2d map builder`): each landing's colliders, shadows and missing paddings. Where there is no thread (the web) a landing is worked out in the frame it is sent.
- The chunk builder thread (`jobs.rs`' `Worker` again, `ryo2d chunk builder`, kept by `stream_maps`): every streamed map's generator calls, so a chunk never waits behind a landing. Where there is no thread (the web) a chunk is generated in the frame it is asked for, within its stream's `web_budget`.
- The world holds no map state of its own beyond the assets' stores, `Messages<MapEvent>`, `Messages<ChunkEvent>`, `PaddedCache` and `WangWarned` (`wang.rs`): everything else is on the map's entities (a stream's chunks in `StreamState` on its root), and the chunk worker with the jobs out is `stream_maps`' own (a `Local`).

## What exists

- `tile.rs`: `Tile` (tileset index, id, `TileFlip`) and `TileFlip` (H, V, D bits as Tiled stores them; `rotated_cw` uses Tiled's table). On a hexagonal map D's bit is a 60° turn (`HEX_ROTATE_60`, an alias) and a fourth bit, 8, a 120° one (`HEX_ROTATE_120`), after the flips (measured, formats note §6). `rotated_hex_cw` writes a half turn as H | V, so the twelve states without both turn bits cycle back after six turns; the four with both (the same half turn written otherwise) come back as the same turn in the other spelling, since sixteen spellings name the dihedral group's twelve (`hex_turns_come_round_after_six`).
- `property.rs`: `PropertyValue` and `Properties` (insertion-ordered, typed getters; `int` accepts a whole float, `float` accepts an int).
- `tileset.rs`: `Tileset` (an `Asset`; atlas or collection; per-tile `TileData` with shapes, animation, probability; `WangSet`s) and `URect`, the engine's own texel rectangle (glam has none).
- `grid.rs`: `TileGrid`, a layer of 4-byte cells (0 empty; the four flip bits in 28..=31, H, V, D and the hex 120° turn, tileset in 20..=27, id + 1 in 0..=19; `four_flip_bits_round_trip_through_a_cell`) in `CHUNK_SIZE` (32) chunks keyed by signed chunk coordinate (`chunk_of` is `div_euclid`, so cell -1 is in chunk -1 and cell -33 in chunk -2) in a `FastMap`, each chunk's cells a boxed array with its version and dirty mark, and a list of the chunk coordinates kept in row order as chunks are made (one moved into place, several sorted), so `chunk_coords` and `drain_dirty` give row order without sorting each call. A bounded grid (`new(size)`, every bounded map's) holds the cells from (0, 0) to its size and refuses the rest, as before; an unbounded one (`unbounded()`, every tile layer of an infinite map) holds any cell. Chunks persist (the `TileGrid` and `TileMap::new` docs say so for games): a spawned bounded layer has every chunk of its bounds and collision, shadows and `Tracked` keep an entry for each, so a huge bounded map built in code is slow to land and costly, where `TileMap::infinite` costs nothing until written. Both make a chunk only when a tile is first written in it (clearing an absent cell makes none, and a clearing `fill` reads only the chunks there are: those of its region or the list of chunks, whichever is shorter), and a chunk stays once made, its cells emptied. **The engine alone takes a chunk out:** `unload_chunk` (crate) takes a chunk of an unbounded grid out whole and returns its cells (`None` for a chunk the grid lacks, and from a bounded grid, which refuses: only unbounded layers stream), the chunk gone as if never made (out of the list of chunks, its dirty mark with it, the extent shrunk to the chunks left) and the grid's version moved on as for any change (the extent is worked out again only when the chunk was on its edge, and then lazily: `extent` works it out from the chunks while it is stale, and `settle_extent`, crate, keeps it once after a run of unloads, so a teleport unloading n chunks costs O(n), not O(n²); `a_run_of_unloads_keeps_the_extent_exact_and_works_it_out_once`); `load_chunk` (crate) puts a whole chunk's cells in at once as one change, the chunk made or its cells replaced whole, made even when every cell is empty (holding none then), refused by a bounded grid and past the chunks `i32` holds (`an_unloaded_chunk_leaves_the_grid_as_one_change`, `a_loaded_chunk_comes_in_whole_as_one_change`, `a_bounded_grid_refuses_to_unload_or_load_chunks`). The grid keeps no tombstone of an unloaded chunk: every consumer keeps something for each chunk it read, and the chunks it keeps that the grid lacks are the ones unloaded (`kinds.rs`, `changed_chunks`), so consumers reading at different times each find an unload, and an unloaded chunk costs the grid nothing. A load is noted on its chunk (`loaded_since(version)`, crate, which later edits leave) and loads and unloads on the grid (`swapped()`, the version of the last one, 0 for a grid that has had none), for class tiles, which follow those and not edits (`spawn.rs`). A chunk tells whether its cells changed since its last whole load and a version (`changed_since(chunk, version)`, crate: its version past both; with 0, since the load, and a chunk never loaded, a Tiled infinite map's own, is told from the version its stream started at), and `fold_into_load` (crate) counts what changed since as part of the load, for the class tiles taken out of a chunk just loaded, which are not an edit; together they tell a stream which chunks a player changed (`a_loaded_chunk_tells_whether_its_cells_changed_since`). A tile `fill` that would make more chunks than a map holds (`MAX_FILL_CHUNKS`, 131,072: `MAX_MAP_CELLS` over a chunk's cells; counted by `missing_chunks`, crate, without making or walking more than the region or the list) changes nothing and returns 0, where `IVec2::MIN..=IVec2::MAX` on an unbounded grid was an out-of-memory abort (`an_unbounded_fill_making_more_chunks_than_a_map_holds_is_refused`; a bounded grid's fill is clipped, so never refused). The cap is read through `fill_cap()`, which in test builds is the thread's `FILL_CAP`: the refusal tests lower it to 4 and ask for 5 chunks, so were the guard ever gone they would allocate 20 KB, not exhaust the machine (a test of a memory guard must stay bounded without it). `set` looks its chunk up once (clearing reads it, a tile makes it). `write_rows` (crate) writes a block of cells (rows of encoded cells, `TileGrid::encode`) from a cell, one lookup per chunk it reaches, as one change, making only the chunks it puts a tile in and leaving out what lies outside a bounded grid or `i32`: the Tiled reader writes a bounded layer's data and each of an infinite layer's chunks with it (a lookup and a version per loader cell cost the `load` guard 1.50 ms against 1.23 to 1.27 before the grids went sparse; written by rows it reads 1.22 ms). A chunk can exist with no cells (`Chunk::cells` `None`): `mark_all_dirty` makes every chunk of a bounded grid's bounds that way (each landing calls it, so an empty chunk is versioned without 4 KB of zeros; so `chunk_coords` on a spawned bounded layer lists every chunk of its bounds), `clear` drops every chunk's cells, and `touch` and `assign` make them for chunks they move with no tile. `bounds()` is `None` for an unbounded grid; `extent()` is the bounds, or for an unbounded grid the smallest rectangle holding all its chunks (kept as chunks are made; it also holds whatever lies between them, chunks or not, and the end of the last chunk `i32` reaches stops at `i32::MAX`): never size anything from an unbounded grid's extent. `tile_extent()` (crate) is the smallest rectangle holding every cell with a tile, found from the chunks along the edges of those holding tiles (a look at each chunk for a tile, then the edge chunks' cells): what `TileMap::bounds()` and `MapsView::extent` give. A chunk never changed has version 0, and versions come from one process-wide counter (`VERSIONS`), as before. Edits mark chunks dirty; `drain_dirty` hands each changed chunk out once in row order. A new grid has no dirty chunk. A tile that does not fit a cell (tileset over 255, id over 1,048,574) is refused by `set`. `assign` (crate) takes another grid's cells (same bounds, or both unbounded), moving on only the chunks whose cells differ (or that its caller names), as one change: what a reload uses, so only the chunks a save changed rebuild; a bounded grid compares every chunk of its bounds, an unbounded one the chunks either grid has, emptying (and keeping) a chunk the other lacks. `assign_where` (crate) does so over the chunks a filter takes alone, the others keeping their cells and versions whatever the other grid holds: a streamed map's reload, over the file's chunks (`assigning_within_some_chunks_leaves_the_others_as_they_are`). `touch` (crate) moves on the chunks it is given, the cells as they are, for IntGrid edits. `chunk_cells` (crate) hands a chunk's cells out row by row, read with `TileGrid::decode`, for a builder walking a chunk without a lookup per cell (the renderer's `chunk_instances`, the classification in `kinds.rs`, class tiles, `edit::clear_parts`). Also crate-private: `chunk_versions` (each chunk with its version, no lookup each), `chunks_within(first, last)` (the chunks there are in a chunk range, in row order, found by walking the range or the list of chunks, whichever is shorter), `chunk_count`, `has_chunk`, and `id`: a number no other grid has, a clone included (`Clone` gives the copy a new one), so a consumer that keeps the id and version it last read a grid at finds what changed since as the chunks of a later version, while the grid is the one it read (`kinds::changed_chunks`). Debug prints the bounds and the chunks holding tiles, so grids holding the same tiles print alike.
  - **Consumers walk the chunks there are**, signed: the renderer (culling floors the view to signed chunks), collision and shadows (a group of bounded layers is bounded by their largest bounds, one with an unbounded layer unbounded), class tiles (`take_class_tiles`, per chunk) and `edit::clear_parts`; edits, Wang terrain and the cell conversions take any cell of an unbounded layer. An unloaded chunk is gone for every one of them: not drawn (the renderer visits the chunks a layer has, and its store frees one as any chunk undrawn for 120 frames: `an_unloaded_chunk_draws_nothing_and_the_store_lets_it_go`, `testing/gpu_world.rs`), not collided, casting no shadow, its class tiles despawned. Nothing is sized from an unbounded grid's extent: an unbounded layer with tiles at (0, 0) and (1,000,000, 1,000,000) lands holding two chunks (`an_unbounded_layer_with_a_tile_a_million_cells_out_lands_holding_only_its_chunks`), and every consumer agrees on the cells -1, 0, -32 and -33, shadows by their geometry too, each solid cell's outline edge by edge in the chunk owning it (`negative_and_chunk_edge_cells_agree_in_every_consumer`; both in `spawn/signed.rs`). A bounded map builds what it built before. IntGrid values (`IntGrid`, LDtk's) stay dense and bounded: LDtk has no infinite maps. An IntGrid is read in any chunk its grid holds cells of (`chunk_kinds`), and a build of collision or shadows visits every chunk of its IntGrid's cells besides its grid's chunks (`kinds::build_chunks`): a game that swaps `TileLayerData::tiles` for a new grid holding a few tiles keeps its IntGrid colliding and casting shadows through a full rebuild (the map disabled and enabled, a layer flag, a tileset's shapes), where the build read only the new grid's chunks and the rest stopped (`an_int_grid_whose_grid_a_game_swapped_collides_and_casts_shadows_after_a_rebuild`).
- `grid_shape.rs`: `MapGrid` (prelude, with `GridShape`, `StaggerAxis`, `StaggerIndex` and `CellOutline`: a shape, a cell's size and an `origin` added to every position it gives), the one geometry for every grid Tiled saves (orthogonal, isometric, staggered, hexagonal, oblique), which every cell-and-pixel question is to go through: a cell's centre, outline (clockwise on screen from its top-most point, the left one of a level top; 4 points, or 6 on hex maps, where a side of length 0 repeats its point), box (`cell_bounds`, `bounds_of` a `CellRect`) and `tile_anchor` (where a tile image's bottom-left stands, before its tileset's offset: the box's bottom-left, on an oblique grid the skewed corner below the cell's top-left), `cell_at`, and the board tools `neighbours` (clockwise from the top: the cell across the top edge, or where the top is a vertex the one across the edge right of it; an oblique grid keeps the unskewed order), `distance`, `line`, `range` and `ring` (on hex grids Red Blob's cube maths through odd-r/even-r offsets for axis Y and odd-q/even-q for axis X, the line nudged off edges; on square lattices steps over the four neighbours, so a range is a diamond, and a line breaks a tie at a corner along x first; staggered grids through their lattice). Crate-side: `chunk_bounds` and `chunks_over` (the storage chunks, `CHUNK_SIZE` cells a side by cell index, whose cells may meet a rectangle: every chunk of a cell overlapping it and of the cell under each of its points, at most a chunk more a side, never one missing; on an orthogonal grid its ends are the chunks of `cell_at`'s cells at the rectangle's corners, floors at both ends as the renderer culls, where a stream's area leaves out a chunk it only touches at its far edge), `lattice` (`Lattice`: the square lattice collision and shadows are to trace in, `to_pixel` its affine to the layer's pixels; the index space of orthogonal, isometric and oblique grids, and on a staggered grid the isometric lattice of its diamonds, indexed through `lattice_cell` and `grid_cell` so that lattice cell centres are the cells' centres; none on hex grids), `paint_key` (Tiled's order in a plain layer: rows, then columns, a row's unshifted columns before its shifted ones on axis-X staggered and hex grids; oblique grids draw as orthogonal ones, whatever the skew), `sort_band` and `band_y` (a band's cells share a sort point: the diagonal c + r on isometric grids, half a row on axis-X staggered and hex grids, the row elsewhere; it sorts at its cells' centre, an orthogonal row at its bottom edge as before; an oblique grid skewed down along its rows has no shared point, so its band sorts at its column 0 cell's centre). `MapGrid::for_map` gives Tiled's origin: a bounded isometric map's cell (0, 0) top vertex at its height times half a cell across, rounded down to a whole pixel; zero otherwise. Every tile layer carries one (`LayerKind::Tiles::grid`, copied from the map's `TileMap::grid()` as `add_tile_layer` adds the layer and by the Tiled reader, a square one of the layer's own cell size from the LDtk reader; then `TileLayerData::grid`): class tiles stand at its `cell_center` (`spawn_class_tile`, and a reload's re-placed ones), `edit::world_to_cell` takes the point into the layer's pixels and asks `cell_at` (`None` for a layer scaled to nothing or of cells with no size) and `cell_to_world` gives `cell_center` out through the layer's transform, and a stream's `ChunkRequest::grid` is its first unbounded layer's (`a_code_built_isometric_map_places_class_tiles_and_picks_through_its_grid`, `negative_and_chunk_edge_cells_of_an_isometric_layer_place_and_pick_through_its_grid`, `a_streamed_request_carries_the_grid`). Drawing (`render/tiles.rs`: the instance's place, culling, the layer stamp, a y-sorted row's sort y), collision (`GroupKey`), occluders (`Lit`), `kinds::chunk_kinds` and the stream's areas (`MapSpace`'s `chunk_px`) read only its `cell`, keeping the orthogonal maths, so a layer on another grid draws, collides and casts as if its cells were rectangles of its cell size; on an orthogonal grid, every one of these is what it was with a bare cell size, bit for bit.
  - **Placement is Tiled's, measured:** `tests/fixtures/tilemap/tiled/measured.json` (written by `scripts/make-fixtures.js`' measure section: `tileToScreen` of 49 cells on each of 31 sample grids, where `toImage()` drew a tile at four cells of each bounded one, `screenToTile` round a hexagon, and the oblique draw order), against which the tests check every cell (`tile_anchors_match_tileds_measurements`, `odd_and_degenerate_grids_place_as_tiled_measures`). The findings are the formats note's section 7 (`docs/research/2026-10-31-tile-shapes-formats.md`): staggered and hex grids step in whole pixels, half a cell rounded down and a hexagon's slant rounded toward zero, so a 33 x 17 staggered cell is a 32 x 16 diamond and its tile stands on that box, reaching a pixel above it (`Lines` keeps those steps: `half`, `step`, `slant`, `depth`); isometric grids step in half pixels from a whole-pixel origin; a hex side longer than the tile spreads the rows apart, the outline then taking no slant (rectangles in brick rows, still six neighbours).
  - **Exact arithmetic:** positions are worked in `f64` on whole and half pixels and rounded to `f32` once, so a vertex two cells share is the same point from either outline, and a point on an edge picks the same cell all along it (`floor_div` rounds a quotient down exactly). An orthogonal grid keeps the engine's `f32` maths to the bit (`an_orthogonal_grid_is_6a_s_rectangles`: `cell_center`, `tile_anchor`, `cell_bounds`, `cell_at`, `band_y`).
  - **Picking follows the outlines, what draws there** (`cell_at_round_trips_and_splits_shared_edges_one_way`, over cells -40..40 a side on every grid): on staggered and hex grids the band of rows (columns on axis X) by division, then which side of the slanted sides the point is on; floor division in the lattice elsewhere. A shared edge goes wholly to one cell: a slanted side to the later row (column), any other side to the later cell along its row, and on the other grids a side to the later cell along the axis it crosses. Tiled picks a hexagon by the nearest centre instead, which on hexagons of other than the regular side hands a sliver by each vertex to a neighbour (measured: (31, 22.5) on 32 x 32 hexagons of side 12 is inside (0, 0), and Tiled picks (0, 1)).
  - Degenerate grids (cells of no size, sides past the tile, skews folding the grid flat or over, cells at the ends of `i32`, points that are not numbers) answer without panicking (`degenerate_grids_answer_without_panicking`): index arithmetic is `i64`, results clamp to `i32`, and a line, range or ring allocates no more than 4,096 cells ahead (a far line is still as long as it is).
- `map.rs`: `TileMap` (an `Asset`) of `MapLayer`s (`LayerInfo` plus a `LayerKind` of tiles, objects or an image) over `TilesetSource`s (asset handle or embedded `Arc`). A tile layer is `LayerKind::Tiles { tiles: TileGrid, intgrid, grid: MapGrid }`. `shape` (a `GridShape`, orthogonal unless set) and `grid()` (`MapGrid::for_map` of the shape, `tile_size`, `size` and `infinite`) are the map's grid, which `add_tile_layer` copies into each layer it adds; `with_shape` sets the shape and moves the tile layers whose grid was the map's onto the new one (setting the `shape` field moves none: `every_layer_copies_its_maps_grid`). `infinite` marks a map whose tile layers are unbounded (a Tiled infinite map; `add_tile_layer` adds an unbounded layer to one; `TileMap::infinite(tile_size)` builds an empty one in code, grown by `MapsView` writes: `a_map_built_infinite_in_code_grows_where_a_game_writes` in `spawn/signed.rs` and the GPU test `a_tile_painted_far_from_the_origin_on_an_infinite_map_draws_with_a_camera_there`): its `size` is zero, and `bounds()` is the smallest rectangle holding every cell of its tile layers with a tile (`tiles_bounds`, the union of the grids' `tile_extent`s; empty with no tile), where it was the engine's 32-cell chunks around them, up to 31 cells wider a side, for games to use for camera limits and world rectangles (`an_infinite_map_s_bounds_hold_its_tiles_exactly`). A bounded map's is (0, 0) to its size. It reads the asset: a spawned map's edits change its layers' copies (`MapsView::bounds`). `file_chunks` (crate) is, for a Tiled infinite map, the engine chunks any layer's Tiled chunks touch, by row (the Tiled reader's `Builder` notes each chunk's span as it decodes it, bounded by the cells cap the chunks were counted against), which a stream leaves to the file; empty for every other map. `ImageLayer::image` is `None` for an image layer given no picture (Tiled saves a new one as `"image": ""`, or an `<imagelayer>` with no `<image>`), which loads and draws nothing (`an_image_layer_tiled_left_without_an_image_loads_empty`; it failed the whole map). `IntGrid::get` returns `None` for 0 as well as outside.
- `spawn.rs`: maps as entities. `MapRoot` (a `TileMap` handle, or an LDtk project and a level by identifier or iid; class tiles, IntGrid collision overrides, collision off, base z) on an entity whose `Transform` places the map's cell (0, 0): its top-left corner, an infinite map's tile origin. `spawn_maps` (`PreUpdate`, chained after the asset pump) lands each ready map whole (below), or sends `MapEvent::Failed` once per failure. `map_asset` resolves a root to its `TileMap`, `root_map` the same from the stores a system holds.
- **A map lands whole.** When a root's asset (and its tilesets) is ready, `spawn_maps` copies the asset's layers (each Tiled tile object given what its tile carries, `inherit_tile_data`: with no class of its own it takes its tile's, and its properties lie over its tile's, which hold the tile class's defaults; an object with a class of its own keeps the tile class's defaults under its own, where Tiled keeps only what the tile wrote; LDtk entities take nothing; done here because a map's external tilesets are not loaded while it loads, `a_tile_object_takes_its_tile_s_class_and_properties`, asserted against Tiled's own resolution), the root's settings, the class-tile table and the tilesets' `ShapeSource`s and stamps into a `LandingJob` for its `Worker`, and marks the root `MapLanding { job }`. The job takes the class tiles out of the grids' copies (marking every chunk dirty), and works out the colliders (`collision::prepare`: every grid classified, traced and packed, the packs' Rapier shapes built) and the shadows (`occluders::prepare`: every chunk's chains) for the layers as they will spawn, layers named by their place (entities are stand-ins until they spawn). When it comes back (polled every `spawn_maps`), `land` spawns the layers and the objects' entities, inserts `MapIds` and `MapLayers`, puts the colliders (with their `Traced`) and the shadows on (`collision::land`, `occluders::land`: entities relinked by place), then gives the objects their components (observers run), spawns the class tiles, and sends `MapEvent::Spawned`: all in one frame, and the fixed step that frame (or the next) builds the parts from the traces before physics steps, so a body an object observer or a `Spawned` reader puts on the map lands on its ground (`a_body_on_a_map_reported_ready_never_falls_through`). Until then nothing of the map is in the world but its root, and `MapsView` reads nothing. A root disabled, despawned or given another root while its landing is out drops the result (`root_discarded` takes `MapLanding` too). The arrival looks roots up with `Allow<Disabled>`, so a disabled one loses its `MapLanding` and is worked out again once enabled (`a_root_disabled_while_its_landing_is_out_lands_once_enabled`; looked up with the default filter, its result was dropped with `MapLanding` left on, and it never landed). A job that panicked is logged and worked out on the main thread. If that panics too, the root gets `MapFailed` holding `landing_stamp` (the versions of its map or LDtk project and of each tileset asset the map uses) and `MapEvent::Failed` is sent once; it is not tried again until one of those versions changes (`a_landing_that_always_panics_is_reported_once_and_not_retried`; before, it was sent again every couple of frames). A test's map makes its landing panic with the `PANICKING_LANDING` property (test builds only). A landing records the loads of the files it was worked out from (`reload::content_stamp`); one that comes back after a load of one of them landed (a save while it was out) is dropped and worked out again from the files as they are, so the map lands as saved, with one `Spawned` (`a_save_while_a_map_lands_lands_the_saved_map_once`; before, it landed the old map and never followed the save). It lands with a `MapApplied` (below). On the web (no threads) the job runs where it is sent, so the map lands in the frame its asset is ready. Layer flags set on layer entities (`collides`, `occludes`, properties) can only change after the landing, through the systems' rebuild path.
- `kinds.rs`: what a cell is, for collision or light, pure so a landing job runs it off the main thread: `ShapeSource` (a tileset's tiles with shapes, read once: each tile's drawn size and shapes, the tileset's offset; `sources` for a map's tilesets), `placed`, `classify` and `tile_kind` (by `Purpose`), `intgrid_table`, the ranked union `over`, `build_chunks` (the chunks a first or full build reads: the layer's grid's and, for an IntGrid layer, every chunk of its IntGrid's cells the grid holds), `chunk_kinds` and `union_kinds` (a chunk's kinds, or a `Part` of one, across a group's layers, read from `chunk_cells` where the cells lie, each tile's kind found once by its cell's value: no lookup per cell), `Tracked` (a group layer's last-read grid id and version, each chunk's version, and its IntGrid kinds) with `changed_chunks` (the same grid: the chunks of a later version, found without a lookup each; a grid swapped for another: every chunk compared with its version; either way a chunk read before that the grid lacks, the old grid's or one unloaded since, counted as changed, to empty, and forgotten. After each read a layer's versions hold every chunk of its grid, so they hold more exactly when the grid lost some, and only then are they compared with it: `consumers_reading_at_different_times_each_see_an_unloaded_chunk_go_once`), `TilesetStamp`, and the `Layers` and `Stores` query aliases both systems use.
- `jobs.rs`: `Worker`, one thread of jobs (started with its first job; `ryo2d map builder` for `spawn_maps`' landings, and `Worker::named` gives `stream_maps` its `ryo2d chunk builder`) taking boxed jobs and handing back each one's id and result (`None` for a job that panicked); where no thread starts (the web) a job runs where it is sent, which `runs_inline` tells once the first job is sent.

A kept chunk stays kept after it lands: it unloads unchanged without being put in again, and its copy is still there. A wasm32 build aborts on a panic, so `catch_unwind` cannot catch it there: a generator's panic ends a web game.

- `collision.rs`: `sync_map_colliders` (`FixedSet::Movement`, before physics' `rebuild_tile_colliders`, so an edit made in `update` collides in that step; `register_tilemap_systems` in `mod.rs`) keeps each spawned map's colliding tile layers in a `TileColliders`, with the crate's `MapCollision` on the map entity. Colliding layers (`LayerInfo::collides` on a root with collision) group by cell size, offset and collision material: the group of the map's `tile_size`, no offset and the map's material unions into one `TileColliders` on the map entity, any other gets its own on its first layer's entity (whose `Transform` carries the offset), so two colliding layers meet without a seam unless they differ in one of the three. A cell takes the strongest kind across its group (`Solid` > `Shape` > `Slope` > `OneWay`); on a tie (two shapes, two slopes) the upper layer's wins. An IntGrid layer collides by its values (`intgrid_table`: an override by value, else by name, else the default names `solid`, `one_way`, `slope_*`, all ignoring ASCII case; an override to `TileCell::Shape` names no shape and collides as nothing, which `plan` warns once a map, `an_int_grid_shape_override_collides_as_nothing_and_warns_once`), any other by its tiles' shapes not marked `occluder`, placed where the tile draws (`placed`, the drawing's rules: a tile stands on its cell's bottom edge from the left, `tile_offset` moves it, flips turn it: diagonal, then horizontal, then vertical) and classified (`classify`): a full-cell rectangle `Solid` (`OneWay` if one-way), three cell corners `Slope` (the right angle opposite the corner left out), anything else a `Shape` added once per distinct geometry (`ShapeKey`, points on a 1/46,080 tile grid). A tile with solid and one-way shapes collides with its solid ones only (`CellShape` has one `one_way`). A colliding layer with parallax other than 1 collides where it would draw without it (parallax is a rendering effect, as in Tiled, and a collider moving with the camera is not a body physics can hold) and the dev log warns once a map per layer (`a_colliding_layer_with_parallax_collides_where_it_is_and_warns_once`). Each tile's kind is worked out once per group (`kinds`), from the map's `ShapeSource`s. Material: the properties `collision_layer`, `collision_mask` (a 32-bit int: -1 is every bit), `friction` and `restitution`, a layer's over its map's over `TileColliders`' defaults (an ice layer saying `friction` 0 is a grid of its own); a wrong type warns once a map per layer and property, and what is under it counts.
  - **The first build** comes with the map's landing (`prepare`, `land`; see `spawn.rs` above): every grid on its target with its `Traced`, so physics only spawns the parts and inserts their shapes as built. Physics packs a grid's outlines by chunk (a part for the loops starting in each 32-cell chunk; physics module notes, Packing), so a map's part count follows its area, not its islands. Whatever builds the grids again after that (enabled again, a layer's flags, the tilesets or the overrides changed) builds at once on the main thread. The landing frame of a 256 x 256 four-layer map adds about 0.03 ms for terrain and about 0.2 ms for 1,024 separate islands in 64 parts (`spawning_a_256_map_adds_under_half_a_millisecond_to_any_frame`, ignored, release, timed after a warm-up since a process's first second runs slow; a part per island took about 1 ms, nearly all of it Rapier taking in the colliders).
  - **Chunks, not cells:** a group's grid is bounded by its layers' largest bounds (`TileColliders::new`), or unbounded (`TileColliders::unbounded`) when a layer is, its cells signed. A build classifies each chunk any of its layers has (an IntGrid layer's IntGrid chunks too, `kinds::build_chunks`), across them (`kinds::union_kinds`), and writes it whole (`TileColliders::put_chunk`, crate: a cell outside the grid or past `MAX_REACH` left out, the latter warned once a grid), with no dense vector of the group's rectangle. There is no cap of the module's own: a 10,000 x 1 level collides end to end (`a_colliding_layer_wider_than_8192_cells_collides`); an unbounded group's cells collide within 186,411 cells of (0, 0) (physics module notes, Sparse and signed), and past that they draw and cast shadows but do not collide. That reach is the outline lattice's, not where f32 positions stay precise: a `Transform`'s pixels are 1/4 px apart there and 1/8 px a million px out, so precise play keeps within about a million px (physics module notes). Parts sit at their chunks' top-left, so a test reading a part's points adds the part's translation (`physics::in_grid_space`, crate tests).
  - **What changed:** every step the group's layers' `TileGrid::id` and `version` are compared with the last seen (never `drain_dirty`, which one consumer would empty for the others); for a layer that moved, each chunk whose version moved (`kinds::changed_chunks`) is classified again across the group and written whole (`TileColliders::set_chunk`, crate), which lists only the cells whose kind changed, as `set` would, so physics' loop-local rebuild stays local. A chunk none of the group's grids has any more (unloaded) and nothing else fills (no IntGrid) leaves its `TileColliders` whole (`TileColliders::unload_chunk`, crate: its cells listed as changes, so physics retraces only the loops through them and a loop running into it closes at its edge, and its storage freed; its extent is worked out once after the group's chunks, `settle_extent`, not once a chunk), so a group streamed across an endless world holds only the chunks there are (`an_unloaded_chunk_leaves_collision_shadows_and_class_tiles`, `a_floor_across_an_unloaded_chunk_closes_at_its_edge_in_collision_and_shadows`, both in `spawn/signed.rs`). An IntGrid layer whose names (seen when `TileLayerData` changes) now give other kinds re-reads all its chunks. A change of what the grids are built from (the colliding layers, their entities, cell sizes, offsets, materials and bounds, whether each has an IntGrid, the map's tile size, the overrides, a tileset's shapes) builds every group again (new `TileColliders`, which physics builds whole); an unbounded layer growing a chunk is an edit, not such a change. A tileset whose content version or embedded `Arc` moved is read again (`kinds::shapes_kept`), and only shapes that differ (`ShapeSource`) count: a tileset image's reload touches its tileset and map, and a tileset saved with other tile data, neither of which rebuilds anything (`saving_a_tileset_or_its_image_redraws_every_map_using_it`; before, an image save replaced every part). An idle step costs a look at each map's layers, tilesets and properties (about 0.1 µs a map in release); an edit's step about 6 µs for one chunk of four 1024-wide layers (`one_tile_edit_sync_timing`, ignored; 18 µs before the chunk reads and the version check without a lookup a chunk).
  - **Disabled, despawned, root gone:** `Disabled` does not reach the layers, so a disabled map's sync takes away every `TileColliders` it put on (the map's and its layers'), and enabling builds them all from the tiles as they then are, on the main thread (the cost: `docs/backlog/tilemap.md`, Limits). A despawned map takes its colliders with it (the map-level parts are its children, a layer-level grid's are its layer's). A map whose root is put over or taken away (no `MapLayers`, or no `MapRoot`) loses its grids and `MapCollision`. A disabled layer entity does not collide. A map with collision owns the `TileColliders` on its entity: one a game put there is replaced.

  - IntGrid values are followed through their layer's grid versions. `MapsView::set_intgrid` and `fill_intgrid` (`edit::fill_intgrid`) write the values and move on only the chunks whose values changed (`TileGrid::touch`, crate: the versions of the chunks named, the cells as they are), so only those chunks collide, occlude and redraw again (`an_int_grid_edit_re_collides_only_its_chunk`); before them a game wrote `TileLayerData::intgrid` and called `grid.mark_all_dirty()`, which rebuilt the whole layer. A value written by hand is seen once its chunk's version moves. LDtk's auto-layer rules are not run: the art changes through `set_tile`.
- `occluders.rs`: `sync_map_occluders` (`PostUpdate`, before `PostUpdateSet::Transforms`) keeps each map's shadows, with the crate's `MapShadows` on the map entity. A layer occludes as `LayerInfo::occludes` says, else as it `collides` (the root's `without_collision` does not change it); occluding layers sharing a cell size and offset occlude as one, each cell the strongest kind across them (collision's `over`). A tile occludes with its shapes marked `occluder`, else its collision shapes (one-way ones too), as one solid shape placed as collision places it (`Purpose::Occlusion` in `kinds.rs`); an IntGrid's `Solid` cells whole and its slopes as their half cell (a one-way cell has no area to occlude with).
  - **Boundary chains, not rectangles:** an occluder whose edge touches another's casts that edge's shadow through the other's lit art (a black wedge at full strength, measured headless), so the occluders are the boundary of what occludes: `physics::Boundary` reads the tile colliders' outline units (each cell's inside, the borders left of and above it; shapes fitted to their cells on the outline grid; edges two cells share cancel, partial overlaps too), reversed to lighting's winding. Each chunk owns the units of its cells and, where it reaches them, a bounded group's right and bottom borders, so the chunks' edges together are the boundary with nothing twice, and nothing at a chunk border. An unbounded group (one with an unbounded layer) has no such border: the borders right of and below its last cells are the next chunk's, built as that chunk is though its layers have none (the cell (-1, -1)'s right and bottom borders are chunk (0, -1)'s and chunk (-1, 0)'s). Its chunks are those whose cells, the column left of them and the row above are cells `i32` holds (`SHADOW_CHUNKS`: all but the first and last chunk of `i32`'s range on each axis). A chunk's edges are chained greedily (`chains`: from the points more edges leave than reach, then round the loops left; straight runs merged; each point's edges a run of the edges sorted by start, found through one map made at its full size: a list a point, maps grown from empty and a chain made for every start tried were half a dense chunk's rebuild) into `LightOccluder2D::chain`s, each a child of the group's first layer marked `MapOccluder { chunk }` (prelude; `chunk` an `IVec2`, signed as `TileGrid::chunk_of` gives it), its entity at the centre of its corners' box (lighting's reach test reads the entity's translation less the chain's extent, so a small light at a chunk-long chain's end still reaches it), so a chain spans one chunk at most. Shapes are clipped to their cells, as collision clips them.
  - **The first build** comes with the map's landing: `prepare` works out every chunk's chains off the main thread, and `land` spawns them all (`World::spawn_batch`) as the layers spawn. After that a rebuild (enabled again: a disabled map keeps its `MapShadows`, emptied; its layers, tilesets or overrides changed) is at once on the main thread.
  - **Edits:** the group's layers' chunk versions, as collision's (`changed_chunks`); a moved chunk's chains are despawned and built again, every other chunk's kept. An unloaded chunk is built again as empty: its chains go, but the borders it owns against cells that remain (left of its first column, above its first row) are still its own, so a floor running into it is closed at its edge by a chain of the unloaded chunk, and its sides gone empty build the chunks right of it and below it again. A chunk's borders read the column left of it and the row above (classified with `kinds::union_kinds` over a `Part` of those chunks, not cell by cell), so each chunk keeps the kinds of its right column and bottom row (`Sides`, in a map by chunk; a chunk whose sides are all empty has no entry, and none counts as all empty, so an unbounded group's building stops at the first chunk past its cells): when they change, the chunk right of it or below it is built again too, row by row in the same pass (a map of due chunks by row, then column, each marked whether its own cells changed). A chunk built again only for its neighbour's side (a chunk loaded, unloaded or edited beside it, left or above) has not changed itself: it reads its first column and row alone and works out only its borders on the left and above (`Boundary::rebuilt_borders`), taking its other edges from those it kept as last built (`Group::edges`, `Boundary::placed_edges`: each edge with its unit's place in the chunk's scan, 20 bytes an edge, shrunk to fit as kept; every occluding group keeps them, bounded and static maps too: about 3 KB for the busiest chunk of the guard's cave rock, 141 edges, so up to about 3 MB for a 1024 x 1024 map of it, and up to about 40 KB for a chunk of scattered single tiles, about 2,000 edges), merged in the scan's order, so its chains are a whole build's; an empty chunk (unloaded, or the frontier past a stream's last chunks) builds only those borders. A stream's chunk landing or unloading rebuilt one or two such neighbours whole, about half of its shadows' cost (`crossing_timing` in `stream/tests.rs`: the shadows of a frame landing or unloading chunks of cave rock, a median 44 µs, then 30). A group keeps its chains, sides and edges by chunk in maps, so it costs the chunks that have them. A disabled map or layer, a layer that stops occluding, a map whose root went, or a change of the layers, tilesets' shapes (`shapes_kept`, as collision) or overrides takes every chain down (built again when it applies).
- `edit.rs`: `LayerRef` (name or index), finding a layer entity, cell reads and edits (tiles and IntGrid values), world/cell conversions. `view.rs`: `MapsView` (`ctx.maps()`), the public face of `edit.rs`. `MapsView::bounds(map)` and `layer_bounds(map, layer)` (`edit::map_bounds`, `layer_bounds`) read a spawned map as it is now, where `TileMap::bounds()` reads the asset, which edits never change: a bounded layer's bounds, an unbounded one's `tile_extent` with its live class tiles' cells (`LayerTiles`, each checked against its `MapTile`), and a bounded map's asset bounds or an infinite map's union of its layers' (`maps_view_reads_a_grown_map_s_bounds_and_each_layer_s`). Named for `TileMap::bounds`, which they agree with on a map nothing edited, not for `TileGrid::extent`, which for an unbounded grid is its chunks' rectangle. A bounded layer refuses cells outside it (its `bounds`); an unbounded one takes any cell, so `set_tile` and `fill` make the chunks a tile goes in and return true for every cell they change (`writing_a_tile_far_away_on_an_unbounded_layer_collides_and_casts_shadows`; on a streamed map, only in its resident chunks: `stream.rs`), but a tile `fill` that would make more than `MAX_FILL_CHUNKS` chunks (a class tile's too, whose cells would each spawn an entity) is refused before anything is made, sub-layers included: 0, and the dev log warns once a layer (`FillRefused`, a world resource of the layers warned about; `a_fill_making_more_chunks_than_a_map_holds_is_refused_and_warns_once`). `clear_parts` reads a sub-layer's chunks in the region (`chunks_within`) where their cells lie, only the region's rows and columns of each: a `set_tile` on an LDtk layer of 16 full sub-layers costs about 0.9 µs where reading every cell of each chunk cost 8.8 µs (release, measured once; 6a made 16 lookups), `an_edit_across_chunk_borders_clears_only_its_region_of_each_sub_layer`.
- `wang.rs`: `MapsView::set_terrain` (Wang auto-tiling, Tiled's terrain brush with corrections on) and `WangSet::best_tile` / `color_index` / `ANY` (public, for procgen). Each `WangTile` carries its tile's probability, copied at load (`build_tileset` builds the sets after the tiles; both readers share it), and `Tileset`/`WangSet` carry the tileset's `transformations` (hflip, vflip, rotate, preferuntransformed). The rules follow Tiled's observed results, never its source (GPL): a paint asks one colour of the kind's positions; the cells sharing one pick again, row by row, painted cell included, each from the candidates (every tile at every flip the transformations allow, turns before mirrors, plus the empty cell, which wins over a tile with no colour) that have the asked colour and what the cells that picked before it show; among those the closest to what the cell shows now (colour distances: steps through tiles holding both colours, 0 the empty colour; a colour no chain reaches rules a candidate out), then an untransformed tile if the set prefers, then probability times its colours' probabilities, drawn by a hash of the cell (Tiled draws at random, so ties cannot match it). A cell that picks a different tile passes the change to the neighbours across an edge whose colours disagree, first-in first-out, within a Chebyshev square around the painted cell as many cells out as the set's longest colour chain plus one (two colours sharing a tile: two cells; deep water, water, sand, grass: four; `Matcher::longest_chain`); one nothing fits keeps its tile and, if it holds a tile of the set or is the painted cell, the set warns once per tileset version (`WangWarned`). Cells read through their flips (D, then H, then V); class tiles are not touched. On an unbounded layer a paint takes any cell and makes the chunks it writes in, as `set_tile` does (`painting_terrain_outside_every_chunk_of_an_unbounded_layer_makes_its_chunks`), but a cell whose reach, and the neighbours a cell at its edge reads, would leave `i32` (within the set's longest chain plus two cells of `i32::MIN` or `i32::MAX`, `reach_fits`) is refused, `set_terrain` returning false, where `cell + offset` panicked in a dev build and wrapped to the far end of the world in release (`painting_terrain_at_the_ends_of_i32_is_refused`); a bounded one keeps a paint within its bounds. The pick's candidates, colour distances and tile-to-wangid index are built once per `WangSet`, on its first pick (`WangCache`, a `OnceLock`; a clone or a reloaded tileset builds its own), so `best_tile` costs a scan of the candidates (about 16 µs at 255 tiles with every flip, down from 60). A set is read-only once built, so the cache cannot go stale: its fields are `pub(crate)` and read through accessors (`name`, `kind`, `colors`, `tiles`, `transformations`), sets are made by `WangSet::new` or the loaders, and no mutator exists (a `compile_fail` doctest pins that a game cannot write a field, and a passing one beside it, the same code reading through an accessor, that nothing else fails it). Add a `&mut self` method only with a caller, and have it drop the cache. Limits: Tiled draws at random among equal fits, so a tie cannot match it (fixtures are built to have one fit); a class tile keeps its colours out of corrections, so painting beside one leaves a seam; an empty cell touched by a chain is judged by its zero colours; erasing in a set with no bare-corner tile warns once per set version. The test fixtures `wang-*` were painted by Tiled: `tests/fixtures/tilemap/tiled/scripts/paint-wang.js` (every job built to have one fit, since Tiled draws at random among equals).
- `reload.rs`: hot reload. `reload_maps` (`PreUpdate`, chained after `spawn_maps`, with `Allow<Disabled>` so a disabled map follows its files and is current once enabled) looks only in frames where a `TileMap`, `Tileset` or `LdtkProject` was added or changed (three `MessageCursor`s; never a store's change list). A spawned map follows its files: its map file or LDtk project with what their loaders read (templates, the Tiled project, LDtk level files: each a `cx.read`, so saving one runs the loader again), and its tileset files. `content_stamp` is their loads (`AssetServer::load_job`, which moves when a file's new value lands: not when a reload starts or fails, a dependency's reload checks it again, or code changes it); a map whose stamp differs from its `MapApplied` (crate, on the map entity: the stamp, each layer's editor id, shape and offset, each object's data and layer, and each class tile by layer editor id and cell, as the files had them) is brought to its asset by `apply_reload`, then `MapEvent::Reloaded` goes. So a tileset image's save, which only touches its tileset and maps, redraws (the padding is stamped by image versions) and reloads nothing; a failed save changes nothing and sends nothing (`a_broken_save_keeps_the_last_good_map`); a file several of a map's files read (the Tiled project: its map and its tilesets) loads each again, the loads landing in any order and frames apart, so the map follows each as it lands, one `Reloaded` a load, ending as saved (`a_project_save_whose_loads_land_apart_ends_with_the_new_defaults`; a test waiting for the first `Reloaded` after such a save saw the tileset's load alone now and then, and waits for every file's load: `until_reloaded_from_every_file`); a map whose asset keeps its last good value after a failed check (a tileset saved that the map no longer fits) waits for the next good load; an asset made in code (no `load_job`) never reloads, though its map follows its tilesets' files. An LDtk project saved without the map's level leaves the map as it is, warned once per load. A tileset file saved naming a larger image, and reloaded before that image, fails its check against the old image (too small) and keeps its last good value; the image's reload then only checks that old value again and never retries the failed load (a registry limit: asset module notes, Reloads), so the tileset stays old until it is saved again. Writing both at once (a `git pull`, a script) can hit it; a fix is the registry's.
  - **Layers** match by editor id (`LayerInfo::id`: Tiled's layer id, LDtk's layer definition uid, one instance a level). A layer the file still has, of the same kind and, for a tile layer, the same bounds (`TileGrid::bounds`: a bounded grid's size, or none for an unbounded one, so an infinite map's layer keeps its entity whatever chunks a save gives it), grid (`MapGrid`: shape, cell and origin, so a kept layer's `TileLayerData::grid` is always the file's) and offset, keeps its entity: its `MapLayerRef` (index, name), `LayerInfo` and `ImageLayer` are put over only where they differ, an object or image layer whose offset changed moves (its `Transform`'s translation set to the new offset, so a Tiled group moved moves its layers, their objects keeping their entities and places in them: `kept_object_and_image_layers_move_with_a_saved_offset`), and its `TileLayerData` takes the file's cells through `TileGrid::assign`, the IntGrid's changed chunks named too (`values_differ`: collision reads IntGrid values through grid versions). An infinite map's layers diff by their chunk sets (`assign` over the chunks either grid has): a chunk the save dropped is emptied and kept, one it added is made, one it changed moves on, and the others keep their versions, the dropped chunk's colliders and shadows going and the new one's coming in the next frame (`saving_an_infinite_map_that_moves_its_chunks_reloads_by_chunk`). **A streamed map** (a `StreamState` on its root) diffs the file's chunks alone (`stream::file_chunks` of the new asset): `stream::before_reload` first hands the chunks the save moved between the file and the stream (`stream.rs` above), its unbounded layers take the file's cells through `assign_where` over the file's chunks, and the class tiles a kept layer lists outside them (`listed_class_tiles`: the stream's, dead entries included, which count as a player's change) stay listed and untouched, so the chunks the stream generated or brought back keep their cells, versions and class tiles, and a tileset save, or any reload of a map built in code with nothing in its asset, changes none of them. So only the chunks a save changed draw, collide and occlude again, each the way an edit does: a chunk collider changes shape in place, keeping its entity and handle, so a character standing on ground the save did not change keeps its contacts and floor (`a_reload_keeps_the_ground_a_character_stands_on`, with chunk versions and shadows of the untouched chunks pinned). Any other layer (a new id, another kind, or a tile layer of another size, cell size or offset) spawns afresh (`spawn::spawn_layer`, shared with the landing), and a layer gone, or replaced, despawns after its objects moved out. There is no landing job for a reload: it runs on the main thread (a dev-time action; cost below).
  - **Objects** reconcile by id (`reconcile`, pure: `keep`, `update`, `spawn`, `despawn`), given their tiles' data first as at landing, so a tileset save that changes a tile's class or properties updates the tile objects taking them, in place (`a_tileset_save_reaches_the_tile_objects_that_take_its_tile_s_data`). Whether the file changed an object is judged against `MapApplied` (its data and layer then), never the entity's components, which the game may have moved. One unchanged keeps its entity untouched (its `Transform`, parent and components as the game has them); one changed takes a new `Transform` and `MapObject` (put over, so `Insert` observers run and `Add` ones do not, and the game's components stay), moving to its new layer's entity if its layer changed; an object the file added or changed with no live entity spawns as at landing (entities first, then `MapIds`, then the components, so observers resolve references); a removed id despawns. Ids are unique in files Tiled and LDtk write; a repeated id counts once on a reload (`MapApplied` notes the first, a landing's `MapIds` names the last spawned, so the first duplicate stays untracked). Class tiles reconcile by layer and cell (`reconcile_class_tiles`), judged against `MapApplied` too (never the live `MapTile`, which the game may change): one the file left as it was keeps its entity untouched (its `MapTile::layer` told a new index), one changed takes a new `MapTile` and `Transform`, and any other live one (a cell the file emptied, or one an edit placed) despawns. On a tile layer spawned afresh, the class tiles that lived on its old entity spawn again on the new one.
  - **What the game took away stays away** unless the save adds or changes it: an object or class tile the game despawned (a coin collected, an enemy killed), or a class tile a runtime `set_tile` replaced or cleared (its cell then takes the file's grid, which holds no tile there), is not spawned again while the file leaves it as it was (`new_and_removed_objects_spawn_and_despawn`, `class_tiles_reconcile_by_layer_and_cell`, `a_tile_layer_spawned_afresh_keeps_away_the_class_tiles_the_game_took`); a save that changes it spawns it. The file does win over the game's tile edits: a dug tile comes back.
  - **Limit, a tileset save that changes shapes:** collision builds every group again (new `TileColliders`), so the floor part under a character is replaced (a new entity and handle, `CharacterState::floor` names the new one, and `CollisionStopped` is sent), though nothing falls through and `on_floor` holds. Image saves and tileset saves that keep the shapes rebuild nothing. Follow-up: reclassify every chunk through `TileColliders::set` instead, as a map save does.
  - **Cost** (`reload_timing`, ignored, release, a 1024 x 1024 map of four layers, on the main thread): `apply_reload` costs about 1 ms per 4 M cells whatever the save changed, since it copies every grid out of the asset and compares it (1.0 ms with one tile changed, 1.4 ms with every chunk); only what follows is in proportion to the change: 40 to 80 µs for the next step's collision and `PostUpdate`'s shadows with one tile, about 80 ms with every chunk of every layer (as a first build on the main thread). Left out of the measure: the registry's main-thread `check` and insert of the new value as it lands, `take_class_tiles`' scan of every chunk of each kept tile layer when the root registers classes (the timed map registers none), and the renderer's rebuild of the visible changed chunks. A dev-time hitch.
- `padded.rs`: each tileset's tiles copied into power-of-two cells of a padded `Image` of its own (edges extruded, so no filter or mip level reads a neighbour). A cell's side is `next_power_of_two(max(2 * T, T + 8))`, T the largest tile's longer side: mip level k samples only a tile's own cell while `2^k` is at most the cell's room past the tile, which is then at least T (every level a tile drawn a pixel wide or more uses) and at least 8 (every level of an atlas page). Power-of-two tiles from 8 px keep cells twice their side; tiles just under one (14, 15, 30 px) take the next power up, and tiles of 30 or 14 px read their neighbours zoomed out with the old `T + 2` rule (`no_seams_at_any_zoom_or_subpixel_camera`'s odd-size legs). The cells sit `margin` texels in from every side (`cell - 8`): with the 8 texel border a texture puts around an image (`atlas::BORDER`), every cell starts on a multiple of its side and the texture's sides are whole cells. A padded image over 256 px gets a texture of its own with every mip level, and the GPU sizes each level by rounding down and spreads it over the whole texture: without the margins its levels from the fifth (16 texels a texel) mixed neighbouring cells into a tile, and those of a texture whose side was not a multiple of the level's texel drifted off the full-size one (`no_seams_at_any_zoom_or_subpixel_camera`, zoom 0.1). Known limit: in a texture of its own, a tile drawn under a pixel wide reaches levels past the cell's room, and from one texel a cell the levels mix cells. `PaddedLayout` says where each tile and animation frame sits; `PaddedTilesets` makes one per tileset, again when the tileset or an image of it changes (in place, keeping the handle), and frees those no round of `get`s (one a frame) has asked for in `KEEP_ROUNDS` (120, as long as the batch keeps an undrawn chunk): a level despawned and another of the same tileset spawned soon after (restarted, or the next level) draws with the same padding, where padding again would cost its landing job the padding and its landing frame a new texture's first write (about 0.4 to 0.6 ms for the 256 x 256 map's tileset in `benches/tilemap.rs`; `a_padding_unasked_for_a_while_is_kept_and_then_freed`). The cost is memory: a padded image (up to 8,176 texels a side, 267 MB of RGBA, with its texture) outlives its last map by those 120 frames, so a level change between two big tilesets holds both for two seconds, about twice the peak. The cache is the world's (`PaddedCache`, a lock `init_world_resources` inserts and the drawer holds each frame, where taking a resource out and putting it back each frame would move an entity twice; inserted before the first scene enters, so a map spawned in its `on_enter` is padded off the frame too, `a_map_spawned_entering_the_first_scene_lands_with_its_tilesets_padded`): a map's landing job pads the tilesets it has no padding of yet and makes their textures' levels (`Image::prepare_upload`) on its thread (`to_pad`, `ToPad::pad`), and its landing hands them over (`adopt`), so its frame only writes them (`a_landing_pads_its_tilesets_off_the_frame_and_hands_them_over`); a tileset padded before and changed since is padded again by the drawer, at once and in place, as below. An inline tileset is known by its `Arc`'s address, so what is kept of one (its padding, a refusal) holds the allocation (a `Weak`) and no tileset made later can take the address and get its padding (`a_gone_embedded_tileset_s_address_is_held_while_its_padding_is_kept`). A tileset whose padded image would pass the device's largest texture side less the atlas's border on both sides draws nothing, and the dev log warns once per version of it, naming it (`a_tileset_too_big_to_pad_draws_nothing_and_warns_once`), or names its largest tile when even one cell would not fit; it is not padded again until it changes, and nothing of the oversized image is made. The limit is the cache's (`PaddedTilesets::set_texture_limit`, which `init_gpu` calls with the device's `max_texture_dimension_2d`; landing jobs carry it in `ToPad`): 8,176 texels under the `Limits::default()` the engine asks for, which the engine does not raise. A larger padded image was refused by the atlas (`atlas.rs`, `width + 2 * BORDER` past the limit) with no warning and drew nothing (`a_padded_image_past_the_device_s_texture_side_is_too_big`). Under it: about 3,800 tiles of 64 px (62 by 62 cells of 128 texels), 15,876 of 32 px, 64,516 of 16 px, and a collection whose largest image is 129 to 256 px holds 196 images, 257 to 512 px 36. Per-size-class cells, or several padded pages per tileset, would lift it. The module is public but doc-hidden, for `tests/tilemap_alloc.rs` (a cache hit allocates nothing) and `benches/tilemap.rs`. A padded image prepared ahead is a first upload, written at once; one padded again in place is made in code, written at once too (below). An animated tile's frames take consecutive cells after the static ones; unequal frame times repeat frames to a common beat (past 128 cells, the mean time). `render/tiles.rs` turns a chunk into instances in layer-local pixels (lane layout in its module docs), and its `TileDrawer` draws spawned maps' layers (an image layer as one quad per view, its image repeating across it; render module notes) and their tile layers: a map's tilesets padded each frame it exists (a disabled map's too, so its images stay; a disabled map draws nothing, `Disabled` not reaching its layers), hidden layers skipped, each visible chunk built once into the batch's chunk store and drawn at the layer's interpolated transform. A layer entity's own `RenderLayers` replace the map's for what it draws. Each padding gets a `serial` never given before, which the chunks' look stamp includes, so a tileset padded again rebuilds the chunks drawn from it. `TileGrid::chunk_version` and `version` stamp every change from one process-wide counter, so a version never repeats, across grids and clones too: a layer whose `TileLayerData::tiles` is swapped for another, even one filled the same way, redraws. A fill or `mark_all_dirty` is one change, one version; consumers keep their last-seen versions. A padding made again in place is made in code, so its upload has nothing made ahead and the renderer writes it at once, never over frames (graphics module notes, Reloads): a re-padded tileset's texture and its chunks' new places change in the same frame (`a_tileset_padded_again_never_draws_its_old_image_with_new_places`, a 752 px padding whose places all move). A padding made again in place must never have its upload prepared ahead (`Image::prepare_upload`, as a landing's first padding has): a large new version would be written over frames while the old texture draws, and the chunks would need to keep the old layout until the new texture shows: with `prepare_upload` added that test fails at the fifth frame, a tile showing its neighbour.

## Speed

`benches/tilemap.rs` holds the spec's targets as guards (`static_frame`, `edit`, `load` with its landing), `tests/tilemap_alloc.rs` the allocation tests (a padded cache hit; a frame drawing a static map under a shadowed light: no allocation of the engine's own beyond an empty frame's under the same light; and an idle frame of a streamed map, its chunks round the view landed and its class tiles spawned: none beyond an empty frame's either), and `docs/backlog/tilemap.md` the numbers measured and the limits. The `edit` guard times the systems an edit runs through on an engine's world, each in a schedule of its own (`edit_schedules`, doc-hidden): the collision sync, physics' tile collider rebuild with its collider sync, and the occluder sync.

## Gotchas

- `tiled/`: Tiled's formats as registry assets. `raw.rs` holds what a file says (serde structs named as Tiled's JSON names them; `xml.rs` fills the same ones from TMX, TSX and TX, so every non-zero default is an `Option` and `build.rs` owns the defaults), `data.rs` decodes gids and layer data (CSV, base64, gzip, zlib, zstd via `ruzstd`, all bounded by the layer's cell count: a small file of each compression inflating to 8 MiB fails, as does data cut short or corrupted, except that Tiled writes zstd frames without a checksum, so bytes changed inside one can decode to other tiles, never to more cells), `build.rs` turns raw into `TileMap` and `Tileset` and holds the checks (a layer's gids become cells in place, `Builder::cells`, and go into the grid by rows, `TileGrid::write_rows`), `json.rs` the `TiledMapLoader` (`.tmj`, `.tmx`) and `TiledTilesetLoader` (`.tsj`, `.tsx`), picking the reader by extension, `objects.rs` the objects of object layers and templates, `wang.rs` Wang sets, `project.rs` the Tiled project file and the property resolution (`Props::read`, `resolve_properties`).
- A path written in a file joins that file's folder; the registry normalises it and refuses one leaving the asset root. An inline tileset's paths resolve against the map's folder.
- **A dependency that fails is named where the file names it.** `load_dep` notes each dependency's normalised path and place (`DependencyPlaces`, crate-private on `TileMap`, `Tileset` and `LdtkProject`, its `Debug` only a count so the XML/JSON twins compare), and each loader's `dependency_failed` turns the server's `AssetError::Dependency` into `place: "path" did not load: why`, as `load_dep` does for one that fails under `load_now`: an inline or LDtk tileset's image names its tileset, an image layer's its layer, an external tileset's file its `tileset N` and that file's error its image (`a_tileset_image_that_does_not_load_fails_the_map_naming_it_and_the_tileset`, both ways, and the LDtk twin). A `.world`'s maps keep the server's error, which names the map.
- External tilesets are dependencies and are not loaded while the map loads, so a gid is matched to a tileset by `firstgid` alone. The ids each tile layer uses are noted in `TileMap::used_ids` and measured against the tilesets in the map's `check`; the atlas image against the declared tiles in the tileset's `check`.
- Group layers flatten: offset adds, opacity and tint multiply, parallax multiplies, visibility ands, a non-normal blend passes down. Layer ids stay as written; a layer without one gets the next free id.
- **Infinite maps** (`infinite` in either format): each tile layer is an unbounded grid of its chunks (`RawChunk`: JSON's `chunks`, TMX's `<chunk>` elements under `<data>`, whose `<tile>` elements read as the layer's do), each decoded in the layer's encoding and compression and written at its own `x`, `y`, `width` and `height` (never an assumed 16: `editorsettings.chunksize` is only how Tiled cut them), so chunks of any size land where Tiled put them, negative cells included (`an_infinite_map_s_chunks_land_where_tiled_put_them`, `chunks_of_any_size_and_every_encoding_load`, and Tiled's chunks of 24 x 24 straddling the engine's borders at x 32 and -32 with a tile layer in a group, `chunks_straddling_the_engine_s_chunks_and_a_grouped_layer_land_where_tiled_put_them`, whose world rectangle holds the grouped layer too, `an_infinite_map_s_world_rectangle_holds_its_grouped_layers_and_straddling_chunks`; over fixtures Tiled saved: `scripts/make-fixtures.js`, the `infinite*` maps). A chunk Tiled left out (it leaves out empty ones, though its JSON layer's `startx`, `starty`, `width` and `height` still count them: never read) has no engine chunk. The map's `width`, `height` and a TMX layer's (0) are not read. Before anything is decoded, every chunk is checked (`check_chunk`: its `x`, `y`, `width` and `height` all stated, `RawChunk`'s being `Option`s in both readers, where a missing one read as 0 (`a_chunk_that_does_not_state_its_place_or_size_fails_naming_it` and its TMX twin; a chunk lacking its place is named by its order in the layer, `chunk 1 (counting from 0)`), a size of a cell or more, within a layer's cells, its cells within `i32`, and their pixels, their outlines' box on the map's grid in exact `f64` (`MapGrid::exact_box`), within `i32`, so a chunk at x = 2,147,483,600 fails, as does one past the cells an `i32` holds, and one up and right whose pixels fit as 64 x 32 squares but not as diamonds, whose x is the column less the row) and counted as the engine will allocate it (`chunked_cells`): a layer counts the more of the cells its chunks hold (what is decoded) and the cells of the engine's chunks they reach (1,024 for each, since a chunk is made whole where a tile goes: a 1 x 1 chunk takes 1,024, a 16 x 16 one at (24, 24) reaches four), the engine chunks found from the chunks' places and sizes, keeping no more of them than a layer holds, so 65,537 one-cell chunks 32 cells apart fail a layer's cap and scattered chunks cannot allocate gigabytes (`infinite_chunks_count_the_engine_chunks_they_take_before_allocating`); a chunk's data must then hold its cells before it is decoded. Errors name `layer "name", chunk (x, y)` and, for a gid, its cell (`hostile_infinite_chunks_are_refused_before_allocating`; the TMX reader's own path, short CSV, a negative width and an `x` past `i64`, `hostile_tmx_chunks_are_refused_naming_their_place`, the last failing in the reader with its line and column). A chunked layer in a bounded map, or an infinite map's layer of data, fails; an infinite layer of no chunks or empty data loads empty. Nothing is sized from the chunks' rectangle: a file with chunks at (0, 0) and (1,000,000, -1,000,000) loads and lands holding two (`a_file_s_chunk_a_million_cells_out_loads_and_lands_holding_only_its_chunks`).
- Limits, each a load error naming the place: 1<<26 cells a layer or map, 256 tilesets a map, 1,048,575 tiles a tileset, an infinite map's chunks within the pixels an `i32` holds. **Cells are counted as the engine allocates them:** a grid makes each `CHUNK_SIZE` chunk whole where a tile goes, so a bounded layer counts every chunk it spans, ceil(w / 32) x ceil(h / 32) x 1,024 cells (`engine_cells`, `layer_cells`: an 8192 x 8192 layer is 2^26 either way, a 10,000 x 64 runner 641,024, a 1 x 1 layer 1,024, and a 1 x 2^26 layer, within a layer's cells, is 2^31 and refused, where the sparse grids would have let a small zlib file allocate 8 GiB; `bounded_layers_count_the_engine_chunks_they_span_and_the_spec_s_maps_fit`, `a_thin_bounded_layer_counts_the_engine_chunks_it_spans_before_allocating`), and an infinite layer the more of the cells its chunks hold and the cells of the engine chunks they reach (`chunked_cells`, above). A map's tile layers take at most 1<<27 such cells together (`MAX_MAP_CELLS`, 512 MiB of cells: an 8192 x 8192 map of two layers, a 1024 x 1024 one of 128), counted from the layers' sizes before any is decoded or allocated (`tile_cells`, groups included), so a small file of many big layers (a 1 MB `.tmj` of 40 zstd layers once asked for 10 GiB) fails with `map: its layers hold N cells, past the M a map holds` (`a_map_whose_layers_hold_too_many_cells_together_is_refused_before_decoding_them`). An LDtk level counts its layers the same way (`level_cells`: every non-entity layer from `__cWid` and `__cHei`, empty ones too, each grid, a sub-layer each, as its whole chunks, an IntGrid layer's values once more, one a cell; a layer spanning more chunks than a layer holds fails naming it, `a_thin_level_counts_the_engine_chunks_its_layers_span_before_allocating`), and the project's levels share the same cap, since a project holds all its levels at once (`a_level_whose_layers_hold_too_many_cells_together_is_refused_before_allocating`). Unsupported: layer blend modes other than normal, add, multiply and screen.

- **Objects on every grid** (`tiled/objects.rs`, `MapGrid::object_point` and `object_step`): `build_object` reads an object's position through the map's grid, so the data holds layer pixels. Isometric positions are tile-height units along the diamond's axes (`((px - py) / th * tw / 2 + origin.x, (px + py) / 2)`), oblique ones unskewed pixels, and staggered and hexagonal ones plain pixels. On the first two a rectangle, ellipse (32 points) or capsule becomes an `ObjectShape::Polygon` of its projected outline with a zero `size`, polygons' and polylines' points are projected as steps from the projected position, and points and text keep their box at the projected position. A tile object keeps its pixel size and moves from its alignment point to its top-left corner in screen space; `Alignment::parse` takes the map's shape because an unspecified alignment means bottom-centre on isometric maps (bottom-left elsewhere, `bottomleft` named always meaning bottom-left). Rotation stays what `MapObjectData` always held, a turn about `position` in screen space, which is what Tiled does on these grids (measured: formats note section 9; `a_rotated_object_matches_tileds_corners_on_every_grid` holds every grid's objects to `measured-objects.json`).
- A tileset's `tileoffset` is kept as `Tileset::tile_offset`, and its image's transparent colour (`transparentcolor` in JSON, `<image trans>` in XML, with or without its `#`) as `Tileset::transparent`, which the padding keys out (`paint`: a texel of its RGB pads clear, its alpha not compared; `a_tileset_s_transparent_colour_pads_transparent`); an image layer's is `ImageLayer::transparent`, which the drawer keys out of a copy of the picture (`render/tiles.rs`, `keyed_image`: made once per version of the picture, again in place when it changes, let go 120 frames after it was last drawn; `an_image_layer_s_transparent_colour_draws_clear`). - **What loads otherwise than the editor shows it warns once per file** for each feature, naming its first place and how many more (`Unread`, collected in `Props` and LDtk's `Defs`, warned when the load succeeds): Tiled's tile render size "grid" (fill mode with it), a collection tile's sub-rectangle of its image (`x`, `y`, `width`, `height`), a render order other than right-down on an orthogonal or oblique map (Tiled draws the other grids right-down whatever they say, and oblique ones in their render order, measured: `render_order_warns_only_on_orthogonal_and_oblique_maps`), a top-down object layer (Tiled's default; TMX leaves `draworder` out for it) two of whose tile objects overlap in the file in the other order from their bottom edges' (`drawn_out_of_order`: elsewhere file order draws as Tiled's sort does, so Tiled's default warns only where it shows), a polyline among a tile's collision shapes; LDtk's entity tile render mode where it draws otherwise than stretched over the box (any mode but `Stretch`, unless the box is the tile's size, or `FitInside` and `Cover` with the box the tile's shape), and a parallax layer with `parallaxScaling` (LDtk zooms it). A capsule among a tile's collision shapes collides as its outline (`capsule_points`: two half circles of 8 edges), as an ellipse does (16 points) (`editor_features_drawn_otherwise_warn_once_a_file_naming_each`, `ldtk_features_drawn_otherwise_warn_once_naming_each`, `a_capsule_among_a_tile_s_collision_shapes_collides_as_its_outline`).
- The map's `parallaxoriginx` and `parallaxoriginy` (TMX attributes, TMJ fields) are `TileMap::parallax_origin`, which the drawer measures parallax from (`render/tiles.rs`, `parallax`: a layer's offset is `(1 - factor) * (camera centre - origin)` in map space, so a camera centred on the origin shows every layer unmoved, as Tiled draws it; `a_parallax_layer_is_where_it_would_be_with_the_camera_on_the_map_s_parallax_origin`). LDtk has none: zero.
- Objects: `MapObjectData::position` is always the top-left corner of the object's rectangle in map pixels and `rotation` (radians, clockwise on screen) turns it about that corner. Tiled rotates about the object's own position, which for a tile object is the tileset's `objectalignment` point (bottom-left by default), so a tile object's position is moved to where its top-left corner ends up. A map cannot look inside an external tileset while it loads, so a map with tile objects `cx.read`s the `.tsj` or `.tsx` for its `objectalignment` (`objects.rs::read_alignment`). Ids are Tiled's, as strings; object-reference properties are `PropertyValue::Object(id)`. Fields of `RawObject` an instance of a template can override are `Option`s: the instance starts as the template's object, its own fields win and properties merge by name. A template tile's gid is relative to the template's tileset, matched to the map's by resolved path (a tileset the map lacks is a load error). Templates load from `.tj` and `.tx`. The XML reader (`roxmltree`) leaves an absent attribute `None` and never defaults it, writes class members and numbers as the JSON would hold them, and bounds group nesting by `build.rs`'s `MAX_DEPTH`; its errors read `line L, column C: what`. An XML fixture's properties must be in Tiled's JSON order (alphabetical) for the twin test, which compares every `xml/` fixture with its JSON export field by field.
- The Tiled project (`project.rs`): `[tilemap] tiled_project` in Ryo.toml, `EngineBuilder::tiled_project` over it, else `project.tiled-project` at the asset root if there is one (a configured file that is missing is a load error). The loaders are registered with the path (`with_project`) after `insert_registry`'s default ones. It is read with `cx.read`, so saving it loads the maps again. `Props::read(place, raw, class)` resolves a thing's properties: written values lie over the class member's default, members it omits take the default, nested classes layer (instance over the member's default over the nested class's own), enums read by name (flags as a `List`). Tiled 1.12's list properties (`"type": "list"` with an array of `{type, propertytype, value}` items in JSON, `<item>` elements in XML, which the XML reader turns into the JSON's items) read as a `PropertyValue::List` of their items, each converted by its own type (a class item resolved against its class, an enum by name, a list item recursively, an unset color left out), and so does a class member's list default, whose items name their custom type `propertyType` as the project file names a member's (Tiled reads them so; with `propertytype` it drops the type); a written list replaces the default whole. Without the project or the class, what is written is kept (a list member of an unknown class keeps its typed items) and `engine_warn!` names the class once per file. Classes holding several members of classes multiply, so a few classes can ask for billions of values: one thing's properties may take 65,536 values to resolve, and a file's things 4,194,304 together (`Budget`), past which the load fails naming the place (`classes_fanning_out_past_the_cap_fail_naming_the_cap`); nesting, lists included, stops at 16 deep.
- Wang sets load as written (`wangid` is clockwise from the top, 0 for no color); colors and tile ids are checked.

- Spawned maps: the map entity gets a child per layer (`MapLayerRef`, the layer's `LayerInfo` as a component, a `Transform` at the layer's offset; `TileLayerData` for a tile layer, `ImageLayer` for an image layer), plus `MapIds` (objects by id) and the crate's `MapLayers` (layer entities by index). `TileLayerData` is the entity's own copy of the tiles (`tiles`, a `TileGrid`), IntGrid and grid (`grid`, the layer's `MapGrid`), with every chunk marked dirty at spawn (a new `TileGrid` has none) so the chunk renderer builds each once. Objects are children of their object layer: `MapObject` with a `Transform` at the centre of the object's rectangle (its point; a polygon's or polyline's origin, Tiled giving those no size), turned by its rotation, polygon points relative to it; a tile object keeps its `tile`, and a hidden object spawns with `visible: false` (games use hidden markers; drawing skips it). Tiles of a class the root registers are taken out of the copied grid and spawn as `MapTile` children of their layer at the cell's centre on the layer's grid (`MapGrid::cell_center`), listed by cell in the layer's `LayerTiles` (crate). The objects' entities are spawned and `MapIds` inserted before the `MapObject`s go on, so an `Add<MapObject>` observer can resolve references.
- Games name the lifecycle events (`Add`, `Insert`, `Remove`, public in `ecs/kernel.rs`), so the skill teaches three routes to an object's behaviour: an observer of `Add<MapObject>`, which runs as each object arrives (`a_game_s_observers_see_each_object_arrive_whole_and_go`: once per object, its fields filled and its references resolved, and `Remove` once per object as the map goes); `MapEvent::Spawned`; and a system over `Added<MapObject>`. The observer and the system also see the objects a reload spawns; one it updates in place fires `Insert` only. At observer time the map's layers, `MapIds`, colliders and shadows are in, and so is every object's entity, though objects later in the file lack their `MapObject` yet and class tiles come after; a body the observer puts down stands on the ground (`a_body_on_a_map_reported_ready_never_falls_through` spawns one from an `Add<MapObject>` observer), while physics queries see nothing of the map until the next step.
- Game observers run as each part arrives and may despawn the map, a layer or an object before its turn: the spawn checks each is alive (`get_entity_mut`, never `entity_mut`), skips what is gone, and stops (no `Spawned`) once the map is gone. Every child is spawned as `(Transform, ChildOf(parent))` first and its observed components inserted after (`child_of`): bevy runs `Add` observers before `ChildOf`'s insert hook, so an observer that despawned the parent of a child spawned whole would orphan it and fail the hook's queued `Children` update on the gone parent.
- **Class tiles follow whole chunks** on an unbounded layer of a map whose root registers classes: `follow_chunk_swaps` (`PreUpdate`, after `reload_maps`, so before anything collides or draws) keeps on each such layer what it last followed (`ChunksFollowed`, crate: the grid's id and version, and the chunks it had). A chunk unloaded since (one it had that the grid lacks) despawns its class tiles; a chunk loaded since (`loaded_since`) despawns the ones it had and has its tiles of a registered class taken out of the grid and spawned, as a landing's are (`loading_a_chunk_back_rebuilds_it_as_new`: a new entity). A layer with no load or unload since it last looked (`TileGrid::swapped`) costs a look and allocates nothing, so maps that never stream pay nothing more (`tests/tilemap_alloc.rs` measures an idle streamed frame). A grid it has not followed yet is noted: on a layer it never followed (one just landed) the chunks loaded whole so far are followed as loads, since a stream lands chunks in the map's own landing frame, before the follower's first look (`chunks_landing_in_the_map_s_own_landing_frame_spawn_their_class_tiles`; noted only, their class tiles stayed in the grid and drew as tiles), and on a layer whose grid a game swapped in nothing more is done. The loaded chunks are walked by row and the tiles found spawn in row order across them, as a landing's; taking them out of the grid is folded into the chunks' loads (`TileGrid::fold_into_load`), so a stream does not count it as a player's change. The table of the map's tiles of a registered class is the map's `ClassTable` (crate, on the map entity), built again only when its tilesets' stamps change, so a stream landing chunk after chunk does not rebuild it for each layer and frame; `MapRoot`'s discard takes it. Edits are not followed: they place their own class tiles. A class tile in a chunk its grid lacks is in no chunk that can unload, and stays: an edit placing one on an unbounded layer clears an absent cell, making no chunk, so a stream loads each chunk it lands into every unbounded layer (empty cells for a layer its generator filled nothing of) and refuses edits outside its resident chunks, the precondition for such a class tile to go with its chunk (`a_class_tile_edited_into_a_layer_the_generator_left_empty_goes_with_its_chunk`).
- Runtime edits place class tiles too: `set_tile`/`fill` with a tile whose class the root registers spawn a `MapTile` (the grid cell cleared) instead of writing the grid; a class tile on a cell any edit touches is despawned first (the same tile again changes nothing). A plain `fill` takes the class tiles in its region through `LayerTiles` and fills the grid in one go; a class-tile `fill` goes cell by cell. `tile()` reads the grid, so a cell holding a class tile reads `None`. `MapObject::reference` reads `PropertyValue::Object(id)`, treats Tiled's unset `"0"` (and an empty id) as none, and checks the entity is alive (no bookkeeping system: a despawned object just stops resolving).
- A map waits while its asset (or, for a map built in code, a tileset asset it names) loads; one despawned meanwhile (a scene's `SceneCleanup::WORLD`) or no longer a `MapRoot` is not in the query and spawns nothing; a disabled one waits until enabled. A failure is reported once per `Arc<AssetError>` (the registry shares one per failure), and a missing LDtk level once per project version; a failed map whose file is saved fixed spawns. `MapRoot`'s `on_discard` hook takes down a spawned map's layers (and `MapIds`, `MapLayers`, `MapApplied`, the reported failure, its stream's `StreamState` and its `ClassTable`, and despawns the entities its chunks owned, `ChunkOwned`) when the root is replaced or removed, so a new root spawns, and streams, afresh.
- `MapsView` finds layers through `MapLayers` (by index, or the first by name), returns `None`/`false`/0 for a map not spawned, a missing layer, a non-tile layer or a cell outside, and marks `TileLayerData` changed only when an edit changed a cell. World/cell conversions take a layer (the grid is per layer) and walk the `Transform`s of the layer and its ancestors as they are now, not `GlobalTransform`, so a map moved this frame converts before propagation; `world_to_cell` gives cells outside the layer too, and `None` for a layer scaled to nothing.
- `ldtk/`: LDtk 1.5.x projects (`.ldtk`) as `LdtkProject` assets, one `LdtkLevel` per level with its `TileMap`. `raw.rs` holds what a file says (LDtk's JSON names), `build.rs` the conversion and the checks (reusing `tiled::build`'s `fail`, `join`, `load_dep`, `check_tileset`, `check_used_ids`), `mod.rs` the types and `LdtkLoader`. A newer `jsonVersion` than 1.5 is a load error naming both versions; older loads. Tilesets are shared: `LdtkProject::tilesets` in definition order, each level's map embeds them all (a tile's `tileset` is the definition's index). A tileset with no `relPath` (LDtk's built-in icons) is a `Collection` with nothing to draw. Its per-tile data reads as Tiled's tile classes and properties (`tile_data`): a tile's enum tags (`enumTags`, in the tag enum's order) give it its class, the first of them, and a bool property `true` a tag; its `customData` is the string property `custom_data`; a tag or data on a tile past the tileset's count fails naming the tileset (`tile_enum_tags_and_custom_data_read_as_class_and_properties`). `.ldtkl` levels are read with `cx.read` (saving one loads the project again); paths join the project's folder.
- LDtk levels: `layerInstances` list the top layer first, so layers are reversed (layer 0 draws first). `LayerKind::Tiles::grid` is a layer's grid: the map's `grid()` for Tiled and for `add_tile_layer`, for LDtk an orthogonal one of the layer's own `__gridSize`, whose grid, int grid and cell counts follow it (`__cWid` and `__cHei` must match the level's pixels over the grid). The map's `tile_size` and `size` come from the bottom tile layer; a level with only entity layers uses `defaultGridSize`. Tiles whose cell is outside the level (auto-tiles of stamps reach past the edge) are dropped. **Stacked, offset and translucent tiles split a layer** (`plan_tiles`): LDtk saves a layer's tiles in display order (the first beneath the next), several in a cell where rules or stamps stack them, at a pixel offset into their cell where a rule moves them, and with an alpha `a` where a rule fades them (1.4 on). Each distinct (stack depth in the cell, offset in the cell, alpha) is a sub-layer (`SubKey`), part of its layer: the layer's own (depth 0, on the grid, opaque; always there, holding the IntGrid and `collides`), then its sub-layers by depth and, within a depth, as LDtk first lists them, each a tile layer named after the layer with `#1`, `#2`..., `LayerInfo::part_of` the layer's uid, its `offset` its tiles' offset and its `opacity` their alpha (both its own, over the layer's), `collides` and `occludes` false, no IntGrid. They are listed after the editor's layers (`build_map`), so `MapLayerRef::index`, and the z of every layer (`root z + index`), stay LDtk's order whatever stacking a save adds (`a_later_layer_keeps_its_place_whatever_stacking_a_save_adds`). The drawer draws a sub-layer as part of its layer (`render/tiles.rs`: the layer found among `MapLayers` by id, so a disabled or gone one takes it along): that layer's `visible`, `y_sorted`, `lit`, parallax, blend, tint, `RenderLayers`, z and interpolated transform, its own offset and opacity over them, its draws tying on the layer's entity just after the layer's own, so a y-sorted layer's stacked rows sort with a character as the layer's do (`a_y_sorted_ldtk_layer_s_stacked_tiles_sort_with_a_character_as_one_layer`, `hiding_an_ldtk_layer_or_keeping_it_from_a_camera_takes_its_stacked_tiles_too`). A game sets a flag on the layer alone. Edits by the layer (`edit::set_tile`, `fill`, and Wang painting through them) clear the cells they touch in its sub-layers (`parts_of`, `clear_parts`; `an_edit_by_name_on_a_split_ldtk_layer_replaces_the_whole_cell`), and `tile` reads the layer's own tiles; a game editing `TileLayerData::tiles` by hand edits the layer's own tiles only. Its `LayerInfo::id` is a hash of the layer's uid and its key with the top bit set (`sub_layer_id`, probed past a clash within the level), so a reload matches it to the sub-layer of the same tiles wherever a save moves it (`a_sub_layer_keeps_its_id_when_a_save_adds_another_before_it`). Past 16 a layer (`MAX_SUBLAYERS`: each is a level-sized grid and a draw a chunk, so 16 bounds a layer at 16 times a plain one's cells, a 1024 x 1024 layer's at 64 MiB) the keys holding the most tiles are kept and every other tile goes to the kept sub-layer whose cell is free and whose offset, then depth, then alpha are nearest, warned once per layer with the count. The sub-layers' cells count toward the level's cap. Measured on LDtk 1.5.3's bundled samples (read by hand, not committed: their art is third-party): every tile of every level now draws (WorldMap_Free_layout, with its `.aseprite` tileset swapped for a blank PNG, kept all 11,684 where 5,069 were lost; Typical_TopDown_example all 2,798, its 240 translucent and 150 offset tiles at their alpha and place), with up to 43 sub-layers a project, and the cap snaps at most 28 tiles of a layer (AutoLayers_6_OptionalRules' rule-heavy IntGrid layer, 44 keys) to a nearest sub-layer (`stacked_offset_and_translucent_tiles_load_as_sub_layers`, and the GPU test `an_ldtk_level_s_stacked_offset_and_translucent_tiles_draw_as_ldtk_shows_them` over `stacked.ldtk`). IntGrid layers hold their auto-tiles as `tiles` and `collides` is true, every other layer's is false. Parallax is `1 - parallaxFactor`. Entity `position` is the top-left (`px` less pivot times size), rotation 0, `class` and `name` the entity identifier, `id` the iid. Field values by `__type`: Point is a `Class` "Point" with `cx` and `cy`, Tile a `Class` "Tile" with `tileset` (identifier), `x`, `y`, `w`, `h`, EntityRef `Object(iid)`, enums `Enum { ty, value }`, arrays `List`; an unset field (null value, or an unset reference) is left out, and null items of an array are skipped. Worlds: a single-world project has one `WorldLayout` named "World" and levels whose `world` is `None`; with multi-worlds each world has its name. A `Neighbour::level` indexes the same world's `WorldLayout::levels`. Linear layouts (`LinearHorizontal`, `LinearVertical`) write no positions, so levels follow one another from the origin, each after the last one's width (or height) plus LDtk's own spacing of 48 px (`World.reorganizeWorld` in LDtk's source; the JSON docs only say "one after the other"). Parallax `1 - factor` is what LDtk's editor shows (it shifts a layer by camera times factor); `parallaxScaling` has no counterpart and warns (above). - **Worlds** (`world.rs`, `tiled/world_file.rs`). `TileWorld` is a Tiled `.world` file: `layout: WorldLayout` plus a `Handle<TileMap>` per level (dependencies, so the world is ready when its maps are; a map that fails fails the world, naming it). An LDtk world is a `WorldLayout` of the project, named by `WorldRef::Ldtk { project, world }`. Tiled neighbours are computed from the rectangles (`direction`): touching along an edge is a cardinal, at a corner a diagonal, overlapping `Overlap`; levels are named by their `fileName` as written. Every listed map is read through `cx.read` (so a save of it reloads the world too), its header only (`map_rect`): its grid is built from the raw fields as its load builds it (`grid_shape`, `MapGrid::for_map`), never by loading the map. **Every map is placed by its tile origin** (the spec's reading: Tiled documents none for infinite or non-orthogonal maps, and its `tiled.loadWorld` returns nothing headless, re-checked with Tiled 1.12.2, so it could not be measured): the world's `x`, `y` are where its pixel (0, 0) sits, `WorldLevel::origin` (cell (0, 0)'s corner, or a bounded isometric map's box's top-left), and its rectangle (`position`, `size`, what neighbours and `levels_in` use) is `grid.bounds_of` its cells from there: a bounded map's every cell (its listed size if it has one), an infinite map's tiles' bounds, whatever `width` and `height` the entry gives (`a_world_places_isometric_and_infinite_hex_levels_by_their_grid_bounds`, over `worlds/shape.world`) (Tiled writes them for every listed map, so with a listed size the rectangle started at the origin and missed the map's negative part: `an_infinite_map_listed_with_a_size_takes_its_tiles_rectangle`). The bounds come from `tiled::build::infinite_bounds`, which counts the map's cells against the caps, then checks, decodes and places its chunks as its load does (`chunked_grid`, shared with the load) and takes their rectangle with `tiles_bounds`, the function `TileMap::bounds()` uses, so the two cannot disagree (`a_world_places_an_infinite_map_by_its_tile_origin`). An infinite map with no tile gets its origin cell as its rectangle, so it can still spawn (`an_empty_infinite_map_in_a_world_takes_its_origin_cell`). A bounded map's `origin` is its `position` unless an oblique skew is negative (its box reaches left or up of its (0, 0)), LDtk's always; `spawn_levels_in` puts each root at its level's `origin`. A bounded map listed with a `width` and `height` takes that size from its box's top-left. Patterns (a pattern's maps are placed as listed ones without a size): the registry cannot list a folder (the web has none), so a pattern is supported only as literal text (escaped punctuation allowed, optional `^`/`$`) with up to two `(\d+)`/`(-?\d+)` numbers; anything else is a load error naming the pattern and "not supported" (a bare `.` is a literal dot, as names are built, never matched; `.*` fails on the `*`; only an unescaped trailing `$` anchors). Placement uses checked i32 arithmetic: a multiplier or offset that overflows fails the load naming the `.world` and the pattern. A probe reads each map (its rectangle as a listed map's without a size), and the map then loads again as a dependency. Names are built by filling the numbers (one is x, two are x then y) and probed with `cx.read`: row by row from y = 0, x from 0 to the first missing file, stopping at the first row whose x = 0 file is missing, at most 1,024 probes. Maps sit at `(x * multiplierX + offsetX, y * multiplierY + offsetY)`. Numbers are written plainly (`to_string`), so zero-padded names (`room_01_02.tmx`) are never built (a literal `0` before a group reaches 00 to 09 only), and numbering from 1 finds nothing, as do negative indices and the maps past a gap (`a_pattern_finds_numbers_from_zero_written_plainly`); a pattern that finds no file fails the load; a world that needs more lists its maps. No regex crate on purpose.
- `MapRoot::world_level` / `ldtk_world_level` make a root with `MapSource::WorldLevel`, which stands for no map until its world loads: `resolve_world_levels` (first thing in `spawn_maps`) swaps the source for `MapSource::Map` or `MapSource::Ldtk`, so every other map system sees only those two (`root_map` reads `None` for an unresolved one). A level the world lacks, or a world that failed, fails the root once per world version. `MapsView::spawn_levels_in(world, area)` spawns a root, a `WorldLevelOf { world, level }` and a `Transform` at the level's position for each level at world depth 0 overlapping the area (`WorldLayout::levels_in(area, depth)`: touching an edge is not overlapping) that has no `WorldLevelOf` for the same world on any entity, disabled ones included (`Allow<Disabled>`: a game parks a level by disabling its root; looked up with the default filter, a parked level spawned again on top of itself), and returns only those entities; a despawned level spawns again. `spawn_levels_in_with(world, area, depth, configure)` streams the given depth and passes each bare root, with its `WorldLevel`, through the game's `configure` before it spawns; the source is put back afterwards, so only the root's settings are the game's and the map stays the level's. `WorldLevel::depth` (and `LdtkLevel::depth`) is LDtk's `worldDepth`, 0 for a Tiled world: streaming one depth keeps a floor above or below from stacking onto the one played (`an_ldtk_world_streams_one_depth_at_a_time`, over `worlds.ldtk`, whose `Upper` lies on depth 1 over `C`). Nothing spawns until the world's asset is loaded. Streaming (when to spawn and despawn) is the game's call. **Hot reload:** each spawned level is an ordinary map root, so saving its map reloads it; saving a `.world` reloads the `TileWorld` (and a level whose map file is read for its size), spawned levels stay where they are, and the next `spawn_levels_in` uses the new layout. Moving or respawning spawned levels on a world save is not done. `WorldLevelOf.level` is an index into the layout at spawn time, so a `.world` save that reorders levels can make `spawn_levels_in`'s dedupe mismatch until the game respawns its levels.
