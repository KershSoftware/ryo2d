# AGENTS.md - Render Pipeline

The engine draws every frame through one `RenderPipeline` (a resource, `RenderPipeline::default_2d()`): `Engine::present_frame` (`engine/extract.rs`) builds a `FrameScene` and `WgpuRenderer::render_frame` runs the enabled passes on **one command encoder with one submit**: the camera passes (`PassScope::Camera`) once per camera in render order, each on that camera's image in `Rgba16Float` linear light, then the frame passes (`PassScope::Frame`) once: `cameras -> hdr_effects -> tonemap -> transition -> post_process -> ui -> composite -> capture`. Games reach it with `ctx.render_pipeline()` (a `Mut<RenderPipeline>`): toggle built-in passes or insert their own. The pipeline belongs to the engine, so a scene's changes persist across scene transitions.

## Default Order (`default_2d`)

| # | Id (`pass_ids`) | Scope | Runs when (`should_run`) | Draws |
|---|-----------------|-------|--------------------------|-------|
| 1 | `CLEAR` | camera | always | clears the camera's image per `CameraClear` (transparent for `None`) |
| 2 | `WORLD` | camera | the draw list has lit items | the camera's lit draws from the batch: entities, `Scene::render` sprites, the engine's particles, parallax, trails, lines and debug shapes, one z-sorted list |
| 3 | `LIGHTING` | camera | lighting is on | the camera's lights and shadows, composed into the lit image (straight-in camera) or back into its own image |
| 4 | `UNLIT_WORLD` | camera | always (returns early with no unlit draws) | the camera's unlit draws (anything `with_lighting(false)`, and debug shapes), by z |
| 5 | `CAMERAS` | frame | always | window cameras' own images into their viewports, in order; clears the scene image first when no camera drew straight into it |
| 6 | `HDR_EFFECTS` | frame | HDR effects are active | bloom, god rays, ambient occlusion and HDR custom effects on the scene image (linear light, may exceed 1) |
| 7 | `TONEMAP` | frame | always | the look: writes the display image (the display stage's buffer A) from the latest scene image; the transition, `post_process` and the composite work on the display image |
| 8 | `TRANSITION` | frame | a transition fade is visible | scene transition fade over the whole frame (not the UI) |
| 9 | `POST_PROCESS` | frame | display effects are active | fade, tint, vignette, flash, CRT, chromatic aberration and display custom effects on the display image |
| 10 | `UI` | frame | the UI recorded something and the UI image was not kept | clears the UI image (`UI_FORMAT`) and draws the UI renderer's frame into it: one pipeline, one draw per texture run (usually one); a UI whose commands are all culled draws nothing but still clears it |
| 11 | `COMPOSITE` | frame | always | to the window or offscreen target through `ScreenMapping` (bars for fit and pixel art), UI blended last in sRGB space |
| 12 | `CAPTURE` | frame | a capture was requested | frame capture readback copy |

## Images and Formats

- **`SCENE_FORMAT`** (`render/mod.rs`, `Rgba16Float`): linear light, premultiplied by alpha, values may exceed 1. The game texture, the lit image, camera images, render-target textures, the lighting pass's scene copy (for a camera lit in place) and the HDR stage's ping-pong pair all use it. Nothing on the CPU writes f16 texels: render passes fill these images.
- **The display image** is buffer A of the display effect stage, `Rgba8UnormSrgb`; the `tonemap` pass writes it and `post_process` ping-pongs it with buffer B. Unchanged formats: atlas and standalone sprite pages (`Rgba8Unorm`, raw sRGB bytes), the surface, the offscreen target and the capture readback.
- **The UI image** (the compositor's, `UI_FORMAT` = `Rgba8Unorm`) holds gamma-encoded colour premultiplied by alpha. Its size is `UiSpace::image` (`render/ui.rs`): the render size, or the window's screen rectangle with `UiResolution::Window` in pixel-art mode. The composite shader (`fullscreen_quad.wgsl`) encodes the frame to sRGB, blends `ui + frame * (1 - ui.a)` and decodes, so UI alpha behaves as on the web.
- `FrameImage` (`frame.rs`) names the latest image: `Game`, `Lit`, `Camera(entity)`, `Hdr(buffer)` (the HDR stage) and `Display(buffer)` (the display stage).
- `RenderContext::format()` is the format of `current_view()`: `Rgba16Float` in camera passes and in frame passes before `tonemap`, `Rgba8UnormSrgb` after it. A game pass builds its pipelines for `ctx.format()`.
- Two `PostProcessPipeline`s (`EffectStages`: `hdr` and `display`) are built, one per format; each effect runs in the stage `PostProcessEffect::stage()` gives (`EffectStage`, `shaders/AGENTS.md`).

## The Look

- `Look` (`look.rs`, resource, `ctx.look()`) holds exposure, the `Tonemap` curve, `ColorGrading` and optional `AutoExposure`. The `tonemap` pass (`passes/tonemap.rs`, `tonemap.wgsl`) applies, in order: exposure (`exposure + auto EV`), white balance (temperature, tint), contrast and saturation, the curve, lift/gamma/gain on the display colour, then sRGB encoding and the LUT.
- **`Tonemap::apply` in `look.rs` mirrors `tonemap.wgsl`: change them together.** `every_curve_on_the_gpu_matches_tonemap_apply` (`tests/e2e/look.rs`) pins them.
- **The LUT** is a 3D texture (`LutTexture`, `passes/tonemap.rs`) uploaded from the strip image's pixels. It follows the image's version, so a reload uploads it again; a version that is not a strip keeps the last good one (warned once, naming the image by its path), and so does an image that is not loaded. Lookups are in sRGB.
- **Auto-exposure** (`exposure.rs`, `exposure.wgsl`): two compute dispatches each frame, one filling a luminance histogram from the scene image and one reducing it (trimmed mean) into a stored EV that moves toward its target at the configured speeds. The tonemap pass binds that stored EV; with auto-exposure off it adds nothing, and turning it off and on again restarts it at its target. The dispatches run inside the tonemap pass, on the scene image it is about to read.

## Lights in the Batch

- `DrawList::lights_for(camera)` gives the lights on the camera's layers whose box meets its view. Lights are batch quads (`lighting/batch.rs`) laid into each lit camera's draws by `Batch2D::prepare`.
- Per lit camera the `lighting` pass replays one `LightStep::Add` draw of all its lights (`Batch2D::draw_lights`), additive into the light buffer's colour (`light_blend`; alpha untouched), the light pipeline binding the camera (group 0) and the shadow atlas (group 1, `batch::shadow_layout`, the atlas's own bind group). Each light reads its own shadow from the atlas, which the frame drew before the first camera pass, or kept from an earlier frame with the same plan (lighting module notes), so one light's shadow never touches another's light, with no mask, stencil or second target: only core WebGPU.

## Cameras in the Frame

- `plan_cameras` (`frame.rs`) orders the cameras: texture cameras, then window cameras, each by `order` (ties by entity). The first window camera draws straight into the scene image when its viewport is `Viewport::FULL` and it clears; every other window camera draws into an image of its own (`CameraImages`, `graphics/camera_images.rs`), sized to its viewport in render pixels (`PixelRect::of_viewport`, edges rounded so viewports that meet share them). A texture camera draws straight into its render target when its viewport covers it, otherwise into an image of its own that `leave_camera` places in its rectangle of the target (premultiplied blending, like the `cameras` pass); one whose target is missing is left out (warned once).
- Each `CameraDraw` carries the view, layers, clear, target, image rectangle and whether it is lit. `RenderContext::enter_camera` points `current_view()` at the camera's image (`FrameImage::Camera`) for its passes; `leave_camera` goes back to the scene image, which a straight-in camera may have left lit.
- Per-camera GPU state: a uniform buffer per camera (`CameraUniforms`: `view_proj`, image size, game and real time, snap), its bind group in the batch and in lighting, camera images and light targets. All of it follows the planned cameras each frame, so a despawned camera's state goes with it.

## Building the Frame (`present_frame`)

Everything is read from the world by query, every frame. There is no render cache: nothing is invalidated, and an entity draws where its `GlobalTransform` says on the frame it exists. Drawables are gathered once, in world space, and sorted once; each camera keeps what it sees. Tile chunks are the one exception: their instances are kept, built again only when their tiles or look change (The 2D Batch, Tile chunks), while where they draw is read every frame.

1. `Scene::render(gpu)` for the visible scenes, bottom-up (`GpuRenderContext`: `gpu.batch`, `gpu.camera()` = the main camera's view, read-only `gpu.world`); the `BatchCollector` keeps submission order.
2. Lights (`(&GlobalTransform, &Light2D)` with their `RenderLayers`, at their world translation; batch quads in the draw list when lighting is on); `LightingSettings` is copied into the lighting renderer. In a lit frame the lighting renderer plans the shadowed lights the lit cameras see and their casting edges (`LightingRenderer::plan_shadows`, reading occluders from the occluder index: no frame gathers them all), then the lights join the draw list, each carrying its atlas slot, and `render_frame` draws the maps into the shadow atlas in the frame's encoder before the first pass, only when a light has a slot and the plan's edges differ from those the atlas holds (internal work, not a pass of the pipeline; lighting module notes).
3. Render targets' textures follow `RenderTargets`; the cameras are planned and their light targets synced (their uniforms and bind groups are synced with the UI camera's, step 7).
4. The `Scene::render` sprites join the draw list, then the engine's particles (`particles::ParticleDrawer`: one run item per emitter whose box a camera on its layers sees; particle module notes); each `ParallaxLayer` is laid out for every camera on its layers (items for that camera alone).
5. The layers of spawned maps (`TileDrawer::collect`, `tiles.rs`): each image layer joins the list as one quad per view, its image repeating across it (a sprite item, `SpriteShading::Repeat`); the visible chunks of tile layers (those whose tiles or look changed built into the batch's chunk store first), the rows of y-sorted ones and tile objects are gathered as `OrderedDraw`s, sorted as entities are. Then `EntityDrawer::collect` (`entities.rs`): one query over the visible renderables (with their `RenderLayers`), each pushed in draw order with the gathered map draws merged in at their places, then the composite tiles. Quads no camera on their layers can see are skipped before their texture uploads. Disabled entities are skipped by the queries themselves. A mesh an entity draws (a skeleton's mesh attachment, skinned as the drawer reaches the skeleton) goes into the batch's mesh stream there and then, an item at its place among its entity's draws (The 2D Batch, Meshes). Then world text (`text.rs`): the `Text2d`s whose text, style, options or fonts changed are laid out again (`layout_world_text`, which syncs the engine's `TextEngine` with `Fonts`), the glyphs `Fonts::prewarm` asked for are built, and each camera that sees a block gets its glyph quads (`emit_world_text`: glyph items for that camera alone, raster glyphs at the size it sees; bitmap cells and inline icons are sprite items). Positions are interpolated like entities', and lifted on a floor (Placement). `TextEngine::end_frame` runs after `Batch2D::prepare`.
6. Trails (`&Trail2D`: world-space points) and lines (`(&GlobalTransform, &Line2D)`: at the entity's translation) join the batch's line stream as their points, one item each (the GPU builds their triangles), unless no camera sees them. That stream and the mesh stream are cleared with the draw list, before anything is gathered, since the list's triangle and mesh items are ranges of them. The entity drawer alone writes the mesh stream; trails, then lines, then each camera's debug shapes write the line stream. The debug overlays are added to `DebugDraw`, whose shapes are built for each camera in its own screen pixels (items for that camera alone).
7. The UI: unless the UI image is kept ("UI render retention"), the UI renderer (`render::ui_renderer`) builds the frame's `UiCommands` (recorded by `Scene::ui` before the fixed steps) into instances of its own, in painter's order (layer, then the order recorded), culling what draws nothing and copying the unchanged fragment runs it kept; texts are laid out through a scratch draw list, never the frame's. When the UI recorded anything, the UI camera's uniforms (`UI_CAMERA`, snapped on the pixel-art target) join the world cameras'. The UI camera is not one of the batch's cameras and not in `FrameScene::cameras`, so no camera pass runs for it.
8. The list is sorted; `Batch2D::prepare` makes the frame's textures resident (the UI's sprite textures with them), lays each camera's lit and unlit items (on its layers, inside its `CameraView::bounds`, not showing its own target, `only_camera`), and a lit camera's lights (`DrawList::lights_for`), into draws and uploads the instances, the line stream and the meshes once; the UI renderer then finishes its frame (its sprites placed in their atlas slots, its texture runs, the upload of what changed with its scroll slots), and the pipeline runs. `present_frame` clears the frame's debug shapes afterwards, drawn or skipped.

`FrameScene.time` (lighting, trails, the transition) is real elapsed time; post-process effects run on `EffectsManager`'s own clock, advanced with real time in `PostUpdateSet::Extract`. Only `CameraGlobals::game_time` (sprite effects, custom sprite shaders) is game time.

## The 2D Batch (`batch/`)

One batch draws the world: sprites, shadows, tiles, composite parts, particles, `Scene::render` sprites, parallax tiles, world text, meshes, trails, lines and debug shapes.

- **Two streams**, each uploaded once per frame into a buffer that doubles when a frame needs more: instanced quads (the 128-byte `SpriteInstance`, remapped into its atlas slot) and the line stream (`LineStream`, `lines.rs`): each line's filtered points (`LinePoint`, 24 bytes: place, half width, `u`, sRGB colour and its line), its entry in the line table (`LineInfo`, 80 bytes: params, the slot a textured line repeats, emission, a two-point capped line's half length, first point, count, join, cap, closed, edge and miter limit) and an index buffer of 32-bit vertex codes (each its piece's point, the piece's kind and one of the piece's fixed slots, three a triangle). The table, the points and two arrays the corner pass writes each frame (each point's 64-byte corner record and its limits, `batch/corners.rs`) are four storage buffers the line pipelines bind as group 2 (the untextured one's group 1 left empty; the table is read by the fragment stage too), their bind group and the corner pass's made again only when one grows, and each never past what one storage binding of the device holds, the index buffer past what one buffer does (`StreamCap`, `LineStream::for_device`: a line past it draws nothing, warned once). Lines have no vertex buffer: a line draw is an indexed `draw_indexed` over its `3 × triangles` indices, and the vertex stage builds each vertex from its code (`shaders/include/line_pieces.wgsl`), so a piece's triangles share its vertices in the GPU's vertex reuse, items merge as index ranges did and z-order holds. Meshes have a stream of their own, built and uploaded the same way (`MeshVertex`, 16 bytes: position and uv, with indices), and draw with one of the quad instances each (Meshes, below).
- **Keys and planning** (`key.rs`, `plan.rs`): every item resolves to a `DrawState` (page, `BatchShader`, `BlendMode`, `Sampling`). Per camera, `plan_draws` merges consecutive items with equal states (and, for triangles, adjacent index ranges) into `Draw`s; each camera's quads have a range of the instance buffer of their own, its lit and unlit draws in one range.
- **Pipelines** (`pipelines.rs`) are made on first use per `PipelineKey` (`BatchShader`, `BlendMode`, `Stream`, page kind, `Sampling` and format; `PipelineKey::new` keeps the draw's sampling for the tile shaders, `Tile` and `TileObject`, whose smooth draws have entries of their own, and makes it `Sampling::Linear` for every other, so no other pipeline is made twice), but the tile chunks' for a plain layer (`Tile`, the default blend, an sRGB page, the presentation's default sampling), which the batch makes when it is built: made on first use it cost the frame the first map landed in about 0.85 ms; a custom sprite shader gets one per blend mode it is drawn with, and one more key for each stream it is drawn on (a mesh's is another first-use pipeline: quads and meshes are checked apart, so a mesh may draw plain for the frames its own check takes after the quads have turned), checked without blocking (`Checked`), and draws plain until its check passes. A new version of a custom shader already drawn is made on the shader thread for every key its old source has, while the old one draws, and taken in at the start of a frame (`Batch2D::sync_shaders`; shaders module notes). Every batch shader writes colour premultiplied by alpha, so each `BlendMode` is one fixed blend state (`blend_state`); `Premultiplied` picks the shader entries that take a texture's colour as it is.
- **Bind groups are made with their resource:** one per camera (its uniform buffer) and one per texture page and sampler (made with the page); none per frame. Every bind group goes through `graphics::bind_groups::create`, which counts them in tests (`steady_frames_create_no_bind_groups`, and a guard test that fails on any other `create_bind_group`); passes that bind frame resources look them up in a `BindGroupCache` keyed by the resources themselves, cleared when those are recreated.
- **A pass sets only what changed.** `Batch2D::draw` takes the render pass's `Bound` (one per pass: the world, unlit world and light passes start each with nothing bound) and skips the scissor, the pipeline, each bind group at its dynamic offset and the quad or triangle buffers that the draw before left as this one needs them; a new pipeline sets every group again, since one of another layout may leave them unusable. Keeping the groups across pipelines that share a layout (a quad's and a mesh's do) was measured and left out: wgpu itself drops a bind-group set that repeats the last one at its index as it records, so the repeats cost a call and a compare each, about 0.012 µs a mesh drawn between two runs of quads (`docs/backlog/skeleton.md`, Meshes). So a run of a layer's chunk draws, which shares its pipeline, camera, page and tile slot, sets only its instances: wgpu checks and records every command, and the repeated ones cost the 1024 x 1024 map's 1080p frame about 7 µs (59 chunk draws).
- **Runs** (`DrawPayload::Run`, `DrawRun`): an emitter's particles, one item sorted as a sprite (`DrawKind::Sprite`, `push_run`), or a stretch of a skeleton's regions of one image and blend with no mesh between them, one item sorted as an entity in the order the entity drawer pushes it (`DrawKind::Entity`, `push_run_as`); either is culled per camera by its layers and world box. Its world-space instances wait in the list's `run_instances` (cleared with the list, so they keep their room); `prepare` finds its texture's slot once, places each instance with `place_in_slot` (growing for built-in effects when its shading is `Effect`) and reports `Placed::Quads`, which `plan_draws` numbers and merges with the quads around it as single quads. `prepare_textures` makes the runs' textures resident after the sprites'.
- **Lines** (`lines.rs`, `shaders/include/line_pieces.wgsl`, `line_cover.wgsl`; design `docs/specs/2026-11-16-line-anti-aliasing-design.md`). Trails and lines are polylines with miter, bevel or round joins (each corner one wedge, fanned from the corner point, so nothing is covered twice) and butt, square or round caps.
  - **Built on the GPU, piece by piece.** The CPU only filters and copies the points (`filter_points`) and writes the vertex codes from the piece list and each kind's template, which depend only on where a point sits in its line (`piece_list`, `piece_template`), all in `lines.rs`. Each kind has fixed slots its triangles name (a segment 6, a miter join 10, each half of its point with a tip of its own, a bevel join 7 of the miter's, naming each place it repeats by one slot, `a_bevel_join_names_each_of_its_places_once`, a round join 15, a square cap 4, a round cap 10; a miter's or bevel's triangles after the middle of its point start with a vertex measuring their own second edge, which their flat attributes come from), and what a slot holds follows the GPU's decision at its corner (miter or bevel, the inner side shared or split), used alike by every triangle naming it (`every_slot_builds_its_role_under_every_decision`; the UI asks the GPU for the same layout, `the_slot_layouts_agree`); a right turn's triangles wind the other way to the reference's, which no culled face shows. Each corner is worked out once a frame, before the first camera pass and after the upload, by one compute dispatch a thread a point (`batch/corners.rs`, `core/line_corners.wgsl`; the frame's encoder runs it after the shadow atlas, and skips it with no lines; past 65,535 workgroups its threads go on in rows, `the_corner_pass_goes_on_in_rows_past_its_width`): the one corner function (`lp_joint`) writes the point's corner record and its limits, and a vertex reads its own record and its neighbours' two limits instead of working out three corners. A stream of fewer than `CORNER_PASS_FROM` points (16,384) skips the pass, and its vertices work their corners out in place as the UI's do (`lp_corner_here`), told by the stream's uniform, which holds the point count and whether the pass ran, written only when the count changes; they build the same vertices bit for bit (`a_small_stream_skips_the_corner_pass`, `vertices_working_their_corners_out_in_place_equal_the_corner_pass_s`, and the count draw draws both ways). Through the batch itself, frame after frame (over the threshold, no lines, under it, a stream that grows the buffers and remakes the bind groups, no lines), the uniform is written so, the pass runs or is skipped and nothing is drawn with no lines, each frame the harness's pixels (`lines_drawn_through_the_batch_cross_the_corner_pass_s_threshold_frame_to_frame`). The vertex stage builds each vertex from its piece's window of the points and that corner: a segment, a join or a cap, self-contained, in a fixed triangle order. It indexes the window by constants only, and a closed line's neighbours wrap by one step round (a modulo cost a sixth of the GPU's time): copying an array to index it by a variable put it in memory, and indexing by constants, in the step that also worked a round join's `acos` out only for round joins, halved the GPU's time (`docs/backlog/lines.md`). The vertex position is `@invariant` and every position is made by one expression from the one record of its corner, so copies of a place agree bit for bit; the WGSL makes and tests no infinity or NaN. A vertex hands its fragments only what varies (its colour, `uv`, distances, flags with its line's style and edge, `k`, its line's number); a fragment reads its line's entry only for a textured line's slot and a two-point line's half length between its caps (`each_line_s_fragments_read_its_own_entry_in_the_line_table`).
  - **The reference.** `polyline.rs` is the CPU builder, compiled for tests alone (with `coverage.rs`, the coverage model it is measured by). The GPU's vertices equal it triangle for triangle, each triangle's first vertex (which flat attributes come from) the same and its other two as a pair (`the_gpu_builds_the_reference_s_vertices`, through a test-only compute entry, `cs_line_dump` in `core/line_test.wgsl`, reading the index buffer's codes after the corner pass, composed with `fs_count` and `cs_slot_dump` into `compose::LINE_TEST` for tests alone; its copies of a place agree bit for bit in place, push, limit and what effects move them by, as the reference's do). The tests draw lines through one entry that uploads a stream, encodes the corner pass and draws it (`LineGpuTest`, `line_gpu_tests.rs`), and drawn with each fragment counted, every pixel is covered as its pushed mesh covers it, never twice but at a split corner's inner overlap (`a_translucent_line_drawn_on_the_gpu_counts_every_pixel_once`; both in `batch/line_gpu_tests.rs`). The rules of the pieces, their tests and the figures are in `polyline.rs`'s module docs.
  - **What a vertex carries**, in the line's units: its signed distance across from the centre line of its triangle's straight piece and the half width there, a second edge's distance where its triangle lies against two edges, a round piece's offset from its corner point, flags, `k`, and a push direction with its rates and limit.
  - **Anti-aliased by coverage, with no derivative.** The vertex stage pushes each vertex one pixel of the camera's image out (the fringe; `CameraGlobals::px_per_unit`, the image's pixels per world unit: `pixels_per_unit`, `the_fringe_is_one_pixel_of_the_image_drawn`) as far as its limit lets it, and the fragment covers each pixel by its distances in pixels: a one-pixel box filter across the strip, a second edge blended by `k`, a round piece's offset length. Drawn into an image of the UI's format and read back as alpha (`batch/line_cover_tests.rs`): straight lines of widths 0.25 to 6 pixels, every 7.5 degrees, at 16 sub-pixel places, give every pixel the model's coverage within 2/255 (`straight_lines_cover_each_pixel_as_the_model_does`); every join, cap and closed corner is within 0.12 of the line's exact area, but in the recorded inner-corner and split-corner zones (`every_pixel_is_within_0_12_of_the_line_s_exact_area`); a half-pixel line draws at half coverage and its summed coverage stays within 2% as it moves by sixteenths of a pixel (`a_half_pixel_line_draws_at_half_coverage_wherever_it_lies`); a translucent corner is no darker than its segments (`a_translucent_corner_is_no_darker_than_its_segments`).
  - **Styles.** Coverage multiplies the straight alpha of every style. Soft and Glow shape by the pixel's true distance over the half width, not by `uv.y`, the shape averaged over the part of the pixel's box the line covers and blended toward its mean (Soft's alpha 0.85, Glow's 0.345 and its brightness 0.475) as the half width falls from 3 pixels to 1 (`soft_and_glow_shape_by_the_distance_over_the_half_width`); a Soft or Glow line under half a pixel in half width covers the pixels one of half a pixel would, its alpha times the ratio of the widths.
  - **Thin lines stay whole as they move:** level, each column's summed alpha never empty and steady within 5% over sixteenth-pixel moves, at half widths 0.25 to 1.5; at 30 degrees within the strip model's own spread for a Solid line of the width covered, 23% at a quarter pixel of half width, 12% at half a pixel and 6% at one (the model's one-pixel box across a slanted line; Soft and Glow, covering at least half a pixel, keep to 12%) (`thin_lines_stay_whole_and_steady_wherever_they_lie`).
  - **Effects and textures.** A displaced line (Lightning, Noise, Ribbon) keeps each column's summed alpha across it, the fringe moving with its vertices (`a_displaced_line_keeps_its_coverage_across_it`). A textured line's `uv.y` runs on over the fringe as the distance does, along a segment and in a round join or cap, so the fringe does not squeeze the texture (`a_textured_line_s_texture_runs_on_across_the_fringe`); its mip level still comes from the uv's derivatives.
  - **Culling.** A line's box grows by `MITER_LIMIT` times its widest half width and its effect's reach, and each camera grows it by one of its pixels (`a_miter_tip_reaching_into_view_is_drawn`). A line no camera sees (by every camera's view and layers, and the one camera a debug shape is for) is not copied into the stream at all, so it costs no upload and no GPU work (`a_line_no_camera_sees_is_not_copied`).
  - **Edges, Smooth or Hard** (`LineEdge`; the line table's `edge`, `edge_code`; `line_hard` and `line_hard_cover` in `line_cover.wgsl`). A line without an edge takes its camera's target's: Hard where the camera's `snap` is set, Smooth elsewhere. The snap is set on the pixel-art target, and on a texture camera in a pixel-art game, which takes the presentation's snap as it does for sprites, so its lines are Hard by default too (intended). A Hard line draws a pixel whole when its centre lies inside it, and not at all otherwise. Across, the distance is taken along the image's axis nearest the line's normal (the distance over the normal's component on that axis, `line_axis`) and the half width, at least half a pixel, is not, so the band is `2 hw` tall along the axis and a line of a pixel is one pixel in each column (each row past 45 degrees), with no gap or double at any angle or sub-pixel place (`a_hard_line_is_one_pixel_per_column_at_any_angle`); one of 2 or 3 pixels is 2 or 3 a column, one narrower than a pixel one (`a_hard_line_is_its_width_in_pixels_per_column`). The band is half-open, `[-hw, hw)` along the axis, signed down or right in the image and moved up by 1/64 of a pixel, so a centre on its edge, as lines on whole and half pixels put them, falls inside above and outside below however the interpolation rounds. A Hard line's vertex is put on a 1/256 pixel grid, which the rasteriser's fixed-point grid holds exactly, and its distance across moves with it (`line_on_grid`, `line_moved`): left to the rasteriser, a vertex moves by up to 1/512 of a pixel while its distances stay, and two triangles meeting in a column disagreed about centres that near an edge (15 columns doubled or empty in about 33,000). Each segment is so drawn its half width times its normal's component on the axis across, its own factor, and the corners follow the segments' drawn edges. A miter's point is two halves, each measuring across its own segment with a tip of its own, its second edge the other segment's band's outer side taken along that segment's axis (`LINE_SECOND_NARROWED`, the edge's normal riding in the vertex as `second_normal`), so the halves meet where the two drawn edges do and a tip narrows evenly to its point: mitered and bevelled Vs 1 to 4 pixels wide, turning 20 to 150 degrees at fractional headings, are one run a row toward the tip, each no wider than the row before and touching it, and a miter's rows past both elbows are exactly the pixels inside both drawn edges (`a_hard_miter_tip_narrows_evenly_to_its_point`). A bevel's middle is likewise two vertices, each half measured across its own segment; its own edge, and a cap's, take the centre inside them with no axis. A round piece takes the centre within its segments' drawn half width of its corner point: its offset over their axis factor, the one before's at the arc's start to the one after's at its end, a cap's its segment's (`line_round_axis`), so in the same Vs it draws no pixel past the wider segment's drawn half width and every one within the narrower's (`a_hard_round_piece_keeps_to_its_segments_drawn_width`; drawn with the plain radius, 1,351 pixels stood past it, up to 1.89 pixels from the point, on the caps of lines at a slant). On a pixel-art target every pixel of every join and cap is whole or empty by default, and a Smooth line's are partly covered; elsewhere the reverse (`a_line_on_a_pixel_art_target_draws_whole_pixels_unless_smooth`). Soft and Glow keep their shape across a Hard line, shaped as a Smooth line of its drawn half width is; only the coverage is whole. `Line2D`, `Trail2D` and the debug pen carry the edge to the line table (`a_line_s_or_trail_s_edge_reaches_its_line_table_entry`, `a_pen_sets_its_edge_and_shapes_take_their_target_s_otherwise`).
  - **Limits** (their figures and tests in `polyline.rs`'s module docs): the inner corner (off the exact area by up to 0.16 at a 60 degree turn, 0.26 at 90, 0.34 at 120, 0.39 at 150 and 0.45 at 165); a split corner (0.09, 0.15, 0.22, 0.32 and 0.37 at those turns); a tapered line can fold when pushed at extreme tapers; a displaced piece is sheared, so it draws narrower across a steep slant (98% on average and 91% at the steepest piece of a moderate Lightning or Ribbon, 62% and 34% for a Ribbon as steep as the trails demo's); a miter's tip can reach a little past its box, so a coverage sliver under 0.1 can be culled at the view's edge (`lines.rs`); a vertex code is its point's place shifted by 7 bits (`vertex_code`), so a stream past 131,071 points draws with index values past 2^24, which Vulkan holds only on a device with full 32-bit index values (`fullDrawIndexUint32`, wgpu's `DownlevelFlags::FULL_DRAW_INDEX_UINT32`): desktop drivers and WebGPU have them, some older mobile Vulkan devices do not, and nothing checks the flag or caps the stream for them.
  - **Limits of Hard lines.** Two segments at a corner are drawn at their own widths, so a miter's tip lies where their drawn edges meet, off the bisector. Where the narrower one's drawn edge passes inside the other's outer corner (the segment before tilted from its axis toward the turn, both in one octant), that corner stands past the edge by at most `hw sin a sin t` (a the segment's tilt, t the turn), under 0.3 of a pixel at 4 pixels wide, and is drawn as its segment's quad has it; the sweep finds no row it makes uneven. A bevel's own edge runs through the segments' outer corners at the plain half width, outside their drawn edges, so it cuts a Hard bevel only where it crosses their bands (moving the middle onto each half's own segment changed one pixel in 1,728 bevelled Vs). Near a corner a Hard line can differ by a pixel from one drawn in pixel art: a corner point's vertex has no normal, so its distance does not move with it onto the grid (up to 1/512 of a pixel off), and a straight-on corner's shared vertex measures across the corner's normal while its segments' far ends measure across their own, so the distance over the axis is not quite affine there. The 1/256 pixel snap assumes a rasteriser with 8 bits below the pixel (D3D12, and common Vulkan and Metal devices); on a Vulkan device with 4 it does no harm, but no longer stops the doubled or empty columns. Two Hard butt-capped lines meeting at a pixel centre both draw it (each cap takes the centre inside it), so translucent lines show a darker pixel there.
  - **The UI's lines** are built by the same piece functions and covered by the same fringe and coverage functions (`shaders/include/line_cover.wgsl`), from points their instances carry, their corners worked out in place in the vertex stage (The UI Renderer, Lines).
  - **Speed** against main (`benches/lines.rs`, CPU and GPU time, the corner pass counted in the GPU's, a frame missing a stamp left out; `docs/backlog/lines.md`, the last round's final run): the CPU's render step is 55% to 80% under main's and its upload 70% to 83% under (the index buffer of vertex codes, 12 bytes a triangle, is most of what goes up). Against the GPU bound (1.15 times main): met on 10,000 mitered lines (0.63), 10,000 round lines (0.60) and 1,000 round lines (1.10); missed on 1,000 mitered lines (1.34) and the mixed thousand (1.27), each a few tens of microseconds, as each vertex still loads its window of points and builds its place; main's own 10,000-line figures in that sitting were well above the sitting before's. 100,000 lines, which main cannot draw, take 5.1 ms (round 5.5). Measured split, the cost is the vertex stage: drawn to one pixel the time hardly falls, and a vertex stage left only the position (its fragment writing a constant) takes six tenths of it. These figures were measured before a miter join and a bevel join took one more vertex each (ten and seven), for their Hard halves.
- **Meshes** (`mesh.rs`, `shaders/core/mesh.wgsl`): an entity's own triangles of an image, drawn as a sprite of that image is, through the sprite shader's own stages. A skeleton's mesh attachments are what draws them: skinned on the CPU as the entity drawer reaches the skeleton, one mesh an item among the skeleton's runs (skeleton module notes, Drawing, Meshes).
  - **One instance a mesh, and a vertex that is only a place and a UV.** A mesh is a `DrawMesh` (`DrawPayload::Mesh`): a range of the batch's mesh stream (`MeshStream`: `MeshVertex`es, each a world position and a UV across the mesh's rectangle of its image, and indices), and one `SpriteInstance` carrying what a sprite's carries for every vertex of it: that rectangle as `uv_rect`, the tint, the effect lanes and the emission (its transform is not read). `vs_mesh` fills the sprite's own `VertexOutput` from the two, so the fragment stage is the one a quad shaded the same way takes: `fs_base`, `fs_effect`, their premultiplied and linear forms, or a game's sprite shader (shader module notes, Meshes).
  - **Built-in effects and a game's shader reach it.** The mesh's `SpriteShading` is the one a sprite would have: plain, a built-in effect, or a game's shader, its parameters packed into the instance and drawn plain until its pipeline is accepted, as a sprite is (`a_mesh_under_an_effect_in_place_draws_as_the_sprite_under_it`: flash, colour shift, silhouette, grayscale, invert, pixelate, wave and dissolve, each equal to the sprite's pixels; `a_game_s_sprite_shader_draws_a_mesh_as_it_draws_the_sprite`, inline and as a `Material`, with parameters and its place in the sprite).
  - **Limit: an effect that grows its sprite's quad cannot grow a mesh.** Under an outline, a glow or a directional outline (`effect_padding` above 0) a mesh draws plain, and the log is told once a run, naming the entity whose mesh it first was (`an_effect_that_grows_a_quad_leaves_a_mesh_plain_and_warns_once`; on a skeleton, whose regions take the effect, `an_effect_that_grows_a_quad_reaches_the_regions_and_leaves_the_mesh_plain` in `tests/e2e/skeleton_mesh.rs`). A sprite's quad is enlarged to hold what such an effect draws round it; a mesh has its own shape.
  - **An item of the entity kind.** `DrawList::push_mesh` pushes it as `DrawKind::Entity`: it sorts by submission among the entities' sprites and runs, where a trail or line follows every entity at its z (`a_mesh_item_sorts_between_two_entities_at_one_z`, `a_mesh_takes_its_place_among_the_entities`). It is lit or not by the flag it is pushed with, as any item (`a_lit_mesh_item_is_lit_and_an_unlit_one_is_not`).
  - **A draw of its own.** `plan_draws` never merges a mesh with a neighbour, since its instance is its alone: `Placed::Mesh` becomes a `Draw` on `Stream::Meshes` whose source names the instance (`a_mesh_is_a_draw_of_its_own_with_the_next_quad_s_instance`), and consecutive meshes keep their order and their own effects (`two_meshes_with_different_effects_draw_in_order_each_with_its_own`). The pass binds the mesh stream's buffers for it and the quads' or the triangles' again after it (`a_mesh_draws_among_trails_and_lines`). What that costs is measured in `benches/skeleton.rs` and recorded in `docs/backlog/skeleton.md` (Meshes): about 1.6 µs of the render step for a mesh between two runs of quads, 0.65 of it in the pass, where the two pipeline changes are the part a shared pipeline would save.
  - **The drawer's way in** is `Emitter::draw_mesh` (`entities.rs`), called inside `EntityDrawer::collect` where the mesh belongs in its entity's draws (for a skeleton by `Emitter::draw_skinned`, from the walk of its parts, `draw_parts`, which ends the run of quads before the mesh; and once more for its drop shadow, the vertices moved by the shadow's cast): a `MeshLook` (the image, the rectangle of it the UVs run across in texels, the blend, the tint as a sprite instance's, and the entity's `RunLook`: effect, game shader and emission), then the vertices (a world position and a UV across the rectangle) and the indices (three a triangle, counted from the mesh's own first vertex), both read once, straight into the stream (`MeshStream::add`), which keeps its room from frame to frame. The entity's filter, layers and lit flag are the emitter's, as for its sprites. The rectangle becomes UVs by `rect_uv`, the function a skeleton's region quad uses, so a mesh of a rectangle reads the texels a region of it does (`a_mesh_of_a_rectangle_draws_as_a_region_quad_of_it`).
  - **What draws nothing.** A mesh with no triangle, with indices that are not whole triangles or reach past its vertices, or with a position that is not finite adds nothing (`a_mesh_that_draws_nothing_leaves_the_stream_as_it_was`); nor does one with no alpha (`a_mesh_with_no_alpha_is_not_pushed`). A triangle of no area is kept and covers no pixel (`a_zero_area_triangle_draws_nothing`). A mesh whose image is not loaded draws nothing in a release build, and the checker over the whole mesh, whatever its rectangle, in a debug build (`an_unloaded_image_s_mesh_is_the_whole_checker_in_debug_and_nothing_in_release`).
  - **Culled by its vertices' box.** A mesh no camera on its entity's layers can see is taken back out of the stream (`MeshStream::drop_last`, which takes only the last mesh added), not pushed, and its image never uploaded (`a_mesh_no_camera_sees_is_not_pushed_or_uploaded`); each camera then keeps the items whose box meets its view.
  - **Placed in `prepare`**, as a sprite is: for each camera that sees it, its instance goes through `place_in_slot` into that camera's range of the instance buffer (never grown), so the list's own instance is left as it was and placing is the same for every camera, each drawing a mesh with the instance in its own range (`each_camera_draws_the_meshes_it_sees_with_their_own_instances`). Its pipeline's key is a quad's but for the stream, the page kind included, so an image on a page of its own, or a render target's page, takes the stages a sprite there takes. Its texture is made resident with the sprites' and the runs'.
  - **The sprite's look**, exactly: a two-triangle mesh of an image draws the pixels a sprite of that image draws, opaque or soft-edged, tinted, half-transparent, mirrored (its triangles wound the other way: no face is culled), premultiplied, additive, multiplying, screening, emissive, sampled nearest or smoothly, from the atlas or a page of its own, however the quad is cut (`a_two_triangle_mesh_draws_as_the_sprite_of_its_image`).
  - **Never snapped.** The pixel-art snap is a quad's (`quad_corner`); a mesh's vertices draw where they are given. On whole pixels the two agree, which is where the tests above compare them on the pixel-art target.
  - **A UV outside the mesh's rectangle reads nothing**: not another region of a packed image, and not the image's neighbours on the page, `place_in_slot` clipping the bounds to the slot (`a_mesh_uv_outside_its_region_reads_no_neighbour`).
- **Glyph items.** Glyphs are `DrawPayload::Glyph`, already placed in their glyph page (the instance carries the atlas UVs) and drawn by `TextMask`, `TextColor` or `TextMsdf`. Their instance lanes, which the UI renderer's glyph quads keep (its rects, untextured with an analytic rounded rect and border, take the last row's):

  | Shader | `tint` | `effect_params` | `effect_extra` |
  |---|---|---|---|
  | `TextMask` | glyph colour (sRGB, straight alpha) | unused | unused |
  | `TextColor` | multiplier (white keeps the glyph's colours) | unused | unused |
  | `TextMsdf` | fill colour, or the soft layer's colour | `[mode (0 fill/outline, 1 soft), width or spread (base px), softness (base px), range (base px)]` | outline colour |
  | UI rect (its quad extends one pixel in UI units past the rect on every side, and `uv_rect` extends by the same fraction past `[0, 1]`, so the outer edge keeps its anti-aliasing) | fill colour | `[corner radius, border width, width, height]` (UI units) | border colour |

  The text emitter (`render/text.rs`) draws an MSDF outline as a quad of its own (mode 0, a transparent fill, the outline colour's alpha times the glyph's) in the outline pass, and the fill (mode 0, width 0) in the fill pass, so no glyph's outline covers a neighbour's fill. Glow and shadows are mode 1 quads in the shadow pass.

- **Tile chunks** (`chunks.rs`, `render/tiles.rs`, `shaders/core/tile.wgsl`; spec `docs/specs/2026-10-29-tilemap-design.md`). The batch's one retained source. Each tileset's tiles of a 32x32-cell chunk of a tile layer (`ChunkKey`: layer entity, signed chunk (`IVec2`, as `TileGrid::chunk_of` gives it), tileset) are instances in one arena (`ChunkStore`: a CPU copy, first-fit free ranges, the end cut off as it frees), built by `chunk_instances` in the layer's own pixels with UVs over the tileset's padded image, and built again only when the grid's `chunk_version` or the layer's look stamp (tint, opacity, the layer's `MapGrid`: shape, cell size and origin, the tilesets' padded `serial`s) differs from what it was built from; the store keeps its own last-seen versions (grid versions never repeat, across grids too, so a swapped grid rebuilds), never `drain_dirty`. `ChunkBuffers::upload` in `prepare` writes only the ranges built since the last write (touching ones joined), the whole arena into a new buffer once it outgrows the old (doubling), and lets the buffer go once nothing is built. The arena is capped at the device's `max_buffer_size` over the 128-byte instance (`Cap`, `ChunkStore::for_device`: 2,097,152 instances, 256 MiB, under the `Limits::default()` the engine asks for), the CPU copy too (its `Vec` never reserves past it): past it `create_buffer` fails validation and the game dies with a GPU fault (a 1024 x 1024 four-layer map seen whole at zoom 0.12 at 1080p would ask for 512 MiB). A chunk that would take the arena past its cap frees the chunks drawn least recently, never one drawn this frame (its draws are made: `evict_oldest`, from a list made once a frame); when that is not enough the chunk is refused, draws nothing that frame, and is not built again from the same stamp until the arena has room for the instances it made (`Built::refused`, so a view too wide does not build its refused chunks every frame); the log warns once (`a_view_past_the_chunk_arena_s_cap_draws_what_fits_and_warns_once`, a cap injected with `ChunkStore::set_cap`). The chunks a view meets first (row by row) are the ones drawn. There is no per-frame build budget: one would leave holes in the view while it caught up on a zoom-out, and would have to tell a landing (which must draw whole) from a zoom; the cap bounds the worst frame. The stamp includes whether the layer is y-sorted, since a y-sorted build splits its rows at each instance that sorts alone (`Planted`'s last part). `ChunkStore::chunk` copies a chunk's parts (and a y-sorted layer's rows) into the drawer's buffers rather than lending them, so the drawn-unchanged path is one map lookup. A chunk is freed when its layer entity loses its `TileLayerData` (despawned: within the frame) or after 120 frames undrawn (`KEEP_FRAMES`), a chunk unloaded from a streamed layer among them: the view visits only the chunks a layer has, so it draws no more at once, and is freed as any undrawn chunk is (`an_unloaded_chunk_draws_nothing_and_the_store_lets_it_go`, `testing/gpu_world.rs`). Each draw binds a tile slot (group 2, a uniform at a dynamic offset of 256 bytes per slot, written each frame only when the slots changed; the bind group made with the buffer): the layer's interpolated world transform (axes and origin; on a floor above the ground lifted by its floor's height, `MapFloors::lift`, in the layer's pixels, as `affine *= Affine2::from_translation(lift)` beside an LDtk sub-layer's offset: the layer stands in ground space, `tilemap/AGENTS.md`, `floors.rs`), the camera's parallax offset (from the map's `TileMap::parallax_origin`), and the padded image's place on its page (`textures.slot`, UV offset and scale), so moving the map or camera, or the atlas moving the image, changes no instance. A slot is one per (view, tileset), a view being one layer for every camera, or for each camera when the layer has parallax (`only_camera` items). Chunk items are `DrawPayload::Chunk` at `MapRoot`'s z plus the layer index (`tilemap::layer_z`; on a map with floors a y-sorted layer's at the first y-sorted layer's, `tilemap::y_sort_z`, Draw Order), `DrawKind::Entity`, lit per `LayerInfo::lit`, on the layer entity's own `RenderLayers` if it has them, else the map's, culled per camera by their world box; `plan_draws` makes each a draw of its own (`DrawSource::Chunk`), never merged. A `DrawChunk` draws its key's instances from `first`, `count` of them: all of a part, one row, or a run. Each tile stands where the layer's grid places it (`MapGrid::tile_anchor`, the bottom-left of its cell's box, then the tileset's offset; `tilemap/AGENTS.md`), so an orthogonal grid's instances are as before, bit for bit; on a hexagonal grid the diagonal bit and the 120 degree bit turn the quad clockwise by 60 and 120 degrees about its own middle, where it stands unturned (the tileset's offset included), after its flips, which mirror its texels (Tiled's order and pivot, measured: `shape-hex-turns-*`), and the quad's axes are a general 2x2 (`TileFlip::quad_turn`, in `tilemap/tile.rs`, which collision turns a hexagonal tile's shapes by too; the square grids' diagonal flip is the swap). A chunk's instances are built in Tiled's paint order (`MapGrid::paint_key`: rows, a row's unshifted cells before its shifted ones on axis-X staggered and hexagonal grids, diagonals on isometric ones), then split by tileset stably, so a tileset's part is in paint order and each paint band of cells (the key's first two parts: the row, or the diagonal, and the phase) is a run of it (`ChunkRun`, its band and first column recorded with its box at build; a chunk's `rows` are each tileset's bands, band by band). A y-sorted layer (`LayerInfo::y_sorted`) draws each of a chunk's `rows` (a tileset's cells of one sort band, `MapGrid::sort_band`: a row, an isometric diagonal, or half a row of an axis-X staggered or hexagonal grid) as an item of its own, sorted at the band's sort point, `band_y`, taken to the world at the layer's left end (x 0 in its pixels) through the layer's transform before its floor's lift (`LayerDraw::ground`: where the row stands, so a floor's lift moves its drawing and not its place among the characters), so every chunk of a band sorts alike, the parallax offset included: the row's bottom edge on an orthogonal grid, the band's cells' centre on the others. A cell sorts as an item of its own (the build splits its band there, `Planted`'s last part) at its own centre on an oblique grid whose `skew.y` isn't 0 (`sorts_per_cell`), and wherever its tile's `sort_offset` moves it, which adds to its sort point (Draw Order). **A plain layer whose tiles leave their cells draws in Tiled's order** across tilesets and chunks. A tileset whose widest and tallest tile, at its offset, flipped diagonally or on a hexagonal grid turned, could leave its cell's box (`may_spill`; an isometric grid of odd sizes always, as pixel art moves its tiles up to a pixel) makes the layer build its chunks knowing how their tiles leave their cells' boxes (each outline's bounding box: `Spill::None`, `Vertical` past the top or bottom only, `Sideways` past a side), and a chunk with a sideways tile keeps its instances' paint order as runs of one tileset (`runs`, each where its first instance is in its part). Such a layer's view gathers its chunks (`Gathered`, lists kept so a warm frame allocates nothing: each chunk's parts, and once the path is known the runs of only the chunks it draws run by run, from `ChunkStore::runs`, since copying every chunk's bands each frame cost a 1080p view of an isometric map about 10 µs) and draws them as few draws as keep Tiled's order (`View::draw_gathered`): while no tile leaves its cell's box, as any plain layer's; while tiles leave only tops and bottoms on a grid whose chunks drawn row by row paint every overlapping pair in order (orthogonal, isometric, oblique skewed down its columns alone: `chunks_keep_order`), chunk by chunk in that order, a chunk of one tileset as one draw, else its rows band by band; otherwise every chunk's runs of each band, sorted by band and first column (a chunk's cells of a band are columns next to each other, which no other chunk's are), each run a draw, one following the last draw in its part joining it. A band's cells' boxes lie side by side, so tiles that leave only tops and bottoms never overlap within a band. A layer whose tiles fit their cells draws as before: per chunk, per tileset. Art that fills a cell's box but not its outline (a rectangle in an isometric cell) overlaps its neighbours without leaving the box, so it draws chunk by chunk, tileset by tileset (`docs/backlog/tilemap.md`, Limits). The costs: a layer of tall art of one tileset draws as one of art that fits (orthogonal and isometric); tiles leaving their cells' sides, or tall ones on staggered and hexagonal grids, draw a run a band a chunk (measured at 1080p, 32 x 16 isometric cells, 48 x 48 art: about 4,000 draws a frame for four layers, against 96 that fit). Chunk and row items take their places among the entities' (Draw Order): `TileDrawer` gathers them before the entities are drawn as `OrderedDraw`s (an order, the layer entity ties go by, the payload), and `EntityDrawer::collect` pushes each before the first entity that sorts after it, so they get their sequence from the entity order itself. Extraction only visits the chunks a camera's view (in layer pixels through the transform the layer draws by, its floor's lift included, so a lifted chunk is culled where it draws, `a_lifted_chunk_is_not_culled_while_its_drawing_shows`; widened by the largest padded cell) can reach: `MapGrid::chunks_over` gives the signed chunks of the cells the box may meet, a superset on every grid but the orthogonal (on an isometric or staggered grid the index rectangle over a screen box is a diamond of about twice the chunks), so each chunk's box is tested against the widened box (touching counts, as flooring a box's ends does) before it is built, from `MapGrid::chunk_boxes` (chunk (0, 0)'s box and the steps to the next chunk's, once a view), since working each box out from its cells cost a 1080p view of an isometric map about 8 µs a frame; within the chunks the layer reaches (its extent's: a bounded layer's every chunk, visited whether it holds tiles or not, as before; an unbounded layer's span, of which only the chunks it has are visited, found by walking the view's chunks or the layer's, whichever are fewer: `TileGrid::chunks_within`), so a frame costs what is on screen, and no chunk an unbounded layer lacks enters the store (`an_unbounded_layer_draws_tiles_at_negative_cells_and_culls_by_signed_chunk`, e2e, reading the store through `HeadlessEngine::tile_chunks`). `vs_tile` places corners through the slot, snaps the slot's origin (map and parallax together) to a whole pixel on the pixel-art target under an unturned camera, so every tile corner lands on one at whole zooms (a quad's own snap skips the turned quads of diagonal flips), and steps an animated tile's UVs to its frame on `game_time`. Every grid but one places tiles on whole pixels; an isometric grid of odd sizes places them on half pixels (half a cell's steps), and pixel art draws them where Tiled's raster does instead: each instance carries the offset from its anchor to Tiled's rounding of it (on an odd cell width x up, but a pixel further right where it is whole for tiles of a tileset whose tile size is wider or taller than the cell is wide; on an odd cell height y one pixel lower where it is whole: `MapGrid::raster_offset`, from the tileset's tile size kept in its `PaddedLayout`, in `transform1.zw`; measured: `measured-raster.json`), which `vs_tile` adds on the pixel-art target, so every corner is on a whole pixel and the texels sample at their centres (`half_pixel_steps_draw_without_seams_in_pixel_art`; a resolution-independent target draws them at the exact point). Sampled nearest (the pixel-art target, or a layer whose `LayerInfo::filter` is `Filter::Nearest`, Tiled's layer property `filter` = `nearest`), tiles draw through the sprite's fragment entries (`fs_base` and its variants), whose nearest sampler keeps the full-size level; sampled smoothly (the smooth target, or a layer whose filter is `Filter::Linear`, `filter` = `linear`, on any target; a layer's tile objects take its filter too, an image layer never does), through the tile fragment stages (`fs_tile`, `fs_tile_premultiplied`, `fs_tile_linear` in `sprite.wgsl`, over `sample_cell` in `shaders/include/sample.wgsl`; `built_in`, `nearest_tile_draws_keep_the_sprite_fragment_stages`): the level from the UV's derivatives (isotropic, log2 of the longer in the page's texels), snapped to a whole level within a thousandth (so zooms of 1, 1/2 and 1/4 read one level), capped at the tile's clean levels (`PaddedCell::levels`, in the instance's `transform2.z`, which `vs_tile` hands on as `effect_params.x`), then each of the two levels round it read at its own explicit level (`textureSampleLevel`), kept half a texel of that level inside the tile's padded cell (`uv_bounds`), and the two blended; transparent outside the cell. The cells are whole texels of every level up to that cap (tilemap module notes, `padded.rs`), so no read reaches the next cell, and the finer level's outer texels stay exact, where one trilinear read kept inside for the coarser level blurred the ring of a 16 px tile zoomed to 0.75 to half and half (`a_tile_zoomed_out_a_little_keeps_its_outer_texels_sharp`). At zoom 1 and above the level is 0 and the one read is the old one's, half a texel inside the cell. Never snap per quad: at a fractional zoom each tile rounding its own corner and size leaves pixel gaps (`testing/tile_bleeding.rs`, `no_seams_at_any_zoom_or_subpixel_camera`, fails at zoom 0.33 with 16 px tiles). Without the origin snap no tile leaves its pixels, but the texels slide under them as the camera moves by fractions of a pixel (`a_sub_pixel_camera_draws_tiles_as_at_the_whole_pixel_they_round_to`, zoom 4/3). Pipelines draw both faces: a diagonal flip turns a quad over.
- **Image layers and tile objects** (`render/tiles.rs`). An image layer (`ImageLayer` on the layer entity, whose `Transform` holds the offset, less its floor's height on a floor above the ground, which the drawer adds back as it does a tile layer's) draws as one quad over the copies of its image a view needs (`SpriteShading::Repeat`, `BatchShader::Repeat`: `vs_repeat` and `fs_repeat` in `tile.wgsl`), `DrawKind::Sprite` at the layer's z (so after the entities there), tinted and faded by the layer, with its blend and lit flag: the image once, or repeated along the axes the editor says over a camera's view. The quad's UVs count copies and the image wraps along both axes (half a texel inside its place on the page, the level picked from the unwrapped derivatives); the layer's origin rides in the transform lanes' unused z, and on the pixel-art target the quad moves as that origin's snap to a whole pixel does, never rounded itself, so the copies are whole multiples of the image from the snapped origin, as a tile layer's tiles are, with no gap between two at any zoom (`a_repeated_image_layer_shows_no_gaps_at_fractional_zoom`). One quad for every camera when it neither repeats nor has parallax, else one per camera, moved by its parallax offset (from the map's `TileMap::parallax_origin`, as a tile layer's). An LDtk sub-layer (`LayerInfo::part_of`) draws as part of its layer, found among the map's layers by id: that layer's visibility, flags, parallax, blend, tint, `RenderLayers`, z and transform, its own offset and opacity over them, its draws tying on the layer's entity after the layer's own (`LayerDraw::ties`), so a y-sorted layer's stacked rows sort with entities as the layer's do. A layer with a transparent colour (`ImageLayer::transparent`) draws from a copy of its picture with that colour clear (`keyed_image`, made once per version of the picture and kept 120 frames past its last draw). A view needing more than 65,536 copies along an axis (`MAX_REPEATS`; fewer for an image over 8 px, whose quad spans at most 524,288 of its texels so its UVs keep a sixteenth of a texel) gets that many about its centre, and the layer is warned about once: an 8 px image covers a 4K view at the smallest zoom. A tile object (a visible `MapObject` with a `tile`, child of a visible object layer) is an `OrderedDraw` sprite from the tileset's padded image at the object's interpolated transform (on a floor above the ground moved by its floor's height in the world, `LayerStyle::lift`: the layer's transform takes the height there), sized to the object, with the tile's flips, an animated tile's frame for the game time chosen on the CPU, the layer's look; plain at the layer's z, or by its bottom edge where it stands (before the lift) on a y-sorted layer. It is shaded as a chunk's tile is (`SpriteShading::TileObject`, `BatchShader::TileObject`: `vs_main` and the sprite's layout, with the tile fragment stages when sampled smoothly and the sprite's when nearest): its instance's `uv_bounds` is its cell, mapped through the image's atlas slot in `prepare` (where a sprite's are its own texels), and its first effect lane the cell's clean levels. A disabled map draws neither.
- **Whole-image draws.** The batch never clips: `draw` takes the image size and sets the scissor to all of it.
- **Format.** The batch draws in the format it is built with, `SCENE_FORMAT` for the world. Built in `UI_FORMAT` (only tests do, chiefly to prove UI lines against the world's line pipeline), its pipelines gamma-encode through the `UI_GAMMA` override and `ui_out` in `color.wgsl`, as the UI pipeline does.
- **Debug draw** (`render/debug_draw.rs`): `DebugDraw` keeps world-space shapes in a fixed-step list (cleared when the next step begins) and a frame list (cleared after the frame); each camera builds them as polylines in its own screen pixels. An odd width's points are moved onto pixel centres (but a circle's) and its open ends drawn square, half a pixel past them, so its pixels are whole, as lines cover pixels by their area (`a_debug_line_is_one_pixel_wide_when_zoomed_out`, `the_overlay_draws_its_marks_at_the_target_and_the_tip`). A point is moved to the middle of the pixel it lies in, and one on a pixel's edge (a whole coordinate) to the pixel above it or to its left, as the rasteriser's top-left rule places sprites and a Hard line's band, so a debug line and a `Line2D` along one whole coordinate draw the same row (`a_debug_line_on_pixel_art_breaks_ties_as_a_line_does`); a rectangle's corners move inward instead, keeping its outline inside it.

## The UI Renderer (`ui_renderer/`)

The UI has a renderer of its own, apart from the world's batch: the UI needs painter's order, clips and a few textures; the world needs cameras, layers and lights. It turns the frame's `UiCommands` into instances and draws them through one pipeline (design: `docs/specs/2026-10-20-ui-renderer-design.md`; scroll slots and fragment runs: `docs/specs/2026-10-21-ui-fragments-design.md`).

- **One instance, seven kinds** (`instance.rs`). `UiInstance` is 144 bytes: eight `vec4` lanes, then the clip, the kind and the flags (the sampler, whether its clip is its own, its scroll slot in bits 8 to 15) and glyph page as four integers. A quad's lanes are a `SpriteInstance` cast as it is (transform rows, uv rect, tint, effect lanes, uv bounds), so its corners come from the function the sprite shader places its quads with (`quad_corner`, `shaders/include/quad.wgsl`), pixel-art snap included. The kinds (`UiKind`, `ui.wgsl`'s `KIND_` constants): rect, raster glyph, colour glyph, MSDF glyph, sprite, linear sprite (a render-target page, linear and premultiplied) and line. A line is two instances a piece (Lines, below), each two triangles of it.
- **One pipeline** (`gpu.rs`, `shaders/core/ui.wgsl`). `vs_ui` places a quad with `quad_corner`, as `sprite.wgsl`'s `vs_main` does, or for a line runs `line.wgsl`'s solid path (no displacement, no snap), in both cases moved by its scroll slot's offset first (Scroll slots, below). `fs_ui` switches on the kind and runs the world entry's body: `ui_rect`, `glyph_mask`, `glyph_color`, `glyph_msdf`, `finish` (sprite), `finish_linear` (render-target sprite) and `styled` (line). Those bodies are include functions the world shaders call too (`src/core/shaders/AGENTS.md`), written once, so the UI cannot drift from them. Every derivative is taken before the switch, where control flow is uniform, and texture reads use `textureSampleGrad`, as WGSL's uniformity rules require inside the switch; glyph pages have one mip level, so that samples as `textureSample` did. The output goes through `ui_out` with `UI_GAMMA` set, premultiplied-alpha blended. Group 0 is the UI camera's, group 1 the textures, group 2 the scroll slots.
- **Clipping in the shader.** An instance in slot 0 carries its clip in whole UI-image pixels (`ClipRect`: `scissor_of`'s rect, or the whole image). One in a scroll slot draws under the slot's clip, read from the slot (the instance carries the whole image, so neither its instances nor its text's cache key change as a nested slot's clip moves), or, with a clip of its own (a text field's view in a scrolled list, `FLAG_OWN_CLIP`), under that clip relative to the slot, moved by the slot's whole-pixel offset and met with the slot's (`clip_in_slot`, `ClipRect::in_slot` on the CPU). The fragment's centre (`@builtin(position).xy`, at k + 0.5) must lie in `[x0, x1) x [y0, y1)`, tested last, after all derivative-taking code; outside it the shader outputs zero, which the premultiplied blend leaves as the image was. With integer bounds that is exactly the scissor test, and clips no longer break draws: per-draw scissors and pipelines made the settings screen 64 draws, and it is now one.
- **Scroll slots** (`SlotUniform`, `slot_uniforms`). The shader reads the frame's slot table, at most 256 slots (`SLOTS`, slot 0 among them, which moves nothing): each slot's offset in UI units, the same offset in whole pixels (to move an instance's own clip exactly) and its clip in image pixels. They live in the instance buffer past the instances (`slots_at(n)`, aligned to 256 bytes, WebGPU's largest minimum uniform offset alignment), bound in group 2 as a uniform array with a dynamic offset, so they need no buffer of their own and go up with the instances (Uploading what changed); 8 KiB, within WebGPU's default uniform limits, and no new feature. The vertex stage adds the slot's offset to an instance's corners before the camera and the pixel-art snap (`quad_corner`'s `by`), so content placed relative to its slot moves by whole pixels exactly and its instances stay the same while it scrolls. Draws in slots past 256, and a draw whose own clip does not fit a `ClipRect` relative to its slot, are built absolute: moved and clipped on the CPU (`UiDraw::placement`). So is every draw in a slot on the pixel-art target, where only slot 0 is written: there a quad's corners are rounded to whole target pixels, and a corner on a half pixel rounds by the last bit of its position, which moving it on the CPU and moving it in the shader compute differently.
- **Vertex-stage culling.** `vs_ui` collapses a quad, or a line instance whose points' box grown by its reach (Lines, below) lies wholly outside its clip, moved where its slot draws it, to one point outside the image (`outside_clip`, `COLLAPSED`): a fragment run built unculled (below) then costs no fill for what its slot does not show. It removes only primitives that cover no pixel centre inside their clip, and the fragment stage's clip test stays the exact scissor test, so no pixel changes.
- **Texture slots and runs** (`runs.rs`). The texture bind group (group 1) holds four slots, the mask, colour and MSDF glyph pages and a sprite page (an atlas page, a standalone image or a render target), and the atlas's linear and nearest samplers; a slot no instance needs holds a 1x1 placeholder. An instance picks its slot by kind and its sampler by a flag. `plan_runs` ends a texture run only when an instance needs a different texture in a slot the run already filled; the next run starts with that texture alone (carrying the others over could only add breaks). Each texture run is one draw: the settings screen, every page of the `ui` demo and breakout draw in one. Bind groups are cached by the textures and samplers they hold (wgpu handles compare by identity, so a recreated texture is a new key). A group holds its textures alive, so it goes once the UI stops needing it: unused for 8 frames whose UI was drawn (`KEEP_FRAMES`; a frame all of whose commands are culled counts), at once when a frame keeps the UI image and the image was drawn without it, and with every other group (and the runs) when a frame's UI records nothing. A title screen's background is not held through a scene with no UI or a still HUD; making a group again takes about 1 µs. Four sampled textures and two samplers fit WebGPU's default limits.
- **The frame.** (1) `UiRenderer::build`, unless the UI image is kept: `build_ui` walks the commands in painter's order (layer, then the order recorded; at one order a line after the rest, as the batch drew them; sorted only when one is out of place), culls, and builds the instances, the texture each needs and the sprite textures to make resident. A fragment's run is copied from the run cache while it is the same, or built whole and kept there (Fragment runs, below). Texts are laid through the renderer's scratch draw list, never the frame's. (2) Residency: `Batch2D::prepare` makes those sprite textures resident with the world's: every texture the commands ask for, culled or not, in the order recorded, so where the atlas places one never depends on culling. (3) `UiRenderer::finish`: each sprite gets its atlas slot's uv (`place_in_slot`, as the batch places sprites) and its page's kind and sampler (a sprite whose texture has no atlas slot is dropped, as the batch skipped it), the texture runs are planned and bound, and what changed goes up into the UI's own buffer with the scroll slots, the buffer doubling when a frame needs more (below). (4) The `ui` pass clears the UI image, sets the pipeline, the UI camera's group, the slots' group (at its dynamic offset) and the buffers once, then binds each texture run's textures and draws its range.
- **Fragment runs** (`ui_retain/fragments.rs`, `build_run`). A kept fragment's commands arrive as one tagged run (`FragmentRun`: its root's id, a version that changes whenever its commands may, its first order, layer and slot, its range and the bounds of its draws' boxes; `src/core/ui/AGENTS.md`, Fragments). `UiRunCache` keeps each run's built instances (`KeptRun`) by its root's id and copies them while building it would give the same: built at its version, in this `UiRenderEnv`, in slot 0 if drawn there and in one of the shader's slots if drawn in one, no command reading the clock, each glyph page it samples at the generation it had (an evicted page is cleared and has another), each sprite texture it draws still in the registry (a prune can forget one), and each command with a stamp (a sprite, a text with icons) at its stamp. A run in one of the shader's slots is built relative to the slot and unculled while runs are kept, so its instances hold wherever the slot draws it; a copy takes the slot's index in its frame. A run built absolute (past the shader's slots, on the pixel-art target, or with a draw whose own clip does not fit relative to its slot) is never kept, as its instances hold only where the slot is now. A copy pins the glyph pages it samples for the frame and holds its texts in the text cache as drawing them would (`UiTextCache::hold`), so the run's next version reuses them. A run not drawn in a frame is dropped, and every run when the environment changes or retention is off. Commands out of painter's order are built one by one and no run is kept.
- **Uploading what changed** (`UiGpu::upload`). The renderer keeps a copy of what its instance buffer holds (the last upload's instances) and writes each stretch that differs from it (`changed_ranges`), compared bit for bit: when the counts are equal, stretches fewer than 128 alike instances apart are written as one (`MERGE_GAP`), and past 4 writes the rest join the last (`MAX_WRITES`), since wgpu makes a staging buffer for each `write_buffer` (about 2 µs a call); when they are not, from the first instance that differs to the end; nothing when nothing differs, and the whole frame into a new or grown buffer. The frame's instance array is written over the last frame's (`InPlace`), so a run copied where the last frame had the same kept run in the same slot (a `Segment`) is left as it is, not copied, and where the last upload had it there too the buffer holds it already: it is not compared (`in_place`). The scroll slots go past the instances when they changed or moved: in the last write when it ends within 128 instances of the end, else in a write of their own. A label changing over the settings screen writes only its own instances (it is recorded last, so even its glyph count changing moves nothing after it); a retained list scrolling between interest steps writes little more than its scrollbar's thumb and a hovered row, as its rows' runs are copied in place and only its slot's offset changes; at an interest step rows leave and enter its runs, and the array is rewritten from the first row to leave. `UiRenderStats::instances_written` counts what each upload wrote.
- **Culling.** A command, and each glyph, sprite or line instance in it (by its points' box grown by its reach), builds nothing when it cannot draw a pixel: its box misses the UI camera's view (the batch's camera cull, exactly), or lies more than a pixel outside its clip where its slot draws it (the margin covers a pixel-art snap moving an edge), or its clip is empty (`scissor_of` gives none). The shader clips the rest exactly as the scissor did, so culling changes no pixel. A fragment run's draws in one of the shader's slots are not culled while runs are kept (the shader collapses what lies outside), and nor is a text in a slot glyph by glyph. With nothing keeping a run (retention off, or the pixel-art target) a run in a slot is culled as a loose draw is, first by resolve's own test (`UiDraw::shows`), so the renderer builds what a full rebuild sends, and a run whose bounds lie wholly outside its slot's view is skipped whole.
- **Texts are cached as instances, and as seeds to lay again where they move.** `UiTextCache<UiInstance>` keeps each text's finished instances (those that survived culling) where they were laid, and its glyphs' seeds (`GlyphSeed`, `render/text.rs`: each glyph quad with its image, before it is placed). A text drawn where its instances were laid is one copy of them: what is culled follows from its glyphs, its clip and its variant (culled glyph by glyph in slot 0; in a slot, whole, under the slot's clip or a clip of its own), all part of the key. A text drawn elsewhere (one whose node moved, or a scrolling list's on the pixel-art target, where a slot's contents are placed absolute) is laid again from its seeds by the emitter's own placing (`quad`: the pixel-grid snap and rounding, and the box it is culled by), straight into the renderer's culling, so its instances are exactly those building it there makes; they are kept again once it is drawn at one place twice, so a text that keeps moving is never copied. The origin changes nothing else but a raster glyph's subpixel bin, picked by its pen's fraction of a pixel along x: a text moved along x is checked bin by bin (`seeds_fit`) and built again when one differs; a vertical move never changes one. Translating the kept instances instead would not be exact: a snapped glyph's centre is its image-pixel position divided by the UI scale, and each line's baseline rounds on its own, so a fractional move shifts lines differently and float division does not commute with the shift. Texts with effects, bitmap-font texts and texts a full atlas cut short are built every frame, icons fresh.
- **Lines** (`build_line`, `UiInstance::line_piece`, `ui.wgsl`'s `ui_line`). A UI line (solid, mitered, butt capped, one width and one colour, its own edge or its target's: `ui_line_points`) is built on the GPU by the world's piece functions (`line_piece_vertex`, `shaders/include/line_pieces.wgsl`; each triangle's slots from `line_piece_slot`, the layout the world's index buffer has, and its corners worked out in place by the one corner function, `lp_corner_here`, where the world reads the corner pass's records), pushed a pixel of the UI image out (`px_per_unit`, the UI camera's pixels per UI unit, its `px_scale`) and covered by its distances in pixels (`line_fringe`, `line_pixel`, `shaders/include/line_cover.wgsl`), as a world line is, with no derivative: drawn through the batch's line pipeline as world lines seen by the UI camera, UI lines are the UI pipeline's pixel for pixel at UI scales 1, 1.25 and 2, joins, closed seams and the image's edges included (`ui_lines_draw_as_world_lines_at_every_ui_scale`). The CPU filters the points and lists the pieces as the world's line stream does (`filter_points`, `piece_list`): segments and miter or bevel joins, four triangles each, so two instances a piece (an instance draws a quad's six vertices, two triangles; `pair` says which two). Each instance carries the points its piece is built from inline, so retention works unchanged (kept runs copied, in-place uploads, the bitwise `changed_ranges` compare): the six about the piece's point (a join reads five), each place as the command lays it and its `u`, which slots hold a point and which is a closed line's seam, the half width, a two-point line's half length between its caps, the params, the colour as two exact 16-bit halves (so the shader unpacks the bytes the world's line stream holds), the miter limit, and the line's offset (`at`). The shader moves every point by the offset and its slot's (`at + by`), which is how the CPU moves a line it places absolute, so a line in a slot is built from the same points as one placed there (`draws_in_slots_draw_as_they_were_placed_on_the_cpu`); adding the slot's offset to each vertex instead differs by a rounding, a level at a pixel. The points are filtered as the command lays them, so the filter does not depend on where a slot is. An instance is culled, on the CPU and by the vertex stage, by the box of the points its triangles lie about (a segment's ends and their neighbours, a join's point and its neighbours), grown by how far a vertex reaches from them: the miter limit times the half width (a mitered tip) and a pixel, a margin for the fringe rather than a figure it needs (`ui_line_reach`), so a line whose miter tip or edge reaches into its clip or the view, its points outside them, is kept (`a_line_whose_fringe_or_miter_tip_reaches_in_is_kept`). `UiOut`'s position is `@invariant`, as the world line's is, so copies of a place in different instances agree. A line's edge rides in its instance's bits (`LINE_EDGE_SHIFT`, as the line table numbers it); without one it takes its target's by the UI camera's `snap`, set on the pixel-art target, so UI drawn there is Hard and UI at window resolution Smooth, each the batch's world line pixel for pixel (`ui_lines_take_their_target_s_edge_unless_given_one`). UI rects on the pixel-art target keep their smooth rounded corners. A line is 144 bytes an instance, two instances a piece (a three-point line is six). No coverage takes a derivative, so UI lines draw the same pixels on every GPU and in every mesh layout.

## Draw Order

- Items sort by (z, kind, submission), once per frame, unstably (every item's submission number is its own, so the order is the same, and the sort allocates nothing, where a stable sort takes a scratch buffer past 20 items); each camera draws the sorted items it sees. `z_order` picks the layer; at equal z entities draw first, then world text (`Text`), then sprites in the order pushed (`Scene::render` sprites, the engine's particle runs in entity order, parallax quads, image layers), then trails and lines (`DrawKind` order). An entity's mesh is one of the entity's items, not a trail: it draws where its entity pushes it (The 2D Batch, Meshes).
- The UI is not in this sort: the UI renderer draws its commands in painter's order (layer, then the order recorded; at one order, a line after the rest).
- Within a layer, plain entities draw in entity index order and y-sorted ones follow, ordered by their sort key: the point `YSort.foot_offset` of the way down the sprite (default the feet), computed from the anchor, so the key is the same whichever `Anchor` places the sprite (`y_sort_key`). At one sort key the lower floor (storey) draws first (`DrawOrder::floor`: a map layer's draws take its floor, `LayerInfo::floor`, on a map with floors; an entity takes its `DrawLift`'s, `Every` and none as 0), so a character on the ground standing at a bridge row's ground y draws under the bridge (`equal_sort_y_draws_the_lower_floor_first`, `under_a_bridge_the_upper_floor_draws_over_the_lower`); plain draws at one z go by floor too. Ties go by index after that (`ecs::entity_order`), never query order. Index order is spawn order only for entities spawned fresh: bevy gives a despawned entity's index to a later spawn, which then draws as that lower index. A query visits archetypes in an order that changes whenever an archetype is made, and every resource is an entity with an archetype of its own, so adding any resource swapped overlapping sprites (`tied_sprites_draw_in_entity_order_whatever_the_resources`).
- Map layers sort as entities do (`OrderedDraw`, merged in by `EntityDrawer::collect`): a plain tile layer's chunks at the layer's z as plain, tied with plain entities by the layer entity's index; a y-sorted layer's rows (a row's cells that share a sort point: `MapGrid::sort_band`) by their sort point, `band_y` (an orthogonal row's bottom edge, else the band's cells' centre, through the layer's transform before its floor's lift: the ground y where the row stands, as an entity's key is its ground y), among the y-sorted entities at its z, with a cell of its own item where it shares none (an oblique grid skewed down its columns) or its tile's `sort_offset` moves it (`ChunkRun::sort`, in layer pixels); tile objects as plain, or by their bottom edges where they stand on a y-sorted layer, tied by the object entity. Image layers are sprites (`DrawKind::Sprite`), after the entities at their z. A map layer's z is the map's plus its index; on a map with floors (`MapFloors`) every y-sorted tile and object layer draws at the first one's (`tilemap::y_sort_z`, `MapsView::y_sort_z`), so characters at that z sort with every floor's rows (`on_a_map_with_floors_every_y_sorted_layer_draws_at_one_z`, `a_character_sorts_with_a_raised_floor_from_both_sides`); a map without floors keeps a z per layer, and plain layers always do.
- Shadows draw just before their entity. Composite tiles draw at their own `z_order`, after the layer's entities.
- A skeleton (`RenderStyle::Skeleton`) is one drawable in this order, as a sprite is: its runs and its meshes are pushed where its entity falls, in its own draw order, its parts' shadows first. Its y-sort key is its entity's own y plus `sort_offset` (it has no image for `foot_offset` to measure). What it draws and how is in the skeleton module notes (Drawing).
- Debug shapes (`DebugDraw`, the overlays) are unlit at `i32::MAX`.

## Placement (`entities.rs`)

- Positions come from `render_global(global, previous, time.fixed.overstep_fraction())`: entities with `PreviousGlobalTransform` (the `Interpolated` ones and their descendants) draw blended between the last two fixed steps. This covers single sprites, tiled runs and composite tiles (lights, occluders and lines too, in `engine/extract.rs`).
- **On a floor** (a storey), an entity's `GlobalTransform` is where it stands on the ground, and it draws lifted by its `DrawLift` (`ecs/floor.rs`, written by the tile map's `lift_floored` on an entity with a `Floor` and everything below it): `collect_entity` adds `lift` to the blended position, so the sprite or tiled run and its drop, blob and contact shadows move together; `collect_composite` adds it to the origin; world text (`emit_world_text`) to the block's position. Its sort key stays the ground y (`y_sort_key` reads `GlobalTransform`) and `YSort::calculate_depth_scale` the ground y too, so sorting and depth never jump as an entity changes floor; `DrawOrder::floor` is the `DrawLift`'s floor. Particles emit at the lifted point and trails record it (`particles/mod.rs`, `systems/trail.rs`), so they stay where they were made; the lift is found in each fixed step before trails record, so a trail spawned on a floor starts lifted and an emitter spawned and fired in one step fires lifted (particle module notes). Lines and the debug overlays (F2) stay in ground space (`a_floor_entity_draws_lifted_by_its_floor_s_height`, e2e; `world_text_on_a_floor_draws_lifted`).
- **Skeleton** (`collect_skeleton`): the skeleton's origin sits on the position; the anchor is ignored. Its bones are placed under the whole blended transform (plus `lift`, times the `YSort` depth scale), mirrored about the position by the renderable's flips; its regions are quads on them and its meshes' vertices are skinned to them, under the same transform. Before any part is built, the box the skeleton keeps in its own space is taken to the world through that transform, grown by an effect's padding and joined by its shadows (`skeleton_reach`); when no camera on the entity's layers sees it (texture cameras included), the skeleton is not walked that frame (`a_skeleton_showing_any_part_is_never_culled`, `an_off_screen_skeleton_is_not_walked`, `a_skeleton_is_walked_for_the_cameras_on_its_layers_texture_cameras_too`; the box and its rules are in the skeleton module notes, Drawing).
- **Single sprite:** the anchor point (`Renderable::anchor`, default `Anchor::Center`) sits on the position; scale and rotation happen about it. **A mirrored transform mirrors it** (`GlobalTransform::is_mirrored`: a negative scale on one axis, on the entity or above it): its turn is read from its x axis, so the mirror is across that axis, which flips its anchor's offset and its image top to bottom, combined with `flip_y` by exclusive or; its drop shadow is the same shape, and its y-sort key does not move (the key takes no account of a turn either). So a sprite on a mirrored parent, or on a flipped skeleton's socket, mirrors with it (`a_sprite_under_a_mirrored_transform_draws_mirrored`, e2e). Not mirrored: a tiled run and a composite tile, which take the transform's turn and axis lengths, and a light occluder, which is placed by its entity's translation and turn alone (`LightOccluder2D::placed`), so a mirrored entity's occluder casts unmirrored.
- **Tiled run** (`RenderStyle::Tiled`): laid out from the entity's position, which is the first tile's top-left (Up/Left runs grow backwards); the anchor is ignored; the run rotates and scales about that position.
- **Composite tile:** parts at `origin + offset` (their top-left), scaled by the global scale, never rotated; the origin is blended for interpolated entities.
- Instances carry world-space quads: centre, size (texels times scale, in world units), rotation and flips. The camera's `view_proj` takes them to its image; in pixel-art mode the sprite vertex shader snaps axis-aligned quads to whole target pixels. A quad is culled per camera by its half-diagonal box, taken from the quad as an effect that draws past it (an outline, a directional outline, a glow) grows it, as the GPU does (`place_in_slot`), both where the entity drawer culls it and in the draw list's item, which each camera culls (`DrawList::push_sprite_reaching`): so an outline reaching into view from a sprite just off screen is drawn, and so is one from a skeleton's region, whose run's box grows by the same padding (`effect_reach`, `padded`, `entities.rs`, shared with the skeleton's box; `an_outline_reaching_into_view_from_a_sprite_just_off_screen_is_drawn` and `an_outline_reaching_into_view_from_a_skeleton_s_region_just_off_screen_is_drawn`, `tests/e2e/sprite_effects.rs`). Blending happens in linear light, on the float scene image.
- Entity sprites are registry textures (`TextureId`) keyed by the image's asset id, uploaded again when its store version moves (a reload, or `get_mut`; a large reload over frames while the old texture draws, graphics module notes, Reloads) and freed with the image (`AssetEvent::Removed`). A renderable with `target: Some(t)` draws the render target's texture at the target's size; the camera drawing into `t` skips it (warned once per entity).

## Ordering Rules

- Order is the list order. `push` adds at the end; `insert_before` / `insert_after` place a pass relative to a named one.
- Pass ids are unique. A duplicate id or an unknown anchor id returns `RenderPipelineError`; nothing panics.
- Camera passes run before frame passes wherever they sit in the list; within a scope, list order holds.
- `set_enabled` is the caller's switch (a disabled pass keeps its place and is skipped); `should_run(&FrameInfo)` is the pass's own per-frame condition, asked only for enabled passes. `passes_to_run(&frame)` says what would run, in run order.
- `remove` hands the boxed pass back (`Box<dyn RenderPass>` is itself a `RenderPass`), or `None` for an unknown id.

  let mut pipeline = ctx.render_pipeline();
  // Passes persist across scenes: add once, or remove in on_exit
  if !pipeline.contains("flash") {
    let _ = pipeline.insert_before(pass_ids::COMPOSITE, Flash);

## Design Decisions

- **Thin passes.** GPU pipelines, bind groups and buffers live in the subsystem renderers (the batch, lighting, post-process, compositor). A pass only calls into them with the `RenderContext`; `world` and `unlit_world` replay the camera's batch draws.
- **A camera image per camera, then a frame-level composite.** Lighting and the passes keep working on whole images, so no pass needs scissor logic; the common single full-window camera draws straight into the scene image and pays nothing extra. Post-processing runs once per frame, not per camera.
- **Latest-image tracking.** `RenderContext` tracks which texture holds the latest image (`FrameImage`: game, lit, a camera's own image, an HDR-stage buffer, or a display-stage buffer: the `tonemap` pass writes the display image, which `post_process` ping-pongs). A pass drawing on "the frame" uses `current_view()` / `encoder_and_current_view()`, so a game pass after `post_process` draws on the post-processed image (`Rgba8UnormSrgb`), one before `tonemap` on a scene image (`Rgba16Float`), and a camera pass on its camera's image. Only passes before `composite` reach the screen.
- **The UI is composited only if the `ui` pass drew or kept this frame** (`RenderContext::ui_drawn`). The UI image is persistent; without that flag a disabled or skipped `ui` pass would blend the previous frame's UI. Otherwise the composite binds a transparent 1x1 image and its uniform says no UI.
- **The UI draws in gamma space, after everything else.** The `ui` pass draws the UI into its own image, after tonemapping and post-processing, so effects never touch it and its alpha blends in sRGB space, as designers expect.
- **A capture is read back only if the `capture` pass ran.** Otherwise `render_frame` reports `CaptureError::Readback` rather than returning a stale image.
- **Scene images follow the render size** (`ScreenMapping::render_size`: the window's physical size, the fit's scaled size, or the pixel-art target); the lit texture is persistent. Camera images and light targets follow their camera's image size.
- **Images are premultiplied.** A camera image clears to a premultiplied colour (transparent for `CameraClear::None`) and sprites blend over it, so the `cameras` pass places images with premultiplied blending.
- **The fade** is the `transition` pass (colour and opacity from `FrameScene::overlay`): it copies the frame and mixes toward the colour in sRGB; blending in linear light held bright areas back and then snapped at the end.

## UI render retention

- **An unchanged UI keeps the UI image.** The composite blends it as it is, so the frame builds, uploads and draws no UI. The UI is composited over the world, so the world changing does not matter. The kept image shows the last build's sprite textures, so the frame marks them used (`SpriteGpuRenderer::mark_shown`), each once (`UiBuild::shown_textures`): a UI left alone keeps its images' textures, and a full atlas or the standalone cap frees others first. A skin is nine sprite commands and a bitmap-font text one a cell, so marking per command would cost a kept frame of 490 commands of two textures about 3.3 µs; once per texture it is about 40 ns.
- **What "unchanged" means** (`UiRetain::keep`): the same slot table (each scroll slot's offset and clip: a slot that moved moved its pixels), each fragment run the same by its tag (root, version, first order, layer, slot and range: its commands are its fragment's, the same while its version is, and the fragment keeps them and what they share alive), the draws outside runs the same one by one and in the same order and slots (shared layouts by address, held by the retainer so an address is not reused under it; line points by value, as immediate widgets allocate them anew each frame; numbers by bits), the same sprite and icon versions (stamps: the version of a sprite's image its texture shows, an older one while a new texture is written over frames; a text's icons, names resolved through `TextIcons`; in a run, those of its commands that have one, by the store's versions, as a kept run holds its sprites before they are placed), no text effect, the same `UiRenderEnv` (UI space, pixel-art snapping, text on, the text engine's font generation, the bitmap faces' sheet versions), and the UI image's epoch (process-unique; a recreated image is blank).
- **Holding a frame looks its runs up among those held before** (`UiRetain::hold`, `seen`), to keep which of a run's commands have stamps and whether one reads the clock without reading its commands again: from past the last run found, up to 16 runs on (`LOOK_AHEAD`: the rows that left a scrolling list between them are passed over), then on through the rest while a budget of as many runs as were held lasts, so a hold takes time linear in its runs however they leave and arrive. A run not found is taken as new.
- **A frame whose only change is a slot's offset is not kept** (its pixels moved), but off the pixel-art target nothing in the slot is built: its runs are copied, in place where they were.
- **The kept frame holds its images' handles.** `UiRetain` keeps the last built frame's draws and `UiTextCache` its layouts, and both carry `Handle<Image>`s (sprite commands, icons), so an image the game let go is freed once a frame's UI is built without it: one built frame later, or longer while presents are skipped. Accepted: it is bounded, it keeps the addresses a kept frame compares by, and it is the one place the renderer holds handles rather than ids.
- **The image record is committed only for a presented frame whose `ui` pass drew.** A kept frame with the `ui` pass disabled shows no UI and leaves the image as it is.
- **A UI drawing nothing still runs the `ui` pass.** When every command is culled the pass clears the image and draws nothing, so the image is recorded and the next unchanged frame keeps it (as a UI with draws does).
- **A changing frame reuses texts' built glyphs by `TextKey`** (layout address, reveal, opacity, seed, clip, the sink's variant, and which of the frame's texts with these it is, in painter's order, so a layout drawn twice keeps two entries) within one environment. The origin is not in the key: it only places the glyphs, which a moved text's seeds are laid again at (the UI renderer's text cache, above). Outside fragment runs only texts are cached (92% of building the UI's draw items in 4g's profile): rects, sprites and lines are built every frame, as that is cheaper than a lookup one by one. A fragment run's instances are kept whole (the UI renderer's fragment runs, above), as one lookup serves all of them. Effects, bitmap-font cells (sprites, re-resolved each frame) and texts a full atlas cut short are not kept.
- **Glyph pages carry process-unique generations, changed when a page is cleared.** A reused text whose page changed is built again. Its pages are those of every glyph it fetched (each seed's), also glyphs that landed nowhere where it was built, so laid elsewhere it still checks every page it draws from. A reused text pins its pages for the frame (counted in the eviction test as "drawn this frame").
- **UI draws must not read time on the GPU.** A UI draw that does must count as time-driven, or a kept image would freeze it.
- **Guarded** (`benches/ui_render.rs`, the settings node screen, retained): the render step over an empty frame's under 5 µs idle, 25 µs with one label changing and 35 µs scrolling, and the UI pass under 18 µs idle, 25 µs with the label and 27 µs scrolling; one label and scrolling no slower retained than not. Scrolling misses the spec's 20 µs for both, so its limits hold it near its measured medians (about +31 and 22.5 µs), and the 20 µs goal is printed beside them. The limits are absolute, and the medians move by up to 2x with the machine's load. The guard also prints a kept skinned menu's render step over an empty frame (twenty nine-slice buttons with bitmap-font labels, 490 sprite commands of two textures), with no target: about the idle settings screen's.
- **Known limit:** text drawn larger than its largest glyph image (world text above 256 px, UI text above 512 px) is scaled from that image with linear filtering, so two runs whose glyph atlases are packed differently (as retention on and off are) can differ by one level at those glyphs' edges. Below those sizes the pixel oracle's equality is exact.

## Presenting

- Present mode: vsync on (the default) is `Fifo`; vsync off is `Mailbox`, else `Immediate`, else `Fifo`. The engine paces frames to `target_fps` (sleep, then spin) when presenting does not block or nothing was presented (`should_pace_frames`): vsync off unless the surface fell back to `Fifo`, or a hidden window. A hidden window (winit's `Occluded`) runs its frames without drawing them, so presenting never waits on a drawable the system will not give.
- Surface states (`gpu_error.rs`): `Suboptimal` draws, then reconfigures; `Timeout` and `Occluded` skip the frame; `Outdated` reconfigures; `Lost` recreates the surface; a validation error is fatal and ends the run, as is a lost device. A skipped frame still ran its update; it just presented nothing.

## Gotchas

- `FrameInfo::world` means the draw list has lit items; `unlit_world` has no flag of its own. `FrameInfo` describes content, not passes: `lighting` and `effects` stay true when the game disabled those passes.
- Disabling `post_process` removes every display effect, including flashes and tints; disabling `hdr_effects` removes bloom, god rays and ambient occlusion.
- A game pass records raw wgpu work on `ctx.encoder_and_current_view()` (`ryo2d::wgpu`); there is no higher-level API for game passes. Custom sprite and effect shaders go through `Material` / `EffectsManager::add_custom` instead (`src/core/shaders/AGENTS.md`).
- `DebugStats::draw_calls` counts the batch's draws (`world`, `unlit_world` and the lights, over every camera) and the UI renderer's (one per texture run).
- Crate-internal checks that need engine internals live in `src/core/testing/gpu_world.rs`; pixel-level behaviour is in `tests/e2e/gpu_world.rs` and `tests/e2e/render_pipeline.rs`. A bare mesh's pixels are checked crate-internally too, in `src/core/testing/mesh_gpu.rs`: nothing public draws one (a skeleton's mesh attachments are the engine's own caller, and their pixels are in `tests/e2e/skeleton_mesh.rs`), so `MeshProbe` (`entities/mesh_probe.rs`, a child module compiled for tests only) is a component the entity drawer draws as a mesh in its entity's place, from the entity's `Renderable` (and its `Material`). It is what compares a mesh with a sprite of its image, which no skeleton can.
