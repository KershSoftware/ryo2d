# AGENTS.md - Render Pipeline

The engine draws every frame through one `RenderPipeline` (a resource, `RenderPipeline::default_2d()`): `Engine::present_frame` (`engine/extract.rs`) builds a `FrameScene` and `WgpuRenderer::render_frame` runs the enabled passes on **one command encoder with one submit**: the camera passes (`PassScope::Camera`) once per camera in render order, each on that camera's image in `Rgba16Float` linear light, then the frame passes (`PassScope::Frame`) once: `cameras -> hdr_effects -> tonemap -> transition -> post_process -> ui -> composite -> capture`. Games reach it with `ctx.render_pipeline()` (a `Mut<RenderPipeline>`): toggle built-in passes or insert their own. The pipeline belongs to the engine, so a scene's changes persist across scene transitions.

## Default Order (`default_2d`)

| # | Id (`pass_ids`) | Scope | Runs when (`should_run`) | Draws |
|---|-----------------|-------|--------------------------|-------|
| 1 | `CLEAR` | camera | always | clears the camera's image per `CameraClear` (transparent for `None`) |
| 2 | `WORLD` | camera | the draw list has lit items | the camera's lit draws from the batch: entities, `Scene::render` sprites (particles), parallax, trails, lines and debug shapes, one z-sorted list |
| 3 | `LIGHTING` | camera | lighting is on | the camera's lights and shadows, composed into the lit image (straight-in camera) or back into its own image |
| 4 | `UNLIT_WORLD` | camera | always (returns early with no unlit draws) | the camera's unlit draws (anything `with_lighting(false)`, and debug shapes), by z |
| 5 | `CAMERAS` | frame | always | window cameras' own images into their viewports, in order; clears the scene image first when no camera drew straight into it |
| 6 | `HDR_EFFECTS` | frame | HDR effects are active | bloom, god rays, ambient occlusion and HDR custom effects on the scene image (linear light, may exceed 1) |
| 7 | `TONEMAP` | frame | always | the look: writes the display image (the display stage's buffer A) from the latest scene image; the transition, `post_process` and the composite work on the display image |
| 8 | `TRANSITION` | frame | a transition fade is visible | scene transition fade over the whole frame (not the UI) |
| 9 | `POST_PROCESS` | frame | display effects are active | fade, tint, vignette, flash, CRT, chromatic aberration and display custom effects on the display image |
| 10 | `UI` | frame | the UI recorded something and the UI image was not kept | clears the UI image (`UI_FORMAT`) and draws the UI renderer's frame into it: one pipeline, one draw per texture run (usually one); a UI whose commands are all culled draws nothing but still clears it |
| 11 | `COMPOSITE` | frame | always | to the window or offscreen target through `ScreenMapping` (bars for fit and pixel art), UI blended last in sRGB space |
| 12 | `CAPTURE` | frame | a capture was requested | frame capture readback copy |

## Images and Formats

- **`SCENE_FORMAT`** (`render/mod.rs`, `Rgba16Float`): linear light, premultiplied by alpha, values may exceed 1. The game texture, the lit image, camera images, render-target textures, the lighting pass's scene copy and the HDR stage's ping-pong pair all use it. Nothing on the CPU writes f16 texels: render passes fill these images.
- **The display image** is buffer A of the display effect stage, `Rgba8UnormSrgb`; the `tonemap` pass writes it and `post_process` ping-pongs it with buffer B. Unchanged formats: atlas and standalone sprite pages (`Rgba8Unorm`, raw sRGB bytes), the surface, the offscreen target and the capture readback.
- **The UI image** (the compositor's, `UI_FORMAT` = `Rgba8Unorm`) holds gamma-encoded colour premultiplied by alpha. Its size is `UiSpace::image` (`render/ui.rs`): the render size, or the window's screen rectangle with `UiResolution::Window` in pixel-art mode. The composite shader (`fullscreen_quad.wgsl`) encodes the frame to sRGB, blends `ui + frame * (1 - ui.a)` and decodes, so UI alpha behaves as on the web.
- `FrameImage` (`frame.rs`) names the latest image: `Game`, `Lit`, `Camera(entity)`, `Hdr(buffer)` (the HDR stage) and `Display(buffer)` (the display stage).
- `RenderContext::format()` is the format of `current_view()`: `Rgba16Float` in camera passes and in frame passes before `tonemap`, `Rgba8UnormSrgb` after it. A game pass builds its pipelines for `ctx.format()`.
- Two `PostProcessPipeline`s (`EffectStages`: `hdr` and `display`) are built, one per format; each effect runs in the stage `PostProcessEffect::stage()` gives (`EffectStage`, `shaders/AGENTS.md`).

## The Look

- `Look` (`look.rs`, resource, `ctx.look()`) holds exposure, the `Tonemap` curve, `ColorGrading` and optional `AutoExposure`. The `tonemap` pass (`passes/tonemap.rs`, `tonemap.wgsl`) applies, in order: exposure (`exposure + auto EV`), white balance (temperature, tint), contrast and saturation, the curve, lift/gamma/gain on the display colour, then sRGB encoding and the LUT.
- **`Tonemap::apply` in `look.rs` mirrors `tonemap.wgsl`: change them together.** `every_curve_on_the_gpu_matches_tonemap_apply` (`tests/e2e/look.rs`) pins them.
- **The LUT** is a 3D texture (`LutTexture`, `passes/tonemap.rs`) uploaded from the strip image's pixels. It follows the image's version, so a reload uploads it again; a version that is not a strip keeps the last good one (warned once, naming the image by its path), and so does an image that is not loaded. Lookups are in sRGB.
- **Auto-exposure** (`exposure.rs`, `exposure.wgsl`): two compute dispatches each frame, one filling a luminance histogram from the scene image and one reducing it (trimmed mean) into a stored EV that moves toward its target at the configured speeds. The tonemap pass binds that stored EV; with auto-exposure off it adds nothing, and turning it off and on again restarts it at its target. The dispatches run inside the tonemap pass, on the scene image it is about to read.

## Lights in the Batch

- `DrawList::lights_for(camera)` gives the lights on the camera's layers whose box meets its view. Lights are batch quads (`lighting/batch.rs`) laid into each lit camera's draws by `Batch2D::prepare`, which also pushes their shadow volumes into the triangle stream.
- Per lit camera the `lighting` pass replays: one `LightStep::Add` draw for all lights without shadow volumes; for each shadowed light, in its quad, `ResetMask`, then `Shadow` (triangles), `Masked`, and `Coloured` if its shadow is coloured.
- `light_blend` (`batch/pipelines.rs`) gives each step's blend state and colour writes: `Add` adds colour (alpha untouched); `ResetMask` writes alpha 1 and no colour; `Shadow` writes only alpha, multiplying it by 1 - strength; `Masked` adds the light times the alpha (`DstAlpha`); `Coloured` adds the shadow-tinted light times 1 - alpha.
- **The mask lives in the light buffer's alpha** so shadows need no stencil, depth or second target: only core WebGPU. One light's shadow never touches another light's colour, because the next light resets the alpha inside its own quad.

## Cameras in the Frame

- `plan_cameras` (`frame.rs`) orders the cameras: texture cameras, then window cameras, each by `order` (ties by entity). The first window camera draws straight into the scene image when its viewport is `Viewport::FULL` and it clears; every other window camera draws into an image of its own (`CameraImages`, `graphics/camera_images.rs`), sized to its viewport in render pixels (`PixelRect::of_viewport`, edges rounded so viewports that meet share them). A texture camera draws straight into its render target when its viewport covers it, otherwise into an image of its own that `leave_camera` places in its rectangle of the target (premultiplied blending, like the `cameras` pass); one whose target is missing is left out (warned once).
- Each `CameraDraw` carries the view, layers, clear, target, image rectangle and whether it is lit. `RenderContext::enter_camera` points `current_view()` at the camera's image (`FrameImage::Camera`) for its passes; `leave_camera` goes back to the scene image, which a straight-in camera may have left lit.
- Per-camera GPU state: a uniform buffer per camera (`CameraUniforms`: `view_proj`, image size, game and real time, snap), its bind group in the batch and in lighting, camera images and light targets. All of it follows the planned cameras each frame, so a despawned camera's state goes with it.

## Building the Frame (`present_frame`)

Everything is read from the world by query, every frame. There is no render cache: nothing is invalidated, and an entity draws where its `GlobalTransform` says on the frame it exists. Drawables are gathered once, in world space, and sorted once; each camera keeps what it sees. Tile chunks are the one exception: their instances are kept, built again only when their tiles or look change (The 2D Batch, Tile chunks), while where they draw is read every frame.

1. `Scene::render(gpu)` for the visible scenes, bottom-up (`GpuRenderContext`: `gpu.batch`, `gpu.camera()` = the main camera's view, read-only `gpu.world`); the `BatchCollector` keeps submission order.
2. Lights (`(&GlobalTransform, &Light2D)` with their `RenderLayers`, at their world translation; batch quads in the draw list when lighting is on) and occluders (`(&GlobalTransform, &LightOccluder2D)`, keeping rotation); `LightingSettings` is copied into the lighting renderer.
3. Render targets' textures follow `RenderTargets`; the cameras are planned and their light targets synced (their uniforms and bind groups are synced with the UI camera's, step 7).
4. The `Scene::render` sprites join the draw list; each `ParallaxLayer` is laid out for every camera on its layers (items for that camera alone).
5. The layers of spawned maps (`TileDrawer::collect`, `tiles.rs`): each image layer joins the list as one quad per view, its image repeating across it (a sprite item, `SpriteShading::Repeat`); the visible chunks of tile layers (those whose tiles or look changed built into the batch's chunk store first), the rows of y-sorted ones and tile objects are gathered as `OrderedDraw`s, sorted as entities are. Then `EntityDrawer::collect` (`entities.rs`): one query over the visible renderables (with their `RenderLayers`), each pushed in draw order with the gathered map draws merged in at their places, then the composite tiles. Quads no camera on their layers can see are skipped before their texture uploads. Disabled entities are skipped by the queries themselves. Then world text (`text.rs`): the `Text2d`s whose text, style, options or fonts changed are laid out again (`layout_world_text`, which syncs the engine's `TextEngine` with `Fonts`), the glyphs `Fonts::prewarm` asked for are built, and each camera that sees a block gets its glyph quads (`emit_world_text`: glyph items for that camera alone, raster glyphs at the size it sees; bitmap cells and inline icons are sprite items). Positions are interpolated like entities'. `TextEngine::end_frame` runs after `Batch2D::prepare`.
6. Trails (`&Trail2D`: world-space points) and lines (`(&GlobalTransform, &Line2D)`: at the entity's translation) become polylines on the batch's triangle stream, one item each. The debug overlays are added to `DebugDraw`, whose shapes are built for each camera in its own screen pixels (items for that camera alone).
7. The UI: unless the UI image is kept ("UI render retention"), the UI renderer (`render::ui_renderer`) builds the frame's `UiCommands` (recorded by `Scene::ui` before the fixed steps) into instances of its own, in painter's order (layer, then the order recorded), culling what draws nothing and copying the unchanged fragment runs it kept; texts and lines are laid out through a scratch draw list, never the frame's. When the UI recorded anything, the UI camera's uniforms (`UI_CAMERA`, snapped on the pixel-art target) join the world cameras'. The UI camera is not one of the batch's cameras and not in `FrameScene::cameras`, so no camera pass runs for it.
8. The list is sorted; `Batch2D::prepare` makes the frame's textures resident (the UI's sprite textures with them), lays each camera's lit and unlit items (on its layers, inside its `CameraView::bounds`, not showing its own target, `only_camera`), and a lit camera's lights (`DrawList::lights_for`), into draws and uploads the instances and triangles once; the UI renderer then finishes its frame (its sprites placed in their atlas slots, its texture runs, the upload of what changed with its scroll slots), and the pipeline runs. `present_frame` clears the frame's debug shapes afterwards, drawn or skipped.

`FrameScene.time` (lighting, trails, the transition) is real elapsed time; post-process effects run on `EffectsManager`'s own clock, advanced with real time in `PostUpdateSet::Extract`. Only `CameraGlobals::game_time` (sprite effects, custom sprite shaders) is game time.

## The 2D Batch (`batch/`)

One batch draws the world: sprites, shadows, tiles, composite parts, particles, `Scene::render` sprites, parallax tiles, world text, trails, lines and debug shapes.

- **Two streams**, each uploaded once per frame into a buffer that doubles when a frame needs more: instanced quads (the 128-byte `SpriteInstance`, remapped into its atlas slot) and indexed triangles (`Vertex2D`, 72 bytes: position, uv, colour, params, across, the slot a textured line repeats).
- **Keys and planning** (`key.rs`, `plan.rs`): every item resolves to a `DrawState` (page, `BatchShader`, `BlendMode`, `Sampling`). Per camera, `plan_draws` merges consecutive items with equal states (and, for triangles, adjacent index ranges) into `Draw`s; each camera's quads have a range of the instance buffer of their own, its lit and unlit draws in one range.
- **Pipelines** (`pipelines.rs`) are made on first use per `(BatchShader, BlendMode, Stream, format)`, but the tile chunks' for a plain layer (`Tile`, the default blend, an sRGB page), which the batch makes when it is built: made on first use it cost the frame the first map landed in about 0.85 ms; a custom sprite shader gets one per blend mode it is drawn with, checked without blocking (`Checked`), and draws plain until its check passes. A new version of a custom shader already drawn is made on the shader thread for every key its old source has, while the old one draws, and taken in at the start of a frame (`Batch2D::sync_shaders`; shaders module notes). Every batch shader writes colour premultiplied by alpha, so each `BlendMode` is one fixed blend state (`blend_state`); `Premultiplied` picks the shader entries that take a texture's colour as it is.
- **Bind groups are made with their resource:** one per camera (its uniform buffer) and one per texture page and sampler (made with the page); none per frame. Every bind group goes through `graphics::bind_groups::create`, which counts them in tests (`steady_frames_create_no_bind_groups`, and a guard test that fails on any other `create_bind_group`); passes that bind frame resources look them up in a `BindGroupCache` keyed by the resources themselves, cleared when those are recreated.
- **Lines** (`lines.rs`, `polyline.rs`): trails and lines become polylines with miter, bevel or round joins (each corner one wedge, fanned from the corner point, so nothing is covered twice) and butt, square or round caps.
- **Glyph items.** Glyphs are `DrawPayload::Glyph`, already placed in their glyph page (the instance carries the atlas UVs) and drawn by `TextMask`, `TextColor` or `TextMsdf`. Their instance lanes, which the UI renderer's glyph quads keep (its rects, untextured with an analytic rounded rect and border, take the last row's):

  | Shader | `tint` | `effect_params` | `effect_extra` |
  |---|---|---|---|
  | `TextMask` | glyph colour (sRGB, straight alpha) | unused | unused |
  | `TextColor` | multiplier (white keeps the glyph's colours) | unused | unused |
  | `TextMsdf` | fill colour, or the soft layer's colour | `[mode (0 fill/outline, 1 soft), width or spread (base px), softness (base px), range (base px)]` | outline colour |
  | UI rect (its quad extends one pixel in UI units past the rect on every side, and `uv_rect` extends by the same fraction past `[0, 1]`, so the outer edge keeps its anti-aliasing) | fill colour | `[corner radius, border width, width, height]` (UI units) | border colour |

  The text emitter (`render/text.rs`) draws an MSDF outline as a quad of its own (mode 0, a transparent fill, the outline colour's alpha times the glyph's) in the outline pass, and the fill (mode 0, width 0) in the fill pass, so no glyph's outline covers a neighbour's fill. Glow and shadows are mode 1 quads in the shadow pass.

- **Tile chunks** (`chunks.rs`, `render/tiles.rs`, `shaders/core/tile.wgsl`; spec `docs/specs/2026-10-29-tilemap-design.md`). The batch's one retained source. Each tileset's tiles of a 32x32-cell chunk of a tile layer (`ChunkKey`: layer entity, signed chunk (`IVec2`, as `TileGrid::chunk_of` gives it), tileset) are instances in one arena (`ChunkStore`: a CPU copy, first-fit free ranges, the end cut off as it frees), built by `chunk_instances` in the layer's own pixels with UVs over the tileset's padded image, and built again only when the grid's `chunk_version` or the layer's look stamp (tint, opacity, cell size, the tilesets' padded `serial`s) differs from what it was built from; the store keeps its own last-seen versions (grid versions never repeat, across grids too, so a swapped grid rebuilds), never `drain_dirty`. `ChunkBuffers::upload` in `prepare` writes only the ranges built since the last write (touching ones joined), the whole arena into a new buffer once it outgrows the old (doubling), and lets the buffer go once nothing is built. The arena is capped at the device's `max_buffer_size` over the 128-byte instance (`Cap`, `ChunkStore::for_device`: 2,097,152 instances, 256 MiB, under the `Limits::default()` the engine asks for), the CPU copy too (its `Vec` never reserves past it): past it `create_buffer` fails validation and the game dies with a GPU fault (a 1024 x 1024 four-layer map seen whole at zoom 0.12 at 1080p would ask for 512 MiB). A chunk that would take the arena past its cap frees the chunks drawn least recently, never one drawn this frame (its draws are made: `evict_oldest`, from a list made once a frame); when that is not enough the chunk is refused, draws nothing that frame, and is not built again from the same stamp until the arena has room for the instances it made (`Built::refused`, so a view too wide does not build its refused chunks every frame); the dev log warns once (`a_view_past_the_chunk_arena_s_cap_draws_what_fits_and_warns_once`, a cap injected with `ChunkStore::set_cap`). The chunks a view meets first (row by row) are the ones drawn. There is no per-frame build budget: one would leave holes in the view while it caught up on a zoom-out, and would have to tell a landing (which must draw whole) from a zoom; the cap bounds the worst frame. `ChunkStore::chunk` copies a chunk's parts (and a y-sorted layer's rows) into the drawer's buffers rather than lending them, so the drawn-unchanged path is one map lookup. A chunk is freed when its layer entity loses its `TileLayerData` (despawned: within the frame) or after 120 frames undrawn (`KEEP_FRAMES`). Each draw binds a tile slot (group 2, a uniform at a dynamic offset of 256 bytes per slot, written each frame only when the slots changed; the bind group made with the buffer): the layer's interpolated world transform (axes and origin), the camera's parallax offset (from the map's `TileMap::parallax_origin`), and the padded image's place on its page (`textures.slot`, UV offset and scale), so moving the map or camera, or the atlas moving the image, changes no instance. A slot is one per (view, tileset), a view being one layer for every camera, or for each camera when the layer has parallax (`only_camera` items). Chunk items are `DrawPayload::Chunk` at `MapRoot`'s z plus the layer index, `DrawKind::Entity`, lit per `LayerInfo::lit`, on the layer entity's own `RenderLayers` if it has them, else the map's, culled per camera by their world box; `plan_draws` makes each a draw of its own (`DrawSource::Chunk`), never merged. A `DrawChunk` draws its key's instances from `first`, `count` of them: all of a part, or one row. A tileset's part of a chunk is in row order, so each row of cells is a run of it (`ChunkRow`, its signed row recorded with its box at build), and a y-sorted layer (`LayerInfo::y_sorted`) draws each row as an item of its own, sorted by the row's bottom edge (the world y of the cell row's bottom at the layer's left end, so every chunk of a row sorts alike, the parallax offset included). Chunk and row items take their places among the entities' (Draw Order): `TileDrawer` gathers them before the entities are drawn as `OrderedDraw`s (an order, the layer entity ties go by, the payload), and `EntityDrawer::collect` pushes each before the first entity that sorts after it, so they get their sequence from the entity order itself. Extraction only visits the chunks a camera's view (in layer pixels, widened by the largest padded cell, floored to signed chunks) can reach, within the chunks the layer reaches (its extent's: a bounded layer's every chunk, visited whether it holds tiles or not, as before; an unbounded layer's span, of which only the chunks it has are visited, found by walking the view's chunks or the layer's, whichever are fewer: `TileGrid::chunks_within`), so a frame costs what is on screen, and no chunk an unbounded layer lacks enters the store (`an_unbounded_layer_draws_tiles_at_negative_cells_and_culls_by_signed_chunk`, e2e, reading the store through `HeadlessEngine::tile_chunks`). `vs_tile` places corners through the slot, snaps the slot's origin (map and parallax together) to a whole pixel on the pixel-art target under an unturned camera, so every tile corner lands on one at whole zooms (a quad's own snap skips the turned quads of diagonal flips), and steps an animated tile's UVs to its frame on `game_time`; the fragment entries are the sprite's. Never snap per quad: at a fractional zoom each tile rounding its own corner and size leaves pixel gaps (`testing/tile_bleeding.rs`, `no_seams_at_any_zoom_or_subpixel_camera`, fails at zoom 0.33 with 16 px tiles). Without the origin snap no tile leaves its pixels, but the texels slide under them as the camera moves by fractions of a pixel (`a_sub_pixel_camera_draws_tiles_as_at_the_whole_pixel_they_round_to`, zoom 4/3). Pipelines draw both faces: a diagonal flip turns a quad over.
- **Image layers and tile objects** (`render/tiles.rs`). An image layer (`ImageLayer` on the layer entity, whose `Transform` holds the offset) draws as one quad over the copies of its image a view needs (`SpriteShading::Repeat`, `BatchShader::Repeat`: `vs_repeat` and `fs_repeat` in `tile.wgsl`), `DrawKind::Sprite` at the layer's z (so after the entities there), tinted and faded by the layer, with its blend and lit flag: the image once, or repeated along the axes the editor says over a camera's view. The quad's UVs count copies and the image wraps along both axes (half a texel inside its place on the page, the level picked from the unwrapped derivatives); the layer's origin rides in the transform lanes' unused z, and on the pixel-art target the quad moves as that origin's snap to a whole pixel does, never rounded itself, so the copies are whole multiples of the image from the snapped origin, as a tile layer's tiles are, with no gap between two at any zoom (`a_repeated_image_layer_shows_no_gaps_at_fractional_zoom`). One quad for every camera when it neither repeats nor has parallax, else one per camera, moved by its parallax offset (from the map's `TileMap::parallax_origin`, as a tile layer's). An LDtk sub-layer (`LayerInfo::part_of`) draws as part of its layer, found among the map's layers by id: that layer's visibility, flags, parallax, blend, tint, `RenderLayers`, z and transform, its own offset and opacity over them, its draws tying on the layer's entity after the layer's own (`LayerDraw::ties`), so a y-sorted layer's stacked rows sort with entities as the layer's do. A layer with a transparent colour (`ImageLayer::transparent`) draws from a copy of its picture with that colour clear (`keyed_image`, made once per version of the picture and kept 120 frames past its last draw). A view needing more than 65,536 copies along an axis (`MAX_REPEATS`; fewer for an image over 8 px, whose quad spans at most 524,288 of its texels so its UVs keep a sixteenth of a texel) gets that many about its centre, and the layer is warned about once: an 8 px image covers a 4K view at the smallest zoom. A tile object (a visible `MapObject` with a `tile`, child of a visible object layer) is an `OrderedDraw` sprite from the tileset's padded image at the object's interpolated transform, sized to the object, with the tile's flips, an animated tile's frame for the game time chosen on the CPU, the layer's look; plain at the layer's z, or by its bottom edge on a y-sorted layer. A disabled map draws neither.
- **Whole-image draws.** The batch never clips: `draw` takes the image size and sets the scissor to all of it.
- **Format.** The batch draws in the format it is built with, `SCENE_FORMAT` for the world. Built in `UI_FORMAT` (only tests do, chiefly to prove UI lines against the world's line pipeline), its pipelines gamma-encode through the `UI_GAMMA` override and `ui_out` in `color.wgsl`, as the UI pipeline does.
- **Debug draw** (`render/debug_draw.rs`): `DebugDraw` keeps world-space shapes in a fixed-step list (cleared when the next step begins) and a frame list (cleared after the frame); each camera builds them as polylines in its own screen pixels.

## The UI Renderer (`ui_renderer/`)

The UI has a renderer of its own, apart from the world's batch: the UI needs painter's order, clips and a few textures; the world needs cameras, layers and lights. It turns the frame's `UiCommands` into instances and draws them through one pipeline (design: `docs/specs/2026-10-20-ui-renderer-design.md`; scroll slots and fragment runs: `docs/specs/2026-10-21-ui-fragments-design.md`).

- **One instance, seven kinds** (`instance.rs`). `UiInstance` is 144 bytes: eight `vec4` lanes, then the clip, the kind and the flags (the sampler, whether its clip is its own, its scroll slot in bits 8 to 15) and glyph page as four integers. A quad's lanes are a `SpriteInstance` cast as it is (transform rows, uv rect, tint, effect lanes, uv bounds), so its corners come from the function the sprite shader places its quads with (`quad_corner`, `shaders/include/quad.wgsl`), pixel-art snap included. The kinds (`UiKind`, `ui.wgsl`'s `KIND_` constants): rect, raster glyph, colour glyph, MSDF glyph, sprite, linear sprite (a render-target page, linear and premultiplied) and line. A line is one instance per triangle its builder makes (`push_polyline`: solid, miter joins, butt caps), carrying its three corners' positions, uvs and colours; the quad's other three vertices repeat the last corner. Per triangle rather than per quad so the geometry is exactly the builder's.
- **One pipeline** (`gpu.rs`, `shaders/core/ui.wgsl`). `vs_ui` places a quad with `quad_corner`, as `sprite.wgsl`'s `vs_main` does, or for a line runs `line.wgsl`'s solid path (no displacement, no snap), in both cases moved by its scroll slot's offset first (Scroll slots, below). `fs_ui` switches on the kind and runs the world entry's body: `ui_rect`, `glyph_mask`, `glyph_color`, `glyph_msdf`, `finish` (sprite), `finish_linear` (render-target sprite) and `styled` (line). Those bodies are include functions the world shaders call too (`src/core/shaders/AGENTS.md`), written once, so the UI cannot drift from them. Every derivative is taken before the switch, where control flow is uniform, and texture reads use `textureSampleGrad`, as WGSL's uniformity rules require inside the switch; glyph pages have one mip level, so that samples as `textureSample` did. The output goes through `ui_out` with `UI_GAMMA` set, premultiplied-alpha blended. Group 0 is the UI camera's, group 1 the textures, group 2 the scroll slots.
- **Clipping in the shader.** An instance in slot 0 carries its clip in whole UI-image pixels (`ClipRect`: `scissor_of`'s rect, or the whole image). One in a scroll slot draws under the slot's clip, read from the slot (the instance carries the whole image, so neither its instances nor its text's cache key change as a nested slot's clip moves), or, with a clip of its own (a text field's view in a scrolled list, `FLAG_OWN_CLIP`), under that clip relative to the slot, moved by the slot's whole-pixel offset and met with the slot's (`clip_in_slot`, `ClipRect::in_slot` on the CPU). The fragment's centre (`@builtin(position).xy`, at k + 0.5) must lie in `[x0, x1) x [y0, y1)`, tested last, after all derivative-taking code; outside it the shader outputs zero, which the premultiplied blend leaves as the image was. With integer bounds that is exactly the scissor test, and clips no longer break draws: per-draw scissors and pipelines made the settings screen 64 draws, and it is now one.
- **Scroll slots** (`SlotUniform`, `slot_uniforms`). The shader reads the frame's slot table, at most 256 slots (`SLOTS`, slot 0 among them, which moves nothing): each slot's offset in UI units, the same offset in whole pixels (to move an instance's own clip exactly) and its clip in image pixels. They live in the instance buffer past the instances (`slots_at(n)`, aligned to 256 bytes, WebGPU's largest minimum uniform offset alignment), bound in group 2 as a uniform array with a dynamic offset, so they need no buffer of their own and go up with the instances (Uploading what changed); 8 KiB, within WebGPU's default uniform limits, and no new feature. The vertex stage adds the slot's offset to an instance's corners before the camera and the pixel-art snap (`quad_corner`'s `by`), so content placed relative to its slot moves by whole pixels exactly and its instances stay the same while it scrolls. Draws in slots past 256, and a draw whose own clip does not fit a `ClipRect` relative to its slot, are built absolute: moved and clipped on the CPU (`UiDraw::placement`). So is every draw in a slot on the pixel-art target, where only slot 0 is written: there a quad's corners are rounded to whole target pixels, and a corner on a half pixel rounds by the last bit of its position, which moving it on the CPU and moving it in the shader compute differently.
- **Vertex-stage culling.** `vs_ui` collapses a quad or line triangle that lies wholly outside its clip, moved where its slot draws it, to one point outside the image (`outside_clip`, `COLLAPSED`): a fragment run built unculled (below) then costs no fill for what its slot does not show. It removes only primitives that cover no pixel centre inside their clip, and the fragment stage's clip test stays the exact scissor test, so no pixel changes.
- **Texture slots and runs** (`runs.rs`). The texture bind group (group 1) holds four slots, the mask, colour and MSDF glyph pages and a sprite page (an atlas page, a standalone image or a render target), and the atlas's linear and nearest samplers; a slot no instance needs holds a 1x1 placeholder. An instance picks its slot by kind and its sampler by a flag. `plan_runs` ends a texture run only when an instance needs a different texture in a slot the run already filled; the next run starts with that texture alone (carrying the others over could only add breaks). Each texture run is one draw: the settings screen, every page of the `ui` demo and breakout draw in one. Bind groups are cached by the textures and samplers they hold (wgpu handles compare by identity, so a recreated texture is a new key). A group holds its textures alive, so it goes once the UI stops needing it: unused for 8 frames whose UI was drawn (`KEEP_FRAMES`; a frame all of whose commands are culled counts), at once when a frame keeps the UI image and the image was drawn without it, and with every other group (and the runs) when a frame's UI records nothing. A title screen's background is not held through a scene with no UI or a still HUD; making a group again takes about 1 µs. Four sampled textures and two samplers fit WebGPU's default limits.
- **The frame.** (1) `UiRenderer::build`, unless the UI image is kept: `build_ui` walks the commands in painter's order (layer, then the order recorded; at one order a line after the rest, as the batch drew them; sorted only when one is out of place), culls, and builds the instances, the texture each needs and the sprite textures to make resident. A fragment's run is copied from the run cache while it is the same, or built whole and kept there (Fragment runs, below). Texts and lines are laid through the renderer's scratch draw list, never the frame's. (2) Residency: `Batch2D::prepare` makes those sprite textures resident with the world's: every texture the commands ask for, culled or not, in the order recorded, so where the atlas places one never depends on culling. (3) `UiRenderer::finish`: each sprite gets its atlas slot's uv (`place_in_slot`, as the batch places sprites) and its page's kind and sampler (a sprite whose texture has no atlas slot is dropped, as the batch skipped it), the texture runs are planned and bound, and what changed goes up into the UI's own buffer with the scroll slots, the buffer doubling when a frame needs more (below). (4) The `ui` pass clears the UI image, sets the pipeline, the UI camera's group, the slots' group (at its dynamic offset) and the buffers once, then binds each texture run's textures and draws its range.
- **Fragment runs** (`ui_retain/fragments.rs`, `build_run`). A kept fragment's commands arrive as one tagged run (`FragmentRun`: its root's id, a version that changes whenever its commands may, its first order, layer and slot, its range and the bounds of its draws' boxes; `src/core/ui/AGENTS.md`, Fragments). `UiRunCache` keeps each run's built instances (`KeptRun`) by its root's id and copies them while building it would give the same: built at its version, in this `UiRenderEnv`, in slot 0 if drawn there and in one of the shader's slots if drawn in one, no command reading the clock, each glyph page it samples at the generation it had (an evicted page is cleared and has another), each sprite texture it draws still in the registry (a prune can forget one), and each command with a stamp (a sprite, a text with icons) at its stamp. A run in one of the shader's slots is built relative to the slot and unculled while runs are kept, so its instances hold wherever the slot draws it; a copy takes the slot's index in its frame. A run built absolute (past the shader's slots, on the pixel-art target, or with a draw whose own clip does not fit relative to its slot) is never kept, as its instances hold only where the slot is now. A copy pins the glyph pages it samples for the frame and holds its texts in the text cache as drawing them would (`UiTextCache::hold`), so the run's next version reuses them. A run not drawn in a frame is dropped, and every run when the environment changes or retention is off. Commands out of painter's order are built one by one and no run is kept.
- **Uploading what changed** (`UiGpu::upload`). The renderer keeps a copy of what its instance buffer holds (the last upload's instances) and writes each stretch that differs from it (`changed_ranges`), compared bit for bit: when the counts are equal, stretches fewer than 128 alike instances apart are written as one (`MERGE_GAP`), and past 4 writes the rest join the last (`MAX_WRITES`), since wgpu makes a staging buffer for each `write_buffer` (about 2 µs a call); when they are not, from the first instance that differs to the end; nothing when nothing differs, and the whole frame into a new or grown buffer. The frame's instance array is written over the last frame's (`InPlace`), so a run copied where the last frame had the same kept run in the same slot (a `Segment`) is left as it is, not copied, and where the last upload had it there too the buffer holds it already: it is not compared (`in_place`). The scroll slots go past the instances when they changed or moved: in the last write when it ends within 128 instances of the end, else in a write of their own. A label changing over the settings screen writes only its own instances (it is recorded last, so even its glyph count changing moves nothing after it); a retained list scrolling between interest steps writes little more than its scrollbar's thumb and a hovered row, as its rows' runs are copied in place and only its slot's offset changes; at an interest step rows leave and enter its runs, and the array is rewritten from the first row to leave. `UiRenderStats::instances_written` counts what each upload wrote.
- **Culling.** A command, and each glyph, sprite or line triangle in it, builds nothing when it cannot draw a pixel: its box misses the UI camera's view (the batch's camera cull, exactly), or lies more than a pixel outside its clip where its slot draws it (the margin covers a pixel-art snap moving an edge), or its clip is empty (`scissor_of` gives none). The shader clips the rest exactly as the scissor did, so culling changes no pixel. A fragment run's draws in one of the shader's slots are not culled while runs are kept (the shader collapses what lies outside), and nor is a text in a slot glyph by glyph. With nothing keeping a run (retention off, or the pixel-art target) a run in a slot is culled as a loose draw is, first by resolve's own test (`UiDraw::shows`), so the renderer builds what a full rebuild sends, and a run whose bounds lie wholly outside its slot's view is skipped whole.
- **Texts are cached as instances, and as seeds to lay again where they move.** `UiTextCache<UiInstance>` keeps each text's finished instances (those that survived culling) where they were laid, and its glyphs' seeds (`GlyphSeed`, `render/text.rs`: each glyph quad with its image, before it is placed). A text drawn where its instances were laid is one copy of them: what is culled follows from its glyphs, its clip and its variant (culled glyph by glyph in slot 0; in a slot, whole, under the slot's clip or a clip of its own), all part of the key. A text drawn elsewhere (one whose node moved, or a scrolling list's on the pixel-art target, where a slot's contents are placed absolute) is laid again from its seeds by the emitter's own placing (`quad`: the pixel-grid snap and rounding, and the box it is culled by), straight into the renderer's culling, so its instances are exactly those building it there makes; they are kept again once it is drawn at one place twice, so a text that keeps moving is never copied. The origin changes nothing else but a raster glyph's subpixel bin, picked by its pen's fraction of a pixel along x: a text moved along x is checked bin by bin (`seeds_fit`) and built again when one differs; a vertical move never changes one. Translating the kept instances instead would not be exact: a snapped glyph's centre is its image-pixel position divided by the UI scale, and each line's baseline rounds on its own, so a fractional move shifts lines differently and float division does not commute with the shift. Texts with effects, bitmap-font texts and texts a full atlas cut short are built every frame, icons fresh.
- **Lines on Apple GPUs.** A UI line's triangles share no vertex. On Metal, `fwidth` near a shared edge of the batch's indexed, shared-vertex line mesh can differ from the same triangles drawn apart, so UI line pixels may differ from what the world's line pipeline would draw by that derivative alone (measured: up to 3/255 along slanted edges, up to about 0.36 coverage at miter tips and closed-outline corners; on the demo tour, 34 pixels of the text demo's page 5, at most 67/255). The owner accepted this class (2026-10-20). `lines_draw_as_the_batch_draws_them_with_no_vertex_shared` (`ui_renderer/gpu_tests.rs`) holds the proof: the batch's own line pipeline, drawing with no shared vertex, matches the UI's pixels exactly. Analytic, derivative-free line anti-aliasing is the follow-up (`docs/backlog/ui-retained-nodes.md`, 4h).

## Draw Order

- Items sort by (z, kind, submission), once per frame, unstably (every item's submission number is its own, so the order is the same, and the sort allocates nothing, where a stable sort takes a scratch buffer past 20 items); each camera draws the sorted items it sees. `z_order` picks the layer; at equal z entities draw first, then world text (`Text`), then `Scene::render` sprites, then trails and lines (`DrawKind` order).
- The UI is not in this sort: the UI renderer draws its commands in painter's order (layer, then the order recorded; at one order, a line after the rest).
- Within a layer, plain entities draw in entity index order and y-sorted ones follow, ordered by their sort key: the point `YSort.foot_offset` of the way down the sprite (default the feet), computed from the anchor, so the key is the same whichever `Anchor` places the sprite (`y_sort_key`). Ties go by index too (`ecs::entity_order`), never query order. Index order is spawn order only for entities spawned fresh: bevy gives a despawned entity's index to a later spawn, which then draws as that lower index. A query visits archetypes in an order that changes whenever an archetype is made, and every resource is an entity with an archetype of its own, so adding any resource swapped overlapping sprites (`tied_sprites_draw_in_entity_order_whatever_the_resources`).
- Map layers sort as entities do (`OrderedDraw`, merged in by `EntityDrawer::collect`): a plain tile layer's chunks at the layer's z as plain, tied with plain entities by the layer entity's index; a y-sorted layer's rows by their bottom edges among the y-sorted entities at its z; tile objects as plain, or by their bottom edges on a y-sorted layer, tied by the object entity. Image layers are sprites (`DrawKind::Sprite`), after the entities at their z.
- Shadows draw just before their entity. Composite tiles draw at their own `z_order`, after the layer's entities.
- Debug shapes (`DebugDraw`, the overlays, `draw_skeleton`) are unlit at `i32::MAX`.

## Placement (`entities.rs`)

- Positions come from `render_global(global, previous, time.fixed.overstep_fraction())`: entities with `PreviousGlobalTransform` (the `Interpolated` ones and their descendants) draw blended between the last two fixed steps. This covers single sprites, tiled runs and composite tiles (lights, occluders and lines too, in `engine/extract.rs`).
- **Single sprite:** the anchor point (`Renderable::anchor`, default `Anchor::Center`) sits on the position; scale and rotation happen about it.
- **Tiled run** (`RenderStyle::Tiled`): laid out from the entity's position, which is the first tile's top-left (Up/Left runs grow backwards); the anchor is ignored; the run rotates and scales about that position.
- **Composite tile:** parts at `origin + offset` (their top-left), scaled by the global scale, never rotated; the origin is blended for interpolated entities.
- Instances carry world-space quads: centre, size (texels times scale, in world units), rotation and flips. The camera's `view_proj` takes them to its image; in pixel-art mode the sprite vertex shader snaps axis-aligned quads to whole target pixels. A quad is culled per camera by its half-diagonal box. Blending happens in linear light, on the float scene image.
- Entity sprites are registry textures (`TextureId`) keyed by the image's asset id, uploaded again when its store version moves (a reload, or `get_mut`; a large reload over frames while the old texture draws, graphics module notes, Reloads) and freed with the image (`AssetEvent::Removed`). A renderable with `target: Some(t)` draws the render target's texture at the target's size; the camera drawing into `t` skips it (warned once per entity).

## Ordering Rules

- Order is the list order. `push` adds at the end; `insert_before` / `insert_after` place a pass relative to a named one.
- Pass ids are unique. A duplicate id or an unknown anchor id returns `RenderPipelineError`; nothing panics.
- Camera passes run before frame passes wherever they sit in the list; within a scope, list order holds.
- `set_enabled` is the caller's switch (a disabled pass keeps its place and is skipped); `should_run(&FrameInfo)` is the pass's own per-frame condition, asked only for enabled passes. `passes_to_run(&frame)` says what would run, in run order.
- `remove` hands the boxed pass back (`Box<dyn RenderPass>` is itself a `RenderPass`), or `None` for an unknown id.

```rust
fn on_enter(&mut self, ctx: &mut SceneContext) {
  let mut pipeline = ctx.render_pipeline();
  // Passes persist across scenes: add once, or remove in on_exit
  if !pipeline.contains("flash") {
    let _ = pipeline.insert_before(pass_ids::COMPOSITE, Flash);
  }
}
```

## Design Decisions

- **Thin passes.** GPU pipelines, bind groups and buffers live in the subsystem renderers (the batch, lighting, post-process, compositor). A pass only calls into them with the `RenderContext`; `world` and `unlit_world` replay the camera's batch draws.
- **A camera image per camera, then a frame-level composite.** Lighting and the passes keep working on whole images, so no pass needs scissor logic; the common single full-window camera draws straight into the scene image and pays nothing extra. Post-processing runs once per frame, not per camera.
- **Latest-image tracking.** `RenderContext` tracks which texture holds the latest image (`FrameImage`: game, lit, a camera's own image, an HDR-stage buffer, or a display-stage buffer: the `tonemap` pass writes the display image, which `post_process` ping-pongs). A pass drawing on "the frame" uses `current_view()` / `encoder_and_current_view()`, so a game pass after `post_process` draws on the post-processed image (`Rgba8UnormSrgb`), one before `tonemap` on a scene image (`Rgba16Float`), and a camera pass on its camera's image. Only passes before `composite` reach the screen.
- **The UI is composited only if the `ui` pass drew or kept this frame** (`RenderContext::ui_drawn`). The UI image is persistent; without that flag a disabled or skipped `ui` pass would blend the previous frame's UI. Otherwise the composite binds a transparent 1x1 image and its uniform says no UI.
- **The UI draws in gamma space, after everything else.** The `ui` pass draws the UI into its own image, after tonemapping and post-processing, so effects never touch it and its alpha blends in sRGB space, as designers expect.
- **A capture is read back only if the `capture` pass ran.** Otherwise `render_frame` reports `CaptureError::Readback` rather than returning a stale image.
- **Scene images follow the render size** (`ScreenMapping::render_size`: the window's physical size, the fit's scaled size, or the pixel-art target); the lit texture is persistent. Camera images and light targets follow their camera's image size.
- **Images are premultiplied.** A camera image clears to a premultiplied colour (transparent for `CameraClear::None`) and sprites blend over it, so the `cameras` pass places images with premultiplied blending.
- **The fade** is the `transition` pass (colour and opacity from `FrameScene::overlay`): it copies the frame and mixes toward the colour in sRGB; blending in linear light held bright areas back and then snapped at the end.

## UI render retention

- **An unchanged UI keeps the UI image.** The composite blends it as it is, so the frame builds, uploads and draws no UI. The UI is composited over the world, so the world changing does not matter. The kept image shows the last build's sprite textures, so the frame marks them used (`SpriteGpuRenderer::mark_shown`), each once (`UiBuild::shown_textures`): a UI left alone keeps its images' textures, and a full atlas or the standalone cap frees others first. A skin is nine sprite commands and a bitmap-font text one a cell, so marking per command would cost a kept frame of 490 commands of two textures about 3.3 µs; once per texture it is about 40 ns.
- **What "unchanged" means** (`UiRetain::keep`): the same slot table (each scroll slot's offset and clip: a slot that moved moved its pixels), each fragment run the same by its tag (root, version, first order, layer, slot and range: its commands are its fragment's, the same while its version is, and the fragment keeps them and what they share alive), the draws outside runs the same one by one and in the same order and slots (shared layouts by address, held by the retainer so an address is not reused under it; line points by value, as immediate widgets allocate them anew each frame; numbers by bits), the same sprite and icon versions (stamps: the version of a sprite's image its texture shows, an older one while a new texture is written over frames; a text's icons, names resolved through `TextIcons`; in a run, those of its commands that have one, by the store's versions, as a kept run holds its sprites before they are placed), no text effect, the same `UiRenderEnv` (UI space, pixel-art snapping, text on, the text engine's font generation, the bitmap faces' sheet versions), and the UI image's epoch (process-unique; a recreated image is blank).
- **Holding a frame looks its runs up among those held before** (`UiRetain::hold`, `seen`), to keep which of a run's commands have stamps and whether one reads the clock without reading its commands again: from past the last run found, up to 16 runs on (`LOOK_AHEAD`: the rows that left a scrolling list between them are passed over), then on through the rest while a budget of as many runs as were held lasts, so a hold takes time linear in its runs however they leave and arrive. A run not found is taken as new.
- **A frame whose only change is a slot's offset is not kept** (its pixels moved), but off the pixel-art target nothing in the slot is built: its runs are copied, in place where they were.
- **The kept frame holds its images' handles.** `UiRetain` keeps the last built frame's draws and `UiTextCache` its layouts, and both carry `Handle<Image>`s (sprite commands, icons), so an image the game let go is freed once a frame's UI is built without it: one built frame later, or longer while presents are skipped. Accepted: it is bounded, it keeps the addresses a kept frame compares by, and it is the one place the renderer holds handles rather than ids.
- **The image record is committed only for a presented frame whose `ui` pass drew.** A kept frame with the `ui` pass disabled shows no UI and leaves the image as it is.
- **A UI drawing nothing still runs the `ui` pass.** When every command is culled the pass clears the image and draws nothing, so the image is recorded and the next unchanged frame keeps it (as a UI with draws does).
- **A changing frame reuses texts' built glyphs by `TextKey`** (layout address, reveal, opacity, seed, clip, the sink's variant, and which of the frame's texts with these it is, in painter's order, so a layout drawn twice keeps two entries) within one environment. The origin is not in the key: it only places the glyphs, which a moved text's seeds are laid again at (the UI renderer's text cache, above). Outside fragment runs only texts are cached (92% of building the UI's draw items in 4g's profile): rects, sprites and lines are built every frame, as that is cheaper than a lookup one by one. A fragment run's instances are kept whole (the UI renderer's fragment runs, above), as one lookup serves all of them. Effects, bitmap-font cells (sprites, re-resolved each frame) and texts a full atlas cut short are not kept.
- **Glyph pages carry process-unique generations, changed when a page is cleared.** A reused text whose page changed is built again. Its pages are those of every glyph it fetched (each seed's), also glyphs that landed nowhere where it was built, so laid elsewhere it still checks every page it draws from. A reused text pins its pages for the frame (counted in the eviction test as "drawn this frame").
- **UI draws must not read time on the GPU.** A UI draw that does must count as time-driven, or a kept image would freeze it.
- **Guarded** (`benches/ui_render.rs`, the settings node screen, retained): the render step over an empty frame's under 5 µs idle, 25 µs with one label changing and 35 µs scrolling, and the UI pass under 18 µs idle, 25 µs with the label and 27 µs scrolling; one label and scrolling no slower retained than not. Scrolling misses the spec's 20 µs for both, so its limits hold it near its measured medians (about +31 and 22.5 µs), and the 20 µs goal is printed beside them. The limits are absolute, and the medians move by up to 2x with the machine's load. The guard also prints a kept skinned menu's render step over an empty frame (twenty nine-slice buttons with bitmap-font labels, 490 sprite commands of two textures), with no target: about the idle settings screen's.
- **Known limit:** text drawn larger than its largest glyph image (world text above 256 px, UI text above 512 px) is scaled from that image with linear filtering, so two runs whose glyph atlases are packed differently (as retention on and off are) can differ by one level at those glyphs' edges. Below those sizes the pixel oracle's equality is exact.

## Presenting

- Present mode: vsync on (the default) is `Fifo`; vsync off is `Mailbox`, else `Immediate`, else `Fifo`. The engine paces frames to `target_fps` (sleep, then spin) when presenting does not block or nothing was presented (`should_pace_frames`): vsync off unless the surface fell back to `Fifo`, or a hidden window. A hidden window (winit's `Occluded`) runs its frames without drawing them, so presenting never waits on a drawable the system will not give.
- Surface states (`gpu_error.rs`): `Suboptimal` draws, then reconfigures; `Timeout` and `Occluded` skip the frame; `Outdated` reconfigures; `Lost` recreates the surface; a validation error is fatal and ends the run, as is a lost device. A skipped frame still ran its update; it just presented nothing.

## Gotchas

- `FrameInfo::world` means the draw list has lit items; `unlit_world` has no flag of its own. `FrameInfo` describes content, not passes: `lighting` and `effects` stay true when the game disabled those passes.
- Disabling `post_process` removes every display effect, including flashes and tints; disabling `hdr_effects` removes bloom, god rays and ambient occlusion.
- A game pass records raw wgpu work on `ctx.encoder_and_current_view()` (`ryo2d::wgpu`); there is no higher-level API for game passes. Custom sprite and effect shaders go through `Material` / `EffectsManager::add_custom` instead (`src/core/shaders/AGENTS.md`).
- `DebugStats::draw_calls` counts the batch's draws (`world`, `unlit_world` and the lights, over every camera) and the UI renderer's (one per texture run).
- Crate-internal checks that need engine internals live in `src/core/testing/gpu_world.rs`; pixel-level behaviour is in `tests/e2e/gpu_world.rs` and `tests/e2e/render_pipeline.rs`.
