# AGENTS.md - Asset Module

The asset registry: ids and handles, the per-type stores, the server with its loaders, sources and worker threads, the pump that lands loads and frees assets each frame, and hot reload. The spec is `docs/specs/2026-10-23-asset-registry-design.md` (where it and the code differ, the code is current); what it costs is measured in `docs/backlog/assets.md` (5a: measured). Using it from a game is the `ryo-assets` skill.

## Ids, handles and lifetimes

- `AssetId<T>` (`id.rs`) is a slot's index and the slot's generation. It is `Copy` and keeps nothing alive. A slot's generation moves on when it is freed, so a stale id finds nothing, never a newer asset in the same slot. `UntypedAssetId` adds the type, for what spans types (`progress`, dependencies).
- `Handle<T>` (`handle.rs`) is an `Arc` over the slot's index, generation and its store's drop channel. Cloning bumps a count; the last drop sends the slot on the channel, and the next pump frees it. Handles compare and hash by id.
- **Only handles keep assets.** Explicit release leaks when forgotten and breaks when called early; drops, applied in one place each frame, do neither. So a game holds what it uses (a scene field, a component such as `Renderable`, a resource for what the whole game uses), and an asset nothing holds is freed at the next pump. Engine caches key by id (the renderer's textures, the shader cache, the text layout cache), so the engine never keeps alive what the game let go. What in the engine does hold a handle holds it on purpose: a font role (`Fonts::set_role`), a `TextFont::Face` in a style, a node tree's UI file, a followed theme, and the UI's kept frame (render module notes).
- A handle can be made again from a live id after the last one dropped (`Ledger::strong`: the server finding a path's asset still in its table, before the pump freed it). The drop notice already sent finds the new handle alive when it arrives and is ignored, so the slot is not freed under it. `Handle::unheld` (crate) names an asset without holding it, for a cache that compares by handle.

## Stores and versions

- `Assets<T>` (`assets.rs`) is a world resource per type: a slot table of values, and a ledger of the live slots shared with the server behind a `Mutex`, so the server reserves ids on any thread without the world.
- **A store comes only from the world.** A handle names a slot of the store that made it, and everything that resolves handles reads the world's store, so a handle from a store of a game's own would find nothing there, or another asset (the first image is the checker, drawn in release builds too). So `Assets::new` is crate-only and the store is neither `Default` nor `FromWorld`: `register_asset` inserts it, and a test with no engine takes `testing::asset_world()`. Two `compile_fail` doctests on `Assets` pin it.
- Every insert and every `get_mut` gives the value the next version from one counter for the whole store (`version`). A version is never given twice in a store, so a cache keyed by `(id, version)` never shows stale content, and the newest version among several assets says whether any of them changed (a UI file and its imports).
- Changes made in code, `add` and `get_mut`, queue the slot's event for the next pump (`Added` or `Modified`), once per slot: the first change decides it, so an asset added and then changed is `Added` only. The pump sends the events of what it lands itself, as it lands them, and drops a queued one for the same slot. A store no server registered (`Assets::new()`, in the crate's tests) queues nothing.
- **A change list has one follower.** A store lists the slots changed since its follower last took them (`take_changes`, by a `follower_token`), so a follower's pass after k changes costs k. `ImageSizes` follows `Assets<Image>` (the UI's image sizes); `Fonts` follows `Assets<Font>` and `Assets<BitmapFont>`. A follower the list is not kept for is given the whole store and the list is kept for it from then on, so no follower misses a change, but two taking turns would each be given the whole store every time (a debug assertion catches them). Anything else that follows a store reads its `AssetEvent<T>`s, or compares versions.

## The server

- `AssetServer` (`server.rs`) is a resource and cheap to clone (an `Arc` inside). Its state is shared with the worker threads and the watcher, so it stays `Send + Sync` (crossbeam channels, `Mutex` and `RwLock`; a poisoned lock is recovered with `PoisonError::into_inner`). The server's table is locked before any ledger, never after.
- `insert_registry` (`mod.rs`) puts a server in a world with the engine's types and loaders registered: `Image` (`ImageLoader`), `Shader` (`ShaderLoader`), `Font` (`FontLoader`), `BitmapFont` (`BitmapFontLoader`), `UiFile` (`UiFileLoader`), `Theme` (`ThemeLoader`), `AudioClip` (`AudioClipLoader`) and `Sound` (`SoundLoader`). The engine's world, the test worlds and `UiHarness` all start this way, so every store exists before anything loads and a loader's `check` finds the stores it reads. A game's loaders are added after (`EngineBuilder::asset_loader`), so for an extension both take, the game's wins.
- **Keys.** An asset is its type, its settings and its path: the table keys by type and settings hash, then by path, so a lookup borrows the path and allocates nothing. One file at two SVG sizes is two images, and a reload of the file updates both. `load` is `load_with` the loader's default settings. Asking for a key again while its asset lives gives the same handle, loaded, loading or failed; a failed asset is not tried again until its file changes, or it is freed and asked for again.
- A load refused before anything is read (`AssetError::InvalidPath`, `NoLoader`, or settings of a type the loader does not take) is a failed asset kept under its key, so asking again gives the same asset and warns once; its `Failed` goes at the next pump. A type never registered has nowhere to keep even that: the load warns and gives a handle that finds nothing.
- **Paths** (`path.rs`) are relative to the asset root (`Workspace::assets_dir()`; an example's root is its own `assets/`), and so are the paths inside asset files (UI file imports, skin and sheet images). Normalisation is lexical: `\` becomes `/`, `.` and empty segments go, and `..` resolves within the path; an absolute path, or one leaving the root, is `InvalidPath`. A path already normal is borrowed, so finding a loaded asset allocates nothing.
- **Where loading is.** `state` is the asset's own `LoadState`; `is_ready` and `dependency_state` count its dependencies too (through the server a loaded asset's dependencies are loaded, so they agree with `state`; the walk is a safety net). `progress(ids)` counts a group, from its handles or anything else `Into<UntypedAssetId>` (untyped ids for a group across types), leaving out ids neither loaded nor loading (freed, or never asked for); `stats()` counts per type. An asset added in code is `Loaded` while it lives.
- **`load_now`** loads on the calling thread with the world (`LoadMode::Now`): its dependencies load at once too, a stack of the paths being loaded catches a cycle, `check` runs, and the asset is inserted with its `Added` (or `Failed`) sent at once. An asset already loaded comes back without a read; one loading on a worker loads here instead, and the worker's result is dropped (its job is not the asset's current one). A failure returns the error, and the failed asset is kept only while a handle holds it (a `load`'s): otherwise the next pump frees it, and asking again tries again. Scenes load what they draw at once this way, so no frame shows a placeholder where an image belongs; `load` is for loading screens and streaming.

## Loaders and sources

- `AssetLoader` (`loader.rs`): `extensions` (`"png"`, `"ui.ron"`; one written with its dot, `".png"`, is taken without it when the loader is registered, `erase`), `load(bytes, settings, cx)`, and the hooks `check` and `dependency_failed`. A type's loader is the one taking the path's longest extension (`menu.ui.ron` tries `ui.ron`, then `ron`), case-insensitively; among a type's loaders for one extension, the latest registered.
- `type Settings: AssetSettings` (`Default + Clone + Hash + Eq + Send + Sync`; `()` for none) is part of the key. `SvgSize::Scale(f32)` compares and hashes by the float's bits, so a key always equals itself.
- `LoadContext`: `path()`, and `load` / `load_with` for dependencies. A loader keeps each dependency's handle in its value (a bitmap font its sheet, a UI file its imports and images, a theme its skins' images), so a dependency lives while what holds it does. The server records the ids, and inserts the value only once they are all loaded. On the workers a dependency is queued; under `load_now` it loads at once into the world. Crate-only: `is_reload` (the image loader borders a large image's first level only for a reload), `queued` and `world`.
- `check(&asset, &CheckContext)` runs on the main thread once the dependencies are loaded, and again whenever one reloads, so a loader can read other stores (`cx.world()`: a UI file builds its root and templates against its imports). `cx.path()` names the asset in its error (`AssetError::decode(cx.path(), error)`), so a value need not keep its own path. An error fails a first load, or keeps a loaded asset's last good value (`ReloadFailed`). The default accepts.
- `dependency_failed(&asset, &error)` runs when a dependency failed on the workers or in a reload. The server's error is `AssetError::Dependency`, naming both paths; a loader that knows where its file names the dependency gives a better one (the UI file loader names the line and column), and the default keeps the server's. Under `load_now` the loader sees the dependency's error from `cx.load` itself.
- A dependency that leads back to the asset fails it with `AssetError::Cycle` and the chain (`a.ui.ron → b.ui.ron → a.ui.ron`). Under `load_now` the stack finds it; on the workers the waiting list does (`wait`), and every value waiting on the cycle fails with it.
- **Panics are caught in native builds** in the source's `read`, the loader's `load`, `check` and `dependency_failed` (`catch_unwind`). Each fails the asset with `AssetError::Decode` (`dependency_failed`'s keeps the server's error), so a bad loader or file fails its asset, never the frame or a worker thread. The web build (`wasm32-unknown-unknown`) aborts on a panic, so `catch_unwind` catches nothing there: a loader or decoder that panics ends the game, on the bytes a `MemorySource` or `add` gives it. Loaders return errors for bad bytes for that reason.
- `AssetError` (`error.rs`, `#[non_exhaustive]`): `NotFound`, `Io`, `Decode` (`AssetError::decode(path, error)` from any error), `NoLoader`, `Dependency`, `Cycle`, `InvalidPath`. Each names the path and keeps its cause as `source()`; `report()` (public) is the error and its causes on one line, what the warnings print. States, events and `load_now` share one `Arc<AssetError>` per failure. An asset warns once per distinct error (by a hash of the error and its causes on one line), and a load or check that passes clears it. A read the source does not support (`Io` with `ErrorKind::Unsupported`: every read on the web) is noted at debug level instead, so a web game falling back to what it embeds does not warn at every launch.
- `AssetSource` (`source.rs`) is where the bytes come from: `read(&AssetPath)`, and `watch(AssetChanges)`, which the engine asks once when hot reload is on (a source that cannot watch returns Ok and never sends). `AssetChanges` wraps the server's channel, so a game's own source names no crossbeam type; `send(path)` is false once the server is gone. `DiskSource` reads files under a folder; the engine's reads `Workspace::assets_dir()` unless `EngineBuilder::asset_source` gives another source. `MemorySource` holds bytes for tests and tools; clones share their files, and an `insert` over an existing path tells a watcher it changed. The web build has no files: `DiskSource::read` is `AssetError::Io` with `ErrorKind::Unsupported` there, so a web game embeds what it needs and adds it.

## Worker threads and the web

- `workers.rs`: one thread fewer than the machine's cores, from one to four, named `ryo2d-assets-<n>`. They start at the first queued load, so a server that only loads at once, or is given its assets, starts none. A job reads and loads one asset and sends the result to the pump; a job whose server was dropped does nothing.
- The web has no threads, and neither has a native machine whose threads would not start: the pump runs the queued jobs itself, for at most `INLINE_BUDGET` (4 ms) a frame, and always at least one, so a large file still loads. With nothing queued it checks one channel.

## The pump

`pump.rs`, run by `asset_registry_system` in `PreUpdate` every frame, chained after `scene_transition_system`: when a transition switches scenes there, what the leaving scene let go is freed and what the entering scene asked for is pumped in that frame, before the new scene's UI pass. A switch made from `update` or `ui` is pumped at the next frame's start. The font registry follows the font stores right after it (`fonts_follow_assets`), so a freed face goes before any text is laid out that frame. In order, the pump:

1. runs the queued jobs where there are no threads, and reloads the paths the watcher reported;
2. lands finished loads. A result whose job is not the asset's current one (freed, overtaken by `load_now`, or read before a change, which queues the load again) drops. One with dependencies waits until they settle. One that settles is checked and inserted, sending `Added` (`Modified` for a reload), and a reload then checks again the assets that hold it; one that fails sends `Failed` (`ReloadFailed` for a reload, which keeps the last good value). Then it settles the waiting values whose dependencies did, until none moves, since settling one can let another go;
3. sends the events queued by changes made in code (`add`, `get_mut`), type by type in the order the types were registered, each type's in the order its assets first changed. An asset step 2 loaded, reloaded or touched has only that event;
4. frees every unheld asset, sending `Removed` for each that was in its store (a load dropped before it landed, or one that failed, is freed with no event, so `Removed` never comes for an id with no `Added`), and goes round again while anything was freed, so the dependencies only a freed asset held go in the same frame; then the server forgets their keys and states.

So an asset's events come in the order its changes happened, `Removed` last; between assets they need not, as a change made in code before the pump is sent after the pump's own events. `AssetEvent`'s rustdoc gives the order exactly. A frame with nothing to load, reload or free polls a few channels and allocates nothing.

## Reloads and hot reload

- `AssetServer::reload(path)` reloads every asset loaded from the path (each settings variant) on the workers. Each keeps its id: once its new dependencies load and `check` passes, the new value takes the old one's place and its version moves on (`Modified`). Then every loaded asset holding it, directly or through others, is checked again, nearest first (breadth first over the dependents, by the fewest steps): one that passes has its version moved on (`Modified`), so what was built from it is built again; one that fails is `ReloadFailed` and keeps its value. Checks only read and a pass only moves a version, so the order changes no outcome, only the order of the events.
- A reload that fails keeps the last good value and warns once (`ReloadFailed`). A reload asked for while a read of the file is in flight runs again once that read is in, so the last write wins. An asset that failed to load is loaded anew, as a first load (`Added` or `Failed`). `kept_after_a_failure` (crate) says an asset holds its last good value after a failed reload or recheck, so the UI does not warn a second time about a tree it could not rebuild.
- **Hot reload** is the watcher (`watch.rs`, native builds) behind `DiskSource::watch`. notify watches the folder and every folder under it; a debounce thread tells the server about a path once 100 ms (`SETTLE`) have passed since the path's last event, looking every 25 ms while any path waits, so a save in several writes, or a temp file renamed over the asset, reloads once with the last bytes. The debounce is written by hand on notify's channel, so the watcher adds no crate. Removed files and editors' temp files (a name starting with `.` or ending in `~`) are not reported: an asset whose file is removed keeps its value. A missing folder is noted at debug level and watched by no one.
- `EngineBuilder::hot_reload(bool)`: the default is on in debug builds with a window, and off in release and headless builds, so players and tests never pay for a watcher. `true` turns it on in any build (tests of reloading do), `false` off; off, no watcher starts. The web build has no folder to watch.

## The renderer and the UI

- The renderer holds ids, never handles (`BatchCollector`, the texture registry by `AssetId<Image>`, `ShaderCache` by `AssetId<Shader>`), so drawing an image never keeps it alive. At extract it takes an image's pixels by `Arc` (`Image::pixels`, shared with the value in the store) with the image's version, so an upload copies no pixels on the CPU. An image's `AssetEvent::Removed` (read at extract) frees its texture at once, and every 120 frames (`PRUNE_EVERY`, in `graphics/sprite_gpu.rs`) the textures are checked against the store, for an event a frame missed. A large reload is written into a new texture over several frames (graphics module notes, Reloads).
- An image that is not loaded (not yet, failed or freed) draws the magenta-and-black checker in debug builds and nothing in release builds: a missing image shows while developing and never to players. The UI draws the checker only where it is given a size or a rect; an unloaded image at its natural size is zero-sized, so a UI lays out the same in both builds.
- The UI sizes images from `ImageSizes`, the image store's follower, brought in line at the start of each UI pass, so the pass never takes the store from the world and a scene's `ui` loads and adds images as anywhere else. An image first loaded or added inside `Scene::ui` is sized from the next pass.

## The asset types

- **Images** (`graphics/image.rs`, `loaders/image.rs`): PNG, JPEG, BMP, GIF (its first frame), WebP, TGA, TIFF, QOI and ICO through the `image` crate, and SVG rasterised by resvg at `ImageSettings::svg` (`SvgSize::Native`, `Scale`, `Fit`). `Image::decode(bytes)` decodes embedded bytes for `add`. Clones share their pixels until one changes its own (`data_mut`). The loader also prepares what uploading takes (bordered pixels, mip levels) on its thread; the graphics module notes (Texture Atlas and Shading) say which, and when.
- **Shaders** (`ecs/material.rs`, `loaders/shader.rs`): `.wgsl` text named by its asset path, or `Shader::from_wgsl(name, source)`. The loader compiles the text with naga as the renderer will (`Shader::check`) and keeps the result with the shader for the renderer, so a file that does not compile is `AssetError::Decode` at its line and column, and a broken save keeps the last good shader (`ReloadFailed`). The shader cache keeps a compiled source per shader id and drops the entry on the shader's `Removed`, its pipelines going with the last shader of that source; a saved shader already drawn has its new pipelines made off the main thread while the old one draws (shaders module notes).
- **Fonts** (`text/fonts.rs`, `loaders/font.rs`, `loaders/bitmap_font.rs`): `.ttf`, `.otf` and `.ttc` files (`FontSettings::face` picks a collection's face, and is part of the key), or `Font::from_bytes` / `from_bytes_face` for embedded bytes; `.bitmap.ron` descriptors make `BitmapFont`s, whose sheet image is a dependency. `Fonts` registers a font's face while the font is in its store, and drops it with its glyphs once the font is freed (text module notes).
- **UI files** (`.ui.ron`, `ui/file/`, `loaders/ui_file.rs`) and **themes** (`.theme.ron`, `ui/theme/`, `loaders/theme.rs`): their imports and images are their dependencies; the UI module notes (Files, Theme) say how trees and the `UiTheme` follow them.
- **Audio clips** (`audio/clip.rs`, `loaders/audio_clip.rs`): `.wav`, `.ogg`, `.mp3` and `.flac`, mono or stereo (else `AssetError::Decode`). `AudioClipSettings::mode` (`ClipMode`: `Auto`, `Decode`, `Stream`) is part of the key. A clip up to 10 s (`DECODE_THRESHOLD`) decodes to a kira `StaticSoundData`; a longer one keeps its encoded bytes (`Arc<[u8]>`) and streams per play, and the loader only probes it, so its channel layout is not checked until it plays. The web decodes every clip (`decodes`). The engine's player (`AudioEngine`, `audio/engine.rs`) plays them; the old one (`audio/legacy.rs`) is not built on clips.
- **Sound definitions** (`.sound.ron`, `audio/sound.rs`, `loaders/sound.rs`): RON read with `IMPLICIT_SOME`, every field but `clips` optional, unknown fields refused. The clips are dependencies loaded with default settings; `check` keeps each clip's `region` inside the clip and its `loop_region` inside the region, since kira reads past a slice that runs off its frames. A bus must be `master`, a standard bus or a path under one; whether a custom bus exists is the player's business (it plays on the nearest bus above, warning once per name).

## Adding an asset type

1. The type: `impl Asset for Level {}` (`Send + Sync + 'static`). A type only ever made in code needs nothing more: `AssetsView::add` registers its type at the first add.
2. Its loader: `impl AssetLoader for LevelLoader` with `type Asset = Level`, `type Settings` (`()` for none), `extensions` and `load`. Load dependencies with `cx.load::<T>(path)?` and keep their handles in the value; fail a bad file with `AssetError::decode(cx.path(), error)`. Add `check` for what needs the dependencies loaded, and `dependency_failed` to say where the file names a dependency.
3. Register it. A game calls `EngineBuilder::asset_loader(LevelLoader)`, which registers the type too. An engine type is registered in `insert_registry` with its loader, and the type and its loader are exported from the prelude (`src/lib.rs`).
4. Whatever is built from the assets keys by `(id, version)` or reads `AssetEvent<T>`; only one consumer of a store may use its change list (above).
5. Test it over a `MemorySource` (`AssetServer::new`, `EngineBuilder::asset_source`, `UiHarness::with_asset_source`), driving frames or calling `pump(world)` (doc-hidden, for tests).
